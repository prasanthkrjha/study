# LLM APIs & Integration

Working with LLM APIs in production is not the same as querying them in a notebook. Production use requires handling streaming responses, implementing retry logic with exponential backoff, managing rate limits and costs, structuring multi-turn conversations correctly, and using function calling to bridge the model's natural language output to your application's typed interfaces. These are the skills that distinguish an engineer who has shipped an AI feature from one who has only experimented with one.

This unit covers the OpenAI and Anthropic APIs in practical depth: the message structure, streaming, tool/function calling with structured schemas, error handling patterns, and the TypeScript/JavaScript integration patterns relevant to full-stack applications. The concepts apply across providers — the APIs differ in naming and some defaults, but the architectural patterns are identical.

Understanding function calling is the most important practical skill in this unit. It is the mechanism that connects an LLM's language capabilities to your application's actual actions — checking databases, calling other services, returning typed data. Everything in Unit 8.6 (agents) and Unit 8.8 (MCP) builds on the function calling pattern established here.

## Theory & Fundamentals

**The Messages API structure**: Modern LLM APIs use a structured conversation format rather than raw text completion. A request contains a list of messages with roles (`system`, `user`, `assistant`), enabling multi-turn conversations where context is maintained by including the full message history. The system message sets persistent instructions (persona, constraints, output format); user messages are human turns; assistant messages are the model's prior responses. This structure is what makes "conversational AI" work — the model sees the entire conversation each time.

**Tokens, context, and cost**: Every API call is metered in tokens — input tokens (everything in your messages array) plus output tokens (the model's response). Costs differ between providers and models; input tokens are typically cheaper than output tokens. Context length is the shared budget for input + output tokens. For long conversations, the message history can grow to fill the entire context window — you must implement truncation or summarization strategies to prevent context overflow in long-running applications.

**Streaming**: By default, the API returns the complete response after generation is finished, causing a delay proportional to output length. Streaming returns tokens as they are generated — users see the response appearing in real time. For web applications this is a significant UX improvement, especially for long RAG answers or complex reasoning. Server-Sent Events (SSE) is the standard transport for streaming in HTTP applications.

**Function calling / tool use**: The API extension that allows the model to request execution of a defined function rather than just generating text. The model decides when a function call is appropriate, generates structured JSON arguments, and your code executes the actual function and returns the result. This creates a structured bridge between natural language and application code, enabling agents that can query databases, call APIs, and take actions.

**Rate limits and retry strategy**: LLM APIs enforce rate limits at the requests-per-minute (RPM) and tokens-per-minute (TPM) level. Exceeding them returns a 429 error. The correct handling is exponential backoff with jitter: retry after an increasing delay (2s, 4s, 8s...) with randomized jitter to avoid thundering-herd retries when multiple clients hit the limit simultaneously. Never retry immediately on a 429 — it will continue to fail.

## Core Concepts / Techniques

**Basic chat completion (Python)**:
```python
from anthropic import Anthropic

client = Anthropic()

def chat(messages: list[dict], system: str = "") -> str:
    response = client.messages.create(
        model="claude-opus-4-5",
        max_tokens=1024,
        system=system,
        messages=messages,
    )
    return response.content[0].text

# Single turn
answer = chat(
    messages=[{"role": "user", "content": "Explain backpropagation in one paragraph."}],
    system="You are a concise technical instructor."
)

# Multi-turn: maintain history manually
history = []
def send(user_msg: str) -> str:
    history.append({"role": "user", "content": user_msg})
    reply = chat(history, system="You are a helpful assistant.")
    history.append({"role": "assistant", "content": reply})
    return reply
```

**Streaming (Python)**:
```python
with client.messages.stream(
    model="claude-opus-4-5",
    max_tokens=512,
    messages=[{"role": "user", "content": "Write a haiku about neural networks."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
    print()  # newline after done
```

**Function calling (OpenAI SDK, Python)**:
```python
from openai import OpenAI
import json

client = OpenAI()

tools = [
    {
        "type": "function",
        "function": {
            "name": "get_user_orders",
            "description": "Retrieve the most recent orders for a user by their ID.",
            "parameters": {
                "type": "object",
                "properties": {
                    "user_id":  {"type": "string", "description": "The user's UUID"},
                    "limit":    {"type": "integer", "description": "Number of orders to return", "default": 5},
                },
                "required": ["user_id"],
            },
        },
    }
]

def get_user_orders(user_id: str, limit: int = 5) -> list[dict]:
    # Real implementation would query a database
    return [{"order_id": f"ORD-{i}", "total": 49.99 + i} for i in range(limit)]

def run_with_tools(user_message: str) -> str:
    messages = [{"role": "user", "content": user_message}]
    while True:
        response = client.chat.completions.create(
            model="gpt-4o",
            messages=messages,
            tools=tools,
            tool_choice="auto",
        )
        msg = response.choices[0].message

        if not msg.tool_calls:
            return msg.content   # no more tool calls — final answer

        # Execute all requested tool calls
        messages.append(msg)
        for tc in msg.tool_calls:
            fn_name = tc.function.name
            fn_args = json.loads(tc.function.arguments)
            result  = get_user_orders(**fn_args) if fn_name == "get_user_orders" else {}
            messages.append({
                "role":         "tool",
                "tool_call_id": tc.id,
                "content":      json.dumps(result),
            })

print(run_with_tools("What are the latest orders for user abc-123?"))
```

## Code Examples

```typescript
// TypeScript/Next.js: streaming chat endpoint with tool calling
// app/api/chat/route.ts

import Anthropic from "@anthropic-ai/sdk";
import { NextRequest } from "next/server";

const client = new Anthropic();

// Tool definitions
const tools: Anthropic.Tool[] = [
  {
    name: "search_products",
    description: "Search the product catalog by keyword or category.",
    input_schema: {
      type: "object" as const,
      properties: {
        query:    { type: "string",  description: "Search terms" },
        category: { type: "string",  description: "Optional product category filter" },
        limit:    { type: "integer", description: "Max results", default: 5 },
      },
      required: ["query"],
    },
  },
];

// Simulated tool execution
function searchProducts(query: string, category?: string, limit = 5) {
  return [
    { id: "P001", name: `Widget matching "${query}"`, price: 29.99, category: "Hardware" },
    { id: "P002", name: `Gadget for "${query}"`,     price: 49.99, category: "Electronics" },
  ].slice(0, limit);
}

export async function POST(req: NextRequest) {
  const { messages } = await req.json();

  // Create a streaming response using SSE
  const encoder = new TextEncoder();
  const stream  = new TransformStream();
  const writer  = stream.writable.getWriter();

  const writeChunk = async (data: string) => {
    await writer.write(encoder.encode(`data: ${JSON.stringify({ text: data })}\n\n`));
  };

  (async () => {
    try {
      let currentMessages = [...messages];

      // Agentic loop: repeat until no more tool calls
      while (true) {
        const response = await client.messages.create({
          model:      "claude-opus-4-5",
          max_tokens: 1024,
          system:     "You are a helpful product assistant. Use the search_products tool to look up items.",
          messages:   currentMessages,
          tools,
        });

        // Stream text blocks to the client
        for (const block of response.content) {
          if (block.type === "text") {
            // Stream word-by-word for demo purposes
            for (const word of block.text.split(" ")) {
              await writeChunk(word + " ");
            }
          }
        }

        if (response.stop_reason !== "tool_use") break;

        // Execute tool calls
        const toolResults: Anthropic.MessageParam = {
          role: "user",
          content: response.content
            .filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use")
            .map((toolUse) => {
              const input = toolUse.input as { query: string; category?: string; limit?: number };
              const result = searchProducts(input.query, input.category, input.limit);
              return {
                type:        "tool_result" as const,
                tool_use_id: toolUse.id,
                content:     JSON.stringify(result),
              };
            }),
        };

        currentMessages = [
          ...currentMessages,
          { role: "assistant" as const, content: response.content },
          toolResults,
        ];
      }
    } catch (err) {
      await writeChunk(`\n[Error: ${(err as Error).message}]`);
    } finally {
      await writer.close();
    }
  })();

  return new Response(stream.readable, {
    headers: {
      "Content-Type":  "text/event-stream",
      "Cache-Control": "no-cache",
      Connection:      "keep-alive",
    },
  });
}
```

```python
# Python: robust API client with retry, rate limiting, and cost tracking
import time
import random
import anthropic
from dataclasses import dataclass, field

@dataclass
class APIStats:
    total_input_tokens:  int = 0
    total_output_tokens: int = 0
    total_calls:         int = 0
    total_retries:       int = 0

    @property
    def estimated_cost_usd(self) -> float:
        # claude-opus-4-5 approximate pricing
        return (self.total_input_tokens / 1_000_000 * 15.0 +
                self.total_output_tokens / 1_000_000 * 75.0)

class RobustLLMClient:
    def __init__(self, max_retries: int = 5, base_delay: float = 1.0):
        self.client      = anthropic.Anthropic()
        self.max_retries = max_retries
        self.base_delay  = base_delay
        self.stats       = APIStats()

    def complete(self, messages: list[dict], system: str = "",
                 max_tokens: int = 1024) -> str:
        for attempt in range(self.max_retries + 1):
            try:
                response = self.client.messages.create(
                    model="claude-opus-4-5",
                    max_tokens=max_tokens,
                    system=system,
                    messages=messages,
                )
                self.stats.total_input_tokens  += response.usage.input_tokens
                self.stats.total_output_tokens += response.usage.output_tokens
                self.stats.total_calls         += 1
                return response.content[0].text

            except anthropic.RateLimitError:
                if attempt == self.max_retries:
                    raise
                delay = self.base_delay * (2 ** attempt) + random.uniform(0, 1)
                self.stats.total_retries += 1
                print(f"Rate limited. Retrying in {delay:.1f}s (attempt {attempt+1})")
                time.sleep(delay)

            except anthropic.APIStatusError as e:
                if e.status_code in {500, 502, 503, 529}:  # transient server errors
                    if attempt == self.max_retries:
                        raise
                    delay = self.base_delay * (2 ** attempt) + random.uniform(0, 1)
                    time.sleep(delay)
                else:
                    raise  # 400, 401, 403 — not retriable

    def report(self) -> None:
        print(f"Calls: {self.stats.total_calls} | "
              f"Tokens: {self.stats.total_input_tokens}in / "
              f"{self.stats.total_output_tokens}out | "
              f"Est. cost: ${self.stats.estimated_cost_usd:.4f} | "
              f"Retries: {self.stats.total_retries}")
```

## Best Practices

- **Never hardcode API keys.** Store them in environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`) or a secrets manager. Rotate them immediately if accidentally committed to version control.
- **Always implement exponential backoff with jitter for rate limit errors.** Immediate retries after a 429 will all fail and waste quota. Exponential backoff with random jitter spreads the retry load.
- **Track token usage on every API call.** Every response includes `usage` metadata (input/output tokens). Log this — you need it to debug runaway cost, enforce per-user quotas, and calculate the actual cost of running a feature.
- **Use `max_tokens` as a cost and safety guard, not just a limit.** Setting `max_tokens` too low silently truncates responses. Set it to a reasonable upper bound for your use case and log when responses approach the limit (it may indicate the model is being asked to do too much in one call).
- **Structure tool definitions with precise descriptions.** The model reads the `description` field to decide when to call a tool. Vague descriptions ("does stuff") produce incorrect or missed tool calls. Precise descriptions ("returns a list of products matching the search query from the product catalog") produce reliable invocations.
- **Validate tool call arguments before executing them.** The model can generate arguments that parse as JSON but violate your business logic (negative quantities, invalid UUIDs, future dates when past dates are required). Validate before passing to your actual function.
- **Use streaming for responses longer than a few sentences.** The perceived latency difference between streaming and non-streaming is dramatic for responses over 200 tokens. Implement streaming in your UI from the start — retrofitting it later requires refactoring both the API layer and the frontend.

## Common Interview Questions

**Q: What is the difference between the `system` prompt and `user` messages in the Messages API?**
A: The system prompt is a persistent instruction that frames the entire conversation — persona, constraints, output format rules. It is set once per session. User messages are the individual turns of the conversation. This separation lets you define guardrails and behavior in the system prompt without repeating them in every user message, and gives the model clear context about its role vs. the human's request.

**Q: How does function/tool calling work at the API level?**
A: You provide a list of tool definitions (name, description, JSON schema for parameters) in the API request. The model can respond either with text or with a `tool_use` block containing the tool name and structured arguments. Your code receives this, executes the actual function, and sends the result back as a `tool_result` message. The model then generates a final response incorporating the result. The model never directly executes code — it only requests calls with typed arguments.

**Q: How do you handle rate limiting in production LLM API calls?**
A: With exponential backoff and jitter. Catch 429 (RateLimitError) exceptions, wait for an exponentially increasing delay (base * 2^attempt seconds), add random jitter to prevent synchronized retries from multiple clients, and retry up to a maximum attempt count. Never retry immediately — it will continue to fail. Log retry counts so you can detect when you are consistently hitting limits and need to increase your API quota or reduce throughput.

**Q: What is token counting and why does it matter?**
A: Each API call consumes tokens (input tokens = everything in the messages array; output tokens = the model's response). Token consumption determines cost (billed per million tokens) and whether the request fits within the model's context window. You need to track usage to manage cost, enforce user quotas, debug runaway spending, and size prompts to fit within context limits.

**Q: How do you implement streaming in a Next.js API route?**
A: Return a `Response` with a `ReadableStream` body and `Content-Type: text/event-stream` headers (Server-Sent Events). As the LLM generates tokens, write each chunk to the stream using `writer.write()`. The React frontend reads the SSE stream with `EventSource` or `fetch()` with a streaming reader, updating the UI as each chunk arrives.

**Q: What error types should you handle when calling LLM APIs?**
A: Rate limit errors (429) — retry with backoff. Transient server errors (500, 502, 503) — retry with backoff. Authentication errors (401) — fail fast, do not retry, alert. Invalid request errors (400) — fail fast, these indicate a prompt or parameter bug. Context length exceeded — fail with a user-visible error or truncate messages and retry.

**Q: How do you manage context length in a long-running conversation?**
A: Several strategies: (1) Rolling window — drop the oldest messages when total tokens approach the limit. (2) Summarization — periodically summarize the conversation so far and replace the history with the summary. (3) Selective retention — always keep the system prompt and the most recent N turns; summarize or discard the middle. The right strategy depends on whether mid-conversation context is important to the specific application.

## Key Takeaways

- LLM APIs use a structured message format (system/user/assistant roles) that maintains conversation context explicitly — you are responsible for including the history in each request.
- Streaming returns tokens as they are generated, dramatically improving perceived responsiveness for long responses — implement it from the start in user-facing applications.
- Function/tool calling is the bridge between natural language and application code — the model requests calls with structured arguments; your code executes them and returns results.
- Rate limits (429) must be handled with exponential backoff and jitter — immediate retries will consistently fail and waste quota.
- Always track token usage per call — it is the only way to manage cost, enforce quotas, and debug spending.
- Tool definitions must have precise descriptions — the model uses the description to decide when to invoke a tool.
- Validate tool arguments before executing them — the model can generate syntactically valid but semantically wrong arguments.
- Context management is a real engineering problem for long conversations — implement a truncation or summarization strategy before you need it.
