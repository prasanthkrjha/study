# Vector Databases

Once you've built a retriever by hand (Unit 8.3) and felt where a linear scan through every embedding gets slow, a vector database is the answer to "how do I do this at real scale."

## Indexing basics

A vector database doesn't compare your query to every stored vector one by one (that's what your from-scratch version did) — it builds an **index** (commonly HNSW — Hierarchical Navigable Small World graphs) that lets it find approximately-nearest vectors in sub-linear time, trading a small amount of accuracy (it's an *approximate* nearest-neighbor search) for a massive speed gain at scale. For most RAG use cases, that tiny accuracy trade-off is invisible in practice, while the speed difference (milliseconds vs. seconds, once you have millions of vectors) is not.

## Similarity search at the database level

The core operation is the same cosine-similarity comparison from Unit 8.2, just handled internally by the database and exposed through a simple API:

```python
import chromadb

client = chromadb.Client()
collection = client.create_collection("docs")

collection.add(
    documents=["The cat sat on the mat.", "Docker containerizes applications."],
    ids=["doc1", "doc2"],
)

results = collection.query(query_texts=["What is Docker?"], n_results=1)
# results["documents"] -> [["Docker containerizes applications."]]
```

Chroma handles embedding, storage, and similarity search all in one call here — the same four-step pipeline from Unit 8.3, just implemented for you.

## Chroma vs. pgvector vs. a managed service

- **Chroma** — the fastest path to a working prototype: lightweight, runs embedded or as a simple local server, minimal setup. Ideal for getting a RAG system working end-to-end quickly (exactly why it's Month 3's recommended starting point).
- **pgvector** — a Postgres extension that adds vector similarity search to a database you likely already have running. The advantage: your vector data lives alongside your relational data, in one database, with one set of operational concerns (backups, access control) instead of two separate systems.
- **Managed services** (Pinecone, Weaviate Cloud, etc.) — handle scaling, replication, and uptime for you, at the cost of a recurring bill and a dependency on a third party. Worth it once you have real production scale and reliability requirements; overkill for a portfolio project.

The interview-relevant judgment: pgvector is a strong "keep it simple" default once you already run Postgres; a dedicated vector database earns its complexity at large scale or when vector search is the primary workload rather than a feature bolted onto an existing app.
