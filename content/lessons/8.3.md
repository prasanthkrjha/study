## What RAG actually solves

An LLM's knowledge is frozen at training time and doesn't include your private data (your company's documents, your product's specifics). RAG (Retrieval-Augmented Generation) fixes this without retraining the model: retrieve relevant chunks of your own data at query time, and include them in the prompt as context, so the model generates an answer **grounded in that retrieved text** instead of relying purely on its training data.

## Chunking strategies

You can't embed and retrieve an entire document as one unit — it's too large, and mixes too many topics for precise retrieval. You split documents into smaller "chunks" first:

- **Fixed-size chunking** — split every N characters/tokens, usually with some overlap between consecutive chunks so a sentence isn't awkwardly cut in half and lose context.
- **Semantic/structural chunking** — split on natural boundaries (paragraphs, headings, sections) so each chunk is a coherent unit of meaning, not an arbitrary character count.

```python
def chunk_text(text, chunk_size=500, overlap=50):
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap  # overlap keeps context across chunk boundaries
    return chunks
```

The trade-off: chunks too large dilute relevance (a chunk about five different topics scores mediocre-similarity to a query about any one of them); chunks too small lose surrounding context needed to make sense of the retrieved text. This is the single most consequential design decision in a RAG system, and exactly the kind of choice you need to be able to defend line-by-line in an interview.

## Building a retriever by hand

Without a framework, the full pipeline is:

```python
# 1. Chunk and embed your documents once, offline
chunks = chunk_text(document)
chunk_embeddings = [embed(chunk) for chunk in chunks]

# 2. At query time: embed the query, compare to every chunk
query_embedding = embed(user_question)
scores = [cosine_similarity(query_embedding, ce) for ce in chunk_embeddings]

# 3. Take the top-k most similar chunks
top_k_indices = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)[:3]
retrieved_chunks = [chunks[i] for i in top_k_indices]

# 4. Build a grounded prompt
context = "\n\n".join(retrieved_chunks)
prompt = f"""Answer the question using ONLY the context below. If the answer isn't in the context, say so.

Context:
{context}

Question: {user_question}"""
```

Building this by hand once — even though production systems use a vector database (Unit 8.4) instead of a linear scan — is exactly what turns "I directed an AI feature" into "I can defend the implementation," because every subsequent framework (LangChain) is automating precisely these four steps.

## Grounding generation in retrieved context

The prompt's explicit instruction ("answer using ONLY the context") is what reduces hallucination — without it, the model may blend retrieved facts with its own (potentially wrong or outdated) training knowledge, and you lose the ability to trust that answers reflect your actual source data.

## Hybrid keyword + semantic search

Combining dense (embedding) retrieval with sparse (keyword/BM25) retrieval and merging the results — often via a weighted combination or a re-ranking step — catches both semantic paraphrases and exact-term matches (product names, error codes) that pure embedding search can miss. This is precisely the kind of retrieval design your own Physynex assistant already conceptually specified — Month 3 is where you implement it yourself for the first time.

## Practice tip

Build the four-step pipeline above with a real, small set of documents (10–20 paragraphs) before touching a framework or vector database. Once you've felt where a naive linear scan gets slow and where chunking choices change retrieval quality, LangChain's abstractions (Unit 8.5) will make sense as *shortcuts for something you already understand*, not magic.
