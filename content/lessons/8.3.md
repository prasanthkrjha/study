# Retrieval-Augmented Generation (RAG)

RAG is the dominant pattern for giving LLMs access to information that was not in their training data — your company's documentation, a product knowledge base, a patient's medical history, a legal corpus. The mechanism is elegant: rather than retraining the model (expensive, slow, produces a static snapshot), you retrieve the relevant information at query time and include it in the prompt, grounding the model's generation in your actual source data.

Understanding RAG deeply means understanding each design decision and its consequences: how you chunk documents affects what gets retrieved; how you retrieve affects what the model sees; how you prompt affects what the model says about what it sees. Every stage is a lever. Senior AI engineers are distinguished not by knowing that RAG exists but by knowing which lever to pull when evaluation reveals a specific failure mode.

This unit builds the RAG pipeline from first principles — no frameworks first, so that when you use LangChain or similar abstractions in a real project, you understand exactly what they are doing and why each design choice matters.

## Theory & Fundamentals

**What problem RAG solves**: An LLM's knowledge is frozen at training cutoff and contains nothing private or organization-specific. Fine-tuning can teach behavioral patterns but is expensive and produces a static snapshot that needs retraining whenever your data changes. RAG dynamically retrieves relevant context at query time — knowledge is always current (update the documents, not the model) and the retrieved content is auditable (you can show the user the source chunks behind any answer).

**The four-stage pipeline**: (1) **Chunking** — split source documents into retrievable units. (2) **Embedding and indexing** — embed each chunk and store the vector in a searchable index. (3) **Retrieval** — embed the query, search the index for the most similar chunk vectors, return the top-k chunks. (4) **Generation** — build a prompt that includes the retrieved chunks as grounding context and call the LLM to generate the final answer.

**Chunking strategies**:
- *Fixed-size with overlap*: Split every N tokens, with an overlap of M tokens between consecutive chunks. Simple, predictable, but may cut sentences mid-thought. The overlap prevents context loss at boundaries.
- *Sentence or paragraph splitting*: Split on sentence boundaries or paragraph breaks. Preserves semantic coherence within a chunk at the cost of variable chunk sizes.
- *Semantic chunking*: Embed each sentence, then merge sentences into a chunk only while cosine similarity between consecutive sentences remains above a threshold — the chunk boundaries are determined by semantic shifts in the text. More complex but produces chunks that are thematically coherent.
- *Structural splitting*: Split on document structure (headings, sections, code blocks). Best for well-structured documents (API docs, handbooks) where the structure maps to semantic units.

**The chunk size trade-off**: Too large — a chunk covers multiple unrelated topics; cosine similarity to any specific query is diluted. Too small — a chunk lacks sufficient context for the answer to be complete; the retrieved fragment is coherent but insufficient. Typical starting range: 256-512 tokens with 10-20% overlap. Evaluated empirically against your specific corpus and query distribution.

**Grounding generation**: The key to making RAG trustworthy is the generation prompt. "Answer using ONLY the context below. If the answer is not in the context, say so explicitly" creates a contract: the model should not blend retrieved facts with potentially outdated or hallucinated training knowledge. Without this instruction, the model freely interpolates between retrieved context and training knowledge, making answers non-auditable.

## Core Concepts / Techniques

**Chunking with overlap**:
```python
def chunk_text(text: str, chunk_size: int = 500,
               overlap: int = 50) -> list[str]:
    """Split text into overlapping fixed-size character chunks."""
    chunks, start = [], 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap   # overlap ensures no context is dropped at boundaries
    return chunks

# Sentence-aware chunking via nltk
import nltk
nltk.download("punkt", quiet=True)
from nltk.tokenize import sent_tokenize

def chunk_by_sentences(text: str, max_tokens: int = 400,
                        avg_chars_per_token: float = 4.0) -> list[str]:
    """Group sentences into chunks that stay under max_tokens."""
    sentences = sent_tokenize(text)
    chunks, current, current_len = [], [], 0
    max_chars = int(max_tokens * avg_chars_per_token)
    for sent in sentences:
        if current_len + len(sent) > max_chars and current:
            chunks.append(" ".join(current))
            current, current_len = [], 0
        current.append(sent)
        current_len += len(sent)
    if current:
        chunks.append(" ".join(current))
    return chunks
```

**Retrieval with cosine similarity**:
```python
import numpy as np

def retrieve(query_vec: np.ndarray, chunk_vecs: np.ndarray,
             chunks: list[str], k: int = 3) -> list[dict]:
    """Return top-k chunks by cosine similarity to the query."""
    # Normalize for cosine
    q_norm = query_vec / (np.linalg.norm(query_vec) + 1e-9)
    c_norm = chunk_vecs / (np.linalg.norm(chunk_vecs, axis=1, keepdims=True) + 1e-9)
    scores = c_norm @ q_norm   # (N,)
    top_k  = np.argsort(scores)[::-1][:k]
    return [{"chunk": chunks[i], "score": float(scores[i])} for i in top_k]
```

**Grounded generation prompt**:
```python
def build_rag_prompt(question: str, chunks: list[str]) -> str:
    context = "\n\n---\n\n".join(
        f"[Source {i+1}]\n{chunk}" for i, chunk in enumerate(chunks)
    )
    return f"""You are a helpful assistant. Answer the question using ONLY the information in the sources below.
If the answer is not fully contained in the sources, say "I don't have enough information to answer that."
Do not use knowledge outside the provided sources.

{context}

Question: {question}
Answer:"""
```

## Code Examples

```python
"""
Complete RAG pipeline from scratch:
document ingestion, chunking, embedding, indexing,
retrieval, generation, and a basic evaluation harness.
"""
import json
import numpy as np
from pathlib import Path
from openai import OpenAI

client = OpenAI()

# ─── 1. Document Corpus ───────────────────────────────────────────────────────
DOCUMENTS = {
    "pricing.txt":    "Our Pro plan costs $49/month and includes unlimited projects. "
                      "The Team plan is $99/month per seat and adds collaboration features. "
                      "Enterprise pricing is custom — contact sales@example.com.",
    "support.txt":    "Support hours are Monday through Friday, 9am to 6pm EST. "
                      "Priority support is available 24/7 for Enterprise customers. "
                      "Submit tickets at support.example.com or email support@example.com.",
    "features.txt":   "The dashboard provides real-time analytics with 30-day data retention. "
                      "API access requires a Pro or higher plan. Rate limit is 1000 calls/hour. "
                      "SSO and SAML 2.0 are available exclusively on the Enterprise plan.",
}

# ─── 2. Chunk + Embed + Index ─────────────────────────────────────────────────
def simple_chunk(text: str, size: int = 200, overlap: int = 40) -> list[str]:
    chunks, start = [], 0
    while start < len(text):
        chunks.append(text[start:start + size])
        start += size - overlap
    return [c.strip() for c in chunks if c.strip()]

all_chunks: list[str] = []
chunk_metadata: list[dict] = []

for filename, content in DOCUMENTS.items():
    chunks = simple_chunk(content)
    for i, chunk in enumerate(chunks):
        all_chunks.append(chunk)
        chunk_metadata.append({"source": filename, "chunk_index": i})

print(f"Total chunks: {len(all_chunks)}")

# Embed all chunks in one batch call
embed_response = client.embeddings.create(
    model="text-embedding-3-small", input=all_chunks
)
chunk_vecs = np.array(
    [item.embedding for item in embed_response.data], dtype=np.float32
)
print(f"Embedding matrix: {chunk_vecs.shape}")

# ─── 3. Retrieval Function ────────────────────────────────────────────────────
def retrieve_top_k(question: str, k: int = 3) -> list[dict]:
    q_resp = client.embeddings.create(
        model="text-embedding-3-small", input=[question]
    )
    q_vec = np.array(q_resp.data[0].embedding, dtype=np.float32)

    # Cosine similarity
    q_norm = q_vec / (np.linalg.norm(q_vec) + 1e-9)
    c_norm = chunk_vecs / (np.linalg.norm(chunk_vecs, axis=1, keepdims=True) + 1e-9)
    scores = c_norm @ q_norm
    top_k  = np.argsort(scores)[::-1][:k]

    return [
        {
            "chunk":  all_chunks[i],
            "source": chunk_metadata[i]["source"],
            "score":  float(scores[i]),
        }
        for i in top_k
    ]

# ─── 4. Generation ────────────────────────────────────────────────────────────
def answer(question: str, k: int = 3) -> dict:
    results = retrieve_top_k(question, k=k)
    context_blocks = [
        f"[{r['source']}]\n{r['chunk']}" for r in results
    ]
    context = "\n\n".join(context_blocks)

    prompt = (
        "Answer using ONLY the sources below. "
        "If the answer is not in the sources, say so.\n\n"
        f"{context}\n\nQuestion: {question}\nAnswer:"
    )
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        temperature=0,
        messages=[
            {"role": "system", "content": "You are a helpful product assistant."},
            {"role": "user",   "content": prompt},
        ],
    )
    return {
        "answer":   response.choices[0].message.content.strip(),
        "sources":  [r["source"] for r in results],
        "top_score": results[0]["score"] if results else 0.0,
    }

# ─── 5. Run Questions ─────────────────────────────────────────────────────────
questions = [
    "How much does the Team plan cost?",
    "Does the free plan include API access?",
    "What are your support hours for enterprise customers?",
    "Can I use SSO on the Pro plan?",
]

for q in questions:
    result = answer(q)
    print(f"Q: {q}")
    print(f"A: {result['answer']}")
    print(f"Sources: {result['sources']}  Top score: {result['top_score']:.3f}\n")

# ─── 6. Basic Evaluation Harness ──────────────────────────────────────────────
TEST_CASES = [
    {
        "question":     "How much does the Pro plan cost?",
        "must_contain": ["49", "month"],
        "must_not":     ["I don't have enough"],
    },
    {
        "question":     "What are support hours?",
        "must_contain": ["Monday", "Friday", "9am"],
        "must_not":     [],
    },
    {
        "question":     "Do you sell cars?",
        "must_contain": ["don't have enough information"],
        "must_not":     ["$49"],
    },
]

passed = 0
for case in TEST_CASES:
    result = answer(case["question"])
    ans    = result["answer"].lower()
    ok = (all(term.lower() in ans for term in case["must_contain"]) and
          not any(term.lower() in ans for term in case["must_not"]))
    status = "PASS" if ok else "FAIL"
    if ok: passed += 1
    print(f"[{status}] {case['question']!r}")

print(f"\nEval: {passed}/{len(TEST_CASES)} passed")
```

## Best Practices

- **Build the pipeline from scratch before using a framework.** Once you have hand-coded the four stages (chunk, embed, retrieve, generate), LangChain or LlamaIndex becomes a shortcut for something you understand — not a black box you depend on.
- **Add source attribution to every answer.** Include which chunk(s) grounded the response. This makes the system auditable, enables users to verify claims, and makes debugging retrieval failures straightforward.
- **Set a retrieval score threshold.** If no chunk has a cosine similarity above a minimum threshold (e.g. 0.6), return "I don't have relevant information" rather than generating an answer from weakly related context — this is a primary guard against hallucination.
- **Implement query rewriting for conversational RAG.** In multi-turn conversations, "it" and "that" in a follow-up question lose their meaning when the question is embedded standalone. Rewrite the query using conversation history before retrieval: "What is its price?" + "previous topic: the Pro plan" → "What is the Pro plan's price?"
- **Evaluate retrieval and generation separately.** Retrieval failure (the right chunks are not returned) looks the same as generation failure (the right chunks are returned but the answer is wrong) from the user's perspective. Separate evaluation lets you identify and fix the right stage.
- **Keep the chunk store versioned.** When you re-chunk or re-embed because of a model upgrade or chunking strategy change, the old index is incompatible with the new embeddings. Use a naming convention or metadata field that tracks the embedding model and chunking configuration.
- **Use streaming for long answers.** Users perceive a system that starts responding in 500ms as faster than one that waits 5 seconds for a complete answer. Streaming the LLM output token-by-token is especially important for RAG systems where generation can take several seconds.

## Common Interview Questions

**Q: What is RAG and what problem does it solve?**
A: RAG (Retrieval-Augmented Generation) grounds LLM responses in specific retrieved documents rather than relying solely on training-time knowledge. It solves two problems: LLMs do not know your private data, and their knowledge is frozen at training cutoff. With RAG, you retrieve relevant document chunks at query time and include them in the prompt — the model generates based on your current, actual source data.

**Q: What is the most consequential design decision in a RAG system?**
A: Chunking strategy. Chunk size and method determine the granularity of what is retrieved. Too-large chunks dilute similarity scores and return a mix of relevant and irrelevant content. Too-small chunks lack sufficient context for the answer to be complete. The optimal chunking depends on the corpus structure and query distribution — it must be evaluated empirically, not assumed.

**Q: What is hybrid retrieval and when do you use it?**
A: Hybrid retrieval combines dense (embedding-based semantic) and sparse (BM25/TF-IDF keyword-based) retrieval, fusing their ranked results via Reciprocal Rank Fusion or weighted combination. Use it when your corpus contains both semantic queries (paraphrases, concepts) and lexical queries (exact product names, error codes, technical identifiers) — neither pure approach handles both well alone.

**Q: What is the difference between RAG and fine-tuning?**
A: RAG retrieves dynamic external context at inference time — the model itself does not change, and knowledge is always current (update documents, not the model). Fine-tuning adjusts the model's weights on specific data — the knowledge is baked in and becomes stale if the data changes. RAG is preferred when knowledge needs to be current and auditable; fine-tuning is preferred when behavior or style (not knowledge) needs to change.

**Q: How do you handle multi-turn conversations in a RAG system?**
A: The key problem is anaphora — follow-up questions reference earlier context ("What is its price?"). Solution: query rewriting — before retrieval, call the LLM to rewrite the user's message as a standalone question using the conversation history. The rewritten query can then be embedded and retrieved without the conversational references that confuse cosine similarity.

**Q: What is a retrieval score threshold and why does it matter?**
A: A minimum cosine similarity threshold (e.g. 0.6) for retrieved chunks. If the highest-scoring chunk falls below the threshold, no chunks are genuinely relevant to the query — returning them to the LLM produces answers hallucinated from weakly-related context. The threshold converts the RAG system's behavior from "always generate something" to "only generate when I have relevant grounding."

**Q: How do you evaluate a RAG pipeline?**
A: In two stages. Retrieval evaluation: for labeled test queries with known relevant documents, measure Recall@k and MRR. Generation evaluation: for queries with known correct answers, use an LLM-as-judge to score faithfulness (is the answer supported by the retrieved context?) and relevance (does the answer address the question?). Evaluate each stage independently so you can identify whether retrieval or generation is the bottleneck.

3. **Score threshold investigation**: Run your RAG system on 30 queries — 20 that should be answerable from your corpus, 10 that should not. What fraction of answerable queries do you lose at that threshold?

4. **Query rewriting for conversation**: Build a two-turn conversational RAG system. For the second turn, implement LLM-based query rewriting that produces a standalone question from (second-turn message + first-turn question and answer). Test with 5 two-turn conversations where the second question uses pronouns referencing the first answer. Verify that retrieval quality improves after rewriting.

5. **Faithfulness evaluation**: Generate 20 answers from your RAG system. For each answer, call the LLM with a judge prompt: "Given only the provided sources, is every factual claim in this answer directly supported by the sources? Answer YES, NO, or PARTIAL." Track what fraction of answers are fully faithful. Identify the most common cause of unfaithfulness in your system's outputs.

## Key Takeaways

- RAG gives LLMs access to current, private data without retraining, and makes responses auditable — you can show which source chunks grounded any answer.
- The four RAG stages are chunking, embedding and indexing, retrieval, and grounded generation — each is a design decision with measurable consequences.
- Chunking strategy is the most consequential design choice — chunk size and method determine the granularity and relevance of what is retrieved.
- A grounded generation prompt ("answer using ONLY the sources") is what makes RAG trustworthy — without it, the model blends retrieved facts with training knowledge.
- Hybrid retrieval (dense + sparse + RRF) outperforms pure dense retrieval on real-world corpora that mix semantic and lexical queries.
- Set a retrieval score threshold: if no chunk is genuinely similar to the query, declining to answer is better than generating from irrelevant context.
- Evaluate retrieval and generation separately — they fail for different reasons and require different fixes.
- Build the pipeline by hand before adopting a framework — then the framework's abstractions will make sense as shortcuts for things you already understand.
