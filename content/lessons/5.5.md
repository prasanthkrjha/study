# Classic Design Problems

This unit is where 5.1–5.4's vocabulary gets exercised against specific, commonly-asked problems. The goal isn't to memorize a "correct" design — it's to practice the same structured approach on all of them.

## Theory & Fundamentals

### A Repeatable Approach for Any "Design X" Question

1. **Clarify requirements and scale.** How many users? Reads vs. writes ratio? Is strong consistency required, or is eventual consistency acceptable? Don't skip this — the right answer changes completely depending on scale.
2. **Back-of-envelope math.** Estimate: requests/second, storage/year, bandwidth. This reveals the actual bottleneck.
3. **Sketch the high-level components** (client → load balancer → API → database, plus cache/queue where relevant) before diving into any one piece.
4. **Identify the bottleneck** the problem is actually testing, and go deep there. Every design problem has one thing it's really asking about.
5. **Name the trade-offs explicitly** as you make choices. "I'm choosing eventual consistency here because X, which means Y" is what separates a strong answer from a list of buzzwords.

### The Five Classic Problems and What Each Tests

| Problem | Core challenge | Key technique |
|---|---|---|
| URL shortener | Unique code generation at scale | Key-value store, cache, base62 encoding |
| Rate limiter | Distributed counter across servers | Redis INCR + EXPIRE, token bucket |
| Chat app | Real-time bidirectional communication | WebSockets, message persistence, fan-out |
| News feed | Personalized feed at scale | Fan-out on write vs. fan-out on read |
| Notification system | Multi-channel reliable delivery | Event-driven, pub/sub, deduplication |

## Core Patterns / Techniques

### Design a URL Shortener

**What it tests**: key generation at scale, cache read-heavy workload, redirect performance.

- **Code generation**: hash the long URL (MD5/SHA256) and take the first 7 characters → collision-check → retry. Or: use a counter converted to base62 (a-zA-Z0-9 = 62 chars; 7 chars = 62⁷ ≈ 3.5 trillion codes).
- **Storage**: a key-value store or simple database: `short_code → long_url`. Reads (redirects) vastly outnumber writes (new codes) — cache the lookup result in Redis with a long TTL.
- **Redirect**: HTTP 301 (permanent, browser caches) for efficiency; HTTP 302 (temporary) if you need accurate click tracking.
- **Extensions**: custom aliases (user-specified codes), expiry (TTL on the code), analytics (click count, geographic distribution).

```
POST /shorten → generate code → store in DB → cache → return short URL
GET /{code}   → cache lookup → DB lookup (miss) → 301/302 to long URL
```

### Design a Rate Limiter

**What it tests**: distributed state, Redis, algorithmic knowledge (token bucket vs. sliding window).

- **Algorithm**: token bucket (allows short bursts) or sliding window counter (smoother enforcement).
- **State storage**: Redis `INCR` + `EXPIRE` for an atomic, shared counter across all API servers. `INCR` increments a counter for `"{userId}:{window}"` and sets a TTL on first creation.
- **Where to enforce**: API gateway (centralized) rather than each service (duplicated logic).
- **Response headers**: include `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` so clients know their limit state.

```
INCR "ratelimit:{userId}:{minute}"
EXPIRE "ratelimit:{userId}:{minute}" 60   (only on first call: use SET NX EX)
If count > limit: return 429 Too Many Requests
```

### Design a Chat Application

**What it tests**: real-time communication, WebSockets, message ordering and persistence.

- **Real-time delivery**: WebSockets, not HTTP polling — persistent bidirectional connection with low overhead.
- **Message persistence**: store messages in a database (Cassandra works well for append-heavy workloads), separate from the real-time delivery layer.
- **Fan-out for group chats**: when a message is sent to a group, it must be delivered to every connected member. For small groups: push directly via WebSocket connections. For large groups: a pub/sub topic per group (Kafka/Redis Pub/Sub) that chat servers subscribe to.
- **Presence/online-status**: a lightweight, high-churn system (status changes constantly). Redis sorted set by last-seen timestamp, or WebSocket connection events update a presence service.
- **Message ordering**: use a monotonically increasing sequence number per conversation (not global) to establish order on the client side.

### Design a News Feed (Twitter/Facebook)

**What it tests**: fan-out trade-off at scale, caching read-heavy workloads.

Two classic strategies for generating a user's feed:

**Fan-out on write**: when someone posts, immediately push it into every follower's pre-computed feed.
- Reads are fast (pre-computed, just fetch the list)
- Writes are slow for users with millions of followers (fan-out to 10M feeds is a background job, not a synchronous step)

**Fan-out on read**: compute the feed at request time by pulling and merging posts from everyone you follow.
- Writes are cheap (just store the post once)
- Reads are slower (query posts from all followed accounts, merge, rank)

**Hybrid** (the real answer): fan-out on write for typical users; fan-out on read for celebrity accounts (millions of followers). Identify "heavy users" (>N followers) at write time and skip them from fan-out; on read, merge celebrity posts with the pre-computed feed.

### Design a Notification System

**What it tests**: event-driven architecture, multi-channel delivery, reliability.

- **Trigger**: any service publishes an event ("order.shipped", "friend.request.received") to a message bus (Kafka or SNS).
- **Notification service subscribes** to relevant events, determines which users should be notified and via which channels (push, email, SMS) based on user preferences.
- **Per-channel workers**: a push notification worker, email worker, SMS worker — each independently scalable, each with its own retry and DLQ.
- **User preferences**: a table mapping `(userId, notificationType) → [channels]`. Check this before dispatching to any channel.
- **Deduplication**: include an event ID; consumers check if they've already processed this event (idempotency).
- **Retry and DLQ**: failed deliveries (email bounce, push token expired) retry with exponential backoff, then go to DLQ for inspection.

## Best Practices

- **Do the problem out loud, not in your head** — the skill being tested is "can you communicate a design under time pressure," not just "do you know the components."
- **Intentionally break the "obvious" approach first** — for news feed: "naive fan-out on read is O(following × post_frequency) per request, which breaks at scale." Then present the optimization.
- **Always ask about consistency requirements** — a URL shortener needs strong consistency (duplicate codes are bad); a news feed tolerates eventual consistency (a 2-second lag in seeing new posts is fine).
- **Go deep where the problem is hard, broad elsewhere** — in 30-45 minutes, you can't design every component in detail. Identify the core challenge and allocate your time to it; wave your hand at the boring parts ("standard load balancer + auto-scaling group here").
- **Know when to use a database vs. cache vs. queue vs. pub/sub** — the taxonomy: database for persistence, cache for read performance, queue for work distribution, pub/sub for event fan-out.

## Common Interview Questions

**Q1: How do you handle race conditions in URL shortener code generation?**
A: Two approaches: (1) Generate a candidate code (hash/counter), check if it exists, insert if not — but two writers can both see "doesn't exist" and both try to insert. Fix with a unique constraint on the code column; the losing writer gets a conflict error and retries. (2) Pre-generate a pool of codes (a "code service" pre-populates a set of unused codes); each API server takes a batch from the pool. Atomicity guaranteed by the database's unique constraint.

**Q2: In a chat application, how do you handle messages sent to a user who is currently offline?**
A: Don't discard them — persist every message to the database as soon as it's received from the sender. When a recipient reconnects via WebSocket, the client sends its last-seen message timestamp/ID, and the server delivers all messages since then. This is a "store-and-forward" model: real-time delivery when online, pull from storage on reconnect.

**Q3: How would you handle "celebrity" users (millions of followers) in a fan-out-on-write news feed?**
A: Skip them from fan-out. When a user with >N followers posts, don't push to N feeds — store the post normally. On read, fetch the user's pre-computed feed (from non-celebrity follows) and merge in recent posts from celebrity accounts they follow. Since celebrities post infrequently relative to read frequency, this is efficient: one additional query per page of feed content.

**Q4: What is the "thundering herd" problem and how do you mitigate it?**
A: When a cache expires, multiple simultaneous requests all see a cache miss and all hit the database simultaneously — creating a load spike. Mitigations: (1) Cache-locking: the first request to see a miss acquires a lock and refreshes the cache; other requests wait or serve stale data. (2) Jittered TTLs: add random variance to cache expiry times so not all entries expire simultaneously. (3) Background refresh: proactively refresh the cache before expiry so it's never cold.

**Q5: How do you ensure exactly-once delivery for notifications?**
A: Exactly-once delivery is very hard in distributed systems. Instead, design for at-least-once delivery + idempotent processing. Include a unique event ID with every event. The notification consumer records processed event IDs in a database (with a TTL for cleanup). Before processing, check if the ID has been seen; if so, skip. This gives effectively-once behavior: the processing is idempotent, so even if a notification is "processed" twice, it's only sent once.

## Practice Exercises

1. **URL shortener with analytics**: Extend the URL shortener design to support: (a) total click count per short URL (updated in real time), (b) click count by country (requiring IP geolocation lookup), and (c) a dashboard that shows clicks per hour for the past 7 days. What new components do you need? Which aggregations can be precomputed?

2. **Rate limiter variants**: Design a rate limiter that supports three different limit types simultaneously: (a) 100 requests/minute per user ID, (b) 10 requests/second per IP address, and (c) 1,000 requests/hour per API key. Which of these is most likely to have hot keys in Redis? How do you handle that?

3. **Feed ranking**: The basic news feed shows posts in reverse chronological order. Design a "ranked" feed that takes into account: post recency, user engagement with the poster (you see more posts from people you interact with), post popularity (likes/comments), and content type (videos scored differently than text posts). What signals do you collect and how do you use them without recomputing the entire feed on every request?

## Key Takeaways

- Every system design answer follows the same flow: clarify → estimate → sketch → identify bottleneck → name trade-offs.
- URL shortener: key-value store, hash/counter-based code generation, heavy cache on reads.
- Rate limiter: Redis `INCR + EXPIRE` for distributed atomic counters; token bucket or sliding window algorithm.
- Chat app: WebSockets for real-time delivery, separate persistent store for messages, pub/sub for group fan-out.
- News feed: fan-out on write for typical users, fan-out on read for celebrities, hybrid for real production systems.
- Notification system: event-driven with pub/sub, per-channel workers, user preferences, deduplication via event IDs.
- Do these problems out loud — interview system design is as much a communication skill as a technical one.
