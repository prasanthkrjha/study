# Classic Design Problems

This unit is where 5.1–5.4's vocabulary gets exercised against specific, commonly-asked problems. The goal isn't to memorize a "correct" design for each — it's to practice the same structured approach on all of them.

## A repeatable approach for any "design X" question

1. **Clarify requirements and scale.** How many users? Reads vs. writes ratio? Is strong consistency required, or is eventual consistency acceptable? Don't skip this — the right answer changes completely depending on scale.
2. **Sketch the high-level components** (client → load balancer → API → database, plus cache/queue where relevant) before diving into any one piece.
3. **Identify the bottleneck** the problem is actually testing, and go deep there.
4. **Name the trade-offs explicitly** as you make choices — this is what separates a strong answer from a list of buzzwords.

## Design a URL shortener

Core challenge: generating short, unique codes for URLs at scale, and looking them up fast on redirect. Approach: a key-value store (code → long URL) is a near-perfect fit — reads (redirects) vastly outnumber writes (new shortened URLs), which argues for a cache in front of the database. Code generation: either a counter converted to base62, or a hash of the URL truncated and checked for collisions. Discuss: custom aliases, expiry, and analytics (click counts) as extensions once the core works.

## Design a rate limiter

Covered in mechanism terms in Unit 5.2 (token bucket, sliding window) — the system design angle adds: where does the rate-limiter state live? A single-instance in-memory counter doesn't work once you have multiple API servers behind a load balancer, because each instance would track its own separate count. The fix is centralizing counters in something shared and fast — Redis is the standard answer, since `INCR` with a TTL gives you an atomic, shared counter across all instances.

## Design a chat app

Core challenge: real-time bidirectional communication. WebSockets (not polling) are the standard answer for low-latency delivery. Discuss: message persistence (a database, separate from the real-time delivery layer), presence/online-status (often a separate lightweight system, since it changes constantly and doesn't need durability), and fan-out for group chats (a message to a group needs to reach every connected member — related to the pub/sub pattern in Unit 5.4).

## Design a news feed

Core challenge: efficiently generating a personalized, ranked feed for millions of users. Two classic strategies: **fan-out on write** (when someone posts, immediately push it into every follower's feed — fast reads, expensive/slow writes for users with huge follower counts) vs. **fan-out on read** (compute the feed at request time by pulling from everyone you follow — cheap writes, more expensive reads). Most real systems use a hybrid: fan-out on write for typical users, fan-out on read for users with huge followings (to avoid a single post fanning out to millions of feeds instantly).

## Design a notification system

Core challenge: reliably delivering notifications across multiple channels (push, email, SMS) without duplicating logic per channel. A queue-based, event-driven design (Unit 5.4) fits naturally: an event ("order shipped") is published once, and separate consumers handle each channel. Discuss: user preferences (which channels they've opted into), deduplication (don't send the same notification twice if an event fires twice), and retry/backoff for failed deliveries.

## Practice tip

Do these out loud, not just in your head — narrate your reasoning as if explaining to an interviewer, and time yourself. The skill being tested is as much "can you communicate a design under time pressure" as "do you know the right components."
