# Component & Integration Testing with React Testing Library

React Testing Library (RTL) was created in response to the pattern of testing React component internals — checking component state, calling instance methods, and querying by CSS class name. Tests written that way pass when the component works but also break when the component is refactored correctly, because they are coupled to the implementation rather than the behavior. RTL's answer is to test components the way a user interacts with them: by what appears in the DOM, by what accessible roles elements have, and by what happens when a user types or clicks.

The core philosophy is stated directly in RTL's documentation: "The more your tests resemble the way your software is used, the more confidence they can give you." This has a concrete implication for how you write tests: the test should not know whether a component manages state with `useState`, `useReducer`, or a state management library. The test should only know what renders in the DOM as a result of user actions.

An important secondary effect of RTL's query priority — preferring queries like `getByRole` and `getByLabelText` over `getByTestId` — is that it acts as an implicit accessibility audit. If you cannot query a button by its accessible role and name, that is evidence the button is not properly accessible to a screen reader user either. Writing RTL tests and making them pass often improves accessibility as a side effect.

---

## Theory & Fundamentals

### Behavior Testing vs. Implementation Testing

Implementation testing: asserting that a specific function was called internally, that state has a specific value, that a specific class name is present. These tests break when you refactor even if the user-facing behavior is unchanged.

Behavior testing: asserting that a specific text appears, a specific button is enabled or disabled, a specific error message shows after an invalid action. These tests survive refactors that do not change user-visible behavior.

The rule: if you can freely change the internals of a component — replacing `useState` with a custom hook, changing a class name, restructuring the component tree — and your tests still pass, they are behavioral. If those internal changes break your tests, they are implementation tests.

### Query Priority

RTL provides multiple query functions and recommends a priority order:

1. **Role queries** (`getByRole`) — queries by ARIA role (button, textbox, heading, etc.) with an optional `name` that matches the accessible label. The most semantically meaningful and accessibility-aligned.
2. **Label queries** (`getByLabelText`) — queries a form input by its associated label. For form fields, this is often the most natural query.
3. **Placeholder/text** (`getByPlaceholderText`, `getByText`) — visible text content, useful for non-input elements.
4. **Display value** (`getByDisplayValue`) — current value of a form element.
5. **Alt text** (`getByAltText`) — for images.
6. **Title** (`getByTitle`) — for elements with title attributes.
7. **Test ID** (`getByTestId`) — escape hatch; use only when no semantic query fits.

The `getBy*` prefix throws if zero or more than one element matches. `queryBy*` returns null on no match (does not throw). `findBy*` returns a promise and retries until the element appears or times out — essential for async rendering.

### Async Rendering

React state updates, data fetching, and effects are asynchronous. After simulating a user action, the DOM may not update synchronously. RTL provides:
- `findBy*`: waits (with retries) until the element appears. Use for elements that appear after async operations.
- `waitFor`: retries an assertion until it passes or times out. Use when the element already exists but you are waiting for a change.
- `waitForElementToBeRemoved`: waits for an element to disappear from the DOM.

## Core Concepts / Techniques

### Rendering Components

```jsx
import { render, screen } from '@testing-library/react';

// render() mounts the component in a jsdom environment
// screen provides queries against the rendered DOM

test('renders the product name and price', () => {
  render(<ProductCard name="Coffee Mug" price={12.99} />);

  // getByRole + name option: matches the heading with that text
  expect(screen.getByRole('heading', { name: /coffee mug/i })).toBeInTheDocument();

  // getByText: find by visible text content
  expect(screen.getByText('$12.99')).toBeInTheDocument();
});
```

### Querying the DOM

```jsx
// getByRole examples — most preferred query type
screen.getByRole('button', { name: /submit/i });   // button with accessible name "Submit"
screen.getByRole('textbox', { name: /email/i });   // input labeled "Email"
screen.getByRole('checkbox', { name: /agree/i });
screen.getByRole('heading', { level: 2 });          // <h2> elements specifically
screen.getByRole('link', { name: /view details/i });
screen.getByRole('img', { name: /product photo/i }); // img with alt text

// getByLabelText: matches <input> associated with <label>
screen.getByLabelText(/email address/i);
screen.getByLabelText(/password/i);

// queryBy: returns null instead of throwing when not found
// Good for asserting something is NOT in the DOM
expect(screen.queryByText(/error/i)).not.toBeInTheDocument();

// findBy: async, retries until element appears (returns a Promise)
const successMessage = await screen.findByText(/order placed/i);
expect(successMessage).toBeInTheDocument();

// getAllBy, queryAllBy, findAllBy: return arrays of matching elements
const buttons = screen.getAllByRole('button');
expect(buttons).toHaveLength(3);
```

### User Events

```jsx
import userEvent from '@testing-library/user-event';
// userEvent simulates real browser interactions (full event sequence)
// Prefer userEvent over fireEvent — it is more realistic

test('submits the login form with valid credentials', async () => {
  const user = userEvent.setup();   // creates a userEvent instance
  const mockSubmit = jest.fn();

  render(<LoginForm onSubmit={mockSubmit} />);

  // type simulates a real user typing character by character
  await user.type(screen.getByLabelText(/email/i), 'test@example.com');
  await user.type(screen.getByLabelText(/password/i), 'secret123');

  // click fires mousedown, mouseup, click events in sequence
  await user.click(screen.getByRole('button', { name: /log in/i }));

  expect(mockSubmit).toHaveBeenCalledWith({
    email: 'test@example.com',
    password: 'secret123'
  });
});

// Other userEvent interactions
await user.clear(screen.getByLabelText(/search/i));  // clears input value
await user.selectOptions(screen.getByRole('combobox'), ['option-1']);
await user.keyboard('{Enter}');                       // keyboard events
await user.tab();                                     // focus navigation
```

### Async Utilities and waitFor

```jsx
test('shows a loading state then displays fetched data', async () => {
  render(<UserProfile userId="42" />);

  // Loading state should be visible immediately
  expect(screen.getByText(/loading/i)).toBeInTheDocument();

  // findBy waits for the element to appear (default 1000ms timeout)
  expect(await screen.findByText('Prasanth Kumar Jha')).toBeInTheDocument();

  // Loading state should be gone after data loads
  expect(screen.queryByText(/loading/i)).not.toBeInTheDocument();
});

// waitFor: retry an assertion until it passes
test('disables the button while submitting', async () => {
  const user = userEvent.setup();
  render(<ContactForm />);

  await user.click(screen.getByRole('button', { name: /send/i }));

  // Button becomes disabled immediately after click
  await waitFor(() => {
    expect(screen.getByRole('button', { name: /send/i })).toBeDisabled();
  });
});
```

## Code Examples

### Testing a Form with Validation

```jsx
// src/components/RegistrationForm.test.jsx
import { render, screen, waitFor } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import RegistrationForm from './RegistrationForm';

describe('RegistrationForm', () => {
  const user = userEvent.setup();

  async function fillAndSubmit({ email, password, confirmPassword }) {
    if (email)           await user.type(screen.getByLabelText(/email/i), email);
    if (password)        await user.type(screen.getByLabelText(/^password/i), password);
    if (confirmPassword) await user.type(screen.getByLabelText(/confirm password/i), confirmPassword);
    await user.click(screen.getByRole('button', { name: /register/i }));
  }

  beforeEach(() => render(<RegistrationForm />));

  it('renders all form fields', () => {
    expect(screen.getByLabelText(/email/i)).toBeInTheDocument();
    expect(screen.getByLabelText(/^password/i)).toBeInTheDocument();
    expect(screen.getByLabelText(/confirm password/i)).toBeInTheDocument();
    expect(screen.getByRole('button', { name: /register/i })).toBeInTheDocument();
  });

  it('shows an error when email is invalid', async () => {
    await fillAndSubmit({ email: 'not-an-email', password: 'abc123', confirmPassword: 'abc123' });
    expect(await screen.findByText(/valid email/i)).toBeInTheDocument();
  });

  it('shows an error when passwords do not match', async () => {
    await fillAndSubmit({ email: 'a@b.com', password: 'abc123', confirmPassword: 'xyz789' });
    expect(await screen.findByText(/passwords must match/i)).toBeInTheDocument();
  });

  it('submits successfully with valid inputs', async () => {
    await fillAndSubmit({ email: 'a@b.com', password: 'secure123', confirmPassword: 'secure123' });
    expect(await screen.findByText(/registration successful/i)).toBeInTheDocument();
  });
});
```

### Mocking API Calls with MSW

```javascript
// src/mocks/handlers.js
import { http, HttpResponse } from 'msw';

export const handlers = [
  http.get('/api/users/:id', ({ params }) => {
    return HttpResponse.json({
      id: params.id,
      name: 'Prasanth Kumar Jha',
      email: 'prasanth@example.com'
    });
  }),

  http.post('/api/orders', async ({ request }) => {
    const body = await request.json();
    return HttpResponse.json({ id: 'order-1', ...body }, { status: 201 });
  }),
];

// src/setupTests.js
import { setupServer } from 'msw/node';
import { handlers } from './mocks/handlers';

export const server = setupServer(...handlers);
beforeAll(() => server.listen());
afterEach(() => server.resetHandlers()); // reset per-test overrides
afterAll(() => server.close());

// In a specific test, override the default handler
test('shows error message on API failure', async () => {
  server.use(
    http.get('/api/users/:id', () =>
      HttpResponse.json({ message: 'User not found' }, { status: 404 })
    )
  );

  render(<UserProfile userId="99" />);
  expect(await screen.findByText(/user not found/i)).toBeInTheDocument();
});
```

### Integration Test: Full User Flow

```jsx
// Test a complete "add to cart and checkout" flow
// This is an integration test — it tests multiple components working together
import { render, screen, within } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import App from './App';

test('user can add a product to cart and view the updated cart count', async () => {
  const user = userEvent.setup();
  render(<App />);

  // Navigate to a product
  await user.click(screen.getByRole('link', { name: /coffee mug/i }));

  // Cart count starts at 0
  const cartIcon = screen.getByRole('button', { name: /cart/i });
  expect(within(cartIcon).getByText('0')).toBeInTheDocument();

  // Add to cart
  await user.click(screen.getByRole('button', { name: /add to cart/i }));

  // Cart count updates to 1
  expect(within(cartIcon).getByText('1')).toBeInTheDocument();
});
```

## Best Practices

- **Query by role first**, then label, then text — reach for `getByTestId` only when no accessible query fits; using role queries first ensures your components have proper accessibility structure.
- **Use `userEvent` instead of `fireEvent`** — `userEvent` simulates the full browser event sequence a real user interaction triggers; `fireEvent` fires only the named event and misses surrounding events that application code may depend on.
- **Use `findBy*` for elements that appear after async operations** — never use `getBy*` followed by manual waits; RTL's async queries handle retry logic correctly with appropriate timeouts.
- **Mock at the network boundary with MSW** rather than mocking module imports in RTL tests — MSW intercepts actual fetch/XHR calls, making tests closer to what the browser actually does.
- **Test user flows, not component trees** — a test that clicks through a real user action (fills a form, submits, sees a result) is more valuable than a test that renders a component and checks its props.
- **Avoid snapshot tests for component logic** — snapshot tests catch any DOM change (including meaningless refactors) and require constant manual verification; prefer explicit assertions about specific text or roles.
- **Wrap provider setup in a custom render utility** — create a `renderWithProviders(ui, options)` wrapper that includes all necessary context providers (Router, Store, Theme) so individual tests don't need boilerplate.

## Common Interview Questions

**Q: What is the guiding philosophy of React Testing Library?**
A: Test components the way users interact with them — through visible text, accessible roles, and simulated user events — rather than by querying internal state or implementation details. This produces tests that are resilient to refactoring and serve as meaningful documentation of expected behavior.

**Q: What is the difference between getBy, queryBy, and findBy queries?**
A: `getBy*` throws if zero or more than one element matches — use it when the element must be present. `queryBy*` returns null when no element matches instead of throwing — use it to assert an element is NOT present. `findBy*` is async and retries until the element appears or a timeout elapses — use it for elements that appear after async operations like data fetching.

**Q: Why is getByRole preferred over getByTestId?**
A: `getByRole` queries by ARIA role and accessible name, which is how assistive technology (screen readers) experiences the page. A component that passes `getByRole` tests is also accessible to users with disabilities. `getByTestId` requires adding `data-testid` attributes to the DOM, which are implementation details that add noise to the HTML and couple tests to markup that has no semantic meaning.

**Q: What is the difference between userEvent and fireEvent?**
A: `userEvent` simulates realistic browser interactions — typing triggers focus, keydown, input, keyup, and change events in sequence. `fireEvent` dispatches only the single specified event. `userEvent` is preferred because it tests the full event chain that application code may depend on; `fireEvent` can produce false-positive test results when event handlers depend on the full sequence.

**Q: How do you test a component that makes an API call on mount?**
A: Mock the API at the network level using MSW (Mock Service Worker), which intercepts fetch/XHR requests and returns controlled responses. Render the component, wait for the async data to appear using `findBy*`, and assert on the rendered content. This approach tests the component's network integration without hitting a real server.

**Q: What is the within utility and when is it useful?**
A: `within(element)` scopes subsequent queries to within a specific DOM element, rather than searching the entire document. Use it when the same text or role appears multiple times in the document and you need to query within a specific section — for example, finding a "Delete" button within a specific list item when multiple list items each have their own "Delete" button.

**Q: How would you test that an error message appears when an API call fails?**
A: Using MSW, override the default handler for the specific test to return an error response. Render the component, trigger the action that initiates the API call (or let it fire on mount), then use `findByText` to wait for the error message to appear in the DOM. Assert that the error message text is present and that the normal success content is absent.

## Practice Exercises

1. **Form with validation**: Write tests for a login form component. Test that: the form renders with email and password fields, an error message appears when the email is left empty and the form is submitted, an error appears for a password under 8 characters, and a success callback is called with the correct values when the form is valid.

2. **Async data fetching**: Test a `ProductList` component that fetches products from `/api/products` on mount. Write tests for: the loading state while fetching, the product names appearing after fetch succeeds, and an error message when the fetch returns a 500. Use MSW to mock the API.

3. **Interactive counter**: Test a `Counter` component with increment, decrement, and reset buttons. Test that the initial value displays correctly, each button changes the count as expected, the count cannot go below zero (if that is a requirement), and the reset button returns the count to zero.

4. **Conditional rendering**: Test a `UserMenu` component that shows a "Log in" button when the user is not authenticated and shows the user's name with a "Log out" button when they are. Use context or props to control the authentication state. Test both states and the transition between them.

5. **Integration flow**: Test a shopping cart flow that spans two components: a `ProductCard` with an "Add to cart" button and a `CartSummary` that displays the item count and total. Test that clicking "Add to cart" updates the count in `CartSummary` and that removing an item decrements it.

## Key Takeaways

- RTL's philosophy: test behavior users can see (text, roles, enabled/disabled state) rather than implementation details (state values, class names, internal function calls).
- Query priority: `getByRole` first (most accessible and semantic), then `getByLabelText`, then `getByText`, then `getByTestId` as a last resort.
- `getBy*` throws if absent; `queryBy*` returns null; `findBy*` is async and retries — match the variant to whether the element is expected to be immediately present, optionally absent, or yet to appear.
- `userEvent` simulates the full browser event sequence; `fireEvent` fires only the single named event — prefer `userEvent` for accurate simulation of user interaction.
- Mock APIs at the network level with MSW rather than mocking imports — this tests the component's actual fetch/XHR code path and produces more realistic tests.
- Wrap provider setup in a custom `renderWithProviders` utility so tests stay focused on behavior, not on boilerplate context setup.
- Async queries (`findBy*`, `waitFor`) are the correct tool for anything that involves React state updates, effects, or data fetching — never use `getBy*` and hope the DOM has already updated.
- A test that cannot be written without querying internal state or bypassing the DOM is often a signal that the component's public interface needs rethinking, not that the test tool is wrong.
