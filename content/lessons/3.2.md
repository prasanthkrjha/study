# Component/Integration Testing (React Testing Library)

RTL's entire philosophy is captured in one sentence from its docs: **"the more your tests resemble the way your software is used, the more confidence they can give you."** This unit is about testing behavior, not implementation.

## Behavior over implementation details

A brittle test reaches into component internals (state variables, class names, instance methods). A good RTL test interacts with the component the way a user would — clicking, typing, reading visible text — so refactors that don't change behavior don't break the test:

```jsx
// Brittle: breaks if you rename a CSS class or refactor internal state
expect(wrapper.find(".submit-btn").prop("disabled")).toBe(true);

// Resilient: only breaks if the actual user-visible behavior changes
expect(screen.getByRole("button", { name: /submit/i })).toBeDisabled();
```

## Querying by role/text, not CSS class

RTL's query priority (accessible-role queries first) exists on purpose — it doubles as an accessibility check, since a query like `getByRole("button", { name: "Submit" })` only works if the element is genuinely accessible (has the right role and an accessible name):

```jsx
screen.getByRole("textbox", { name: /email/i });
screen.getByText(/welcome back/i);
screen.getByLabelText(/password/i);
```

Reach for `getByTestId` only as a last resort when no accessible query fits — it's an escape hatch, not the default.

## Simulating user events

```jsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("submits the form with entered email", async () => {
  const user = userEvent.setup();
  render(<LoginForm onSubmit={handleSubmit} />);

  await user.type(screen.getByLabelText(/email/i), "test@example.com");
  await user.click(screen.getByRole("button", { name: /log in/i }));

  expect(handleSubmit).toHaveBeenCalledWith({ email: "test@example.com" });
});
```

`userEvent` (not the lower-level `fireEvent`) is preferred because it simulates the full sequence of real browser events (focus, keydown, keyup, input) a user's action would actually trigger.

## Async utilities

Anything involving a fetch call, a timeout, or a state update after a promise resolves needs `findBy*` (returns a promise, retries until found) or `waitFor`:

```jsx
test("shows fetched user name", async () => {
  render(<UserProfile userId={1} />);
  expect(await screen.findByText("Prasanth Kumar Jha")).toBeInTheDocument();
});
```

Using `getBy*` here would fail immediately, before the async data has arrived — `findBy*` polls until it appears or times out.

## Mocking API calls

Intercept network requests at the boundary (commonly with `msw` — Mock Service Worker) so components are tested with realistic request/response cycles without hitting a real backend:

```js
const server = setupServer(
  http.get("/api/user/:id", () => HttpResponse.json({ name: "Prasanth" }))
);
```

## Practice tip

Pick one component with actual user interaction (a form, a toggle, a list with filtering) and test it purely through what a user sees and does — no direct state or prop inspection. If you can't write the test without reaching into internals, that's often a sign the component's public interface needs rethinking, not that RTL is being difficult.
