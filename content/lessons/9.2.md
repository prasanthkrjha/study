# Technical Conceptual Q&A

Technical conceptual questions test your understanding of mechanisms, trade-offs, and consequences — not your ability to recite a definition. A weak answer is a definition. A strong answer explains why something exists, what problem it solves, and what breaks when you misuse it.

This unit teaches each concept first, then shows you what a strong interview answer looks like. The goal is genuine understanding — not a memorized script.

**Answer format**: what it is (1-2 sentences) + why it exists / what problem it solves + the key trade-off or failure mode. Don't over-hedge: "it depends on the context" is true of almost everything and not useful by itself. Give the answer that applies to the most common scenario first, then name the exception.

## Theory & Fundamentals

### React: Reconciliation and the Virtual DOM

**Understanding the problem first**

The browser's DOM (Document Object Model) is the live, in-memory representation of your page. When you change it — add an element, update a class, modify text — the browser has to do work: recalculate layout, repaint pixels, re-evaluate CSS. This work is not instant. When a JavaScript application updates the DOM directly on every state change, those updates trigger repeated layout recalculations, and for complex UIs this becomes visibly slow.

React's solution is to never touch the real DOM directly until it's absolutely necessary. React maintains an in-memory copy of the UI structure called the virtual DOM — a plain JavaScript object tree. When your component's state changes, React constructs a NEW virtual DOM tree representing what the UI should look like. It then COMPARES this new tree to the previous one (this is "diffing" or "reconciliation") and calculates the minimum set of changes needed to make the real DOM match. Only those minimum changes are applied to the real DOM.

**Walking through what happens when state changes**

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <div><p>Count: {count}</p><button onClick={() => setCount(count + 1)}>+</button></div>;
}
```

When the user clicks the button:

1. `setCount(count + 1)` is called, scheduling a re-render.
2. React calls the `Counter` function again, producing a new virtual DOM tree. The new tree's `<p>` element has text "Count: 1" instead of "Count: 0".
3. React diffs the new tree against the previous tree. It finds that one text node changed: `"Count: 0"` → `"Count: 1"`.
4. React applies exactly one change to the real DOM: updating that text node's content.
5. The button, the div, the paragraph element itself — none of those are touched. They didn't change.

Without React, you might write `document.querySelector('p').textContent = 'Count: 1'` — which also works. React's value becomes apparent in complex applications with many components where you don't want to manually track which parts of the DOM need updating.

**The diffing heuristic**

React's diffing algorithm uses heuristics to stay fast:

*Same type at same position → update, don't replace*. If the old tree had a `<div>` at a position and the new tree has a `<div>` at the same position, React updates the div's attributes rather than destroying and recreating it. This preserves any DOM state (like input focus) and avoids expensive DOM construction.

*Different type at same position → destroy and rebuild*. If a `<div>` becomes a `<span>`, React destroys the entire `<div>` subtree and creates a new `<span>` subtree from scratch. The assumption: if the type changed, the old subtree's state is probably no longer relevant.

**The `key` prop**

Lists are where the diffing heuristic breaks down without help. Consider a list of items:

```jsx
// Before: ['Alice', 'Bob', 'Carol']
// After: ['Dave', 'Alice', 'Bob', 'Carol'] (Dave inserted at the front)

<ul>
  {items.map(name => <li>{name}</li>)}
</ul>
```

Without keys, React compares by position: position 0 was "Alice", now it's "Dave" → update. Position 1 was "Bob", now it's "Alice" → update. Position 2 was "Carol", now it's "Bob" → update. Position 3 is new → insert "Carol". React makes four DOM changes when it could have made one (inserting Dave at the top).

With keys:

```jsx
<ul>
  {items.map(name => <li key={name}>{name}</li>)}
</ul>
```

React sees that "Alice", "Bob", and "Carol" (matching keys) are the same elements they were before — just in different positions. It moves them and inserts "Dave." One operation instead of four, and component state (like a checkbox being checked) is preserved across the reorder.

**The key misconception**: "using index as the key is fine." Using index as the key works when the list is static, but breaks when items are reordered or inserted in the middle. React associates the key with the component's state. If you add an item at the front of a list and the existing items all shift their index by one, React thinks every component mapped to a new element — component state gets misassigned. Use a stable, unique ID (a database ID, a UUID, a slug) as the key.

**Another common misconception**: "React re-renders the entire DOM on every state change." No. React re-renders COMPONENTS whose state or props changed. Of those components' output, only the actual DOM mutations (from the diff) are applied. `React.memo` can prevent a child component from re-rendering if its props didn't change. `useMemo` prevents expensive computations from re-running when unrelated state changes.

**Interview Q&A**

*Q: What is the virtual DOM and why does React use it?*

A: The virtual DOM is an in-memory JavaScript object representation of the UI. React uses it to avoid touching the real DOM (which triggers expensive layout recalculations) on every state change. When state changes, React generates a new virtual DOM tree, diffs it against the previous tree, and applies only the minimum necessary mutations to the real DOM. This makes updates faster for complex UIs where changes are small and scattered across many components.

*Common misconception to call out*: React doesn't re-render the entire DOM on every state change — it re-renders affected components and applies only the diffed changes. Modern browsers are also faster at DOM manipulation than when React was designed, so the performance benefit is less dramatic than early React marketing suggested, but the programming model (describing what the UI should look like rather than imperative DOM mutations) remains a significant advantage.

### React: Hooks Rules and Why They Exist

**Understanding the WHY first**

React tracks hook state by the ORDER of hook calls within a component render, not by name. There is no identifier attached to a hook — React just knows "the first hook called in this component is slot 0, the second is slot 1, the third is slot 2" and so on. Every re-render, React expects the hooks to be called in the same order so it can match each call to its stored state.

This is not an arbitrary design choice. It enables hooks to work without any special syntax — no IDs, no registrations, no descriptors. You just call `useState` and React knows which state it belongs to by position.

**What breaks when you violate this**

```jsx
// BROKEN — do not do this
function BadComponent({ showExtra }) {
  const [name, setName] = useState('');     // slot 0 on every render
  
  if (showExtra) {
    const [extra, setExtra] = useState(''); // slot 1 ONLY when showExtra is true
  }
  
  const [count, setCount] = useState(0);   // slot 1 when showExtra is false
                                            // slot 2 when showExtra is true
  // ...
}
```

Trace through two renders:

Render 1 (`showExtra = false`): React calls useState twice. Slot 0 gets `name`'s state. Slot 1 gets `count`'s state.

Render 2 (`showExtra = true`): React calls useState three times. Slot 0 gets `name`'s state. Slot 1 now returns `count`'s state (from the previous render's slot 1) — but we just called it to initialize `extra`. So `extra` is initialized with `count`'s old value. Slot 2 is a new hook call React has never seen — React creates a new state slot for `count`, losing its previous value.

State is now corrupted: `extra` contains stale count data, `count` lost its state. And this happens silently — React won't throw an error about this in production, the state just becomes wrong.

**The rules as direct consequences of this design**

*"Always call hooks at the top level"* means: never put them inside if-statements, loops, or nested functions. Any code path that might skip a hook call will shift the slot numbers of subsequent hooks.

*"Only call hooks from React function components (or custom hooks)"* means: React's slot tracking only works during a component's render phase. Calling useState inside a regular function or a setTimeout callback runs outside the render phase — there's no component instance to attach the state to.

**Interview Q&A**

*Q: Why do hooks have to be called in the same order every render? Why can't they be inside if-statements?*

A: React tracks hook state by call order, not by name. The first useState call is always "slot 0," the second is "slot 1," and so on. If you put a hook inside a conditional, the condition might be false on one render (causing subsequent hooks to shift to earlier slots) and true on the next (shifting them back). This mismatch causes React to return the wrong state for each hook call — state gets corrupted silently. The rule "always call hooks at the top level" exists to guarantee the call order is identical on every render.

*Common misconception*: "I can call hooks conditionally as long as I'm careful." You can't be careful enough — the bugs appear in subtle cases (a prop changes, a feature flag flips) and are very hard to diagnose. The rule is absolute.

### React: Stale Closures in useEffect

**Understanding closures first**

A closure is a function that "closes over" variables from its surrounding scope — it captures references to those variables at the time the function is created. In React, every function you define inside a component (effect callbacks, event handlers, memoized values) is a closure over the component's current state and props.

```javascript
function makeCounter(start) {
  let count = start;
  return function increment() {
    count += 1;
    return count;
  };
}

const counter = makeCounter(0);
counter(); // 1
counter(); // 2
```

The `increment` function closes over `count`. It carries a reference to that specific `count` variable from when `makeCounter` was called.

In React components, closures work the same way — but the "surrounding scope" is the render. Each render creates a new function scope with new copies of state variables. Effect callbacks, event handlers, and other callbacks created during a render close over THAT RENDER'S values.

**The stale closure bug**

```jsx
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    // This effect is created on the initial render
    // It closes over count = 0 (the value at initial render time)
    const id = setInterval(() => {
      console.log(count); // always logs 0!
      setCount(count + 1); // always sets to 0 + 1 = 1 (never increments beyond 1)
    }, 1000);

    return () => clearInterval(id);
  }, []); // empty dependency array: effect only runs once

  return <div>{count}</div>;
}
```

What the user expects: the count increments by 1 every second.

What actually happens: the count stays at 1. Here's why: the effect is created once (empty dependency array) and its callback closes over `count = 0`. Every time the interval fires, it reads `count` from the closure — always 0. It calls `setCount(0 + 1)`, which sets count to 1, but the closure's `count` never updates. The interval is forever stuck reading the initial value.

**Fixing it: the dependency array approach**

```jsx
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);
  }, 1000);
  return () => clearInterval(id);
}, [count]); // tell React: recreate this effect when count changes
```

Now when count changes, React clears the old interval and creates a new one — a new closure over the NEW value of count. The interval always has the current count.

**Fixing it: the functional update approach (often better)**

```jsx
useEffect(() => {
  const id = setInterval(() => {
    setCount(prev => prev + 1); // functional update: no dependency on count
  }, 1000);
  return () => clearInterval(id);
}, []); // empty dependency array is now correct
```

`setCount(prev => prev + 1)` doesn't need to read `count` from the closure — React passes the current state value as an argument to the updater function. The closure doesn't capture `count` at all, so it never goes stale.

**Fixing it: useRef for "always current" access**

```jsx
const countRef = useRef(count);
countRef.current = count; // updated on every render

useEffect(() => {
  const id = setInterval(() => {
    console.log(countRef.current); // always reads the latest value
  }, 1000);
  return () => clearInterval(id);
}, []); // safe with empty deps because we read from the ref, not the closure
```

Refs are mutable — updating `countRef.current` doesn't cause a re-render. The effect's closure captures the ref object (stable reference), and reading `.current` always gives the latest value. This pattern is useful when you need to access current state inside an async operation without adding the state to the dependency array.

**Interview Q&A**

*Q: What is a stale closure in a React effect, and how do you fix it?*

A: Every render creates a new scope with new copies of state values. Effect callbacks are closures over the state at the render when they were created. If an effect has a timer, async operation, or event listener that outlives the render, it reads the state values from when it was created — not the current values. The fix depends on the situation: add the variable to the effect's dependency array (React recreates the effect with a fresh closure when the value changes), use the functional update form of setState so you don't need to read the value in the closure, or use useRef to always access the latest value without triggering re-renders.

*Common misconception*: "empty dependency array means the effect runs once and that's fine." Empty dependency array means the effect's closure captures the initial values of everything — which is only fine if the effect genuinely doesn't need current values from the component.

### Node.js: The Event Loop

**Understanding the problem first**

Node.js is a JavaScript runtime built on V8 (Chrome's JS engine). JavaScript is single-threaded — there is one execution stack, one set of running code at a time. You cannot run two JavaScript functions simultaneously.

This creates an obvious problem for web servers: a server needs to handle thousands of concurrent connections. If each connection runs JavaScript on the single thread, connection #2 can't start until connection #1 finishes. A server that blocks other users while processing one request is not a usable server.

The insight that makes Node.js work: most of the time a web server is waiting, not computing. A server receives a request, queries the database (wait), reads a file (wait), calls an external API (wait). The actual CPU work is small — a few milliseconds of JavaScript. The waiting can be hundreds of milliseconds.

The event loop exploits this: while waiting for I/O (database, files, network), the main thread is free to process other requests. When the I/O finishes, the callback is queued and executed when the main thread is available. Many requests can be "in progress" simultaneously even with a single thread — they're mostly just waiting.

**Walking through the event loop**

```javascript
console.log('1 - start');

setTimeout(() => {
  console.log('3 - timer callback');
}, 0);

fs.readFile('data.txt', (err, data) => {
  console.log('4 - file read complete');
});

console.log('2 - end of synchronous code');

// Output:
// 1 - start
// 2 - end of synchronous code
// 3 - timer callback (or 4, depending on how fast the file read is)
// 4 - file read complete
```

The synchronous code runs first (1 and 2). `setTimeout` schedules a callback to run after all pending I/O callbacks, with a delay of at least 0 ms. `fs.readFile` hands off the file read to libuv's thread pool (not the main thread) and returns immediately. The main thread then processes callbacks as they arrive.

The key phases:
1. **Synchronous code** runs first — the call stack must be empty before any callbacks run.
2. **I/O callbacks** — when the filesystem or network signals completion, the callback goes here.
3. **Timer callbacks** — setTimeout and setInterval callbacks run here, after I/O.
4. Back to waiting for new events.

**The blocking problem**

```javascript
// This blocks EVERYTHING
const result = crypto.pbkdf2Sync(password, salt, 100000, 64, 'sha512');
// ...this runs on the MAIN THREAD for ~500ms
// Every other request is frozen for those 500ms
```

`pbkdf2Sync` runs on the main JavaScript thread. For 500 milliseconds, the event loop cannot process any other callbacks — no HTTP requests, no database responses, nothing. This is "blocking the event loop," and it's the fundamental mistake you must avoid in Node.js.

The fix:

```javascript
// This doesn't block — hands off to libuv's thread pool
crypto.pbkdf2(password, salt, 100000, 64, 'sha512', (err, key) => {
  // This callback runs on the main thread AFTER the computation finishes
  // But during the 500ms computation, other requests are processed normally
});
```

The async version hands the computation to libuv's C++ thread pool (separate from the JS thread). The main thread returns to the event loop immediately and processes other requests. When the computation finishes, the callback is queued and runs on the main thread when available.

**Interview Q&A**

*Q: How does Node.js handle concurrent requests if JavaScript is single-threaded?*

A: Node.js uses the event loop. Most of a web server's time is spent waiting for I/O (database, network, file system). Instead of blocking the main thread during I/O, Node.js delegates I/O operations to libuv's thread pool. The main thread returns to the event loop and processes other requests while waiting. When I/O completes, the callback is queued and runs on the main thread. This means many requests can be "in progress" (waiting) simultaneously, even with a single JavaScript thread. The failure mode is synchronous CPU-intensive work (heavy computation, synchronous crypto, large JSON.parse) — these run on the main thread and block all other requests for their duration.

*Common misconception*: "Node.js is multithreaded." The JavaScript execution is single-threaded. libuv (which handles I/O) uses a thread pool internally, but your JavaScript code is always on one thread.

### Backend: JWT vs Sessions

**Understanding sessions from first principles**

When you log in to a website, the server needs to remember who you are on subsequent requests — HTTP is stateless, so each request arrives with no memory of previous ones.

Sessions solve this with a server-side record:

1. You submit your username and password.
2. The server verifies them, creates a session record in its database or Redis: `{sessionId: "abc123", userId: 42, createdAt: "..."}`.
3. The server sends you back a cookie containing just the session ID: `session_id=abc123`.
4. Every subsequent request, your browser sends the cookie automatically.
5. The server receives `session_id=abc123`, looks it up in the database, finds your user data, and knows who you are.

To log you out, the server deletes the session record. Your cookie still exists but the session ID no longer matches anything. The session is revoked instantly.

**Understanding JWTs from first principles**

JWT (JSON Web Token) takes a different approach:

1. You submit your username and password.
2. The server verifies them, creates a JSON object with your claims: `{userId: 42, role: "admin", exp: 1700000000}`.
3. The server SIGNS this object using a secret key (HMAC-SHA256 or RSA). The signature proves the token was created by this server and hasn't been tampered with.
4. The server encodes the claims + signature into a base64 string and sends it to you.
5. Every subsequent request, you include the JWT in the Authorization header.
6. The server VERIFIES THE SIGNATURE — no database lookup needed. If the signature is valid, the server trusts the claims in the token.

The critical difference: the server doesn't store anything. Any server that knows the secret key can verify the JWT. This makes JWTs inherently stateless — useful for distributed systems where multiple server instances don't share memory.

**The trade-off made concrete**

*Sessions*: simple, instant revocation (delete the session record), but requires a database or Redis lookup on every request, and requires shared storage if you have multiple server instances.

*JWTs*: no database lookup (fast, stateless, scales horizontally), but you cannot revoke them before they expire. If a user's JWT expires in 24 hours and you need to ban them immediately, the JWT is still valid until expiry. You can build a blacklist (a database of revoked tokens that you check on each request), but now you're making a database lookup again — you've reintroduced the state you were trying to avoid.

This is the core JWT revocation problem. Practical workarounds:
- Use short expiry times (15-60 minutes) + a refresh token flow. The refresh token IS stored server-side, but the access token is short-lived so the revocation window is small.
- Accept that instant revocation isn't possible for JWT access tokens (acceptable for most consumer apps).
- Maintain a blacklist if instant revocation is required (bank account bans, security incidents).

**When to use which**:

Sessions: simple apps where instant revocation is critical (admin banning a user, immediate security response), monolithic apps with a single server instance, or when you're already using a database on every request anyway.

JWTs: stateless/distributed systems (multiple servers, microservices, mobile apps talking to an API), when you need to verify tokens in multiple services without shared session storage, and when short-lived tokens make the revocation trade-off acceptable.

**Interview Q&A**

*Q: What is the difference between JWT and session-based authentication?*

A: Sessions store state server-side: the server keeps a session record and gives the client only a random session ID. Every request, the server looks up the ID to find user data. This enables instant revocation (delete the record) but requires a server-side store and a lookup per request. JWTs are self-contained signed tokens — the server signs the claims and gives them to the client. Every request, the server verifies the signature (no database lookup). This scales horizontally without shared storage, but JWT revocation before expiry is difficult — you'd need a server-side blacklist, reintroducing the state you were trying to avoid. Use sessions when you need instant revocation and have a single data store. Use JWTs for stateless distributed systems where the revocation trade-off is acceptable.

*Common misconception*: "JWTs are encrypted." By default, JWTs are signed but NOT encrypted — anyone can decode and read the claims. The signature only proves the token wasn't tampered with, not that its contents are secret. Don't put sensitive information (password, credit card, private data) in a JWT payload without explicit encryption.

### Web: CORS

**Understanding the same-origin policy first**

Browsers enforce a rule called the same-origin policy: JavaScript running on `site-a.com` cannot make requests to `site-b.com`. This is a security boundary. Without it, a malicious website could use your browser (with your logged-in cookies) to make requests to your bank, read your emails, or perform actions on your behalf on any site you're logged into.

"Same origin" means: same protocol (http vs https), same domain, AND same port. `http://example.com` and `https://example.com` are different origins. `https://example.com` and `https://api.example.com` are different origins (different subdomain).

**What CORS actually is**

CORS (Cross-Origin Resource Sharing) is a mechanism that lets a SERVER opt out of the same-origin restriction for specific origins. It says: "I trust requests from `site-a.com`, so let them through even though the browser would normally block them."

The mechanism:

For "simple" requests (GET, POST with standard headers), the browser makes the request but holds the response until it sees the right headers:

```
// Server response must include:
Access-Control-Allow-Origin: https://site-a.com
// Or for any origin (use carefully):
Access-Control-Allow-Origin: *
```

If the `Access-Control-Allow-Origin` header is missing or doesn't match, the browser throws a CORS error and refuses to give the response to the JavaScript that made the request. The request still went to the server — the server processed it. CORS is enforced by the BROWSER, not the server.

**Preflight requests**

For "non-simple" requests — custom headers (like `Authorization: Bearer token`), methods other than GET/POST (PUT, DELETE, PATCH), or `Content-Type: application/json` — the browser first sends a preflight OPTIONS request:

```
OPTIONS /api/users/42
Origin: https://site-a.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: Authorization
```

The server must respond to the OPTIONS request:

```
Access-Control-Allow-Origin: https://site-a.com
Access-Control-Allow-Methods: GET, POST, DELETE
Access-Control-Allow-Headers: Authorization
```

Only if the preflight succeeds does the browser send the actual DELETE request. If your server doesn't handle OPTIONS requests, all non-simple requests fail even if you've set the right headers on your GET/POST responses.

**Why CORS errors only appear in browsers**

`curl`, Postman, and server-to-server calls have no same-origin policy. They will successfully call any server regardless of its CORS headers. This is why "it works in Postman but not in the browser" is such a common debugging experience — Postman doesn't enforce CORS because it's not a browser. The restriction is implemented in the browser as a security feature for end users, not in servers or non-browser clients.

**Interview Q&A**

*Q: What is CORS and why does it only appear in browsers?*

A: CORS (Cross-Origin Resource Sharing) is a browser-enforced mechanism that controls which cross-origin requests JavaScript is allowed to make. The same-origin policy blocks JavaScript on site A from reading responses from site B — this prevents malicious scripts from using your browser to make authenticated requests to other sites. CORS lets a server opt in to allowing specific cross-origin requests by including `Access-Control-Allow-Origin` headers in its responses. Non-simple requests (custom headers, PUT/DELETE/PATCH) require a preflight OPTIONS request that the server must also handle correctly. CORS is enforced by browsers only — curl, Postman, and server-to-server calls are unaffected, which is why a request that fails in a browser often works in Postman.

*Common mistake*: adding CORS headers to GET and POST responses but forgetting to handle the OPTIONS preflight. All your non-simple requests (anything with an Authorization header or JSON body) will fail because the preflight never gets a proper response.

### RAG: How It Works End to End

**Why RAG exists**

A language model's knowledge is frozen at training time. It doesn't know about your company's internal documents, recent events after its cutoff date, or the specific data in your database. You could put relevant information directly in the prompt, but a model's context window has a limit — you can't fit 10,000 pages of documentation in a single prompt.

RAG (Retrieval-Augmented Generation) solves this by retrieving only the relevant portions of your knowledge base and including them in the prompt. Instead of "know everything," the system does "find the relevant piece, then answer from it."

**The offline (indexing) phase**

This happens once (then incrementally as data changes):

```
Document → Split into chunks → Each chunk → Embedding model → Vector → Store in vector database
```

*Why chunks?* A document might have 50 pages. Embedding the entire document produces one vector that averages all its content — a query about paragraph 12 might not be similar to that averaged vector. Chunking splits the document into smaller pieces (typically 512-1000 tokens) so each chunk has a coherent topic.

*What an embedding is*: the embedding model (like `text-embedding-3-small`) converts a chunk of text into a dense numerical vector (e.g., 1536 numbers). The key property: text with similar *meaning* gets similar vectors, even if the exact words are different. "How do I return a product?" and "What is your return policy?" will produce vectors that are geometrically close in the 1536-dimensional space.

*What the vector database stores*: both the vector and the original chunk text (so you can retrieve the text later). Popular options: Pinecone, Chroma, Weaviate, pgvector (Postgres extension).

**The online (query) phase**

This happens on every user request:

```
User question → Embedding model → Query vector → 
Vector database similarity search → Top-k chunks → 
Insert chunks into prompt → LLM generates answer from chunks
```

Concretely:

```
User: "What is your return policy?"
Embed query → [0.23, -0.11, 0.84, ...] (1536 numbers)
Vector DB finds chunks with nearest vectors:
  - chunk from return-policy.pdf: similarity 0.91
  - chunk from FAQ.pdf: similarity 0.87
  - chunk from shipping-info.pdf: similarity 0.74
Top-2 chunks inserted into prompt:
  "Based on the following information:
   [chunk 1 text]
   [chunk 2 text]
   Answer: What is your return policy?"
LLM generates answer grounded in those specific chunks.
```

**The key insight**: similarity is measured in vector space, not by word overlap. "How do I send something back?" and "return policy" share no words, but their embedding vectors are close — they mean the same thing. This is why embedding-based retrieval catches paraphrases and semantic variations that keyword search misses.

**Interview Q&A**

*Q: Walk me through how a RAG system works end to end.*

A: Two phases. The offline phase: documents are split into chunks (typically 512-1000 tokens), each chunk is converted to a dense vector using an embedding model, and those vectors are stored in a vector database alongside the original text. The online phase: the user's question is embedded using the same model, the vector database finds the top-k chunks with the most similar vectors, those chunks are inserted into the prompt as context, and the LLM generates an answer grounded in that specific retrieved context. The core mechanism is semantic similarity in vector space — two questions that mean the same thing produce similar vectors even if they share no words, which is why RAG retrieval catches paraphrases that keyword search misses.

*Common misconception*: "larger chunks are always better." Larger chunks reduce the number of pieces but also dilute specificity — a 5,000-token chunk contains many topics, and a query about one topic may not be similar to the averaged embedding. Smaller, more focused chunks give more precise retrieval at the cost of losing some surrounding context. The right chunk size depends on your document structure and query type, which is why testing different chunk sizes with your evaluation harness matters.

### LLM: Fine-Tuning vs RAG vs Prompting

**Three levers, three different things they change**

The most important conceptual frame: these three approaches operate at completely different levels. They are not alternatives to each other — they serve different needs.

**Prompting** changes the INSTRUCTIONS the model receives at inference time. Nothing about the model itself changes — its weights, its knowledge, its fundamental capabilities are all the same. You're telling an unchanged model how to behave for your task. Cost: free. Speed: instant. Limitation: you cannot teach the model facts it doesn't have, and you cannot fundamentally change its deep behavioral patterns beyond what its training allows.

**RAG** changes what INFORMATION the model has access to during a specific request. The model is unchanged. Its knowledge base hasn't changed. But you've retrieved relevant documents and put them in the context window, so the model can answer questions using information it doesn't intrinsically "know." Cost: retrieval infrastructure. Speed: fast at query time, slower to set up initially. Limitation: the model still has to know how to reason about the retrieved information — RAG adds data, not capability.

**Fine-tuning** changes the MODEL ITSELF. You train further on your data, updating the model's weights. The changes are baked in — they affect every inference without needing prompts or retrieval. Cost: significant (compute, data collection, training jobs). Speed: slow to iterate. Limitation: teaches behavioral patterns, not factual knowledge — fine-tuned models are not more factually accurate about new information, and they can still hallucinate if retrieval is absent or poor.

**The decision tree**

*The model doesn't know about our company's internal documents or recent data*: RAG. This is a missing information problem. Fine-tuning doesn't help because you'd have to retrain every time your documents change.

*The model doesn't reliably follow our response format (always outputs JSON in our schema, always uses bullet points, always responds in formal English)*: Try prompting first — give explicit instructions and few-shot examples. If prompting reliably fails after serious effort, fine-tuning can encode the behavioral pattern directly into the weights.

*The model answers questions incorrectly or hallucinates facts about our domain*: First check retrieval (is the right information getting into the context?). Hallucination in RAG is usually a retrieval failure, not a model problem. Fine-tuning on your domain won't fix retrieval problems.

*The model's reasoning style needs to be fundamentally different (domain-specific jargon, specialized logical patterns)*: This is a legitimate fine-tuning case — after exhausting prompting.

**Why fine-tuning is overreached for**

Most "the model doesn't do X" problems are actually one of:
- Bad prompting (add explicit instructions, add few-shot examples)
- Missing information (add RAG)
- Unclear task definition (the desired behavior isn't actually well-defined enough to encode)

Fine-tuning requires collecting and curating 1,000+ high-quality examples, running training jobs, managing model versions, and re-running training every time your requirements change. The iteration speed is measured in days, not minutes. Exhaust prompting and RAG before accepting that fine-tuning cost.

**Interview Q&A**

*Q: When would you choose fine-tuning over RAG or better prompting?*

A: Fine-tuning changes HOW the model responds — its behavior, tone, format, reasoning style — baked into the weights. RAG changes WHAT INFORMATION the model has access to. Prompting changes the instructions for a specific request. Use RAG when the problem is missing information (company docs, recent data, domain-specific knowledge that changes). Use prompting when the problem is behavioral instructions the model can follow given clear guidance. Consider fine-tuning only when: the desired behavior is consistent and well-defined, prompting reliably fails even with many few-shot examples, and you have 1,000+ high-quality input/output examples. The most common mistake is reaching for fine-tuning when better prompting or RAG would solve the problem at a fraction of the cost.

*Common misconception*: "fine-tuning will make the model not hallucinate." Fine-tuning teaches behavioral patterns. If the model hallucinates because its retrieval didn't return the relevant information, fine-tuning won't fix that — the model still won't have the fact in context. Hallucination in RAG systems is primarily a retrieval problem. Fix retrieval first.

## Best Practices

- **Answer what + why + trade-off in 30-60 seconds, then stop**. If they want more, they'll ask follow-up questions. A tight, complete answer is more impressive than a meandering one.
- **Use concrete examples** — "JWT is like a signed library card: anyone who knows the library's official stamp can verify it's real without calling the library" is more memorable than a definition alone.
- **Know the failure mode** — interviewers frequently follow up with "what can go wrong with X?" If you only know the happy path, you'll stall. For every concept here, the failure mode is described explicitly.
- **Don't over-hedge** — "it depends on the context" is true of everything and not useful alone. Give the most common case first, then acknowledge the exceptions.

## Key Takeaways

- **Answer format**: what it is (1-2 sentences) + why it exists / what problem it solves + the key trade-off or failure mode. Not just a definition.
- **React reconciliation**: virtual DOM diffing finds minimum DOM mutations. The `key` prop enables correct reordering of lists — use stable IDs, not array indices.
- **Hooks rules**: React tracks hook state by call order, not by name. Conditional hooks corrupt state silently by shifting slot assignments. The rules are consequences of this design, not arbitrary restrictions.
- **Stale closures**: effect callbacks close over state from the render they were created in. Fixes: add to dependency array (recreate the closure), use functional state updates (no closure dependency), or use useRef (mutable, always-current access).
- **Node.js event loop**: single-threaded JS, but I/O delegates to libuv's thread pool — many I/O operations in flight simultaneously. Synchronous CPU work (crypto.pbkdf2Sync, large JSON.parse) blocks the main thread and freezes all concurrent requests.
- **JWT vs sessions**: sessions are stateful, stored server-side, instantly revocable but require lookup per request. JWTs are stateless, self-contained, scale without shared storage, but cannot be revoked before expiry without a blacklist. JWTs are NOT encrypted by default — don't put sensitive data in the payload.
- **CORS**: browser-enforced mechanism allowing servers to opt into cross-origin requests. CORS errors never appear in server-to-server calls or Postman — only in browser-based JavaScript. Non-simple requests require preflight OPTIONS handling in addition to CORS headers on responses.
- **RAG**: offline — chunk → embed → store in vector DB. Online — embed query → find similar vectors → retrieve chunks → include in prompt → generate answer. Semantic similarity catches paraphrases keyword search misses.
- **Fine-tuning vs RAG vs prompting**: prompting changes instructions, RAG changes available information, fine-tuning changes the model itself. Reach for fine-tuning only after exhausting prompting and RAG — it's expensive, slow to iterate, and won't fix retrieval problems.
