# Technical Conceptual Q&A

This unit is a rapid-reference for the conceptual questions that recur across full-stack and AI interviews — the goal is being able to answer each crisply in 30-60 seconds, then go deeper if asked.

## Theory & Fundamentals

### How to Answer Conceptual Questions

Technical conceptual questions test your understanding of mechanisms, trade-offs, and consequences — not your ability to define a term. A weak answer is a definition. A strong answer is a definition + the "why" + a trade-off or consequence.

**Weak**: "JWT is a stateless token."
**Strong**: "JWT is a self-contained, signed token — no server-side state lookup. The upside is scalability: any server can verify a JWT without a database call. The downside is revocation: you can't invalidate a JWT before it expires unless you maintain a server-side blacklist, which reintroduces the state you were trying to avoid."

Every conceptual answer should have: what it is (1-2 sentences) + when you'd use it + the key trade-off.

## Core Topics

### Frontend / React

**Reconciliation**: React compares the new element tree to the previous one (virtual DOM diffing) and computes the minimal set of real DOM mutations needed, rather than re-rendering the whole DOM on every state change. Uses a heuristic algorithm: elements of the same type at the same position are updated, not replaced; different type = full subtree replacement. The `key` prop helps React correctly identify list items across re-renders.

**Hooks rules**: hooks must be called in the same order on every render (never inside conditionals/loops) because React tracks hook state by call order index, not by name. Violating this causes state to shift to the wrong hook on the next render.

**Closure bugs in effects**: a callback or effect captures the value of a variable at the time it was created, not its latest value. `setTimeout(() => console.log(count))` inside a component captures the count from the render when the timeout was set. Fix: add `count` to the dependency array, or use a ref (`useRef`) to always access the latest value.

**Virtual DOM vs. real DOM**: the virtual DOM is an in-memory JavaScript object tree. React mutates the real DOM only for the differences (diffing result), not by replacing the entire tree. This makes updates faster when changes are small and scattered — though modern browsers are faster than early React assumed, so the benefit is less dramatic now.

### Backend / Node.js

**Event loop**: Node is single-threaded for JS execution but non-blocking for I/O. Expensive I/O (file reads, network calls, database queries) is delegated to the system/libuv thread pool; their callbacks are queued to run on the main thread once current synchronous code finishes. This is why one slow synchronous computation (e.g., `crypto.pbkdf2Sync`) blocks everything — there's only one JS thread — but many concurrent I/O operations don't block each other.

**REST API design**: resources as nouns (`/users/42`, not `/getUser`). HTTP verbs carry the action (GET to read, POST to create, PUT/PATCH to update, DELETE to remove). Status codes communicate outcome precisely (200 OK, 201 Created, 204 No Content, 400 Bad Request, 404 Not Found, 500 Internal Server Error). Idempotency: GET/PUT/DELETE are safely repeatable; POST typically isn't.

**JWT vs. sessions**:
- **Session**: the server stores state (session data in memory or Redis); the client holds only a session ID cookie. Easy to revoke instantly (delete the session). Requires a lookup on every request.
- **JWT**: self-contained, signed token; the client holds all claims. No server lookup needed — any server can verify the signature. Harder to revoke before expiry (you'd need a server-side blacklist, which reintroduces state). Choose JWTs for stateless, distributed systems; sessions for simpler apps where instant revocation matters.

**CORS**: a browser security mechanism that blocks a webpage from making requests to a different origin (domain/port/protocol) unless the server explicitly allows it via `Access-Control-Allow-Origin` response headers. Enforced by the browser, not the server — which is why CORS errors only appear in browser-based clients, never in server-to-server or `curl` requests. Non-simple requests (those with custom headers or non-GET/POST methods) trigger a preflight OPTIONS request the server must also allow.

### Databases

**SQL vs. NoSQL** (see Unit 5.3 for depth): SQL for relational, consistent, join-heavy workloads. NoSQL when you need horizontal write scaling, flexible schema, or a specialized access pattern (key-value, document, graph).

**Indexes**: a B-tree or hash data structure that enables O(log n) row lookup by a column value instead of O(n) full table scan. Speeds reads, slows writes (index must be updated on every insert/update/delete). Index columns you frequently filter, sort, or join on.

**N+1 query problem**: fetching a list of N records, then making one query per record to fetch related data — N+1 queries total. Fix: use a JOIN (single query) or batch fetch (one query for all related IDs). Common in ORMs when you access a relationship field inside a loop.

**Transactions and ACID**: Atomicity (all operations succeed or all fail), Consistency (DB moves from one valid state to another), Isolation (concurrent transactions don't see each other's partial results), Durability (committed data survives crashes). Use transactions whenever you need multiple writes to succeed or fail together.

### AI/LLM Conceptual

**How RAG works end-to-end**: chunk documents → embed chunks into vectors → store in a vector database → embed the incoming query → retrieve the most similar chunks → include them in the prompt as context → generate an answer constrained to that context.

**Chunking trade-offs**: too large = each chunk contains too much content, diluting relevance for a specific query. Too small = each chunk loses surrounding context needed to answer questions. Typical starting point: 512-1000 tokens with 10-20% overlap.

**Vector vs. keyword search**: dense/semantic search (embeddings) catches paraphrases and meaning but can miss exact terms. Sparse/keyword search (BM25, TF-IDF) catches exact terms but misses paraphrases. Production systems often combine both (hybrid search / reciprocal rank fusion).

**Hallucination mitigation**: ground the prompt explicitly in retrieved context. Instruct the model to say "I don't have enough information" when context is insufficient. Evaluate with an LLM-as-judge checking faithfulness to context.

**Agent architecture patterns**: the ReAct loop (reason → act → observe), single-agent vs. multi-agent (specialization at the cost of coordination complexity), and MCP as the tool-interoperability layer.

**Fine-tuning vs. RAG vs. prompting**: prompting = zero cost, no new knowledge, limited by context window. RAG = adds retrievable knowledge without retraining, knowledge is trivially updatable. Fine-tuning = changes how the model behaves, most expensive, doesn't update knowledge easily.

**Temperature and sampling**: temperature controls randomness — lower (0-0.3) for factual, deterministic tasks; higher (0.7-1.0) for creative or diverse outputs. Most production applications use low temperature for consistency.

## Best Practices

- **Answer "what it is" + "why it matters" + "the key trade-off"** in 30-60 seconds, then stop. If they want more, they'll ask.
- **Use concrete examples** — "JWT is like a signed driver's license: anyone can verify it without calling the DMV" is more memorable and verifiable than a definition alone.
- **Don't over-hedge** — "it depends on the context" is often true but not useful by itself. Give the answer that applies to the most common context first, then acknowledge exceptions.
- **Know the failure mode of each concept** — interviewers often follow up with "what goes wrong with X?" If you only know the happy path, you'll stall on the follow-up.

## Practice Exercises

1. **Timed answers**: Pick five questions from this unit at random and answer them out loud, unscripted, in under a minute each. Record yourself. Review for clarity, completeness (what + why + trade-off), and whether you hedge too much or too little.

2. **Follow-up drilling**: For each concept you can define, prepare an answer to the follow-up: "What can go wrong with X?" and "When would you NOT use X?" These are the questions that distinguish surface-level knowledge from genuine understanding.

3. **Peer quiz**: Have a peer or mentor ask you 10 of these questions in sequence with 5 minutes per question (including follow-ups). Simulate interview conditions: no notes, camera on, answer out loud.

## Key Takeaways

- Answer format: what it is (1-2 sentences) + when you'd use it + the key trade-off. Not just a definition.
- React: reconciliation via virtual DOM diffing; hooks must be called in the same order every render; closures in effects capture stale values.
- Node.js event loop: single-threaded for JS, non-blocking for I/O — slow synchronous computation blocks everything; concurrent I/O calls don't.
- JWT = stateless, no revocation without a blacklist. Sessions = stateful, instant revocation, requires server-side store.
- CORS = browser-enforced; never applies to server-to-server calls.
- RAG: chunk → embed → store → retrieve → prompt → generate. Hallucination = model fabricates content not in retrieved context.
- Fine-tuning vs. RAG: RAG adds knowledge (no retraining), fine-tuning changes behavior (expensive, slow to iterate).
