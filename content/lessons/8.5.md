# LangChain Fundamentals

You already know how to build a RAG pipeline from scratch — load text, split it, embed it, store vectors, retrieve the most similar chunks, stuff them into a prompt, call the model. If you did Unit 8.3, you wrote all of that glue code by hand. Every step was explicit: you called the embedding API yourself, you wrote the loop to insert vectors, you formatted the prompt string.

Now imagine you need to do this again for a different project. Different document format. Different vector store. Different model provider. You rewrite almost everything — not the logic, just the plumbing.

LangChain exists to solve that plumbing problem. It packages the most common patterns — document loading, text splitting, embedding, vector storage, retrieval, prompt formatting, model calling, output parsing — into composable building blocks with standardized interfaces. Swap the vector store from Chroma to Pinecone? Change one import. Swap the model from OpenAI to Anthropic? Change one import. The pipeline itself doesn't change.

This lesson teaches you how each building block works and *why* it's designed the way it is — not just how to call it.

## Theory & Fundamentals

### Why LangChain Exists: The Plumbing Problem

Here is what a bare-metal RAG pipeline looks like:

```python
# Everything you write manually without a framework
import openai
import chromadb
from pypdf import PdfReader

# Step 1: Load the PDF
reader = PdfReader("handbook.pdf")
text = ""
for page in reader.pages:
    text += page.extract_text()

# Step 2: Split into chunks (naive approach)
chunks = [text[i:i+1000] for i in range(0, len(text), 1000)]

# Step 3: Embed each chunk
embed_client = openai.OpenAI()
embeddings = []
for chunk in chunks:
    response = embed_client.embeddings.create(
        model="text-embedding-ada-002",
        input=chunk
    )
    embeddings.append(response.data[0].embedding)

# Step 4: Store in vector database
db = chromadb.Client()
collection = db.create_collection("handbook")
for i, (chunk, embedding) in enumerate(zip(chunks, embeddings)):
    collection.add(documents=[chunk], embeddings=[embedding], ids=[str(i)])

# Step 5: Query
query = "What's the vacation policy?"
query_embedding = embed_client.embeddings.create(
    model="text-embedding-ada-002", input=query
).data[0].embedding
results = collection.query(query_embeddings=[query_embedding], n_results=3)
context = "\n\n".join(results["documents"][0])

# Step 6: Generate
response = openai.OpenAI().chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {"role": "user", "content": f"Answer based on: {context}\n\nQuestion: {query}"}
    ]
)
print(response.choices[0].message.content)
```

This works. But notice: none of this logic is specific to your application. Loading PDFs, splitting text, calling embedding APIs, querying Chroma — this is infrastructure that every RAG application needs. If your company switches from Chroma to Pinecone, you rewrite Step 4 and Step 5. If you switch from OpenAI to Anthropic, you rewrite Steps 3 and 6. You are maintaining integration code, not application logic.

LangChain's value proposition: replace all of that with standardized components. The same `.invoke()` call works regardless of which vector store or model you're using underneath.

### The Core Mental Model: Chains and LCEL

A "chain" in LangChain is exactly what it sounds like: a pipeline where each step's output becomes the next step's input.

Think of it like Unix pipes. Instead of:

```bash
cat file.txt | grep "error" | sort | uniq -c
```

You have:

```python
prompt | model | output_parser
```

The `|` operator is LangChain Expression Language (LCEL). It wires components together so the output of the left side flows into the input of the right side — automatically, without you writing `result = step1(input); result2 = step2(result)` for every step.

Here is the mathematical intuition. If you have two functions f and g, then `f(g(x))` means "apply g first, then apply f to the result." In LCEL:

```
g | f
```

means the same thing: g runs first, then f runs on g's output. This is function composition — just written left-to-right instead of inside-out.

Why is this better than calling functions manually? Three reasons:

**1. Every step automatically gets streaming, batching, and async.** Every LangChain component is a "Runnable" — something with `.invoke()`, `.batch()`, `.stream()`, and `.astream()` methods. When you chain them with `|`, all of these capabilities work across the entire chain automatically. You don't have to implement streaming yourself.

**2. Error handling and retries propagate across the chain.** You can attach retry logic to the whole chain, not just individual steps.

**3. Tracing and observability.** Tools like LangSmith can observe every intermediate step in the chain because LCEL makes the structure explicit.

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# Three components
prompt = ChatPromptTemplate.from_template("Summarize this in one sentence: {text}")
model = ChatOpenAI(model="gpt-4o-mini")
parser = StrOutputParser()

# Wire them together with |
chain = prompt | model | parser

# Invoke the whole chain — each step runs in sequence
result = chain.invoke({"text": "Long article text here..."})

# Stream the result — works automatically because of LCEL
for chunk in chain.stream({"text": "Long article text here..."}):
    print(chunk, end="", flush=True)
```

What happens when you call `chain.invoke({"text": "..."})`:
1. The `prompt` component takes the dict and formats it into a prompt message
2. The `model` component takes the formatted prompt and calls the LLM
3. The `parser` component takes the LLM's response object and extracts the text string

You don't write any of that data passing yourself. LCEL handles it.

## Core Patterns / Techniques

### Document Loaders

**The problem they solve:** your data lives in the real world — PDFs, Word documents, web pages, Notion pages, GitHub repositories, SQL databases. The LLM can only read text. You need to extract that text before you can do anything with it.

LangChain provides loaders for dozens of formats. Each loader returns a list of `Document` objects. Every `Document` has two fields:
- `page_content`: the actual text content (a string)
- `metadata`: a dict with source information (filename, page number, URL, etc.)

```python
from langchain_community.document_loaders import PyPDFLoader, WebBaseLoader

# Load a PDF — returns one Document per page
loader = PyPDFLoader("company_handbook.pdf")
documents = loader.load()

print(len(documents))          # one Document per page
print(documents[0].page_content[:300])  # raw text from page 1
print(documents[0].metadata)   # {'source': 'company_handbook.pdf', 'page': 0}

# Load a web page — extracts the visible text content
web_loader = WebBaseLoader("https://docs.python.org/3/tutorial/")
web_docs = web_loader.load()

print(web_docs[0].page_content[:300])  # extracted text from the page
print(web_docs[0].metadata)   # {'source': 'https://...', 'title': '...'}
```

**Common misconception:** Document loaders do NOT understand documents. They extract raw text. This distinction matters a lot in practice.

A PDF with tables will have those tables extracted as garbled text strings — the rows won't line up, the column headers won't correspond to their values. A PDF with columns will have the text from both columns interleaved. A scanned PDF (an image, not a text PDF) will return empty `page_content` entirely — you need OCR for that.

When retrieval quality is poor, always inspect the raw extracted text first. You may be working with garbled input and need a smarter loader (there are loaders with OCR support, table extraction, etc.).

### Text Splitters

**The problem they solve:** a 200-page document is probably 200,000 tokens. Embedding models have token limits (typically 512 to 8192 tokens). Even if you could embed the whole document, huge chunks produce terrible retrieval — you retrieve a 200-page document when you needed one paragraph. You need to split the document into smaller pieces before embedding.

But HOW you split matters enormously. If you split naively — every 1000 characters, no matter what — you might cut a sentence in half, separate a question from its answer, or break up a code example. The split point becomes a retrieval blind spot.

LangChain's `RecursiveCharacterTextSplitter` is the workhorse. It tries a priority list of split points, in order, until the chunk is small enough:

1. `\n\n` — paragraph breaks (best: preserves semantic units)
2. `\n` — line breaks
3. ` ` — word boundaries
4. `""` — individual characters (worst: only if nothing else works)

This is "recursive" splitting: it tries to split on paragraphs first, and if a paragraph is still too large, it splits that paragraph on sentences, and if a sentence is still too large, it splits on words. The result preserves as much semantic coherence as possible.

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,    # maximum characters per chunk
    chunk_overlap=150,  # how many characters overlap between adjacent chunks
    separators=["\n\n", "\n", " ", ""],  # priority order for split points
)

chunks = splitter.split_documents(documents)
# Returns a list of Document objects with smaller page_content
# Metadata is preserved: each chunk knows which source document it came from

print(len(chunks))              # many more chunks than documents
print(len(chunks[0].page_content))  # <= 1000 characters
print(chunks[0].metadata)      # same metadata as the source document
```

**Why `chunk_overlap` exists — this is important:** imagine a key sentence sits right at the boundary between two chunks. Without overlap, that sentence is split in half: the first half is at the end of chunk 5, the second half is at the start of chunk 6. A query about that sentence will retrieve a chunk containing half a sentence — useless.

With `chunk_overlap=150`, the last 150 characters of chunk 5 are also the first 150 characters of chunk 6. That boundary sentence appears fully in both chunks. Retrieval will find a complete sentence no matter which chunk it lands in.

**Concrete example — what gets lost without overlap:**

```
Original text (300 chars):
"...The refund will be processed within 5-7 business days.
Refunds are only available for purchases made in the last 30 days.
Store credit is available for all other cases..."

With chunk_size=200, chunk_overlap=0:
  Chunk 1: "...The refund will be processed within 5-7 business days."
  Chunk 2: "Refunds are only available for purchases made in the last 30"  ← cut!
  Chunk 3: " days. Store credit is available for all other cases..."

With chunk_size=200, chunk_overlap=50:
  Chunk 1: "...The refund will be processed within 5-7 business days."
  Chunk 2: "within 5-7 business days. Refunds are only available for..."  ← repeated context
  Chunk 3: "...made in the last 30 days. Store credit is available..."
```

With overlap, "Refunds are only available for purchases made in the last 30 days" appears fully in chunk 2. Without overlap, it's split across chunks 2 and 3.

**Choosing chunk_size and chunk_overlap:**
- `chunk_size=500-1000`: the sweet spot for most use cases. Too small = too many chunks, each with insufficient context. Too large = poor retrieval precision.
- `chunk_overlap=10-20%` of chunk_size: overlap of 50-200 characters for a 1000-character chunk is typical.
- The right values depend on your content. Legal documents, where every sentence matters, need smaller chunks. Narrative text tolerates larger chunks.

### Embeddings

**What an embedding is:** a list of numbers (a vector) that represents the "meaning" of a piece of text. Here is what an embedding looks like:

```
"The dog ran across the park" → [0.023, -0.187, 0.441, 0.091, -0.332, ...]
                                  (1536 numbers for text-embedding-ada-002)
```

1536 numbers. They mean nothing individually. What matters is their relationship to other embeddings.

**Why this works:** the embedding model is trained on an enormous corpus of text. During training, it learns to place semantically similar text close together in this 1536-dimensional space. "Dog" and "puppy" end up with similar vectors. "Dog" and "airplane" end up with very different vectors. "Return policy" and "how do I send something back" end up with similar vectors, even though they share no words.

This is the core insight: embeddings capture semantic similarity, not lexical similarity. Keyword search matches exact words. Embedding search matches meaning.

**Keyword search vs. embedding search — a concrete example:**

Query: "What's the return policy?"

Document 1: "Items can be returned within 30 days of purchase for a full refund."
Document 2: "Our policy on refunds: customers have 30 days to send back any item."
Document 3: "We offer free returns within one month of the purchase date."

Keyword search for "return policy" might find Document 1 ("returned") but miss Documents 2 ("refunds") and 3 (no overlap at all).

Embedding search finds all three — because all three have similar embeddings to the query. The model learned that "return", "refund", "send back", and "returns" are semantically related in this context.

```python
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(model="text-embedding-ada-002")

# Embed a single text
vector = embeddings.embed_query("What's the return policy?")
print(len(vector))  # 1536
print(vector[:5])   # [-0.02, 0.19, -0.44, 0.11, 0.28, ...]

# Embed multiple documents at once (more efficient)
vectors = embeddings.embed_documents([
    "Items can be returned within 30 days.",
    "Free shipping on orders over $50.",
])
print(len(vectors))    # 2
print(len(vectors[0])) # 1536
```

**Tradeoffs between embedding providers:**

| Provider | Quality | Cost | Privacy | Setup |
|---|---|---|---|---|
| OpenAI text-embedding-ada-002 | Excellent | ~$0.0001/1K tokens | Sends data to OpenAI | API key only |
| OpenAI text-embedding-3-small | Good, cheaper | ~$0.00002/1K tokens | Sends data to OpenAI | API key only |
| all-MiniLM-L6-v2 (open-source) | Good | Free | Runs locally | Requires HuggingFace |
| BAAI/bge-large (open-source) | Very good | Free | Runs locally | Requires HuggingFace |

For prototyping: OpenAI's APIs are easiest. For production with sensitive data: open-source models run locally. The quality difference is smaller than you'd expect — open-source models are competitive for most use cases.

### Vector Stores

**The problem they solve:** you have 10,000 embedded chunks. You have a query embedding. You need the top 5 most similar chunks — fast. Checking every single chunk against the query (brute-force nearest-neighbor) is too slow for large collections.

A vector store is a database designed for this exact problem. It indexes the vectors and uses approximate nearest-neighbor algorithms to return the most similar vectors in milliseconds, even for millions of entries.

**How similarity search works conceptually:** two vectors are "similar" if they point in roughly the same direction. Cosine similarity measures the angle between them — vectors pointing in the same direction have cosine similarity close to 1.0; vectors pointing in opposite directions have similarity close to -1.0.

```
Query vector:    [0.1, 0.8, 0.3, ...]   → "return policy"
Chunk A vector:  [0.15, 0.75, 0.28, ...]  → "items can be returned..."  cosine: 0.97 ← high
Chunk B vector:  [0.9, -0.1, 0.5, ...]   → "free shipping policy"       cosine: 0.31 ← low
Chunk C vector:  [0.12, 0.82, 0.31, ...] → "30-day refund guarantee"    cosine: 0.99 ← high
```

The vector store returns chunks A and C as the most relevant — not because they share keywords with the query, but because their meaning vectors are geometrically close.

**Vector store options:**

```python
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings()

# Chroma: simplest to get started. In-memory by default, can persist to disk.
# Great for development and small-to-medium collections.
vectorstore = Chroma.from_documents(
    documents=chunks,          # your Document objects
    embedding=embeddings,      # how to embed them
    persist_directory="./db",  # optional: save to disk
)

# Search for similar documents
results = vectorstore.similarity_search("What's the return policy?", k=3)
for doc in results:
    print(doc.page_content)
    print(doc.metadata)
    print("---")
```

```python
# FAISS: Facebook AI Similarity Search. Runs locally, scales to millions of vectors.
# Fast, no network calls, free. Must manage your own persistence (save/load manually).
from langchain_community.vectorstores import FAISS

vectorstore = FAISS.from_documents(chunks, embeddings)
vectorstore.save_local("faiss_index")  # save to disk

# Later: load it back
vectorstore = FAISS.load_local("faiss_index", embeddings)
```

```python
# Pinecone: managed cloud vector database. You don't run it yourself.
# Best for production at scale where you need managed infrastructure and filtering.
from langchain_pinecone import PineconeVectorStore
import pinecone

pinecone.init(api_key="your-api-key", environment="your-env")
vectorstore = PineconeVectorStore.from_documents(
    chunks, embeddings, index_name="your-index"
)
```

**Which to use:**

- **Development / prototyping:** Chroma (in-memory, zero setup, great for iteration)
- **Local production / single server:** FAISS (fast, free, no network dependency)
- **Cloud production / multi-server / large scale:** Pinecone or Weaviate (managed, scalable, supports metadata filtering)

The LangChain interface is the same for all of them — `.similarity_search()`, `.from_documents()`, `.as_retriever()`. Switching is truly one import change.

### Building a Full RAG Chain — End to End

Now let's wire all of these components together into a complete RAG pipeline using LCEL. We'll go step by step, and for each step we'll explain what's happening and why.

```python
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_chroma import Chroma
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

# ─── Step 1: Load Documents ───────────────────────────────────────────────────
# PyPDFLoader reads the PDF and returns one Document per page.
# Each Document has .page_content (the text) and .metadata (source info).
loader = PyPDFLoader("company_handbook.pdf")
raw_documents = loader.load()

print(f"Loaded {len(raw_documents)} pages")
print(f"First page preview: {raw_documents[0].page_content[:200]}")

# ─── Step 2: Split into Chunks ────────────────────────────────────────────────
# We split because:
#   1. Embedding models have token limits
#   2. Smaller chunks = more precise retrieval
#   3. chunk_overlap ensures no sentence is cut across a boundary
splitter = RecursiveCharacterTextSplitter(
    chunk_size=800,    # ~200 tokens — reasonable for retrieval
    chunk_overlap=100, # 12.5% overlap prevents boundary blind spots
)
chunks = splitter.split_documents(raw_documents)

print(f"Split into {len(chunks)} chunks")
print(f"Average chunk length: {sum(len(c.page_content) for c in chunks) / len(chunks):.0f} chars")

# ─── Step 3: Embed and Store ──────────────────────────────────────────────────
# Chroma.from_documents does two things in one call:
#   1. Calls OpenAI's embedding API for every chunk (this costs money and takes time)
#   2. Stores both the text and its embedding vector in the Chroma database
# This is the expensive step — for 100 chunks at ~500 tokens each, expect ~50K tokens of embedding cost.
embeddings = OpenAIEmbeddings(model="text-embedding-ada-002")
vectorstore = Chroma.from_documents(chunks, embeddings, persist_directory="./handbook_db")

print(f"Stored {len(chunks)} chunks in vector store")

# ─── Step 4: Create a Retriever ───────────────────────────────────────────────
# A retriever is just a standardized interface around the vector store.
# .as_retriever() wraps the vector store so it works in LCEL pipelines.
# k=3 means "return the 3 most similar chunks for each query".
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

# You can test retrieval independently — and you SHOULD.
# If retrieval is wrong, generation will always be wrong.
test_docs = retriever.invoke("What is the vacation policy?")
print("\n--- Retrieved chunks for test query ---")
for i, doc in enumerate(test_docs):
    print(f"Chunk {i+1}: {doc.page_content[:150]}...")
    print(f"  Source: {doc.metadata}")

# ─── Step 5: Create the Prompt Template ──────────────────────────────────────
# This template instructs the model to answer based ONLY on the retrieved context.
# The {context} placeholder will be filled with the retrieved chunks.
# The {question} placeholder will be filled with the user's question.
prompt = ChatPromptTemplate.from_template("""
Answer the question based only on the following context. If the answer is not
in the context, say "I don't have that information in the handbook."

Context:
{context}

Question: {question}

Answer:""")

# ─── Step 6: Wire Everything Together with LCEL ──────────────────────────────
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
parser = StrOutputParser()

def format_docs(docs):
    """Convert a list of Document objects into a single context string."""
    return "\n\n---\n\n".join(doc.page_content for doc in docs)

# This is the LCEL chain. Here's what happens when you invoke it:
#   1. The input dict {"question": "..."} arrives
#   2. "context" branch: retriever runs on the question, format_docs joins the results
#   3. "question" branch: RunnablePassthrough passes the question through unchanged
#   4. Both branches produce a dict: {"context": "...", "question": "..."}
#   5. The prompt template formats that dict into a prompt message
#   6. The model generates a response
#   7. The parser extracts the text from the response object
rag_chain = (
    {
        "context": retriever | format_docs,   # retrieve → format as text
        "question": RunnablePassthrough(),     # pass question through unchanged
    }
    | prompt    # format into a prompt message
    | model     # call the LLM
    | parser    # extract text from the response
)

# ─── Using the Chain ──────────────────────────────────────────────────────────
answer = rag_chain.invoke("How many vacation days do new employees get?")
print(f"\nAnswer: {answer}")

# Streaming — shows tokens as they're generated
print("\nStreaming answer:")
for chunk in rag_chain.stream("What is the remote work policy?"):
    print(chunk, end="", flush=True)
print()
```

**What the model actually sees:** when you call `rag_chain.invoke("How many vacation days...")`, the model receives something like this as its input:

```
Answer the question based only on the following context. If the answer is not
in the context, say "I don't have that information in the handbook."

Context:
New employees are entitled to 15 days of paid vacation per year for their
first three years of employment.

---

Vacation days accrue at a rate of 1.25 days per month. Unused days may be
carried over to the following year, up to a maximum of 10 days.

---

Employees should submit vacation requests at least two weeks in advance
through the HR portal at hr.company.com/requests.

Question: How many vacation days do new employees get?

Answer:
```

That's it. There's no magic — it's just retrieved text stuffed into a prompt. Understanding this makes it much easier to debug retrieval problems: if the answer is wrong, print the formatted context and check whether the right information was retrieved.

**The most common RAG mistake:** building the pipeline and then assuming it works. Test retrieval independently. Call `retriever.invoke("your question")` and inspect the returned chunks. If the right information isn't in the returned chunks, generation will always fail — because the model can only answer based on what's in the context window. Retrieval quality and generation quality are separate problems to fix separately.

### Conversation Memory

**The problem:** LangChain chains are stateless by default. Each call to `chain.invoke(...)` starts fresh — the model has no memory of previous messages in the conversation.

This is by design: LLMs are stateless. They only see the current prompt. "Memory" means explicitly including past conversation turns in the current prompt. Without a memory component, you have to manage message history yourself.

**Why memory must be explicit:** contrast this with how humans remember conversations. When you talk to a friend, your brain automatically recalls earlier context. When you talk to an LLM, it sees only the text in the current request. If you want it to remember what was said before, you must literally include the earlier messages in the current request. Memory = more text in the prompt.

```python
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

# ConversationBufferMemory approach: store full conversation history
# Simple, but gets expensive as conversations grow — every message adds tokens

# Create a simple chain (no retrieval here for clarity)
model = ChatOpenAI(model="gpt-4o-mini")
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a helpful assistant."),
    ("placeholder", "{chat_history}"),  # conversation history goes here
    ("human", "{input}"),
])

chain = prompt | model | StrOutputParser()

# A store to hold per-session histories
session_histories = {}

def get_session_history(session_id: str) -> InMemoryChatMessageHistory:
    if session_id not in session_histories:
        session_histories[session_id] = InMemoryChatMessageHistory()
    return session_histories[session_id]

# Wrap the chain with message history management
chain_with_memory = RunnableWithMessageHistory(
    chain,
    get_session_history,
    input_messages_key="input",
    history_messages_key="chat_history",
)

config = {"configurable": {"session_id": "user-alice"}}

# First turn
response1 = chain_with_memory.invoke(
    {"input": "My name is Alice and I work in marketing."},
    config=config
)
print(response1)  # "Nice to meet you, Alice! ..."

# Second turn — the model remembers Alice's name
response2 = chain_with_memory.invoke(
    {"input": "What department do I work in?"},
    config=config
)
print(response2)  # "You work in marketing, Alice."
```

**What `get_session_history` does:** each session (identified by `session_id`) gets its own history store. Before each call, the chain loads the stored messages for that session and prepends them to the prompt. After each call, the new messages are appended to the history. The result: the model "remembers" the conversation even though each underlying LLM call is stateless.

**The two main memory strategies:**

**ConversationBufferMemory (full history):**
- Stores every message verbatim
- Simple and lossless — the model sees everything
- Gets expensive fast: a 20-turn conversation might be 3,000 tokens of context before your actual question
- Use for: short conversations, high-stakes applications where losing detail is not acceptable

**ConversationSummaryMemory (summarized history):**
- Periodically summarizes older messages ("Alice said she works in marketing and prefers email communication...")
- Keeps token count bounded regardless of conversation length
- Loses detail — exact phrasing, specific numbers mentioned, subtle context
- Use for: long conversations where staying within token limits matters more than exact recall

```python
from langchain.memory import ConversationSummaryMemory

# Automatically summarizes older conversation turns
# to keep the prompt from growing indefinitely
memory = ConversationSummaryMemory(
    llm=ChatOpenAI(model="gpt-4o-mini"),  # uses a model to write the summary
    max_token_limit=500,  # summarize when history exceeds this many tokens
)
```

**The token cost reality:** with `gpt-4o-mini` at $0.15/million input tokens, a 20-turn conversation with 100 tokens per message means the 20th message carries 1,900 tokens of history overhead just to maintain context. In production applications with many users and long conversations, this adds up quickly. Design your memory strategy based on your actual usage patterns.

## Best Practices

- **Understand before abstracting** — LangChain hides complexity. If retrieval quality is poor, you need to understand what `RecursiveCharacterTextSplitter` actually does, why `chunk_overlap` matters, and what the raw extracted text looks like. Build the pipeline manually first (Unit 8.3), then use LangChain to remove boilerplate.
- **Test retrieval before testing generation** — when a RAG system gives a wrong answer, check the retrieved chunks first. Add `print(retriever.invoke("your question"))` early in debugging. If the right chunk isn't retrieved, the model can't answer correctly no matter how good your prompt is.
- **Inspect your raw document text** — run `loader.load()` and print `documents[0].page_content` before building the rest of the pipeline. PDFs with complex formatting, tables, or columns often produce garbled text that defeats retrieval.
- **Use LCEL over legacy chains** — LangChain's older `LLMChain`, `ConversationalRetrievalChain`, and similar classes are deprecated in favor of LCEL. New code should always use the `|` syntax.
- **Swap providers by changing one import** — if you build with OpenAI and need to switch to Anthropic: `from langchain_anthropic import ChatAnthropic`. The rest of the chain is unchanged. This is the core value of standardized interfaces.
- **Persist your vector store** — building a vector store from documents is slow and costs money (embedding API calls). Save it to disk with `persist_directory` (Chroma) or `save_local` (FAISS) and reload it on subsequent runs.

## Common Interview Questions

**Q1: What problem does LangChain solve?**
A: Integration boilerplate. Every LLM application needs the same plumbing: load documents, chunk them, embed them, store vectors, retrieve relevant chunks, format prompts, call a model, parse output. LangChain provides standardized components for each step, so you can swap providers (OpenAI ↔ Anthropic ↔ local models) and vector stores (Chroma ↔ Pinecone) without rewriting your pipeline.

**Q2: What is LCEL and how does it work?**
A: LangChain Expression Language. The `|` operator chains "Runnables" — components with `.invoke()`, `.batch()`, and `.stream()` methods. `prompt | model | parser` passes the output of the prompt component to the model, then the model's output to the parser, without you writing any data-passing code. The full chain automatically supports streaming, batching, and async because all components share the same Runnable interface.

**Q3: Why does RecursiveCharacterTextSplitter try multiple separator types?**
A: To preserve semantic coherence. Splitting on every N characters blindly might cut a sentence in half or separate a heading from its content. By trying paragraph breaks first (`\n\n`), then line breaks, then words, it minimizes the chance of cutting at a semantically meaningless boundary. The "recursive" part means it applies this logic recursively to oversized chunks until they're small enough.

**Q4: What is the purpose of chunk_overlap in text splitting?**
A: To prevent sentences at chunk boundaries from being split across two chunks. A sentence that ends at the 1000th character and continues at the 1001st character would be cut in half without overlap. With overlap=100, those 100 characters appear in both the current chunk and the next one, so the sentence appears fully in at least one chunk and retrieval doesn't miss it.

**Q5: When would you NOT use LangChain?**
A: When the pipeline is simple (one prompt, one call), when you need precise debugging control over every step, or when the abstraction layer is making it harder to reason about what's happening. LangChain is most valuable when you're swapping providers frequently or building complex multi-step pipelines. For a simple chatbot, raw API calls are often more maintainable.

**Q6: What is the difference between a LangChain chain and a LangGraph agent?**
A: A chain is a fixed, linear sequence of steps (A → B → C). A LangGraph agent is a graph with conditional branching — the model decides which step to take next based on its output. Chains work for deterministic pipelines where every input takes the same path. Agents work for dynamic, multi-step reasoning where the path depends on intermediate results.

## Key Takeaways

- LangChain's value is standardized interfaces — the same `.invoke()` call works with any provider or vector store, so you can swap components without rewriting pipelines.
- LCEL (`|` syntax) chains Runnables: output flows left-to-right without manual data passing. Every chain automatically supports `.invoke()`, `.stream()`, `.batch()`, and `.astream()`.
- Document loaders extract raw text — they do NOT understand documents. Inspect the extracted text early; formatting issues (tables, columns) will corrupt retrieval.
- `RecursiveCharacterTextSplitter` preserves semantic coherence by splitting on paragraphs before lines before words. `chunk_overlap` prevents sentences from being cut across chunk boundaries.
- Embeddings capture semantic meaning, not keywords. Embedding search finds "items can be returned" for "return policy" even with zero word overlap.
- Vector stores (Chroma for dev, FAISS for local scale, Pinecone for managed cloud) index embeddings for fast nearest-neighbor search.
- Always test retrieval before testing generation. Wrong retrieval = wrong generation, no matter how good the prompt.
- Memory = explicitly including past messages in the current prompt. Buffer memory is lossless but grows; summary memory is bounded but lossy.
