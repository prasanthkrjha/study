# SQL Fundamentals

SQL is one of the most universally required skills across full-stack engineering roles — nearly every backend system stores relational data, and almost every engineering interview that touches data access will expect you to write or reason about SQL queries. Understanding SQL deeply, not just syntactically, is what separates candidates who can debug a slow query in production from those who can only follow a tutorial schema.

The key mental shift is recognizing that SQL is declarative: you describe the data you want, not the steps to retrieve it. The database's query planner chooses how to execute your query. This means writing better SQL is partly about writing clearer intent (which the planner understands better) and partly about understanding what the planner does so you can avoid traps like accidental full-table scans.

SQL query clauses execute in a logical order that differs from their written order: `FROM` and `JOIN` first (which tables), then `WHERE` (filter individual rows), then `GROUP BY` (aggregate), then `HAVING` (filter groups), then `SELECT` (project columns), then `ORDER BY`, then `LIMIT`. This ordering explains many "why doesn't this work?" moments — you cannot use a `SELECT` alias in `WHERE` because `WHERE` runs before `SELECT` assigns those aliases.

## Theory & Fundamentals

### Relational Model

Relational databases store data in tables (relations) of rows (tuples) and columns (attributes). Every table has a primary key — one or more columns that uniquely identify each row. Tables relate to each other via foreign keys, which reference a primary key in another table. This relational structure is what makes JOIN possible: when you JOIN two tables on matching key values, the database assembles composite rows from both.

### Logical Query Execution Order

Written order vs. execution order is one of the most misunderstood aspects of SQL:

```
Written order:    SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT
Execution order:  FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

Consequences:
- `WHERE` cannot reference aliases defined in `SELECT` (those don't exist yet at WHERE time).
- `HAVING` can reference aggregate functions because it runs after `GROUP BY`.
- `ORDER BY` can reference `SELECT` aliases because it runs after `SELECT`.

### Aggregation

Aggregate functions collapse multiple rows into a single value. When used with `GROUP BY`, they produce one result per group rather than one result for the entire table.

Common aggregate functions: `COUNT(*)` counts all rows; `COUNT(column)` counts non-NULL values; `SUM`, `AVG`, `MIN`, `MAX` work as expected. Nulls are ignored by all aggregates except `COUNT(*)`.

### Subqueries

A subquery is a complete SELECT statement nested inside another query. Subqueries can appear in three positions:
- **In WHERE** — often with `IN`, `EXISTS`, or comparison operators
- **In FROM** — treated as a derived table (must be aliased)
- **In SELECT** — scalar subqueries returning a single value per row

## Core Concepts / Techniques

### SELECT Syntax and Filtering

```sql
-- Basic projection and filtering
SELECT first_name, last_name, email
FROM users
WHERE created_at > '2024-01-01'
  AND status = 'active'
ORDER BY created_at DESC
LIMIT 25 OFFSET 0;

-- Using LIKE for pattern matching
SELECT * FROM products
WHERE name ILIKE '%coffee%';  -- ILIKE is case-insensitive in PostgreSQL

-- NULL handling — use IS NULL / IS NOT NULL, not = NULL
SELECT * FROM orders
WHERE shipped_at IS NULL;
```

### JOIN Types

```sql
-- INNER JOIN: only rows with a match on both sides
SELECT u.name, o.total, o.created_at
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN: all rows from users, order data or NULL where no match
SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name;

-- Find users with NO orders (anti-join pattern)
SELECT u.name
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.id IS NULL;

-- FULL OUTER JOIN: all rows from both sides
SELECT u.name, o.total
FROM users u
FULL OUTER JOIN orders o ON u.id = o.user_id;
```

Mental model: INNER = intersection, LEFT = "keep everything from the left table," FULL OUTER = "keep everything from either table, fill gaps with NULL."

### GROUP BY and HAVING

```sql
-- HAVING filters groups after aggregation — not the same as WHERE
SELECT
  user_id,
  COUNT(*)         AS total_orders,
  SUM(total)       AS lifetime_value,
  AVG(total)       AS avg_order_value
FROM orders
WHERE status = 'completed'          -- filters individual rows BEFORE grouping
GROUP BY user_id
HAVING COUNT(*) >= 3                -- filters groups AFTER aggregation
   AND SUM(total) > 100
ORDER BY lifetime_value DESC;
```

### Subqueries

```sql
-- Correlated subquery: references outer query's row
SELECT name, salary
FROM employees e
WHERE salary > (
  SELECT AVG(salary)
  FROM employees
  WHERE department_id = e.department_id  -- references outer e
);

-- EXISTS: efficient "does at least one matching row exist?"
SELECT u.name
FROM users u
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id
    AND o.total > 500
);

-- Subquery in FROM (derived table)
SELECT dept, avg_sal
FROM (
  SELECT department_id AS dept, AVG(salary) AS avg_sal
  FROM employees
  GROUP BY department_id
) AS dept_averages
WHERE avg_sal > 75000;
```

## Code Examples

### Complete Query: Sales Report with Aggregates

```sql
-- Monthly sales summary by product category
SELECT
  DATE_TRUNC('month', o.created_at)       AS month,
  c.name                                   AS category,
  COUNT(DISTINCT o.id)                     AS order_count,
  COUNT(DISTINCT o.user_id)                AS unique_customers,
  SUM(oi.quantity * oi.unit_price)         AS revenue,
  AVG(oi.quantity * oi.unit_price)         AS avg_order_value
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
JOIN categories c ON c.id = p.category_id
WHERE o.status = 'completed'
  AND o.created_at >= '2024-01-01'
GROUP BY DATE_TRUNC('month', o.created_at), c.name
HAVING SUM(oi.quantity * oi.unit_price) > 1000  -- only categories with meaningful revenue
ORDER BY month DESC, revenue DESC;
```

### Common Table Expressions (CTEs)

```sql
-- CTEs make complex queries readable by naming intermediate results
WITH active_customers AS (
  SELECT user_id, COUNT(*) AS order_count
  FROM orders
  WHERE created_at > NOW() - INTERVAL '90 days'
    AND status = 'completed'
  GROUP BY user_id
  HAVING COUNT(*) >= 2
),
customer_tiers AS (
  SELECT
    u.id,
    u.name,
    u.email,
    ac.order_count,
    CASE
      WHEN ac.order_count >= 10 THEN 'platinum'
      WHEN ac.order_count >= 5  THEN 'gold'
      ELSE 'silver'
    END AS tier
  FROM users u
  JOIN active_customers ac ON ac.user_id = u.id
)
SELECT tier, COUNT(*) AS count, AVG(order_count) AS avg_orders
FROM customer_tiers
GROUP BY tier
ORDER BY avg_orders DESC;
```

### Window Functions

```sql
-- Rank products by revenue within each category
SELECT
  p.name,
  c.name AS category,
  SUM(oi.unit_price * oi.quantity) AS revenue,
  RANK() OVER (
    PARTITION BY c.id
    ORDER BY SUM(oi.unit_price * oi.quantity) DESC
  ) AS rank_in_category
FROM products p
JOIN categories c ON c.id = p.category_id
JOIN order_items oi ON oi.product_id = p.id
GROUP BY p.id, p.name, c.id, c.name
ORDER BY category, rank_in_category;
```

## Best Practices

- **Use explicit column names in SELECT** rather than `SELECT *` — it makes queries self-documenting, prevents breakage when a table's schema changes, and avoids transmitting columns you don't need.
- **Prefer JOINs over correlated subqueries in WHERE** when retrieving data — the query planner can optimize JOIN strategies far better than re-executing a subquery per row.
- **Use `EXISTS` instead of `COUNT(*)` for presence checks** — `EXISTS` short-circuits as soon as it finds one matching row, while `COUNT(*)` must scan all matching rows.
- **Filter early with WHERE before aggregating** — every row eliminated by WHERE is one less row the GROUP BY and HAVING clauses must process.
- **Use CTEs for complex queries** instead of nested subqueries — they execute once, are named, and can be referenced multiple times, which improves both readability and (in some databases) performance.
- **Be explicit about NULL handling** — use `COALESCE(column, default)` to substitute NULLs in arithmetic, and `IS NULL` / `IS NOT NULL` for comparisons; `column = NULL` always evaluates to NULL (not TRUE or FALSE).
- **Avoid functions on indexed columns in WHERE** — `WHERE YEAR(created_at) = 2024` prevents index use; `WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'` does not.

## Common Interview Questions

**Q: What is the difference between WHERE and HAVING?**
A: WHERE filters individual rows before grouping occurs. HAVING filters groups after GROUP BY and aggregation. You cannot use aggregate functions (COUNT, SUM, etc.) in a WHERE clause — those require HAVING.

**Q: What is the difference between INNER JOIN and LEFT JOIN?**
A: INNER JOIN returns only rows where a matching row exists in both tables. LEFT JOIN returns all rows from the left table, with NULL values for columns from the right table when no match exists. Use LEFT JOIN when you need to preserve records from one table even when the other table has no matching row.

**Q: What does GROUP BY do and what is the rule about SELECT columns when using it?**
A: GROUP BY collapses rows that share the same value(s) in the grouped column(s) into a single output row. The rule: every column in SELECT must either appear in GROUP BY or be wrapped in an aggregate function. Violating this is a SQL error in strict databases.

**Q: What is a correlated subquery and when is it a performance concern?**
A: A correlated subquery references columns from the outer query, so it must re-execute for every row of the outer result set. This is an O(n) penalty on top of the outer query's cost, making it slow on large datasets. It can often be rewritten as a JOIN or a non-correlated subquery with better performance.

**Q: When would you use a CTE versus a subquery?**
A: CTEs improve readability by naming intermediate result sets and allowing them to be referenced multiple times. Subqueries are fine for simple, one-time use within a single expression. Prefer CTEs when the logic is complex, when the intermediate result is reused, or when recursive queries are needed (`WITH RECURSIVE`).

**Q: What is the difference between COUNT(*) and COUNT(column_name)?**
A: `COUNT(*)` counts all rows including those with NULL values in any column. `COUNT(column_name)` counts only rows where that specific column is not NULL. This distinction matters when counting optional/nullable fields.

**Q: What is a window function and how does it differ from GROUP BY?**
A: Window functions (using `OVER`) perform calculations across a set of rows related to the current row without collapsing those rows into a single output row. GROUP BY collapses rows — you get one row per group. Window functions let you compute running totals, rankings, and lag/lead values while keeping every original row in the result.

**Q: How would you find duplicate records in a table?**
A: Use GROUP BY on the columns that define uniqueness, then filter with HAVING COUNT(*) > 1: `SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;`

## Practice Exercises

1. **Order analysis**: Given `users`, `orders`, and `order_items` tables, write a query that returns each user's name, total number of orders, total amount spent, and average order value — but only for users who have placed at least 3 completed orders. Sort by total amount spent descending.

2. **Category leaderboard**: Write a query that returns the top 3 best-selling products (by total quantity sold) within each product category. The result should include category name, product name, and total quantity. You may use either a window function or a subquery approach.

3. **Churn detection**: Given an `orders` table with `user_id` and `created_at`, identify users who placed at least one order in 2023 but zero orders in 2024. Write this two ways: once using a NOT IN subquery and once using a LEFT JOIN anti-join pattern.

4. **Running total**: Write a query that shows each order alongside a running total of revenue for all orders placed on or before that order's date, ordered chronologically. Use a window function.

5. **Hierarchical data**: Given an `employees` table with `id`, `name`, and `manager_id` (self-referencing foreign key), write a query using a recursive CTE that returns the full reporting chain from any given employee up to the CEO (the employee whose `manager_id` is NULL).

## Key Takeaways

- SQL executes in logical order — FROM, JOIN, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT — not written order; this explains many "why can't I use this alias here?" errors.
- INNER JOIN returns the intersection; LEFT JOIN preserves all rows from the left table; anti-joins (LEFT JOIN ... WHERE right.id IS NULL) find records with no match.
- WHERE filters rows before grouping; HAVING filters groups after aggregation; only HAVING can use aggregate functions.
- Subqueries in WHERE and SELECT re-execute per row; prefer JOINs or CTEs for performance at scale.
- Window functions (RANK, ROW_NUMBER, SUM OVER, LAG) enable per-row analytics without collapsing rows like GROUP BY does.
- NULL is not a value — it represents absence of a value; use IS NULL, COALESCE, and NULLIF to handle it explicitly.
- CTEs make complex queries readable and maintainable; recursive CTEs handle hierarchical/graph traversal without application-level loops.
- Aggregate functions ignore NULLs except COUNT(*), which counts all rows regardless of NULL values in any column.
