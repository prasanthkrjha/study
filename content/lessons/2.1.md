# SQL Fundamentals

SQL is the one skill your gap analysis flagged as "near-universal" — almost every Full Stack posting expects it regardless of whether the product uses Postgres, MySQL, or something else. This unit covers the core query vocabulary.

## SELECT and the anatomy of a query

```sql
SELECT column1, column2
FROM table_name
WHERE condition
GROUP BY column1
HAVING aggregate_condition
ORDER BY column1
LIMIT 10;
```

Logical execution order (not written order!): `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. This is why you can't reference a `SELECT` alias in `WHERE`, but you can in `ORDER BY` — `WHERE` runs before the alias exists, `ORDER BY` runs after.

## JOIN types

```sql
-- INNER JOIN: only rows with a match on both sides
SELECT u.name, o.total
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN: all rows from the left table, matched data from the right (NULL if no match)
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;

-- RIGHT JOIN: mirror of LEFT — all rows from the right table
-- FULL JOIN: all rows from both sides, matched where possible
```

Mental model: **INNER** = intersection, **LEFT/RIGHT** = "keep everything from this side, fill gaps with NULL," **FULL** = union of both. `LEFT JOIN ... WHERE right.id IS NULL` is the standard idiom for "find users with no orders."

## WHERE vs. GROUP BY vs. HAVING

`WHERE` filters **individual rows** before grouping. `HAVING` filters **groups** after aggregation — you need `HAVING` (not `WHERE`) to filter on an aggregate like `COUNT(*)` or `SUM(total)`:

```sql
SELECT user_id, COUNT(*) AS order_count
FROM orders
WHERE status = 'completed'   -- filters rows first
GROUP BY user_id
HAVING COUNT(*) > 5;         -- filters groups after counting
```

## Aggregate functions

`COUNT`, `SUM`, `AVG`, `MIN`, `MAX` collapse many rows into one value per group. Without `GROUP BY`, they collapse the **entire table** into a single row.

## Subqueries

A query nested inside another, usable in `WHERE`, `FROM`, or `SELECT`:

```sql
-- Find users who have placed at least one order
SELECT * FROM users
WHERE id IN (SELECT DISTINCT user_id FROM orders);
```

Subqueries are often rewritable as JOINs (and vice versa) — JOINs are usually faster since the query planner can optimize them better, but subqueries are often more readable for "does X exist" checks.

## Practice tip

Don't just read SQL — write queries against a real schema (your Postgres setup from Month 1). Reading `LEFT JOIN` syntax and *predicting* what a query returns before running it is what actually builds the skill.
