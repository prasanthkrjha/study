# Model Context Protocol (MCP)

MCP is explicitly listed as a "must-have" in current senior full-stack-AI postings — worth knowing conceptually even before you're using it daily, which is exactly this unit's scope.

## Why MCP exists

Before MCP, every agent framework (LangChain, CrewAI, a custom setup) had its **own** way of defining and wiring up tools — a tool built for one framework couldn't be reused in another without rewriting it. MCP is a standardized protocol for how an AI application talks to external tools and data sources, so a tool (or "MCP server") built once can be used by any MCP-compatible client — LangGraph, Claude Agent SDK, OpenAI's Agents SDK, and others — without rewriting it per framework.

The analogy worth using in an interview: MCP is doing for AI tool integration roughly what REST/HTTP did for web APIs — a common protocol so that clients and servers built by different people, for different purposes, can interoperate without custom one-off integration code for every pair.

## The core architecture

- **MCP server** — exposes tools, resources (data the model can read), and/or prompts, over a standardized interface.
- **MCP client** — the AI application (an agent framework, an IDE, a chat client) that connects to one or more MCP servers and makes their tools available to the model.

A single MCP server (say, one that exposes "search our internal docs" and "create a support ticket") can be plugged into any MCP-compatible client without the server needing to know anything about which specific agent framework is consuming it.

## Building a trivial MCP server from scratch

A minimal MCP server (using Python's official SDK) exposes one tool:

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo-server")

@mcp.tool()
def get_weather(city: str) -> str:
    """Get the current weather for a given city."""
    return f"The weather in {city} is sunny, 24°C."

if __name__ == "__main__":
    mcp.run()
```

The `@mcp.tool()` decorator and the docstring are doing real work here: the docstring becomes the tool's description that the model sees when deciding whether to call it, and the type hints (`city: str`) become the parameter schema — this is the exact same "name, description, parameters" shape from Unit 8.6's tool-calling primitive, just exposed through MCP's standard protocol instead of a framework-specific format.

## How MCP relates to everything else in this module

MCP doesn't replace tool-calling (8.6) or LangGraph (8.7) — it standardizes how tools get **defined and connected**, so the same tool works across whichever agent framework or client you (or someone else) choose. Think of it as the interoperability layer sitting underneath the agent logic, not a competing way of building agents.

## Practice tip

Build the trivial single-tool MCP server above, then connect it to an MCP-compatible client (several editors and agent frameworks support this natively) and watch the tool actually get called through the protocol. Seeing one real tool call flow through MCP end-to-end is worth far more for interview readiness than reading the spec alone — you'll be able to explain concretely what problem it solves instead of reciting the concept.
