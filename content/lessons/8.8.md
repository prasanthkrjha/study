# Model Context Protocol (MCP)

MCP is explicitly listed as a "must-have" in current senior full-stack-AI postings — worth knowing conceptually even before you're using it daily, which is exactly this unit's scope.

## Theory & Fundamentals

### Why MCP Exists

Before MCP, every agent framework (LangChain, CrewAI, custom setups) had its **own** way of defining and wiring up tools — a tool built for one framework couldn't be reused in another without rewriting it. The same "search our Notion docs" tool would need to be reimplemented separately for LangGraph, for Claude, for OpenAI's assistant, and for any IDE plugin that wanted to use it.

MCP (Model Context Protocol) is a standardized protocol for how an AI application (the "client") talks to external tools and data sources (the "server"), so a tool built once can be used by any MCP-compatible client without rewriting it per framework.

**The HTTP/REST analogy**: MCP is doing for AI tool integration roughly what REST/HTTP did for web APIs — a common protocol so that clients and servers built by different teams can interoperate without custom one-off integration code for every pair. Once you've built an MCP server, it works with Claude, ChatGPT, Cursor, any LangGraph agent, and any IDE extension that speaks MCP.

### The Core Architecture

- **MCP server** — exposes tools, resources (data the model can read), and/or prompts over a standardized interface. A server is a process that listens for tool call requests.
- **MCP client** — the AI application (an agent framework, an IDE, a chat client) that connects to one or more MCP servers and makes their tools available to the model.

A single MCP server ("internal docs search + create support ticket") can be plugged into any MCP-compatible client without the server knowing which specific framework is consuming it.

### Three Primitives

MCP exposes three types of capabilities:

| Primitive | Description | Example |
|---|---|---|
| **Tools** | Functions the model can call | `search_docs(query)`, `create_ticket(title, body)` |
| **Resources** | Data sources the model can read | Current file in the IDE, database schema, config files |
| **Prompts** | Pre-defined prompt templates | "Summarize this PR", "Generate a commit message" |

Most MCP usage today is tools — the other two are less commonly implemented.

## Core Patterns / Techniques

### Building a Minimal MCP Server (Python)

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo-server")

@mcp.tool()
def get_weather(city: str) -> str:
    """Get the current weather for a given city.
    
    Returns a string describing current conditions and temperature.
    """
    # In production: call a real weather API
    return f"The weather in {city} is sunny, 24°C."

@mcp.tool()
def search_docs(query: str, limit: int = 5) -> list[dict]:
    """Search the internal documentation for relevant articles.
    
    Returns a list of matching articles with title, url, and excerpt.
    """
    # In production: query a vector database or search engine
    return [{"title": "Getting Started", "url": "/docs/start", "excerpt": "..."}]

if __name__ == "__main__":
    mcp.run()  # starts the MCP server over stdio
```

Three things to notice:
1. The docstring becomes the tool description the model sees when deciding whether to call it.
2. The type hints (`city: str`, `limit: int = 5`) become the parameter schema automatically.
3. This is the exact same "name, description, parameters" shape from Unit 8.6's tool-calling primitive — just expressed through MCP's standard protocol.

### Building a Minimal MCP Server (TypeScript/Node.js)

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "demo-server", version: "1.0.0" });

server.tool(
    "get_weather",
    "Get the current weather for a given city",
    { city: z.string().describe("The city name") },
    async ({ city }) => ({
        content: [{ type: "text", text: `The weather in ${city} is sunny, 24°C.` }],
    })
);

const transport = new StdioServerTransport();
await server.connect(transport);
```

### Connecting to an MCP Server

Most MCP clients configure servers in a JSON file (e.g., `~/.claude/claude_desktop_config.json` for Claude Desktop):

```json
{
  "mcpServers": {
    "demo-server": {
      "command": "python",
      "args": ["/path/to/server.py"]
    }
  }
}
```

The MCP client starts the server process, establishes a connection over stdio, and discovers the available tools. From the model's perspective, tools from an MCP server are indistinguishable from tools defined directly in the application.

## Best Practices

- **Write descriptive docstrings** — the docstring is the tool's description. "Get weather" gives the model no information about when to call it or what it returns. "Get the current weather conditions and temperature for a city by name, using the OpenWeatherMap API" is actionable.
- **Use type hints (Python) or Zod schemas (TypeScript)** — these are automatically converted to the parameter JSON schema. Missing type hints means the model doesn't know what arguments the tool expects.
- **One MCP server per domain** — a server for "internal docs" and a server for "ticketing system" are easier to manage, test, and reuse than one server with every tool.
- **Implement error handling and return informative error messages** — if a tool fails, return a descriptive error string rather than raising an exception; the model can reason about the error and try a different approach.
- **Test your server with the MCP Inspector** — the official CLI tool that lets you invoke tools directly without needing a full client setup.

## Common Interview Questions

**Q1: What is MCP and why was it created?**
A: Model Context Protocol is a standardization layer for how AI applications connect to external tools and data sources. Before MCP, every agent framework (LangChain, OpenAI Assistants, Claude) had its own tool format, so a tool built for one framework couldn't be used in another. MCP provides a common protocol so a tool built once works in any MCP-compatible client — analogous to how REST/HTTP standardized web API interoperability.

**Q2: What are the three primitives MCP exposes?**
A: Tools (functions the model can call, like `search_docs(query)`), Resources (data sources the model can read, like the current file in an IDE or a database schema), and Prompts (pre-defined prompt templates). Tools are the most commonly implemented and most directly relevant to agent use cases.

**Q3: How does MCP differ from just defining tools directly in your agent?**
A: Directly defined tools are framework-specific — they work only in the framework they were written for. An MCP server exposes the same tools through a standard protocol that any MCP-compatible client can consume. This enables sharing tools across frameworks (LangGraph, Claude, OpenAI), across teams, and across applications without duplication.

**Q4: What transport does MCP use to communicate between client and server?**
A: The most common is stdio (standard input/output) — the client starts the server as a subprocess and communicates through stdin/stdout. HTTP with SSE (Server-Sent Events) is another transport, used when the server needs to be a long-running process accessible over a network rather than a subprocess.

**Q5: How does an MCP server's tool definition relate to the tool-calling primitive from Unit 8.6?**
A: It's the same underlying concept: a tool has a name, a description, and a parameter schema. The model uses this information to decide when to call the tool and what arguments to pass. MCP standardizes how this definition is communicated from the server to the client, and how the call and result are transmitted, but the model's experience is identical to calling any other tool.

## Practice Exercises

1. **Minimal server**: Build the trivial single-tool MCP server from the examples above (`get_weather`). Connect it to an MCP-compatible client (Claude Desktop, the MCP Inspector CLI, or a LangGraph agent) and observe a real tool call flow through the protocol end-to-end.

2. **Real tool**: Replace the stub implementation with a real API call — a weather API, your own database, or a search index. Verify that the model calls it correctly when given a relevant query and uses the returned data in its response.

3. **Multi-tool server**: Add three tools to your server: `search_docs(query)`, `get_document(id)`, and `create_ticket(title, body)`. Connect to a client with all three tools available. Design a task that requires using all three in sequence (search → get the full doc → create a ticket referencing it) and verify the agent completes it correctly.

## Key Takeaways

- MCP standardizes how AI applications connect to tools and data sources — a tool built once works in any MCP-compatible client.
- The three primitives: Tools (callable functions), Resources (readable data), Prompts (pre-built templates). Tools are the most commonly implemented.
- Python: use `@mcp.tool()` decorator; TypeScript: use `server.tool()`. Docstrings and type hints become the tool description and parameter schema automatically.
- The HTTP/REST analogy: MCP is to AI tool integration what REST/HTTP is to web APIs — a common protocol enabling interoperability without custom one-off integration code for every client-server pair.
- Transport: stdio (subprocess communication) for local tools; HTTP+SSE for network-accessible servers.
