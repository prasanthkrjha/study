# Model Context Protocol (MCP)

Every tool you build for an AI application has a hidden cost: it only works in one place. You write a "search our Notion docs" tool for your LangChain agent, and it works great. Then your team wants to use Claude Desktop to also search Notion. You rewrite the tool — different format, different wiring, different runtime. Then your IDE plugin wants the same capability. Rewrite again.

This is the N×M integration problem: N AI applications times M tools equals N×M completely separate implementations. Every new tool has to be built again for every framework that wants to use it. This is the problem MCP solves.

**The HTTP/REST analogy** is the clearest way to understand why MCP matters. Before REST became a standard, every web API had its own custom format. You couldn't reuse a client library between APIs — you wrote custom integration code for each one. REST standardized the shape of web API interactions: resources identified by URLs, actions expressed as HTTP verbs, responses in a predictable format. Once that standard existed, any HTTP client could talk to any REST API without custom integration code. MCP does the same thing for AI tool integrations. Write a tool once as an MCP server, and any MCP-compatible client — Claude Desktop, Cursor, a LangGraph agent, a custom chatbot — can use it without rewriting.

## Theory & Fundamentals

### The Two Parties

Every MCP interaction involves exactly two parties:

**The MCP server** is the process that exposes tools, data, and capabilities. It knows nothing about which AI application is using it. It just listens for requests and responds to them. You write MCP servers when you have a capability you want to make available to AI systems — searching your database, creating tickets, reading files, calling an API.

**The MCP client** is the AI application that connects to the server and makes its tools available to the model. Claude Desktop, Cursor, and LangGraph are all MCP clients. When you configure a client to connect to your server, it discovers what tools are available and adds them to the model's tool list.

The key architectural insight: the server and client are developed independently. The server doesn't know or care whether it's talking to Claude Desktop or a LangGraph agent. The client doesn't know or care how the server is implemented — Python, TypeScript, Go, anything. The protocol is the contract.

### How They Communicate

The default transport between client and server is **stdio (standard input/output)**. Here is exactly what happens when you use MCP with stdio:

1. The MCP client reads its configuration file and finds a server to start.
2. The client launches the server as a child subprocess (like running a command in a terminal).
3. The client sends JSON messages to the server's stdin.
4. The server reads those messages, processes them, and writes JSON responses to its stdout.
5. The client reads the responses from the server's stdout.

Why stdio? It is simple, requires no network configuration, works on every operating system, and ties the server process lifecycle to the client — when the client closes, the server process exits automatically. No ports to configure, no firewall rules, no authentication tokens for local tools.

The alternative transport is **HTTP with Server-Sent Events (SSE)**. This is used when the server needs to be a long-running network process rather than a subprocess — for example, a centralized MCP server that multiple people or services connect to. HTTP+SSE introduces network configuration overhead, but enables a server to serve many clients at once.

For most use cases during development and for tools running on the same machine, stdio is the right choice.

### The Three Primitives

MCP exposes three types of capabilities. Understanding what each one is — and what it is NOT — is important for building servers correctly.

**Tools** are functions the model can call. The model sees the tool's name, description, and parameter schema. When the model decides to call a tool, it provides arguments, the server executes the function, and returns a result that the model can read and reason about. Tools are the most commonly implemented primitive and what most people mean when they talk about MCP.

**Resources** are data the model can READ — not functions to call. Think of resources as files or database records that the model can fetch as context. The current file open in your IDE is a resource. Your database schema is a resource. The contents of a configuration file are a resource. Resources are read-only context that the model can request before generating a response. They are distinct from tools in a meaningful way: the model doesn't "call" a resource with arguments, it reads it like reading a file.

**Prompts** are pre-defined prompt templates the server can provide. "Summarize this pull request" or "Generate a commit message for these changes" — prompts that your server knows how to build properly, which the client can invoke on behalf of the user. Prompts are the least commonly implemented of the three primitives and appear mainly in IDE integrations and workflow tools.

For most backend integrations, you will implement Tools. Resources and Prompts become relevant when you're building deeply integrated IDE or workflow tooling.

## How a Tool Call Actually Works

Before writing code, it helps to understand the full round-trip of a single tool call — what happens step by step.

**Step 1 — Discovery**: When the MCP client connects to your server, it sends a `tools/list` request. Your server responds with a list of all available tools, including each tool's name, description, and parameter schema. The client stores this list.

**Step 2 — Tool injection**: The client takes the list of available tools and adds them to the model's tool list, alongside any locally defined tools. From the model's perspective, there is no difference between an MCP tool and a tool defined directly in the application. They all appear in the same list.

**Step 3 — Model decides to call a tool**: The user sends a message. The model reads the tools list and decides which tool (if any) to call. It produces a tool call with the tool's name and the arguments it chose.

**Step 4 — Client forwards the call**: The client sends a `tools/call` request to your MCP server over stdio, including the tool name and the arguments.

**Step 5 — Server executes and responds**: Your server receives the request, runs the tool function, and sends back the result.

**Step 6 — Model sees the result**: The client adds the tool result to the conversation. The model reads the result and continues generating its response.

This entire loop can happen multiple times in a single conversation turn if the model decides it needs to call multiple tools.

## The Three Primitives in Depth

### Tools

A tool has three components the model sees:
- **Name**: the function identifier. Use snake_case, be specific (`search_internal_docs` not `search`).
- **Description**: the critical part. This is what the model reads to decide whether to call the tool. If your description is vague, the model will call the wrong tool or not call it at all.
- **Parameter schema**: the shape of the arguments. Automatically generated from type hints (Python) or Zod schemas (TypeScript).

The tool also has one component the model never sees but you write: the actual implementation.

### Resources

Resources are identified by a URI (like `file:///path/to/file` or `postgres://mydb/schema`). The client can request any resource by its URI, and the server returns the contents. Resources are useful when the model needs to read something that isn't a function call — the current state of a file, the structure of a database, the contents of a configuration.

### Prompts

A prompt has a name and produces a fully-formed prompt message when invoked, potentially with arguments. A "generate commit message" prompt might accept a diff as an argument and return a structured prompt that tells the model exactly how to format the commit message. Prompts standardize recurring prompt patterns that would otherwise be copy-pasted across applications.

## Building an MCP Server — Line by Line

### Python with FastMCP

FastMCP is the Python library that makes building MCP servers as simple as adding a decorator. Here is the minimal server:

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("internal-docs-server")

@mcp.tool()
def search_docs(query: str, limit: int = 5) -> list[dict]:
    """Search the internal documentation for articles matching the query.
    
    Returns a list of matching articles, each with 'title', 'url', and 'excerpt'.
    Call this when the user asks a question that might be answered by internal docs.
    """
    # In production: query your vector database or search engine
    return [
        {"title": "Onboarding Guide", "url": "/docs/onboarding", "excerpt": "..."},
        {"title": "API Reference", "url": "/docs/api", "excerpt": "..."},
    ]

if __name__ == "__main__":
    mcp.run()  # starts the server listening on stdio
```

Let's go through what each piece does and WHY it's written that way.

**`FastMCP("internal-docs-server")`** creates the server object and gives it a name. The name appears in logs and in the client's tool list — it helps distinguish this server from others when you have multiple servers connected.

**`@mcp.tool()`** is a decorator that registers the function as an MCP tool. When `mcp.run()` is called, FastMCP inspects all decorated functions and builds the tool metadata automatically. Without this decorator, the function is just a regular Python function — the server has no idea it exists.

**The docstring** is not optional — it IS the tool description the model sees. FastMCP reads your docstring and sends it to the client as the tool's description. This is what the model reads when deciding whether to call this tool.

Here is a bad docstring vs. a good docstring:

```python
# BAD — gives the model no useful information
def search_docs(query: str) -> list[dict]:
    """Search docs."""
    ...

# GOOD — tells the model WHEN to call this, WHAT it returns, and HOW to use it
def search_docs(query: str) -> list[dict]:
    """Search the internal documentation for articles matching the query.
    
    Returns a list of matching articles, each with 'title', 'url', and 'excerpt'.
    Call this when the user asks a question that might be answered by internal 
    documentation, policies, or procedures. For questions about code or external
    APIs, use a different tool.
    """
    ...
```

The bad docstring will cause the model to call the tool at the wrong times (or not call it when it should). The model is making a decision based on the description — treat the docstring as the interface that the model programs against.

**Type hints** (`query: str`, `limit: int = 5`) are automatically converted to the parameter JSON schema. FastMCP reads the type annotations and builds:

```json
{
  "type": "object",
  "properties": {
    "query": { "type": "string" },
    "limit": { "type": "integer", "default": 5 }
  },
  "required": ["query"]
}
```

Without type hints, FastMCP cannot generate the schema. The model won't know what arguments the tool expects, and many clients will refuse to make the tool available at all.

**`mcp.run()`** starts the server and begins listening on stdin for incoming requests. The process will run until the client closes its end of the connection (or the process is killed).

### TypeScript with the MCP SDK

The TypeScript SDK requires a bit more explicit code because TypeScript doesn't have Python's runtime type introspection — you must provide the schema explicitly using Zod:

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({
    name: "internal-docs-server",
    version: "1.0.0"
});

server.tool(
    "search_docs",               // tool name
    "Search the internal documentation for articles matching the query. " +
    "Returns a list of articles with title, url, and excerpt. " +
    "Call this when the user asks about internal policies or procedures.",
    {                            // Zod schema → converted to JSON schema automatically
        query: z.string().describe("The search query to find relevant articles"),
        limit: z.number().optional().default(5).describe("Max articles to return")
    },
    async ({ query, limit }) => {
        // Implementation
        const results = await searchInternalDocs(query, limit);
        return {
            content: [{
                type: "text",
                text: JSON.stringify(results, null, 2)
            }]
        };
    }
);

const transport = new StdioServerTransport();
await server.connect(transport);
```

The Zod schema (`z.string()`, `z.number().optional()`) serves the same purpose as Python's type hints — Zod schemas have a one-to-one mapping to JSON Schema, so the SDK can automatically generate the parameter schema the client and model will see.

The description string (second argument to `server.tool()`) is the equivalent of the Python docstring — same rule applies: make it specific and tell the model when to call this tool.

## A Real Tool with Error Handling

Here is a more realistic tool — one that queries a database — showing what the model sees, the implementation, and how to handle failures correctly:

```python
from mcp.server.fastmcp import FastMCP
import sqlite3

mcp = FastMCP("customer-service-tools")

@mcp.tool()
def get_order_status(order_id: str) -> str:
    """Look up the current status of a customer order by order ID.
    
    Returns the order status (pending, processing, shipped, delivered, cancelled)
    and estimated delivery date if available. Returns an error message if the
    order ID is not found. Use this when the customer asks about their order.
    """
    try:
        conn = sqlite3.connect("orders.db")
        cursor = conn.execute(
            "SELECT status, estimated_delivery FROM orders WHERE id = ?",
            (order_id,)
        )
        row = cursor.fetchone()
        conn.close()

        if row is None:
            # Return a descriptive error string — do NOT raise an exception
            return f"Order {order_id} not found. Please verify the order ID and try again."

        status, delivery = row
        if delivery:
            return f"Order {order_id} is {status}. Estimated delivery: {delivery}."
        return f"Order {order_id} is {status}."

    except sqlite3.Error as e:
        # Return an error string the model can read and act on
        return f"Database error while looking up order {order_id}: {str(e)}"
```

**Why return error strings instead of raising exceptions?** When your tool raises an exception, the MCP protocol catches it and sends back a generic error. The model sees "tool call failed" — it has no information about why it failed or what to do next.

When your tool returns a descriptive error string, the model sees the error as part of the conversation. The model can read "Order 12345 not found. Please verify the order ID." and respond helpfully: "I couldn't find that order ID. Could you double-check the number?" The model can reason about errors when they're returned as readable strings. It cannot reason about exceptions.

**What the model sees** for this tool (after the client discovers it):

```
Tool: get_order_status
Description: Look up the current status of a customer order by order ID.
  Returns the order status (pending, processing, shipped, delivered, cancelled)
  and estimated delivery date if available. Returns an error message if the
  order ID is not found. Use this when the customer asks about their order.
Parameters:
  - order_id (string, required): the order ID to look up
```

**What happens when it succeeds** — the model calls the tool with `order_id: "ORD-5521"`, the server queries the database, returns `"Order ORD-5521 is shipped. Estimated delivery: 2026-08-10."`, and the model incorporates that into its response.

**What happens when it fails** — the model calls the tool with `order_id: "ORD-9999"`, the server returns `"Order ORD-9999 not found. Please verify the order ID and try again."`, and the model tells the user: "I couldn't find order ORD-9999 in the system. Could you check the order number?"

## Connecting a Server to a Client

Most MCP clients use a JSON configuration file. For Claude Desktop, this is `~/.claude/claude_desktop_config.json`. Here is an example configuration:

```json
{
  "mcpServers": {
    "customer-service": {
      "command": "python",
      "args": ["/home/user/mcp-servers/customer_service.py"]
    },
    "internal-docs": {
      "command": "node",
      "args": ["/home/user/mcp-servers/docs-server/index.js"]
    }
  }
}
```

Let's understand each field:

**The key (`"customer-service"`)** is the server's display name in the client. This is how the client identifies it in logs and (sometimes) how it namespaces tools to avoid conflicts between servers.

**`"command"`** is the executable that starts the server. `"python"` will run the Python server; `"node"` will run the Node.js server. This is literally the same as running the command in a terminal.

**`"args"`** is the list of arguments passed to the command. The path to your server file goes here.

When the client starts (Claude Desktop opens, Cursor launches), it reads this config file, starts each server as a subprocess, and connects over stdio. The initialization sequence:

1. Client sends `initialize` request → server responds with its capabilities.
2. Client sends `tools/list` request → server responds with all available tools.
3. Client makes all discovered tools available to the model.
4. User starts chatting. The model now has those tools available in every message.

From the model's perspective, there is no distinction between a tool defined locally in the application and a tool from an MCP server. Both appear in the same tools array. Both are called the same way. The MCP layer is invisible to the model.

## Best Practices

### Write Specific, Actionable Docstrings

The docstring (or description string in TypeScript) is not documentation for developers — it is the interface the model uses to decide when and how to call your tool. If the description is vague, the model will make wrong decisions.

Bad: `"""Get weather."""`
Good: `"""Get the current weather conditions and temperature for a city. Returns temperature in Celsius and a description of conditions (clear, cloudy, rainy). Call this when the user asks about current weather in a specific location."""`

The key information to include:
- What the tool returns (specifically)
- When the model should call it (the triggering condition)
- What it does NOT cover (if there's a similar tool that might be confused with this one)

### Always Use Type Hints

Python type hints and TypeScript/Zod schemas are both automatically converted to the JSON Schema the model sees. Without them, the model doesn't know what arguments to provide. Some clients will refuse to expose tools with no schema at all.

### Return Error Strings, Not Exceptions

When a tool fails, return a human-readable description of what went wrong and (when possible) what the caller can do about it. Exceptions become generic error messages that give the model nothing to work with.

### Keep Servers Focused

A server with 5-10 closely related tools is easier to understand, test, and maintain than a kitchen-sink server with 50 tools. Focused servers are also less likely to confuse the model: when all tools in a server have a coherent domain ("customer order management"), the model can reliably choose the right tool. When a server has 50 unrelated tools, the model must distinguish between many more options, and description quality becomes even more critical.

A practical split: one server per domain area. `customer-service-tools` (order lookup, refund request, ticket creation), `internal-docs` (search, fetch article), `code-tools` (run tests, check linting). Each can be connected to or disconnected from a client independently.

### Test with the MCP Inspector

The MCP Inspector is a CLI tool (`npx @modelcontextprotocol/inspector`) that lets you connect to your server and call tools directly without needing a full client. Essential for verifying that your tool descriptions make sense and that the implementation actually works before connecting to a model.

## Common Mistakes

**Vague docstrings**. If the description doesn't explain when to call the tool and what it returns, the model will misuse it. This is the single most common mistake in MCP tool design. The docstring is not optional polish — it is the model's only instruction for using your tool correctly.

**Missing type hints**. Without type annotations, there is no parameter schema. The model cannot know what arguments to provide. FastMCP will still register the tool, but it will be unusable in practice.

**Raising exceptions instead of returning error strings**. Exceptions give the model nothing to reason about. Return descriptive strings that tell the model what went wrong and what it can do next.

**One giant server with every tool**. When a server exposes 50 loosely related tools, the model struggles to choose correctly between them, and the tool list becomes cognitively overwhelming. Split by domain: a server should have a single, clear responsibility.

**Not testing the description from the model's perspective**. After writing a tool, read its description as if you know nothing about the implementation. Would you know when to call it? Would you know what it returns? If not, the model won't either.

## Common Interview Questions

**Q1: What is MCP and why was it created?**
A: Model Context Protocol is a standardized protocol for how AI applications connect to external tools and data sources. Before MCP, every agent framework had its own tool format — a tool built for LangChain couldn't be used in Claude Desktop without rewriting it. The N×M problem: N frameworks times M tools equals N×M separate implementations. MCP provides a common protocol analogous to how REST standardized web APIs — write a tool once as an MCP server and any MCP-compatible client can use it without rewriting.

**Q2: What are the three primitives MCP exposes, and what is the difference between them?**
A: Tools (functions the model can call — they take arguments, execute logic, and return results), Resources (data the model can read, like files or database schemas — read-only context, not executable actions), and Prompts (pre-built prompt templates a server can provide). Tools are the most commonly implemented. Resources and Prompts appear mainly in IDE integrations and workflow tooling.

**Q3: How does MCP communicate between client and server?**
A: The default transport is stdio — the client starts the server as a subprocess and communicates through stdin (requests) and stdout (responses) using JSON messages. This requires no network configuration, works on every OS, and ties the server's process lifecycle to the client. HTTP+SSE is the alternative for servers that need to be long-running network processes accessible from multiple clients.

**Q4: How does an MCP server's tool definition relate to tool-calling that models already understand?**
A: The underlying concept is identical — a tool has a name, a description, and a parameter schema. The model uses this information to decide when to call the tool and what arguments to pass. MCP standardizes how this information is communicated from the server to the client, and how calls and results are transmitted over the wire. From the model's perspective, MCP tools and locally defined tools are indistinguishable.

**Q5: Why should MCP tools return error strings instead of raising exceptions?**
A: When a tool raises an exception, the protocol catches it and sends back a generic error message — the model sees "tool call failed" and has no information about why or what to do next. When a tool returns a descriptive error string ("Order 12345 not found — please verify the ID"), the model reads that string and can respond intelligently to the user. Returning errors as strings lets the model reason about failures.

## Practice Exercises

1. **Minimal server**: Build a single-tool MCP server that does something real — call a public API (a weather API, a currency converter, a word definition API). Write a good docstring. Connect it to an MCP client (Claude Desktop or the MCP Inspector) and verify the model calls the tool at the right times.

2. **Error handling**: Intentionally trigger an error case in your tool (wrong argument, API down). Verify that the model receives a useful error string and can explain the failure to the user in a natural way.

3. **Multi-tool server**: Build a server with three related tools: `list_items`, `get_item_details`, and `create_item`. Write descriptions that clearly distinguish when to call each one. Connect to a client and test a multi-step conversation that uses all three.

4. **Description quality test**: After writing a tool, give someone else only the tool name and description (not the code). Ask them: "Based on only this, when would you call this tool? What does it return?" If they get it wrong or are uncertain, rewrite the description.

- MCP solves the N×M integration problem: write a tool once as an MCP server, and any MCP-compatible client can use it without rewriting. The HTTP/REST analogy: MCP is to AI tool integration what REST/HTTP is to web APIs.
- Two parties: the MCP server (exposes tools, resources, prompts) and the MCP client (AI application that connects and makes those capabilities available to the model).
- Default transport is stdio — client starts the server as a subprocess, communicates via stdin/stdout with JSON messages. HTTP+SSE for network-accessible servers.
- Three primitives: Tools (callable functions), Resources (readable data, not executable), Prompts (pre-built templates). Tools are the most commonly implemented.
- The docstring IS the tool description the model reads to decide when to call the tool. Write it for the model, not for developers.
- Type hints (Python) and Zod schemas (TypeScript) are automatically converted to the JSON parameter schema. Without them, the model doesn't know what arguments to provide.
- Return error strings, not exceptions — strings give the model something to reason about; exceptions produce generic "tool call failed" messages.
- Keep servers focused on one domain (5-10 related tools) rather than building kitchen-sink servers with 50 unrelated tools.
