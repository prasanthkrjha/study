# LLM Evaluation & Fine-Tuning Concepts

Building an AI system is the easy part. Knowing whether it is actually working — and knowing what to do when it isn't — is the hard part. This unit is about developing the judgment to measure, diagnose, and improve LLM systems systematically rather than by guessing.

---

## Why LLM Evaluation is Hard

Start with traditional software testing. You have a function that adds two numbers. Testing it is simple:

```python
assert add(2, 3) == 5
assert add(-1, 1) == 0
assert add(0, 0) == 0
```

Binary. Deterministic. Unambiguous.

Now test an LLM system. A user asks "What are your business hours?" Your RAG system might respond:

- "We're open Monday through Friday from 9am to 5pm."
- "Our business hours are 9:00 AM to 5:00 PM, Monday to Friday."
- "Weekdays, we open at 9 in the morning and close at 5 in the evening."

All three answers are correct. None of them match the string you'd write as an expected value. You cannot write `assert response == "We're open Monday through Friday from 9am to 5pm."` — that assertion would fail for every correct answer except one specific phrasing.

So how do you actually test an LLM system? You have three tools:

**Substring presence**: check that the response CONTAINS certain terms. "9" and "Monday" must appear in any correct response about business hours. Not foolproof (a response could contain "9" for the wrong reason), but catches obvious failures.

**Substring absence**: check that the response does NOT contain failure phrases. "I don't know" or "I'm not sure" in response to a question your system should be able to answer means something went wrong — retrieval failed, or your instructions aren't working.

**Semantic evaluation (LLM-as-judge)**: use another model call to evaluate whether the response is correct. "Given this question and this answer, is the answer accurate and complete? YES or NO." This can catch correctness problems that substring checks miss.

These three tools, combined, form the foundation of an LLM evaluation harness. None is perfect individually — but together they catch the most important failure modes.

## Theory & Fundamentals

### The Three Layers of RAG Evaluation

A RAG system has two distinct components: the retriever (which fetches relevant documents) and the generator (which produces an answer from those documents). Evaluating them together makes diagnosis impossible — if the system gives a wrong answer, is it because the wrong documents were retrieved, or because the model hallucinated despite having the right documents? You need to evaluate each layer separately.

#### Layer 1 — Retrieval Evaluation

**The problem**: even if your generator is perfect, if the retriever returns the wrong documents, the generator cannot produce a correct answer. Retrieval is the foundation. A problem here propagates to every answer the system produces.

**How to test it**: create test cases where you know, in advance, which source document contains the correct answer for each question. Run your retriever and check whether that document appears in the top-k results.

For example: you know the answer to "What is your return policy?" is in the document `return-policy.pdf`. You retrieve the top-5 chunks for that query. Did `return-policy.pdf` appear? If not, your retriever has a problem.

**The key metrics**:

*Precision@k*: of the k documents you returned, what fraction are actually relevant? If you return 5 documents and only 2 are relevant to the question, your precision@5 is 0.4 (40%). Low precision means you're filling the model's context with irrelevant information, making it harder for the model to find the actual answer.

*Recall@k*: of all documents that ARE relevant to this question, what fraction did you return? If there are 3 relevant documents and you retrieved 2 of them in your top-5, your recall@5 is 0.67 (67%). Low recall means you're missing important information — the model can't answer from documents it never sees.

*MRR (Mean Reciprocal Rank)*: is the best relevant document ranked first? Fifth? Tenth? MRR penalizes cases where the correct document IS retrieved but buried at the bottom of the list. If you retrieve 5 documents and the correct one is ranked 3rd, the reciprocal rank for this query is 1/3. MRR is the average of reciprocal ranks across all test queries.

Why does MRR matter? Most RAG implementations only insert the top-3 or top-5 chunks into the prompt. If the correct document is ranked 8th out of 10, it will never make it into the prompt. MRR catches this problem — precision and recall alone would say "we retrieved it" without flagging that it was too buried to be used.

#### Layer 2 — Generation Evaluation (LLM-as-Judge)

**The problem**: even when retrieval works correctly and the right documents are in the prompt, the model might not use them faithfully. It might extrapolate beyond the context, contradict the source, or confidently state something that isn't supported. This is hallucination in its most specific form.

**The solution**: use another model call to evaluate. You give the judge model the retrieved context and the generated answer, and ask: "Is this answer fully supported by the context? YES or NO." This is called LLM-as-judge.

```python
def faithfulness_judge(context: str, answer: str) -> dict:
    """Ask a model whether the answer is supported by the context."""
    judge_prompt = f"""You are evaluating whether an AI assistant's answer is 
supported by the provided context. Read the context carefully, then evaluate 
the answer.

Context:
{context}

Answer:
{answer}

Is every factual claim in the answer directly supported by the context?
Do not use outside knowledge — evaluate only based on what the context says.

Respond with:
- VERDICT: YES or NO
- REASON: one sentence explaining your verdict
"""
    response = client.messages.create(
        model="claude-haiku-4-5-20251001",  # use a cheap model for judging
        max_tokens=200,
        messages=[{"role": "user", "content": judge_prompt}]
    )
    text = response.content[0].text
    verdict = "YES" in text.upper()
    return {"faithful": verdict, "reason": text}
```

Let's look at WHY each part of the judge prompt is written the way it is:

"Do not use outside knowledge — evaluate only based on what the context says." Without this instruction, the judge model might confirm a claim as true because it knows from its training data that it's true — even if it isn't in the context. You don't want the judge to check if the answer is factually accurate in general; you want it to check if the answer is *grounded in the provided context*.

"Read the context carefully" is included because judge models can be lazy — they sometimes skim and give fast verdicts. Explicitly instructing careful reading improves accuracy.

Using a cheap model (Haiku, GPT-4o-mini) for judging: the judge task is simple reading comprehension with a yes/no output. You don't need the most powerful model. A cheap, fast model works nearly as well and costs far less — this matters when you're running the eval harness after every deployment or code change.

**Why LLM-as-judge works**: modern language models are genuinely good at reading comprehension and factual checking — better than any keyword matching approach at catching semantic mismatches between claims and supporting evidence.

**Why it's imperfect**: the judge model can itself hallucinate. It can be fooled by confident, fluent-sounding wrong answers — confident phrasing correlates with "truthful" in the judge's training data even when the claim is false. The judge may also be biased toward responses in the style of its own model family. Treat judge verdicts as an approximation, not ground truth. Calibrate your judge on a set of examples where you know the correct answer before trusting its output at scale.

#### Layer 3 — End-to-End Evaluation

**The purpose**: regression testing. Every time you change a component of your RAG pipeline — the system prompt, the chunk size, the embedding model, the number of retrieved chunks — you need to know whether that change helped or hurt overall system performance.

This is the test suite for your LLM system. It plays exactly the same role as unit tests in regular software: it tells you, after every change, whether you broke something that used to work.

```python
test_cases = [
    {
        "question": "What are your business hours?",
        "must_contain": ["9", "5", "Monday"],
        "must_not_contain": ["I don't know", "I'm not sure"],
    },
    {
        "question": "Do you accept credit cards?",
        "must_contain": ["yes", "credit"],
        "must_not_contain": ["I don't know", "unable to answer"],
    },
    {
        "question": "How do I request a refund?",
        "must_contain": ["return", "email"],
        "must_not_contain": ["I don't know", "not sure"],
    },
]

def run_eval(rag_chain, test_cases):
    results = []
    for case in test_cases:
        answer = rag_chain.invoke(case["question"])
        answer_lower = answer.lower()

        passed_contains = all(
            term.lower() in answer_lower
            for term in case.get("must_contain", [])
        )
        passed_not_contains = not any(
            term.lower() in answer_lower
            for term in case.get("must_not_contain", [])
        )
        passed = passed_contains and passed_not_contains

        results.append({
            "question": case["question"],
            "answer": answer,
            "passed": passed,
        })

    total = len(results)
    passing = sum(r["passed"] for r in results)
    print(f"Pass rate: {passing/total:.0%} ({passing}/{total})")
    return results
```

Why `must_not_contain` is important: checking for the absence of "I don't know" and "I'm not sure" is one of the most valuable tests in an evaluation harness. These phrases are explicit signals that something failed — the retriever didn't find relevant documents, the model couldn't extract an answer from the context, or the instructions aren't working. When "I don't know" appears in a response to a question your system should be able to answer, you've caught a real failure.

**Running it before and after a change**:

```python
# Baseline: chunk_size=500
chain_v1 = build_rag_chain(chunk_size=500)
results_v1 = run_eval(chain_v1, test_cases)

# After change: chunk_size=1000
chain_v2 = build_rag_chain(chunk_size=1000)
results_v2 = run_eval(chain_v2, test_cases)

# Compare: what changed?
for r1, r2 in zip(results_v1, results_v2):
    if r1["passed"] != r2["passed"]:
        print(f"CHANGED: {r1['question']}")
        print(f"  Before (chunk=500): {'PASS' if r1['passed'] else 'FAIL'}")
        print(f"  After  (chunk=1000): {'PASS' if r2['passed'] else 'FAIL'}")
        print(f"  New answer: {r2['answer']}")
```

This before/after comparison is the most defensible thing you can bring into an interview discussion about LLM systems — concrete evidence that you measured the effect of a change rather than guessing.

## Hallucination — A Deep Explanation

Hallucination is one of the most misunderstood concepts in LLM systems. Let's build a precise mental model.

**What hallucination actually is**: the model "fills in" from its training data when the retrieved context doesn't contain the answer. It is not "lying" — the model has no concept of deception. It is doing exactly what it was trained to do (produce helpful, fluent text) in a situation where the retrieved context doesn't contain what it needs. The model generates the most plausible-sounding continuation based on patterns from training, which may or may not correspond to reality.

**Why it happens in RAG specifically**: your retriever returns the top-5 chunks for a query. Those chunks are similar to the query in vector space, but similarity doesn't guarantee the chunks contain the specific answer. If a user asks "What is Alice's employee ID?" and your retrieval returns chunks about Alice that don't include her employee ID, the model may still produce an answer — extrapolating from the surrounding context into something that sounds right but isn't.

The failure mode is subtle: the model might say "Alice's employee ID is 45821" with complete confidence, because it's generating the most plausible-looking employee ID given the surrounding context about Alice. It wasn't told to be uncertain; it was trained to be helpful and complete.

**Three mitigation strategies, and why each works**:

*Strategy 1: Explicit instruction*. In your system prompt, tell the model: "Answer only based on the provided context. If the context does not contain the information needed to answer the question, say 'I don't have enough information to answer this.' Do not use outside knowledge."

Why it works: the model tries to follow instructions. Clear instructions about when to say "I don't know" give the model an explicit policy to apply. It's not a perfect fix — the model can still fail to recognize when context is insufficient — but it substantially reduces hallucination.

*Strategy 2: LLM-as-judge faithfulness check*. After generating an answer, run the faithfulness judge. If the judge returns NO, flag the response for review or substitute a safe fallback ("I'm not sure about this — please contact support").

Why it works: the judge model is doing a separate reading comprehension task — it's not generating the answer, it's evaluating it. This creates an independent check on the generator's output. Even when the generator hallucinates, the judge often catches it.

*Strategy 3: Better retrieval*. This is the real fix. If the correct information IS in the retrieved chunks, the model is much less likely to hallucinate — it has the answer right there in context. Hallucination most often occurs when retrieval fails. Improving retrieval (better chunking, better embeddings, hybrid search) reduces hallucination more than any prompt-level mitigation.

**The common misconception**: "hallucination is a model quality problem and fine-tuning will fix it." In RAG systems, hallucination is almost always a retrieval problem, not a model problem. The model hallucinated because the correct information wasn't in the retrieved context. Fine-tuning on your data teaches the model to mimic your data's patterns — it doesn't give the model a way to know what's in your documents at inference time. If the retriever fails, a fine-tuned model will hallucinate just as readily as the base model. Fix retrieval first.

## Fine-Tuning — When and Why

### Building the Decision Framework

There are three levers for improving LLM behavior, and they operate at very different levels:

**Prompting** changes the INSTRUCTIONS the model receives at inference time. You write (or rewrite) the system prompt, add few-shot examples, chain the model's reasoning. This is free and instant — change a prompt, see the effect immediately. Prompting is limited by what the model already knows and how it was trained to behave. You cannot prompt a model into knowing your internal documents. You cannot prompt it into having a fundamentally different reasoning style.

**RAG** changes what INFORMATION the model has access to. You retrieve relevant documents and put them in the context window. The model's weights haven't changed — it still knows the same things it always knew — but it now has your company's documents to reason about. RAG is the right tool when the problem is "the model doesn't have access to X information." It requires no model changes and knowledge is trivially updatable (add or remove documents from your index).

**Fine-tuning** changes the MODEL ITSELF. You update the model's weights by training it further on your data. The most powerful lever, but also the most expensive, slowest to iterate, and hardest to reverse. Fine-tuning affects HOW the model responds — its tone, format, reasoning style, behavior patterns — not just what information it has access to.

### When Fine-Tuning Actually Helps

This is where most practitioners go wrong. Fine-tuning is often reached for prematurely when the actual problem is a prompt engineering issue or a retrieval issue.

Fine-tuning might be worth exploring when ALL of these are true:

**The desired behavior is consistent and well-defined**. "Always respond in formal English with bullet points" is well-defined. "Be more helpful" is not. If you can't describe the desired behavior precisely enough to write it in a system prompt, you can't encode it in fine-tuning examples either.

**Prompting reliably fails even with many examples**. Before fine-tuning, you should have tried: a clear system prompt with explicit instructions, multiple few-shot examples showing the desired behavior, chain-of-thought prompting, and at least a few iterations of prompt refinement. If the model still doesn't follow the behavior after all that, fine-tuning might help. But most "the model doesn't follow my instructions" problems are solved by clearer prompts, not fine-tuning.

**You have 1,000+ high-quality examples**. Each example is an input→output pair demonstrating the desired behavior. Writing 1,000 high-quality examples is a significant investment. If you don't have this data, you'll either need to generate it (synthetically, or through human labeling) or reconsider whether fine-tuning is the right approach.

**The behavior is about HOW the model writes, not WHAT it knows**. Fine-tuning teaches behavioral patterns, not new facts. "Always respond with JSON in this specific schema" is a behavior. "Know our entire product catalog" is a knowledge problem — that's what RAG is for.

**Common mistake**: a team notices the model doesn't format its responses consistently, decides to fine-tune, spends two weeks generating training data and running training jobs, and achieves a modest improvement. Then they try adding one clear formatting instruction to the system prompt and get 90% of the fine-tuning benefit for free. Exhaust prompting before fine-tuning.

### LoRA — Building Real Intuition

**Full fine-tuning**: you load the entire model into GPU memory and update every parameter during training. A 7B-parameter model has 7 billion individual numbers, each of which needs a gradient computed for every training step. You need massive GPU memory (multiple A100s) and significant training time. At the end, you have a completely separate copy of the model — tens of gigabytes for the fine-tuned version.

**The insight behind LoRA**: when researchers studied how model weights change during full fine-tuning, they found something surprising. The weight changes (deltas) tend to have low "intrinsic rank" — they can be closely approximated by two small matrices multiplied together. You don't need to update all 7 billion parameters; you can represent the weight update as A × B, where A and B are much smaller matrices.

```
Original weight matrix W: frozen (no gradients, no memory cost)
LoRA update: ΔW ≈ A × B
             A: model_dim × rank  (e.g., 4096 × 8)
             B: rank × model_dim  (e.g., 8 × 4096)
             rank is typically 4-64 (you choose)
```

The rank is a hyperparameter you choose. A rank of 8 means instead of updating a 4096×4096 matrix (16.8 million parameters), you train two small matrices totaling 4096×8 + 8×4096 = 65,536 parameters. You've reduced trainable parameters by ~256x for this matrix alone.

**Concrete numbers**: a 7B model fine-tuned with LoRA (rank 16) typically trains only 0.1-1% of the total parameters. This means:
- Training fits on a single consumer GPU (24GB VRAM) instead of a multi-GPU cluster
- Training is 3-10x faster
- The adapter file is 10-100MB instead of 14GB for the base model

**The result**: the base model weights are frozen. You produce a small adapter file. To use the fine-tuned model, you load the base model (unchanged) and apply the adapter. You can have multiple adapters for different tasks — one for customer service tone, one for code formatting, one for a specific JSON schema — and swap between them without keeping multiple copies of the 14GB base model.

**Why this matters practically**: LoRA made fine-tuning accessible. Before LoRA, fine-tuning a large model required institutional GPU resources. With LoRA, a small team with a single GPU can fine-tune a capable model on their domain-specific data in an afternoon.

## Best Practices

- **Build an eval harness before you start iterating**. Without baseline measurements, you cannot tell whether a change helped or hurt. Write your test cases first, run the baseline, then make changes and compare.

- **Separate retrieval evaluation from generation evaluation**. When your system gives a wrong answer, you need to know whether retrieval failed (wrong chunks) or generation failed (hallucination despite right chunks). Test them independently so you know where to focus.

- **Use a cheap model as the LLM judge**. The judge task (reading comprehension, yes/no verdict) doesn't require your most powerful model. Claude Haiku or GPT-4o-mini costs a fraction of larger models and performs nearly as well on this specific task.

- **Write test cases for real user queries, not synthetic ones**. Your eval harness is most valuable when it covers the actual questions your users ask, especially the edge cases and failure modes you discover in production. Every time you find a bug in production, add it to the eval harness.

- **Exhaust prompting before considering fine-tuning**. Most "the model doesn't do X" problems are solved by clearer prompting, few-shot examples, or better retrieval. Fine-tuning is expensive, slow to iterate, and often doesn't help with problems that are really about knowledge (use RAG) or instructions (use better prompts).

## Common Interview Questions

**Q1: How do you evaluate whether a RAG system is working correctly?**
A: Three layers. First, retrieval evaluation: for queries where you know the correct source document, check whether it appears in the top-k retrieved results — metrics include precision@k (fraction of retrieved docs that are relevant), recall@k (fraction of relevant docs you retrieved), and MRR (how highly ranked the correct document is). Second, generation evaluation: given retrieved context, does the answer use it faithfully? Check with an LLM-as-judge that reads both the context and the answer and returns a YES/NO faithfulness verdict. Third, end-to-end evaluation: a curated set of representative questions with must_contain and must_not_contain checks, re-run whenever you change any component. This is the regression test suite for the system.

**Q2: What is an LLM-as-judge and what are its limitations?**
A: Using a second model call to evaluate the output of the first. You give the judge the retrieved context and the generated answer and ask "Is this answer fully supported by the context?" Scales well — automated and handles non-deterministic LLM output better than string matching. Limitations: the judge model can itself hallucinate, may be biased toward outputs in its own style, and can be fooled by confident-sounding wrong answers. It's a useful approximation, not ground truth. Calibrate on examples where you know the correct verdict before trusting it at scale.

**Q3: What is hallucination in the context of RAG, and how do you mitigate it?**
A: Hallucination is when the model states something not supported by the retrieved context — it fills in from training data when the retrieved chunks don't contain the actual answer. Three mitigations: (1) Explicit instruction in the system prompt to only answer from context and say "I don't have enough information" otherwise. (2) LLM-as-judge faithfulness check after generation, to catch unsupported claims in post-processing. (3) Better retrieval — the real fix. If the correct information is in the retrieved chunks, the model is much less likely to hallucinate. Hallucination in RAG is usually a retrieval failure, not a model quality problem.

**Q4: When should you consider fine-tuning vs. improving prompting or RAG?**
A: Fine-tuning when: the desired behavior is consistent and well-defined, prompting reliably fails even with many few-shot examples, you have 1,000+ high-quality input→output examples, and the problem is about HOW the model responds (tone, format, style) rather than WHAT it knows. Exhaust prompting first (including few-shot examples and chain-of-thought), then RAG if the problem is missing knowledge, before considering fine-tuning. Fine-tuning is expensive, slow to iterate, and won't fix hallucination caused by bad retrieval.

**Q5: What is LoRA and why is it used instead of full fine-tuning?**
A: Low-Rank Adaptation. During full fine-tuning, you update all of a model's billions of parameters — memory-intensive and slow. LoRA's insight: weight changes during fine-tuning have low intrinsic rank, meaning ΔW can be approximated as A × B where A and B are small matrices. Only A and B are trained; the base model weights are frozen. This reduces trainable parameters to 0.1-1% of the full model, enabling fine-tuning on a single GPU instead of a multi-GPU cluster. The result is a small adapter file (10-100MB) you apply to the frozen base model, and you can have multiple adapters for different tasks without storing multiple full model copies.

## Key Takeaways

- LLM evaluation can't use exact string matching — use substring presence/absence checks, LLM-as-judge, and faithfulness scoring instead.
- Three evaluation layers for RAG: retrieval (does the right chunk come back — precision@k, recall@k, MRR?), generation (does the answer use the context faithfully — LLM-as-judge?), end-to-end (does the full system answer real queries correctly — the regression test suite).
- Hallucination in RAG is usually a retrieval failure: the model fills in from training data when the correct information isn't in the retrieved chunks. Improve retrieval first; don't assume fine-tuning will fix it.
- Fine-tuning changes HOW the model responds (behavior, tone, format). RAG changes what information it has access to. Most products never need fine-tuning — prompting and RAG cover the large majority of real requirements.
- LoRA enables efficient fine-tuning by training small adapter matrices (A × B ≈ ΔW) instead of all model parameters — typically 0.1-1% of parameters, enabling single-GPU training and small adapter files instead of multiple full model copies.
- Build your eval harness before iterating: without a baseline, you cannot tell whether a change helped or hurt.
