# LLM Evaluation & Fine-Tuning Concepts

Once you've built RAG and agents, this is about knowing whether they're actually working — and knowing when the answer to "make it better" is fine-tuning versus everything you've already learned in this module.

## Theory & Fundamentals

### Why LLM Evaluation Is Different

Traditional software testing is binary: either the function returns the expected value or it doesn't. LLM systems are probabilistic: the same input can produce differently-worded outputs, both of which may be equally valid. You can't write `assert response == expected_string`.

Instead, LLM evaluation checks:
- **Faithfulness**: is the answer supported by the retrieved context?
- **Relevance**: does the answer address the question?
- **Correctness**: does the answer contain factual errors (hallucinations)?
- **Format**: does the output match the expected structure?

### Three Layers of RAG Evaluation

**Retrieval evaluation** — for a set of test queries with known-correct source documents, check whether your retriever returns those documents in its top-k results. This isolates retrieval quality from generation quality. Key metrics: precision@k, recall@k, MRR (Mean Reciprocal Rank).

**Generation evaluation** — given retrieved context, does the final answer use it correctly? Use an **LLM-as-judge**: a second model call that scores the response against a rubric. Imperfect (the judge can hallucinate too), but far more scalable than manually reviewing every response.

**End-to-end evaluation** — a curated set of representative questions with expected answer properties, re-run automatically whenever you change a prompt, chunking strategy, embedding model, or retriever. This is your regression test suite for LLM systems.

### Hallucination

A hallucination is when the model states something confidently that is not supported by (or contradicts) the retrieved context. Common in RAG when the retrieved chunks don't contain the answer and the model fills in from its training data instead.

Detection approaches:
1. **LLM-as-judge**: "Given only the context below, is the following answer fully supported? Answer YES or NO and explain." Catches most hallucinations scalably.
2. **Factual span checking**: extract specific claims (numbers, names, dates) from the answer and verify each appears verbatim in the context.
3. **Confidence signals**: instruct the model to include "I don't have enough information to answer this" when the context is insufficient — then check for its presence.

## Core Patterns / Techniques

### Minimal Eval Harness

```python
test_cases = [
    {
        "question": "What are your business hours?",
        "must_contain": ["9", "5", "Monday"],
        "must_not_contain": ["I don't know", "I'm not sure"],
    },
    {
        "question": "Do you accept credit cards?",
        "must_contain": ["yes", "credit"],
    },
]

def run_eval(rag_chain, test_cases):
    results = []
    for case in test_cases:
        answer = rag_chain.invoke(case["question"])
        answer_lower = answer.lower()

        passed_contains = all(
            term.lower() in answer_lower
            for term in case.get("must_contain", [])
        )
        passed_not_contains = not any(
            term.lower() in answer_lower
            for term in case.get("must_not_contain", [])
        )
        passed = passed_contains and passed_not_contains

        results.append({
            "question": case["question"],
            "answer": answer,
            "passed": passed,
        })

    pass_rate = sum(r["passed"] for r in results) / len(results)
    print(f"Pass rate: {pass_rate:.0%} ({sum(r['passed'] for r in results)}/{len(results)})")
    return results
```

Even this simple harness (checking for expected substrings, absence of failure phrases) catches real regressions when you tweak a prompt — the same principle as unit tests, applied to a non-deterministic system.

### LLM-as-Judge

```python
def faithfulness_judge(context: str, answer: str) -> dict:
    """Ask a model whether the answer is supported by the context."""
    judge_prompt = f"""Given the following context and answer, determine if the answer is fully supported by the context.

Context:
{context}

Answer:
{answer}

Is the answer fully supported by the context? Respond with:
- VERDICT: YES or NO
- REASON: one sentence explaining why
"""
    response = client.messages.create(
        model="claude-haiku-4-5-20251001",  # cheap model for judging
        max_tokens=200,
        messages=[{"role": "user", "content": judge_prompt}]
    )
    text = response.content[0].text
    verdict = "YES" in text.upper()
    return {"faithful": verdict, "reason": text}
```

### Running Evals Before and After Changes

```python
# Before: chunk_size=500
chain_v1 = build_rag_chain(chunk_size=500)
results_v1 = run_eval(chain_v1, test_cases)

# After: chunk_size=1000
chain_v2 = build_rag_chain(chunk_size=1000)
results_v2 = run_eval(chain_v2, test_cases)

# Compare: did the change help?
for r1, r2 in zip(results_v1, results_v2):
    if r1["passed"] != r2["passed"]:
        print(f"CHANGED: {r1['question']}")
        print(f"  v1 passed: {r1['passed']}")
        print(f"  v2 passed: {r2['passed']}")
```

This before-and-after comparison is the most defensible artifact you can bring into an interview about LLM evaluation — evidence that you actually measured a change.

## Fine-Tuning: Conceptual

### When Fine-Tuning Beats RAG/Prompting

**RAG wins** when the need is "give the model access to information it doesn't have" — your documents, current data, private knowledge. No retraining needed, knowledge is trivially updatable (add/remove documents).

**Prompting wins** when you need the model to follow instructions or adopt a persona — system prompts are free and instantly adjustable.

**Fine-tuning wins** when you need to change *how* the model behaves — a specific tone or style the model doesn't reliably follow from prompting, a specific output format (structured JSON with a complex schema), or domain-specific reasoning that prompting alone can't induce. Signs that fine-tuning might help: the same system prompt instruction is violated frequently, the desired behavior is consistent and well-defined, and you have 1,000+ high-quality examples of the desired behavior.

In practice: most applied-AI products never need fine-tuning. Prompting plus RAG covers the large majority of real requirements.

### LoRA / PEFT (Conceptual)

Fine-tuning adjusts a pretrained model's weights on your own data. **Full fine-tuning** updates all weights — expensive, requires significant GPU compute, and you need a full copy of the model per fine-tuned version.

**PEFT** (Parameter-Efficient Fine-Tuning), most commonly **LoRA** (Low-Rank Adaptation), freezes the original weights and trains small additional "adapter" layers instead:

```
Original model weights: frozen (no gradient, no memory cost)
LoRA adapters: small matrices A, B where ΔW = A × B (low-rank)
                trained on your data (only a few % of parameters)
                swappable per task without multiple full model copies
```

LoRA dramatically reduces compute and storage cost — you can fine-tune a large model with a single GPU and swap between fine-tuned behaviors by swapping adapter weights, without multiple copies of the base model.

## Best Practices

- **Build an eval harness before you start iterating** — without baseline measurements, you can't tell if a change helped or hurt.
- **Separate retrieval eval from generation eval** — a RAG system has two components; testing them together makes it hard to diagnose which is failing.
- **Use a cheap model as judge** (Claude Haiku, GPT-4o-mini) — the judge model doesn't need to be the most capable; it just needs to evaluate a specific yes/no question reliably.
- **Test the actual queries your users ask** — synthetic test cases often miss the edge cases that real usage reveals. Add test cases for every failure you find in production.
- **Before considering fine-tuning, exhaust prompting** — most "the model doesn't do X reliably" problems are solved by better prompt engineering, chain-of-thought instructions, or few-shot examples. Fine-tuning should be a last resort.

## Common Interview Questions

**Q1: How do you evaluate whether a RAG system is working correctly?**
A: Three layers: (1) Retrieval eval — do test queries with known-correct source documents return those documents in top-k? (2) Generation eval — given retrieved context, does the answer use it faithfully? Often checked with an LLM-as-judge. (3) End-to-end eval — a curated set of representative questions with expected answer properties, re-run whenever you change any component. This is the regression test suite.

**Q2: What is an LLM-as-judge and what are its limitations?**
A: Using a second model call to evaluate the output of the first — "given this context and this answer, is the answer fully supported?" Scales well (automated) and handles the non-deterministic nature of LLM outputs. Limitations: the judge model can also hallucinate, may be biased toward its own model family's outputs, and can be fooled by confident-sounding but wrong answers. It's a useful approximation, not a ground truth.

**Q3: What is hallucination in the context of RAG, and how do you mitigate it?**
A: Hallucination is when the model states something not supported by (or contradicted by) the retrieved context — it's "filling in" from training data when the retrieved chunks don't contain the answer. Mitigations: (1) Explicitly instruct the model to say "I don't know" when the context is insufficient. (2) Use an LLM-as-judge to check faithfulness. (3) Check whether specific claims in the answer appear in the retrieved chunks. (4) Improve retrieval so the answer IS in the chunks.

**Q4: When should you consider fine-tuning vs. improving your prompting or RAG?**
A: Fine-tuning when: the desired behavior is consistent and well-defined, prompting reliably fails to achieve it even with many examples in the system prompt, and you have 1,000+ high-quality examples of the correct behavior. Try prompting (including chain-of-thought and few-shot), then RAG (add relevant knowledge), before resorting to fine-tuning. Fine-tuning is expensive, slow to iterate, and doesn't help with "the model doesn't know X" — that's a RAG problem.

**Q5: What is LoRA and why is it used instead of full fine-tuning?**
A: Low-Rank Adaptation. Instead of updating all of a model's billions of parameters, LoRA freezes the original weights and trains small adapter layers (low-rank matrix pairs A and B, where ΔW = A × B). This reduces trainable parameters by 10,000x or more, enabling fine-tuning on a single GPU rather than a multi-GPU cluster. The adapters can be swapped between task-specific versions without storing multiple full copies of the base model.

Run it before and after one deliberate change (a different chunk size or a different prompt) and report the pass rate change.

2. **LLM-as-judge**: Implement the faithfulness judge from the code example. Test it on 5 real (question, context, answer) triples from your RAG system: 3 that should be faithful and 2 that are hallucinated (you can create hallucinated answers deliberately). Does the judge correctly classify them?

3. **Retrieval-only eval**: For 10 test queries where you know the correct source document, measure: what percentage of the time is the correct document in the top-3 retrieved results? How does changing from `k=3` to `k=5` affect recall? From `chunk_size=500` to `chunk_size=1000`?

## Key Takeaways

- LLM evaluation can't use exact string matching — use substring checks, LLM-as-judge, and faithfulness scoring instead.
- Three layers of RAG eval: retrieval (does the right chunk come back?), generation (does the answer use the context faithfully?), end-to-end (does the full system answer real queries correctly?).
- Hallucination = the model states something not in the retrieved context. Mitigation: explicit "I don't know" instruction + LLM-as-judge faithfulness check.
- Fine-tuning changes how the model behaves; RAG changes what it knows. Most products never need fine-tuning — prompting + RAG is sufficient.
- LoRA enables efficient fine-tuning by training small adapter layers instead of all model weights, reducing compute by 10,000x or more.
- Build an eval harness before iterating — you can't tell if a change helped without baseline measurements.
