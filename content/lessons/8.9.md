# LLM Evaluation & Fine-Tuning Concepts

The final unit in the AI track — once you've built RAG and agents, this is about knowing whether they're actually working, and knowing when the answer to "make it better" is fine-tuning versus everything you've already learned in this module.

## How to know if a RAG/agent system is actually working

Unlike traditional software, an LLM system's "correctness" isn't a simple pass/fail unit test — the same input can produce differently-worded (but equally valid) outputs. Evaluation approaches:

- **Retrieval evaluation** — for a set of test queries with known-correct source documents, check whether your retriever actually returns those documents in its top-k results. This isolates retrieval quality from generation quality.
- **Generation evaluation** — given retrieved context, does the final answer correctly use it? This is often checked with an **LLM-as-judge**: a second model call that scores the response against a rubric (faithfulness to context, relevance to the question) — imperfect, but far more scalable than manual review of every response.
- **End-to-end evaluation** — a curated set of representative real questions with expected answers (or expected answer *properties*, since exact wording varies), re-run whenever you change a prompt, chunking strategy, or model.

## Building an eval harness, minimally

```python
test_cases = [
    {"question": "What are your business hours?", "must_contain": ["9", "5", "Monday"]},
    {"question": "Do you accept insurance?", "must_not_contain": ["I don't know"]},
]

def evaluate(rag_chain, test_cases):
    results = []
    for case in test_cases:
        answer = rag_chain.invoke(case["question"])
        passed = all(term in answer for term in case.get("must_contain", [])) and \
                 not any(term in answer for term in case.get("must_not_contain", []))
        results.append({"question": case["question"], "passed": passed, "answer": answer})
    return results
```

Even this simple a harness (checking for expected substrings, or absence of "I don't know"-style failures) catches real regressions when you tweak a prompt — the same principle as unit tests from Module 3, applied to a system whose output isn't perfectly deterministic.

## Hallucination checks

A hallucination is the model confidently stating something not supported by (or contradicted by) the retrieved context. Checks include: asking a judge model "is this answer fully supported by the provided context, yes/no," or checking whether specific facts in the answer (numbers, names, dates) actually appear in the retrieved chunks. This directly extends the guardrail/red-flag thinking already demonstrated at the product level in your Physynex work — now backed by a concrete, testable mechanism.

## Fine-tuning — conceptual only: LoRA / PEFT

Fine-tuning adjusts a pretrained model's weights on your own data, so the model itself changes (as opposed to RAG, which keeps the model frozen and changes what's in the prompt). **Full fine-tuning** updates all of a model's weights — expensive and requires significant compute. **PEFT** (Parameter-Efficient Fine-Tuning) methods, most commonly **LoRA** (Low-Rank Adaptation), freeze the original weights and train small additional "adapter" layers instead — dramatically cheaper, and the adapters can be swapped in/out without needing multiple full copies of the base model.

## When fine-tuning beats RAG/prompting, and vice versa

- **RAG wins** when the need is "give the model access to information it doesn't have" (your documents, current data) — no retraining needed, and the knowledge is trivially updatable (just add/update documents).
- **Fine-tuning wins** when the need is "change *how* the model behaves" — a specific tone, a specific output format the model doesn't reliably follow from prompting alone, or domain-specific reasoning patterns that prompting can't reliably induce.
- In practice, most applied-AI products (including RAG systems like yours) never need fine-tuning at all — prompting plus RAG covers the large majority of real product requirements, which is exactly why this unit stays conceptual rather than hands-on.

## Practice tip

Write a 10-case eval harness (like the one above) for your own Month 3 RAG project, run it before and after one deliberate change (a different chunk size, a different prompt), and note what changed. That comparison is the single most concrete, defensible artifact you can bring into an interview discussion about LLM evaluation.
