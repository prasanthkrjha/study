# CI/CD & Observability

Shipping code manually is a bottleneck and a source of error. A CI/CD pipeline automates the build, test, and deployment steps that happen on every code change — applying them consistently regardless of who wrote the code or how confident they felt about the change. This consistency is what makes a CI/CD pipeline a correctness gate, not just a convenience: a failing test stops a deployment before it reaches production, which manual deployment cannot guarantee.

Observability is the flip side of deployment: once code is running in production, how do you know it is working correctly, and how do you find out when it is not? The traditional approach — waiting for a user to report a bug — is too slow and too incomplete. Structured logging, error tracking, and metrics give you visibility into production behavior before users notice problems, and provide enough context to diagnose issues quickly when they occur.

These two disciplines — automated delivery and production visibility — are what separate a code-shipping workflow from an engineering practice. Candidates who can articulate both demonstrate that they think about production, not just about getting features to pass code review.

## Theory & Fundamentals

### What CI/CD Means

**Continuous Integration (CI)**: every push to the repository triggers an automated build and test run. The intent is to catch integration problems (your code breaking someone else's feature, or vice versa) immediately rather than discovering them days later when the branch is merged.

**Continuous Delivery (CD)**: every successful CI run produces an artifact (a tested, built Docker image or deployment package) that is ready to deploy with one click. The deploy step is still manual.

**Continuous Deployment**: every successful CI run automatically deploys to production without manual intervention. Appropriate for mature teams with high test confidence; requires automated rollback capability.

Most teams practice Continuous Delivery rather than Continuous Deployment — they want a human review step before production even if the technical pipeline could proceed automatically.

### The Three-Gate Model

A well-structured pipeline has three gates, each blocking the next if it fails:

1. **Build gate**: does the code compile/bundle without errors? Catches syntax errors, type errors, missing imports.
2. **Test gate**: do all automated tests pass? Catches behavioral regressions.
3. **Deploy gate**: does the deploy script complete successfully? Catches infrastructure and configuration errors.

The critical constraint: the deploy gate should only execute if both the build and test gates passed, AND only on the target branch (typically `main`). Deploying from a feature branch or deploying without tests passing is the failure mode the pipeline is designed to prevent.

### Structured Logging

An unstructured log line like `console.log("user 42 placed order 1001 for $59.99")` is human-readable but machine-opaque. You cannot query it programmatically, you cannot filter by user ID, and you cannot aggregate order totals. Structured logging emits logs as JSON or consistent key-value pairs:

```json
{"level":"info","event":"order_created","userId":42,"orderId":1001,"total":59.99,"timestamp":"2026-08-07T10:30:00Z"}
```

Every field is queryable, filterable, and aggregatable. A log management system (CloudWatch Logs Insights, Datadog, Elastic Stack) can answer "how many orders were created in the last hour" or "show me all events for userId 42" as first-class queries.

## Core Concepts / Techniques

### GitHub Actions Pipeline Structure

```yaml
# .github/workflows/ci.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

env:
  AWS_REGION: us-east-1
  ECR_REPOSITORY: my-app

jobs:
  # Job 1: Build and Test (runs on all pushes and PRs)
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'         # cache node_modules based on package-lock.json

      - name: Install dependencies
        run: npm ci

      - name: Run linter
        run: npm run lint

      - name: Run tests with coverage
        run: npm test -- --coverage --ci
        env:
          CI: true

      - name: Build application
        run: npm run build

  # Job 2: Deploy (only on push to main, only if test job passed)
  deploy:
    needs: test                 # only runs if the test job succeeds
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'

    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Login to Amazon ECR
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: Build, tag, and push Docker image to ECR
        env:
          ECR_REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build -t $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG .
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG
          docker tag $ECR_REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG \
                     $ECR_REGISTRY/$ECR_REPOSITORY:latest
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:latest

      - name: Deploy to Elastic Beanstalk
        run: |
          pip install awsebcli
          eb deploy production --label "deploy-${{ github.sha }}"
```

### Secrets in GitHub Actions

```yaml
# Secrets are stored in GitHub repository Settings → Secrets and variables
# They are injected as environment variables and masked in logs

steps:
  - name: Run database migrations
    run: npm run db:migrate
    env:
      DATABASE_URL: ${{ secrets.DATABASE_URL }}   # never appears in logs
      STRIPE_SECRET_KEY: ${{ secrets.STRIPE_SECRET_KEY }}

# Never hardcode secrets in workflow files — they appear in logs and
# are visible to anyone with repository read access
```

### Structured Logging with Pino

```javascript
// src/logger.js — application-wide logger using Pino
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  // In production, output plain JSON for log aggregators to parse
  // In development, use pino-pretty for human-readable output
  transport: process.env.NODE_ENV === 'development'
    ? { target: 'pino-pretty', options: { colorize: true } }
    : undefined,
  // Add default fields to every log line
  base: {
    service: 'api',
    env: process.env.NODE_ENV,
    version: process.env.APP_VERSION,
  },
});

// Usage — structured, queryable fields in every log call
logger.info({ userId: req.user.id, action: 'order_created', orderId: order.id }, 'Order created');
logger.error({ err: error, userId: req.user.id, orderId }, 'Order creation failed');
logger.warn({ threshold: 100, current: itemCount }, 'Cart item count approaching limit');
```

### Request Logging Middleware

```javascript
// src/middleware/requestLogger.js
export function requestLogger(req, res, next) {
  const start = Date.now();
  const requestId = crypto.randomUUID(); // correlate request across log lines

  // Attach to request so route handlers can use the same ID
  req.requestId = requestId;
  req.log = logger.child({ requestId });

  res.on('finish', () => {
    req.log.info({
      method: req.method,
      path: req.path,
      statusCode: res.statusCode,
      durationMs: Date.now() - start,
      userAgent: req.headers['user-agent'],
      ip: req.ip,
    }, 'Request completed');
  });

  next();
}
```

### Error Tracking with Sentry

```javascript
// src/app.js — Sentry setup
import * as Sentry from '@sentry/node';

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.NODE_ENV,
  release: process.env.APP_VERSION,    // ties errors to specific deploys
  tracesSampleRate: 0.1,               // capture 10% of transactions for performance
});

// Must be before routes
app.use(Sentry.Handlers.requestHandler());

// Routes...
app.use('/api', routes);

// Must be after routes, before other error handlers
app.use(Sentry.Handlers.errorHandler());

// Custom error handler
app.use((err, req, res, next) => {
  logger.error({ err, requestId: req.requestId }, 'Unhandled error');
  res.status(err.status ?? 500).json({
    error: process.env.NODE_ENV === 'production'
      ? 'Internal server error'
      : err.message
  });
});

// Manually capture non-fatal errors with context
try {
  await sendEmail(user.email);
} catch (error) {
  Sentry.captureException(error, {
    extra: { userId: user.id, emailType: 'welcome' }
  });
  // Continue — email failure is non-fatal, don't crash the request
}
```

## Code Examples

### Matrix Testing Across Node Versions

```yaml
# Test across multiple Node versions to catch compatibility issues
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node-version: ['18', '20', '22']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node-version }}
      - run: npm ci
      - run: npm test
```

### Caching Dependencies for Speed

```yaml
# Cache node_modules to avoid re-downloading on every run
- name: Cache node modules
  uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-

# Or use setup-node's built-in cache (simpler)
- uses: actions/setup-node@v4
  with:
    node-version: '20'
    cache: 'npm'   # automatically caches based on package-lock.json hash
```

### CloudWatch Log Queries (Structured Log Querying)

```sql
-- CloudWatch Logs Insights query syntax
-- Find all errors for a specific user in the last 24 hours
fields @timestamp, event, orderId, @message
| filter level = "error" and userId = "42"
| sort @timestamp desc
| limit 50

-- Count order creations per hour
filter event = "order_created"
| stats count(*) as orderCount by bin(1h)

-- P99 latency by endpoint
filter @logStream like /api/
| stats pct(durationMs, 99) as p99, avg(durationMs) as avg by path
| sort p99 desc
```

## Best Practices

- **The deploy job must `needs` the test job** — if tests are on a separate job from deploy, use `needs: [test]` to guarantee deploy never runs when tests fail; running them in sequence in one job also works.
- **Deploy only on pushes to the main branch** — use `if: github.ref == 'refs/heads/main' && github.event_name == 'push'` to ensure PRs trigger tests but not deployments.
- **Store all secrets in GitHub Actions secrets, never in workflow files** — workflow files are committed to the repository; any secret in them is visible to anyone with read access; secrets in the GitHub repository settings are masked in logs.
- **Use `npm ci` instead of `npm install` in CI** — `npm ci` installs exactly what is in `package-lock.json`, fails if it does not exist, and does not modify it; this ensures reproducible installs.
- **Add correlation IDs to every log line** — generate a UUID per request and attach it to every log emitted while handling that request; this allows tracing a complete request across multiple log lines.
- **Never log sensitive data** — scrub or omit passwords, API keys, full credit card numbers, and personally identifiable information from log output; structured logging makes this easier because you can explicitly choose which fields to include.
- **Set up error alerting, not just error tracking** — Sentry and similar tools can alert via Slack or email when a new error occurs or when an error rate spike is detected; tracking errors without notifications means you only see them when you happen to look.

## Common Interview Questions

**Q: What is the difference between continuous integration, continuous delivery, and continuous deployment?**
A: CI: every push triggers automated build and test. Continuous delivery: every successful CI run produces a deploy-ready artifact; the actual deploy is manually triggered. Continuous deployment: successful CI runs automatically deploy to production without manual intervention. Most teams practice continuous delivery — automated testing, manual deploy trigger.

**Q: How do you prevent a broken build from being deployed to production in a GitHub Actions pipeline?**
A: Use `needs: [test]` to make the deploy job depend on the test job. GitHub Actions will not start the deploy job if the test job fails. Additionally, use `if: github.ref == 'refs/heads/main'` to prevent feature branch pushes from triggering deploys.

**Q: What is the difference between structured logging and unstructured (plain text) logging?**
A: Unstructured logs are human-readable strings — impossible to query programmatically, aggregate, or filter reliably. Structured logs emit consistent JSON or key-value records where each field has a name and a value — queryable by field name, aggregatable (count errors by user ID, average latency by endpoint), and parseable by log management systems like CloudWatch, Datadog, or Elastic Stack.

**Q: What is a correlation ID and why is it useful in distributed systems?**
A: A correlation ID is a unique identifier (UUID) generated at the start of a request and attached to every log line, downstream service call, and database query made while handling that request. It allows you to reconstruct the full path of a single request across multiple services and log entries, which is otherwise impossible when logs from multiple concurrent requests are interleaved.

**Q: What should a production error tracking setup tell you about an exception?**
A: At minimum: the exception type and message, the full stack trace, the release/version that introduced it (to narrow down when it started), the request context (endpoint, user ID if available), the environment, and how many times it has occurred and whether the count is rising. Sentry groups repeated occurrences of the same error into one issue, reducing noise.

**Q: Why should you use `npm ci` instead of `npm install` in CI pipelines?**
A: `npm ci` installs exactly the versions specified in `package-lock.json`, fails if `package-lock.json` is missing or inconsistent with `package.json`, and never modifies either file. `npm install` resolves dependencies fresh each time and may update `package-lock.json`, introducing subtle version inconsistencies between CI runs.

**Q: How would you handle a deployment that introduced a critical production bug?**
A: Immediately roll back by deploying the previous known-good image tag (which is why image tags should be commit SHAs, not just `latest`). Elastic Beanstalk supports `eb deploy --version-label <previous-label>`. Simultaneously, investigate the Sentry error and log data to understand the root cause, write a test that reproduces it, fix it, and deploy forward.

## Practice Exercises

1. **Pipeline from scratch**: Write a complete GitHub Actions workflow for a Node.js application that: runs on all pushes and pull requests, runs linting and tests with coverage, builds and pushes a Docker image to ECR on pushes to main only, and deploys to Elastic Beanstalk only after a successful image push. Store AWS credentials as repository secrets.

2. **Structured logging retrofit**: Take an Express application that uses `console.log` for logging and replace it with Pino. Add a request logging middleware that logs each request's method, path, status code, and duration. Add a child logger to each request with a correlation ID. Verify that the output in production mode is valid JSON.

3. **Error tracking integration**: Add Sentry to a Node.js Express application. Verify that an unhandled exception in a route is automatically captured. Then add manual error capturing to a try/catch block in an email-sending function, including the user ID as extra context. Test that the error appears in the Sentry dashboard with the correct context.

4. **Deployment notification**: Extend a GitHub Actions pipeline to send a Slack notification (using a Slack webhook stored as a secret) when a deployment to production succeeds, including the commit SHA, the deploying user's GitHub username, and a link to the workflow run.

5. **Log query practice**: Given a set of structured JSON logs from a Node.js application, write CloudWatch Logs Insights queries to answer: (a) what were the 5 slowest API endpoints by P95 latency in the past day, (b) how many 5xx errors occurred per hour in the past 24 hours, (c) what are all the log lines for a specific correlation ID.

## Key Takeaways

- A CI/CD pipeline is a correctness gate, not just automation — it ensures every push goes through the same build-and-test gauntlet regardless of who wrote it or how confident they felt.
- The deploy job must depend on the test job (`needs: [test]`) and must be gated to the main branch only — these two constraints prevent broken code from reaching production.
- `npm ci` is the correct install command for CI — it installs exactly what is in `package-lock.json` and fails if that file is absent or inconsistent.
- Structured logging (JSON with named fields) enables programmatic querying, filtering, and aggregation; plain text logs are human-readable but machine-opaque.
- Correlation IDs attached to every log line for a request allow reconstructing the complete request path across multiple services and log entries.
- Error tracking (Sentry or equivalent) surfaces production exceptions immediately, with stack trace and context, rather than waiting for a user complaint.
- Store all secrets in GitHub Actions secrets (or equivalent) — never in workflow files, environment files committed to the repository, or hardcoded anywhere in the pipeline configuration.
- Rolling back a bad deployment means redeploying the previous image tag — this is why Docker images should be tagged with commit SHAs rather than overwriting `latest`.
