# CI/CD & Observability

Shipping code manually doesn't scale, and you can't fix what you can't see failing. This unit covers the automation and visibility layer that sits on top of a working deployment.

## GitHub Actions pipeline stages

A CI/CD pipeline typically has three stages, each gating the next:

```yaml
name: CI
on: [push, pull_request]

jobs:
  build-test-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }

      - name: Install dependencies
        run: npm ci

      - name: Build
        run: npm run build

      - name: Test
        run: npm test

      - name: Deploy
        if: github.ref == 'refs/heads/main'
        run: ./deploy.sh
```

- **Build:** does the code even compile/bundle successfully?
- **Test:** does it behave correctly (unit + integration tests from Module 3)?
- **Deploy:** only runs if build and test both passed, and typically only on the main branch — this is what prevents broken code from ever reaching production, because a failing step stops the pipeline before deploy runs.

## Why this matters beyond convenience

CI/CD isn't just "automating a chore" — it's a correctness gate. Every push gets the same build+test treatment regardless of who wrote it or how confident they felt, which is exactly the kind of consistency a solo developer's memory can't reliably provide.

## Structured logging

Plain `console.log("something happened")` is nearly useless once you have real traffic — you can't search, filter, or correlate it. Structured logging emits logs as consistent key-value data (usually JSON):

```js
logger.info("order_created", { userId: 42, orderId: 1001, total: 59.99 });
```

This makes logs queryable: "show me every `order_created` event for `userId: 42` in the last hour" is a real query against structured logs, but not against free-text strings.

## Error tracking (Sentry-style)

An error-tracking service automatically captures unhandled exceptions in production — with the stack trace, the request context, and the ability to group repeated occurrences of the same underlying bug into one issue instead of one alert per occurrence:

```js
import * as Sentry from "@sentry/node";
Sentry.init({ dsn: process.env.SENTRY_DSN });

app.use(Sentry.Handlers.errorHandler());
```

Without this, the first person to learn about a production bug is often a user complaining — with it, you learn about it the moment it happens, with enough context to actually fix it.

## Recognizing why this is a "recommended," not "essential," tier item

Structured logging and error tracking meaningfully differentiate a candidate ("this person thinks about production, not just shipping"), but you can be interview-competent without hands-on Sentry experience — whereas skipping DSA or SQL entirely is a hard blocker. Prioritize accordingly if time gets tight (see Part 9's priority order).
