# AWS Hands-On Deployment

This unit is where Docker (4.1) and AWS fundamentals (4.2) stop being separate concepts and become one working, internet-accessible system. Reading about EC2 and VPCs is useful background; deploying an actual containerized application to AWS — hitting your own API from a different network — is the experience that makes cloud concepts concrete and interview-ready.

The deployment pipeline for a containerized full-stack application follows a predictable shape regardless of which AWS deployment service you choose: build and push a Docker image to a registry, provision compute to run it, configure networking so traffic can reach it, and inject runtime configuration (database URLs, API keys) through environment variables — never through the image itself. Understanding each step in this pipeline, and what can go wrong at each step, is the practical skill this unit builds.

The two most common paths for a first AWS deployment are raw EC2 (install Docker on a VM and run your container manually) and Elastic Beanstalk (upload a Docker image or Dockerrun config and let AWS manage the infrastructure). Beanstalk is the recommended starting point: it handles load balancer provisioning, auto-scaling configuration, and rolling deployments, leaving you free to focus on the application rather than infrastructure plumbing.

## Theory & Fundamentals

### The Deployment Pipeline Shape

A containerized deployment follows these stages in order:

1. **Build**: compile the application and build a Docker image locally or in CI.
2. **Push**: push the tagged image to a container registry (ECR, Docker Hub, GHCR).
3. **Provision**: create or update the compute resource that will run the container.
4. **Configure**: inject runtime environment variables (DB URL, secrets, region) into the running environment — these values should never be baked into the image.
5. **Expose**: configure security groups and load balancers to allow traffic to reach the container on the right port.
6. **Verify**: confirm the deployment from a different network — this rules out "it's only reachable from my VPN" failures.

### Why Environment Variables for Configuration

The Twelve-Factor App methodology (a well-known set of deployment best practices) defines configuration as anything that varies between deployments: database credentials, API keys, feature flags. These must come from environment variables, not code or image layers, for three reasons: the same image can be deployed to staging and production with different config; secrets are not baked into image layers (which are inspectable); and config can be changed without rebuilding.

### Container Registry (ECR)

Amazon Elastic Container Registry (ECR) is AWS's managed Docker registry. Using ECR instead of Docker Hub keeps images within your AWS account, where they are subject to IAM access controls and do not count against Docker Hub pull rate limits. ECR images are private by default. Your CI pipeline authenticates to ECR, pushes the image, and ECS/Beanstalk pulls it — all within AWS's network.

## Core Concepts / Techniques

### ECR: Pushing a Docker Image

```bash
# Authenticate Docker to ECR
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin \
    123456789.dkr.ecr.us-east-1.amazonaws.com

# Create a repository (one per application, one-time setup)
aws ecr create-repository --repository-name my-app --region us-east-1

# Build, tag, and push
docker build -t my-app:latest .

docker tag my-app:latest \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:latest

docker push \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:latest

# Tag with git commit SHA for traceability
GIT_SHA=$(git rev-parse --short HEAD)
docker tag my-app:latest \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:${GIT_SHA}
docker push \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:${GIT_SHA}
```

### EC2 Deployment (Manual)

```bash
# On a fresh EC2 instance running Amazon Linux 2023:

# Install Docker
sudo yum update -y
sudo yum install -y docker
sudo systemctl start docker
sudo systemctl enable docker
sudo usermod -a -G docker ec2-user

# Log out and back in for group change to take effect, then:

# Authenticate to ECR
aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin \
    123456789.dkr.ecr.us-east-1.amazonaws.com

# Pull and run the application container
docker pull 123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:latest

docker run -d \
  --name my-app \
  -p 3000:3000 \
  --restart unless-stopped \
  -e DATABASE_URL="${DATABASE_URL}" \
  -e REDIS_URL="${REDIS_URL}" \
  -e NODE_ENV=production \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:latest

# Verify
docker ps
docker logs my-app
curl http://localhost:3000/health
```

### Elastic Beanstalk Docker Deployment

```json
// Dockerrun.aws.json (v2 — for single-container Beanstalk environments)
{
  "AWSEBDockerrunVersion": "1",
  "Image": {
    "Name": "123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:latest",
    "Update": "true"
  },
  "Ports": [
    {
      "ContainerPort": 3000
    }
  ],
  "Logging": "/var/log/app"
}
```

```bash
# Deploy to Elastic Beanstalk
eb init my-app --platform "Docker" --region us-east-1
eb create production

# Set environment variables (not in code or Dockerrun — in EB config)
eb setenv \
  DATABASE_URL=postgres://user:pass@host:5432/db \
  NODE_ENV=production \
  REDIS_URL=redis://host:6379

# Deploy new image version
eb deploy

# View deployment status and logs
eb status
eb logs
eb health
```

### Security Group Configuration

```
Application Load Balancer Security Group:
  Inbound:  TCP 80 from 0.0.0.0/0 (allow HTTP from anywhere)
            TCP 443 from 0.0.0.0/0 (allow HTTPS from anywhere)
  Outbound: TCP 3000 to EC2 security group

EC2 / App Server Security Group:
  Inbound:  TCP 3000 from ALB security group ONLY
            TCP 22 from your IP for SSH (dev/debugging)
  Outbound: All traffic (to reach database, Redis, ECR, internet)

RDS Security Group:
  Inbound:  TCP 5432 from EC2 security group ONLY
  Outbound: None required (database does not initiate connections)
```

## Code Examples

### Health Check Endpoint (Required for Load Balancers)

```javascript
// app.js — add a health check endpoint that load balancers and EB can poll
// This endpoint should return 200 when the app is ready to receive traffic

app.get('/health', async (req, res) => {
  try {
    // Check that database connection works
    await db.query('SELECT 1');

    res.json({
      status: 'healthy',
      timestamp: new Date().toISOString(),
      version: process.env.APP_VERSION ?? 'unknown',
    });
  } catch (error) {
    // Return 503 if database is unreachable — ALB will stop routing to this instance
    res.status(503).json({
      status: 'unhealthy',
      error: error.message,
    });
  }
});
```

### NGINX Reverse Proxy (for SSL Termination on EC2)

```nginx
# /etc/nginx/conf.d/app.conf
# NGINX terminates SSL and proxies requests to the Node.js app on port 3000

server {
    listen 80;
    server_name yourdomain.com;
    return 301 https://$host$request_uri;    # redirect HTTP to HTTPS
}

server {
    listen 443 ssl;
    server_name yourdomain.com;

    ssl_certificate     /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;

    location / {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection 'upgrade';
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
    }
}
```

### Diagnosing Common Failures

```bash
# Can't reach the app at all?
# → Check security group inbound rules first
aws ec2 describe-security-groups --group-ids sg-xxxx

# App starts but immediately crashes?
# → Missing environment variable (most common on first cloud deploy)
docker logs my-app              # look for "cannot connect to database"
eb logs                         # Elastic Beanstalk log stream

# Database connection refused?
# → Check that RDS security group allows traffic from app security group
# → Check DATABASE_URL uses the RDS endpoint (not localhost)
aws rds describe-db-instances --query 'DBInstances[*].Endpoint'

# App works locally but returns 502 Bad Gateway from ALB?
# → App is crashing before it finishes starting; check health check path
# → Health check interval may be too aggressive for cold start

# Deployed but changes not appearing?
# → Beanstalk: did the deployment actually complete?
eb events -f
# → Cached by CDN/browser? Hard refresh or check different network
```

## Best Practices

- **Build and push a tagged image to ECR before deploying** — never deploy by building on the production instance itself; the image should be a versioned, immutable artifact that the deployment command pulls.
- **Configure a health check endpoint and register it with the load balancer** — without a health check, the load balancer cannot detect when an instance is unhealthy and traffic continues to route to broken instances.
- **Pass all environment-specific configuration as environment variables at deploy time** — database URLs, API keys, and feature flags should be set in the Beanstalk environment or passed with `-e` flags to `docker run`; they should never be baked into the Docker image.
- **Use a database that is managed separately from the application lifecycle** — RDS should not be inside the same Elastic Beanstalk environment as the app; it should be a separate, persistent resource that survives application redeployments.
- **Verify the deployment from a network that is not your local machine** — use a mobile hotspot or a completely different connection to confirm the application is genuinely internet-accessible and not just reachable within your VPN or local network.
- **Set `--restart unless-stopped` on production containers on raw EC2** — this ensures your container automatically restarts after a crash or after the EC2 instance reboots.
- **Start with Elastic Beanstalk** before considering ECS or raw EC2 management — Beanstalk handles the load balancer, auto-scaling, rolling deployments, and health checks automatically; move to ECS/Fargate or raw EC2 when Beanstalk's abstractions become a constraint.

## Common Interview Questions

**Q: What is the deployment pipeline for a Dockerized application on AWS?**
A: Build the Docker image locally or in CI, push it to ECR (or Docker Hub), then provision compute (EC2 or Beanstalk) to run it. Configure the runtime environment variables (database URL, secrets) separately from the image, configure security groups to allow traffic to the app port, and verify from an external network.

**Q: Why should configuration like database URLs be passed as environment variables rather than baked into the Docker image?**
A: Three reasons: the same image can run in staging and production with different configuration; secrets are not stored in image layers (visible via `docker history` to anyone with image access); and configuration can be changed without rebuilding and redeploying the image.

**Q: What does a health check endpoint do and why is it important for load balancers?**
A: A health check endpoint (commonly `/health`) returns HTTP 200 when the application is ready to receive traffic and HTTP 503 when it is not. Load balancers poll this endpoint regularly and stop routing traffic to instances that fail it. Without a health check, the load balancer has no way to detect a crashed or degraded instance.

**Q: What is the most common cause when an application cannot be reached from the internet after deployment?**
A: A misconfigured security group — the most frequent cause is that the inbound rule for the application's port (e.g., 3000 or 443) was not added, or was scoped to a CIDR range that excludes the requester. The second most common is the application binding to `127.0.0.1` instead of `0.0.0.0`, making it only reachable locally within the container.

**Q: What is the difference between deploying to EC2 directly versus Elastic Beanstalk?**
A: EC2 gives you full control over the instance, OS, and Docker runtime, but you manage everything manually: installing Docker, handling restarts, configuring load balancers, and setting up auto-scaling yourself. Elastic Beanstalk automates all of that — it provisions EC2, a load balancer, and auto-scaling, and handles rolling deployments. Beanstalk is the right choice until its abstractions prove to be a constraint.

**Q: How would you update a running application to a new version with zero downtime?**
A: Build and push a new image with a version tag, then deploy via Elastic Beanstalk rolling deployment (which replaces instances one at a time, keeping healthy instances in rotation) or via ECS with a rolling update deployment strategy. The load balancer routes traffic only to healthy instances, ensuring users never hit an instance that is being replaced.

**Q: How do you prevent database credentials from appearing in process lists or logs?**
A: Pass credentials through environment variables (not command-line arguments, which appear in `ps` output) and ensure the application does not log the full DATABASE_URL string. In production, use AWS Secrets Manager or Parameter Store to retrieve secrets at runtime, rather than injecting them as environment variables directly — this also enables credential rotation without redeploying.

## Practice Exercises

1. **End-to-end deployment**: Take a Node.js/Express API with a PostgreSQL database. Containerize both with Docker Compose for local development, then deploy the API to Elastic Beanstalk with an RDS PostgreSQL instance in a private subnet. Verify the deployed API can query the database by hitting a GET endpoint from your browser.

2. **Health check implementation**: Add a `/health` endpoint to an Express application that checks database connectivity and returns JSON with status, timestamp, and version. Test it locally, then configure Elastic Beanstalk to use `/health` as the health check path and confirm that stopping the database makes the environment go unhealthy.

3. **Security group audit**: After a deployment, audit the security group configuration and verify that: the database is not reachable from the public internet (try connecting directly), the app is reachable only on the expected port, and SSH is restricted to your IP. Document the security group rules.

4. **Environment variable management**: Deploy the same Docker image to two Elastic Beanstalk environments (staging and production) with different `DATABASE_URL` values. Verify that each environment connects to its own database by checking which database rows appear in each environment's API responses.

5. **Failure diagnosis**: Intentionally introduce each of the common failure scenarios: (a) remove an inbound security group rule, (b) unset the `DATABASE_URL` environment variable, (c) set the container to listen on port 8080 but expose port 3000. For each failure, practice diagnosing it from the symptoms (error code, log output, health check status) without looking at the known cause.

## Key Takeaways

- The containerized deployment pipeline is: build → push image to ECR → provision compute → configure runtime environment → expose via security group/load balancer → verify from external network.
- Configuration (database URLs, API keys) must come from environment variables at runtime, never from the Docker image — the same image artifact should be deployable to any environment.
- Elastic Beanstalk manages EC2, load balancer, auto-scaling, and rolling deployments automatically — it is the correct starting point before managing raw EC2 infrastructure.
- A health check endpoint is required for load balancer health checking — without it, broken instances continue to receive traffic.
- The most common "cannot reach deployment" causes are: missing security group inbound rule, missing environment variable causing an immediate crash, and application binding to loopback instead of 0.0.0.0.
- RDS should live in a private subnet as a persistent resource separate from the Beanstalk environment — it should survive application redeployments intact.
- Tag Docker images with git commit SHAs for traceability — `my-app:abc1234` is far more auditable than `my-app:latest` in a production registry.
- Verify deployments from a different network (mobile hotspot, different machine) to confirm genuine internet accessibility rather than VPN/local-network accessibility.
