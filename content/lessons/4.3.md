# AWS Hands-On Deployment

This unit is where 4.1 (Docker) and 4.2 (AWS fundamentals) stop being separate concepts and become one working, live-on-the-internet system. There's no substitute for actually doing this once, start to finish.

## The end-to-end shape

1. **Containerize** your app (Dockerfile from 4.1), and confirm it runs correctly locally via `docker build` + `docker run`.
2. **Provision** compute — either a raw EC2 instance (install Docker on it yourself, `docker run` your image) or Elastic Beanstalk (upload the Dockerized app, let Beanstalk handle the underlying EC2 + load balancer + scaling).
3. **Configure networking** — open the right inbound port in the security group (typically 80/443, proxied to your app's internal port), and point a domain or use the provided AWS URL.
4. **Handle environment/config** — database URL, API keys, and other secrets should come from environment variables set on the instance/Beanstalk environment, never baked into the Docker image itself.
5. **Verify** — hit the live URL from a browser on a different network than the one you deployed from, to confirm it's genuinely public, not just reachable from your own machine.

## A gentler on-ramp: Render or Railway first

If AWS's surface area feels like too much to debug all at once, deploying to Render or Railway first (both take a Dockerfile or a Git repo directly, with far less configuration) validates that your **app and Dockerfile** are correct before you also have to debug AWS-specific networking/IAM issues. Once that's confirmed working, redoing the same deployment on AWS isolates what's actually AWS-specific.

## Common failure points (and what they usually mean)

- **Can't reach the app at all:** almost always a security-group inbound rule blocking the port, not an application bug.
- **App starts but crashes immediately in the cloud, works locally:** almost always a missing environment variable (database URL, API key) that was only ever set in your local `.env` file.
- **Database connection refused:** check whether the database is reachable from the app's subnet/security group — a private-subnet database is often unreachable to instances outside its own VPC configuration by design.
- **Works, then stops after a redeploy:** check whether you're relying on the container's local filesystem for anything that needs to persist (uploaded files, SQLite databases) — container filesystems are ephemeral unless backed by a volume or moved to S3/RDS.

## Why this project matters more than it looks

"I deployed something to AWS once" and "I can explain exactly what happens between a browser request and my app responding, across DNS, load balancer, security group, and container" are very different levels of readiness — and the second one is what actually gets tested when a system design interview asks you to reason about a request's path through a real architecture.

## Practice tip

Don't stop at "it works." Intentionally break one thing — close the security group's port, or unset an environment variable — and diagnose the resulting failure from the symptoms alone. That debugging loop is where the real learning happens, not the initial successful deploy.
