# AWS Fundamentals

Amazon Web Services is the dominant cloud platform, and almost every "deploy to the cloud" requirement in a full-stack job posting implies AWS or a platform built on top of it. You do not need to know all of AWS — it has hundreds of services — but you do need to know the five to eight that come up in nearly every web application deployment: compute (EC2), storage (S3), identity and access (IAM), networking (VPC), and managed deployment options (Elastic Beanstalk or ECS for containers).

The mental model that ties AWS together: you are renting infrastructure at a fine-grained level instead of owning physical hardware. You pay for what you use, you can scale up in minutes, and you trade operational simplicity for control (managed services) or control for flexibility (raw VMs). Knowing when to choose a managed service versus managing the underlying infrastructure yourself is the real cloud engineering skill — and the answer is almost always "start with the managed service and move to raw infrastructure only if the managed service proves to be a genuine constraint."

AWS's security model is default-deny: nothing is accessible unless you explicitly grant access. Every resource starts private. Opening access happens through two mechanisms: IAM (controls which AWS principals can call which AWS APIs) and security groups / network ACLs (controls which network traffic can reach which resources). Understanding both layers is essential — a misconfigured security group is usually the first thing to check when something is unreachable.

## Theory & Fundamentals

### The Shared Responsibility Model

AWS is responsible for the security OF the cloud (physical infrastructure, hardware, the hypervisor, the managed service software). You are responsible for security IN the cloud: your data, your IAM configuration, your security group rules, your application code. This distinction matters: if you misconfigure an S3 bucket to be public, that is your security failure, not AWS's.

### AWS Regions and Availability Zones

AWS infrastructure is divided into Regions (geographic areas — `us-east-1`, `eu-west-1`, `ap-south-1`) and Availability Zones (AZs) within a Region. Each AZ is one or more physically separate data centers with independent power and networking. Deploying across multiple AZs within a Region makes your application resilient to a single data center failure — traffic is automatically routed away from a failed AZ. For most applications, multi-AZ within a single Region is sufficient; multi-Region is reserved for extremely high availability or data sovereignty requirements.

### IAM Principals and Policies

An IAM principal is anything that can make API calls to AWS: IAM users (humans), IAM roles (assumed by services or humans temporarily), and federated identities (users from an external identity provider). Policies are JSON documents that specify what actions are allowed or denied on what resources, with optional conditions. The effective permissions of a principal are the intersection of all attached policies.

## Core Concepts / Techniques

### EC2 (Elastic Compute Cloud)

```bash
# EC2 instance types follow a pattern: family + generation + size
# Examples: t3.micro (burstable, small), c6i.large (compute-optimized), r6g.xlarge (memory-optimized)
# t3.micro: 2 vCPU (burstable), 1GB RAM — free tier eligible

# Connecting to a running EC2 instance
ssh -i ~/.ssh/my-key.pem ec2-user@<public-ip-or-dns>

# Amazon Linux 2023 / Ubuntu instance bootstrap (user data script — runs at launch)
#!/bin/bash
yum update -y
yum install -y docker
systemctl start docker
systemctl enable docker
usermod -a -G docker ec2-user
```

Key EC2 concepts:
- **AMI (Amazon Machine Image)**: the OS image an EC2 instance boots from. AWS provides official AMIs for Amazon Linux, Ubuntu, Red Hat, Windows. Custom AMIs let you pre-bake your dependencies.
- **Security Group**: a stateful firewall attached to an EC2 instance. Controls inbound and outbound traffic by port, protocol, and source IP or CIDR. By default, all inbound traffic is blocked.
- **Key Pair**: an SSH key pair used to authenticate to the instance. The public key is stored in AWS; you keep the private key locally. If you lose the private key, you cannot SSH in.
- **Instance Store vs EBS**: Instance store is temporary storage — data is lost if the instance stops. EBS (Elastic Block Store) is persistent block storage that survives instance stops and can be moved between instances.

### S3 (Simple Storage Service)

```bash
# AWS CLI examples for S3
# Create a bucket (bucket names must be globally unique)
aws s3 mb s3://my-app-uploads-prod

# Upload a file
aws s3 cp ./image.jpg s3://my-app-uploads-prod/images/image.jpg

# Sync a local directory to S3 (useful for static site deploys)
aws s3 sync ./dist s3://my-app-static-prod --delete

# Generate a pre-signed URL (temporary, expiring access to a private object)
aws s3 presign s3://my-app-uploads-prod/private/file.pdf --expires-in 3600

# Set bucket policy to allow public read (for static websites)
# IMPORTANT: only for buckets meant to be publicly accessible
aws s3api put-bucket-policy --bucket my-site --policy file://public-read-policy.json
```

S3 object storage characteristics: objects are addressed by key (path-like string), not filesystem operations. There are no directories — just key prefixes that look like paths. Storage classes (Standard, Standard-IA, Glacier) trade cost for retrieval speed, useful for backups and archival.

### IAM

```json
// Example IAM policy: allow an EC2 instance to read from one specific S3 bucket
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadUploads",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-app-uploads-prod",
        "arn:aws:s3:::my-app-uploads-prod/*"
      ]
    }
  ]
}
```

```bash
# Attach a role to an EC2 instance profile so the instance can call AWS APIs
# without credentials in the environment or code
aws iam create-role --role-name AppServerRole \
  --assume-role-policy-document file://ec2-trust-policy.json

aws iam attach-role-policy --role-name AppServerRole \
  --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess

# On the EC2 instance, the AWS SDK automatically picks up the role credentials
# from the instance metadata service — no key files needed
```

IAM best practices in brief: never use the root account for day-to-day operations, use roles instead of long-lived access keys for EC2 and Lambda, grant minimum required permissions (least privilege), enable MFA on all human IAM users.

### VPC (Virtual Private Cloud)

```
VPC: 10.0.0.0/16 (65,536 addresses)
├── Public Subnet: 10.0.1.0/24  — has route to Internet Gateway
│   └── EC2 web server (public IP, reachable from internet on port 443)
├── Public Subnet: 10.0.2.0/24  — second AZ for redundancy
│   └── EC2 web server
└── Private Subnet: 10.0.3.0/24 — NO route to Internet Gateway
    └── RDS database (no public IP, unreachable from internet)
        (accessible only from resources within the VPC)
```

A VPC is your isolated network within AWS. Key components:
- **Internet Gateway (IGW)**: allows traffic between VPC resources and the internet. A public subnet has a route to an IGW; a private subnet does not.
- **NAT Gateway**: allows resources in private subnets to initiate outbound connections to the internet (e.g., to install packages) without being directly reachable inbound. Lives in a public subnet.
- **Security Group**: instance-level firewall (stateful). Controls which traffic can reach an EC2/RDS instance.
- **Network ACL**: subnet-level firewall (stateless). Less commonly configured explicitly — default NACLs allow all traffic.

### Elastic Beanstalk

Elastic Beanstalk is a Platform-as-a-Service layer that manages the underlying EC2 instances, load balancer, auto-scaling group, and deployment process. You provide application code (or a Docker image), Beanstalk provisions and manages the infrastructure. It is significantly easier to use than manually configuring EC2 + ALB + Auto Scaling, at the cost of reduced control over the underlying infrastructure.

```bash
# Install the EB CLI
pip install awsebcli

# Initialize an Elastic Beanstalk application in your project
eb init my-app --platform "Node.js 20" --region us-east-1

# Create an environment and deploy
eb create production --elb-type application

# Deploy the current code to the existing environment
eb deploy

# Open the deployed app in a browser
eb open

# View logs from running instances
eb logs
```

For Dockerized applications, provide a `Dockerrun.aws.json` v2 or use Beanstalk's Docker platform — it pulls your image, starts the container, and handles the rest.

## Code Examples

### AWS SDK in Node.js

```javascript
// Using AWS SDK v3 — modular, tree-shakeable
import { S3Client, PutObjectCommand, GetObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';

// When running on EC2 with an instance role attached, credentials are
// loaded automatically from the instance metadata service — no keys in code
const s3 = new S3Client({ region: 'us-east-1' });

// Upload a file
async function uploadFile(key, buffer, contentType) {
  await s3.send(new PutObjectCommand({
    Bucket: process.env.S3_BUCKET,
    Key: key,
    Body: buffer,
    ContentType: contentType,
  }));
  return `https://${process.env.S3_BUCKET}.s3.amazonaws.com/${key}`;
}

// Generate a pre-signed URL for temporary private access (e.g. file downloads)
async function getDownloadUrl(key, expiresInSeconds = 3600) {
  const command = new GetObjectCommand({
    Bucket: process.env.S3_BUCKET,
    Key: key,
  });
  return getSignedUrl(s3, command, { expiresIn: expiresInSeconds });
}
```

### Environment Variables vs. IAM Roles

```javascript
// WRONG: hardcoded credentials — these will end up in version control
const s3 = new S3Client({
  credentials: {
    accessKeyId: 'AKIAIOSFODNN7EXAMPLE',
    secretAccessKey: 'hardcoded-secret-bad'
  }
});

// WRONG: credentials in environment variables on an EC2 instance
// (better than hardcoded, but still long-lived and rotatable by accident)
const s3 = new S3Client({
  credentials: {
    accessKeyId: process.env.AWS_ACCESS_KEY_ID,
    secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY
  }
});

// CORRECT: let the SDK pick up credentials automatically
// On EC2 with an instance role: uses instance metadata service (IMDSv2)
// On Lambda: uses function execution role
// Locally: uses ~/.aws/credentials or AWS CLI profile
const s3 = new S3Client({ region: process.env.AWS_REGION });
// No credentials parameter — SDK handles credential chain automatically
```

## Best Practices

- **Use IAM roles for EC2 instances and Lambda functions**, never long-lived access keys — roles provide temporary, automatically-rotated credentials through the instance metadata service, eliminating the risk of key leakage.
- **Apply least-privilege IAM policies** — grant only the specific actions on specific resources each service actually needs; a policy allowing `s3:*` on `*` is a security liability even if it is convenient.
- **Put databases in private subnets** — an RDS or ElastiCache instance should never have a public IP; it should only be reachable from within the VPC via security group rules, reducing the attack surface dramatically.
- **Use security groups as firewalls between services** — rather than opening ports to `0.0.0.0/0`, configure security groups to allow traffic only from the specific security group of the service that needs access (e.g., allow the app's security group to reach the database's port 5432).
- **Tag all AWS resources** — at minimum, tag with environment (prod/staging/dev) and project name; tags make cost allocation, access control, and resource discovery much more manageable.
- **Use S3 versioning on buckets that hold important data** — versioning protects against accidental deletion and allows recovery of previous object versions.
- **Know the Free Tier limits before experimenting** — 750 hours/month of t2.micro or t3.micro EC2 (not cumulative across instances), 5GB S3 Standard storage, 20GB RDS storage; exceeding these generates real charges.

## Common Interview Questions

**Q: What is the difference between EC2 and Elastic Beanstalk?**
A: EC2 is raw virtual machine infrastructure — you manage the OS, runtime, scaling, and deployment yourself. Elastic Beanstalk is a managed PaaS layer that provisions and manages EC2, load balancers, auto-scaling, and deployments for you. Beanstalk is faster to get started with; raw EC2 gives more control but requires more operational work.

**Q: Why should you use IAM roles instead of access keys for EC2 instances?**
A: IAM roles provide temporary, automatically-rotated credentials through the instance metadata service. Access keys are long-lived credentials that can be accidentally committed to version control, leaked in logs, or exposed in environment variables. With a role, no credentials exist in the environment or filesystem — the SDK fetches them dynamically from the metadata service.

**Q: What is the difference between a security group and a network ACL?**
A: Security groups are stateful firewalls attached to individual instances — if you allow inbound traffic on port 443, the response is automatically allowed back out. Network ACLs are stateless firewalls at the subnet level — they evaluate inbound and outbound rules independently and affect all traffic for the subnet. Security groups are the primary tool; NACLs are typically used for subnet-level rules or to block specific IPs.

**Q: Why does a database belong in a private subnet?**
A: A private subnet has no route to the Internet Gateway, meaning resources in it cannot be reached from the public internet. A database should never be directly internet-reachable — it should only accept connections from the application tier. Placing it in a private subnet, and using security groups to allow only the app's traffic to reach the database port, reduces the attack surface dramatically.

**Q: What is an S3 presigned URL and when would you use it?**
A: A presigned URL is a time-limited URL (generated server-side with AWS credentials) that grants temporary access to a specific private S3 object. Use it when users need to download a private file directly from S3 without your server proxying the bytes — the user gets a URL that works for a limited time, and the S3 object remains private to everyone else.

**Q: What does "Availability Zone" mean and why does it matter?**
A: An Availability Zone is one or more physically separate data centers within a Region with independent power, cooling, and networking. Deploying across multiple AZs (multi-AZ) means your application continues running even if one data center fails. AWS managed services like RDS and Elastic Load Balancer support multi-AZ deployments automatically.

**Q: What is the IAM principle of least privilege?**
A: Least privilege means granting a principal (user, role, or service) only the minimum permissions it needs to perform its specific function — no more. A Lambda function that only reads from DynamoDB should have only `dynamodb:GetItem` and `dynamodb:Query` on its specific table, not `dynamodb:*` on all tables. This minimizes the blast radius if a credential is compromised.

## Practice Exercises

1. **IAM policy writing**: Write IAM policies for three different services in a hypothetical application: an API server that needs to read/write objects in one S3 bucket and write to CloudWatch Logs, a background worker that needs to read from an SQS queue and write to DynamoDB, and a CI/CD role that needs to push Docker images to ECR and deploy to Elastic Beanstalk.

2. **VPC architecture**: Draw a VPC architecture for a two-tier web application (API server + database) that: uses two public subnets in different AZs for the API tier, two private subnets in different AZs for the database tier, security groups that allow the load balancer to reach the API on port 3000, and the API to reach the database on port 5432. Label each security group rule.

3. **S3 file upload flow**: Implement a complete file upload flow where: the client requests a presigned PUT URL from your API server, uploads the file directly to S3 using that URL (no proxying through your server), and then the client notifies your server that the upload is complete. Explain why this pattern is preferable to proxying the upload through your server.

4. **Cost estimation**: Estimate the monthly AWS cost for a small production application running: one t3.small EC2 instance 24/7, one db.t3.micro RDS PostgreSQL instance (single-AZ), 50GB S3 storage with 100GB outbound transfer, and one Application Load Balancer. Identify which parts of this are within the free tier.

5. **Security group audit**: Given a security group configuration where the database instance allows inbound traffic from `0.0.0.0/0` on port 5432, describe the security risk and propose the correct configuration. Explain the difference between allowing traffic from a CIDR block versus allowing traffic from a security group ID.

## Key Takeaways

- AWS is a collection of rented infrastructure services; the most important for web applications are EC2 (compute), S3 (object storage), IAM (identity and access), VPC (networking), and managed deployment platforms like Elastic Beanstalk.
- AWS security is default-deny — nothing is reachable until you explicitly allow it through security groups and IAM policies; every "cannot reach this" problem starts with checking those two layers.
- Use IAM roles for services instead of long-lived access keys — roles provide automatic, temporary credential rotation through the instance metadata service with no credentials in code or environment files.
- Databases belong in private subnets — no public IP, only reachable from within the VPC through specific security group rules; this is the single most important network architecture decision for most applications.
- Least-privilege IAM policies (specific actions on specific resources) minimize the blast radius of any credential compromise.
- Elastic Beanstalk trades infrastructure control for operational simplicity — it is the correct starting point before you have a reason to manage raw EC2 infrastructure directly.
- Know the Free Tier limits to avoid surprise bills: 750 hours/month of t2/t3.micro EC2, 5GB S3, 20GB RDS storage — these limits are per-account, not per-resource.
- The AWS SDK automatically discovers credentials from the instance metadata service, environment variables, and local credential files — never put credentials in application code.
