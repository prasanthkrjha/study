# AWS Fundamentals

You don't need to know all of AWS — you need to know the handful of services that come up in almost every "one cloud platform" requirement, and how they fit together.

## EC2 (Elastic Compute Cloud)

A virtual machine you rent by the hour (or second) — the closest AWS equivalent to "a Linux server you SSH into." You choose an instance type (CPU/RAM tradeoff), an AMI (the OS image it boots from), and a security group (firewall rules for inbound/outbound traffic). EC2 is the most flexible option and also the one requiring the most manual ops work (patching, scaling, process management) compared to managed alternatives.

## S3 (Simple Storage Service)

Object storage — think "a folder in the cloud with effectively unlimited capacity," not a filesystem you mount. You store and retrieve whole objects (files) by key, typically over HTTPS. Common uses: static assets, file uploads, backups, and as the origin for a CDN. S3 is not a database — don't reach for it when you need to query/filter structured data.

## IAM (Identity and Access Management) basics

IAM controls **who can do what** across your AWS account. Core concepts:

- **Users** — an identity for a person or service.
- **Roles** — a set of permissions that can be **assumed** temporarily (e.g. an EC2 instance assumes a role to read from S3, without embedding permanent credentials in code).
- **Policies** — JSON documents that grant or deny specific actions on specific resources.

The principle to internalize: **least privilege** — grant only the specific permissions a service actually needs, not broad admin access, because a compromised credential with narrow permissions does far less damage.

## VPC (Virtual Private Cloud) basics

A VPC is your own isolated network within AWS — you define IP ranges, subnets (public vs. private), and routing rules. A **public subnet** has a route to the internet (for things like a load balancer); a **private subnet** doesn't (for things like a database, which should never be directly internet-reachable). You won't design complex VPCs at this stage, but you should be able to explain why a database sits in a private subnet and a web server sits in a public one.

## Elastic Beanstalk

A "platform as a service" layer on top of EC2/S3/load-balancing/auto-scaling — you upload your code, and Beanstalk handles provisioning the underlying infrastructure. It trades some flexibility for a much gentler on-ramp than manually wiring EC2 + load balancer + auto-scaling group yourself. A reasonable first deployment target before you're ready to manage raw EC2 infrastructure directly.

## Free-tier limits

AWS's free tier has real caps (e.g. 750 hours/month of a `t2.micro` or `t3.micro` EC2 instance, 5GB of S3 standard storage) — know roughly what they are so you don't get a surprise bill, and so you can reason in an interview about what a workload would cost in production versus what's free to experiment with.

## Practice tip

Before touching AWS hands-on (Unit 4.3), be able to explain in one sentence each: what EC2 is, what S3 is, why IAM roles beat hardcoded credentials, and why a database belongs in a private subnet. That vocabulary is what lets the hands-on deployment click instead of feeling like following a script.
