# Embeddings & Semantic Search

Embeddings are the mathematical foundation everything in RAG (Unit 8.3) is built on. Understanding them concretely — not just "it turns text into vectors" — is what lets you defend chunking and retrieval decisions later.

## What an embedding actually is

An embedding is a list of numbers (a vector — typically hundreds to thousands of dimensions) that represents the **meaning** of a piece of text, produced by a neural network trained so that semantically similar texts end up close together in that vector space, and dissimilar texts end up far apart:

```python
from openai import OpenAI
client = OpenAI()

response = client.embeddings.create(
    model="text-embedding-3-small",
    input="The cat sat on the mat."
)
vector = response.data[0].embedding  # e.g. a list of 1536 floats
```

Critically: "close together" is learned from training data patterns, not programmed by hand — the model has learned that "the cat sat on the mat" and "a feline rested on the rug" should map to nearby points, despite sharing almost no words.

## Cosine similarity

The standard way to measure "how close" two embedding vectors are — it measures the angle between two vectors, ignoring their magnitude, which makes it robust to differences in text length:

```python
import numpy as np

def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

similarity = cosine_similarity(query_vector, document_vector)  # ranges -1 to 1
```

A similarity near 1 means "very similar meaning," near 0 means "unrelated," negative means "opposite meaning" (rare in practice for embeddings of normal text).

## Comparing embedding models

Not all embedding models are equal, and the choice matters for RAG quality:

- **Dimension count** — more dimensions can capture more nuance, but cost more to store and search.
- **Domain fit** — a general-purpose embedding model may underperform a domain-specific one (legal, medical, code) on specialized vocabulary.
- **Cost and latency** — hosted API embeddings (OpenAI, Cohere) vs. self-hosted open models (e.g. from Hugging Face) trade convenience for cost and control.
- **Context window** — how much text can be embedded in a single call, which directly constrains your chunking strategy in Unit 8.3.

## Dense vs. sparse retrieval

**Dense retrieval** (embeddings) captures semantic meaning — it can match "car" to "automobile" even with zero shared words. **Sparse retrieval** (classic keyword search, e.g. BM25/TF-IDF) matches on exact or near-exact term overlap — it's precise about exact terminology (product codes, proper nouns, error messages) but blind to synonyms and paraphrasing. Neither is strictly better: dense retrieval can miss an exact SKU number a user typed verbatim; sparse retrieval can miss a paraphrased question that shares no vocabulary with the source document. This is exactly why production RAG systems (including the hybrid approach your own Physynex assistant already conceptually uses) often combine both — hybrid search, covered in Unit 8.3.

## Practice tip

Embed a handful of sentences yourself — some clearly related, some clearly unrelated, some tricky paraphrases — and compute cosine similarity between every pair. Seeing the actual numbers (a paraphrase scoring 0.89, an unrelated sentence scoring 0.12) is what makes "semantic similarity" concrete instead of a phrase you've only read about.
