# LangGraph & Multi-Step Agents

In Unit 8.6 you built a working agent. A `while True` loop, a model call, a tool dispatch, a result fed back in. It ran. It called tools. It produced answers. For simple tasks, that loop is enough.

But now imagine you're deploying that agent to 10,000 users. They have conversations that span multiple days. Some actions need manager approval before the agent can proceed. Users want to see what the agent is doing as it works, not stare at a spinner for 30 seconds. Occasionally the agent hangs because it hit an edge case, and you need to inspect its exact state to diagnose what went wrong.

Your `while True` loop handles none of this. It has no persistent state. It cannot pause and resume. It provides no visibility into intermediate steps. Its control flow is implicit — buried in `if` statements — rather than inspectable.

LangGraph is the answer to all of these problems. It takes the agent loop you already understand and makes its structure *explicit* — as a graph. In doing so, it unlocks state persistence, human-in-the-loop patterns, streaming, and multi-agent coordination. This lesson teaches you why that explicitness matters, and how to use it.

## Theory & Fundamentals

### The Motivation: What the Simple Loop Cannot Do

Here is the while-loop agent from Unit 8.6, unchanged:

```python
messages = [{"role": "user", "content": user_message}]

while True:
    response = call_model(messages)
    if response.stop_reason == "end_turn":
        break
    results = execute_tools(response)
    messages.append(results)
```

This works. But ask yourself: what happens in each of these scenarios?

**Scenario 1: The user closes the browser tab mid-conversation.**
The process exits. `messages` is a local variable. It's gone. When the user returns, they start over from scratch. For a casual chatbot, this is acceptable. For an agent that spent 2 minutes executing a complex research task, this is unacceptable.

**Scenario 2: The agent wants to send an email. You need a human to approve the content first.**
There is no way to pause the while loop, return control to your web server, wait for a human to click "Approve," and then resume exactly where the loop was. You would have to implement this yourself — serializing the message history, saving it somewhere, deserializing it later, and rebuilding the loop state. This is complex plumbing that LangGraph handles for you.

**Scenario 3: The agent is taking 45 seconds. The user is watching a blank screen.**
The while loop produces no output until it exits. You can't show the user what's happening. Every tool call is invisible. Every intermediate reasoning step is hidden.

**Scenario 4: You need a "research" agent and a "writing" agent to collaborate.**
Your single while loop would need to manage two separate conversation threads, coordinate between them, and route outputs from one to the other. The control logic becomes a tangled mess of conditionals.

LangGraph addresses all four of these by making the agent's control flow explicit as a graph. Nodes are steps. Edges are connections. State is a typed object that every node reads from and writes to. The graph engine handles persistence, streaming, and routing.

### The Graph Model — Building Intuition

A graph has two components: nodes and edges.

- **Nodes** are where computation happens. Each node is a Python function that receives the current state and returns an update to that state.
- **Edges** connect nodes: after this node runs, which node runs next?
- **Conditional edges** are decision points: which node to go to depends on the current state.

This maps directly to the while loop you already know:

```
while loop:                        LangGraph graph:
───────────────────────────────    ─────────────────────────────────────
call_model(messages)               [agent node] → reads state.messages,
                                                  calls model, writes result

if stop_reason == "end_turn":      [conditional edge] → "if last message
    break                            has tool calls → go to tools node,
                                     otherwise → END"

execute_tools(response)            [tools node] → reads state.messages,
                                                  runs tool calls, writes results

loop back                          [edge] → "after tools → go back to agent"
```

The graph is the same logic — just explicit rather than implicit. Here it is as ASCII art:

```
         ┌─────────────────────────────────────────────────┐
         │                                                   │
    START │                                                   │
         ▼                                                   │
   ┌─────────────┐                                           │
   │             │  if last message has tool calls           │
   │  agent node │ ──────────────────────────────────►  ┌───────────┐
   │ (call LLM)  │                                      │ tools node│
   └─────────────┘                                      │(run tools)│
         │                                              └───────────┘
         │ if no tool calls                                  │
         ▼                                                   │
        END ◄──────────────────────────────────────────────-┘
```

Two nodes. One conditional edge. One unconditional edge. This is the complete ReAct loop from Unit 8.6, drawn as a graph.

The value of making it explicit: you can now add a node between "tools" and "agent" — for example, a "human approval" node that pauses execution. You can add another conditional edge that routes to a different node if the tools returned an error. You can add a "summarize conversation" node that runs every 10 iterations to manage token count. In a while loop, each of these additions requires modifying the control flow. In a LangGraph graph, you add a node and an edge.

### State: The Key Concept

Every node in the graph reads from and writes to a shared **State** object. State is a TypedDict — a Python dictionary with typed fields.

```python
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]  # the conversation history
    # add any custom fields your agent needs:
    # user_id: str
    # task_type: str
    # accumulated_cost: float
```

The `messages` field is the conversation history — the same `messages` list you managed manually in the while loop. But notice the annotation: `Annotated[list, operator.add]`.

**Why `Annotated[list, operator.add]`?**

When a node returns `{"messages": [new_message]}`, LangGraph needs to decide: should it *replace* the messages list, or *append* to it? The annotation tells it what to do. `operator.add` means concatenate — append new messages to the existing list rather than replacing it.

Without this annotation, every node would wipe the message history and replace it with only its own output. That would mean the agent forgets everything that happened before the most recent step.

With this annotation, each node's returned messages are appended to the growing conversation. Round 1 adds the user message. The agent node adds the model response. The tools node adds the tool results. The agent node adds the next model response. The history accumulates exactly as it did in your manual while loop.

**Common mistake:** trying to pass data from one node to another through function arguments or global variables. Don't do this. If the agent node needs to tell the tools node something, it should put that information in the state — either in `messages` (as a message) or in a custom state field. Nodes communicate through state, not directly.

```python
# WRONG: direct communication between nodes
result_from_agent = None  # global variable

def agent_node(state):
    global result_from_agent
    response = model.invoke(state["messages"])
    result_from_agent = response  # bad: side-effectful, not inspectable
    return {"messages": [response]}

# RIGHT: communicate through state
def agent_node(state):
    response = model.invoke(state["messages"])
    return {"messages": [response]}  # response becomes part of state
    # tools_node reads it from state["messages"][-1]
```

## Core Patterns / Techniques

### Building the Graph — Step by Step

Let's build the complete LangGraph agent. We'll explain every line. At each step, I'll describe what would happen if you stopped there.

**Step 1: Define the State**

```python
from typing import TypedDict, Annotated
import operator
from langchain_core.messages import BaseMessage

class AgentState(TypedDict):
    messages: Annotated[list[BaseMessage], operator.add]
```

This is the shape of data that flows through every node. Every node receives a dict matching this schema and returns a dict with a subset of these keys (the keys it wants to update).

If you ran the graph with only this defined, it would fail — no nodes, no edges.

**Step 2: Define the Agent Node**

```python
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, AIMessage, ToolMessage

model = ChatOpenAI(model="gpt-4o-mini").bind_tools(tools)  # bind tool definitions

def call_model(state: AgentState) -> dict:
    """
    The 'agent' node. 
    - Reads the full conversation from state["messages"]
    - Calls the LLM with those messages
    - Returns the LLM's response as a state update
    """
    messages = state["messages"]
    response = model.invoke(messages)
    # Return a state update: {"messages": [response]} will be APPENDED
    # to state["messages"] (because of the operator.add annotation)
    return {"messages": [response]}
```

If you stopped here with only this node and no edges, the graph would run the agent once and stop — no routing, no tools, no loop.

**Step 3: Define the Tools Node**

```python
import json
from langchain_core.messages import ToolMessage

def execute_tools(state: AgentState) -> dict:
    """
    The 'tools' node.
    - Reads the last message from state (which should be an AIMessage with tool_calls)
    - Executes each tool call
    - Returns the results as ToolMessages (which will be appended to state)
    """
    last_message = state["messages"][-1]
    tool_results = []
    
    for tool_call in last_message.tool_calls:
        print(f"  [Executing tool: {tool_call['name']}({tool_call['args']})]")
        
        # Dispatch to the right function
        result = run_tool(tool_call["name"], tool_call["args"])
        
        tool_results.append(
            ToolMessage(
                content=json.dumps(result),
                tool_call_id=tool_call["id"],  # links this result to the specific call
            )
        )
    
    return {"messages": tool_results}
```

ToolMessages are the format LangChain uses to represent tool results in a conversation. They carry the `tool_call_id` so the model can match each result to the request that generated it.

**Step 4: Define the Routing Function**

```python
from langgraph.graph import END

def should_continue(state: AgentState) -> str:
    """
    The conditional edge.
    - Reads the last message from state
    - Returns the name of the next node, OR END
    
    This is the decision point of the loop.
    """
    last_message = state["messages"][-1]
    
    # If the last message has tool calls, the agent wants to use tools
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"  # go to the tools node
    
    # No tool calls — the agent produced a final answer
    return END  # end the graph
```

This function is not a node — it is an edge function. It determines which node to route to, but it doesn't modify state. It is called after the agent node runs.

**Step 5: Assemble the Graph**

```python
from langgraph.graph import StateGraph

# Create the graph with AgentState as the state schema
graph_builder = StateGraph(AgentState)

# Add nodes — each is a function that takes state and returns a state update
graph_builder.add_node("agent", call_model)
graph_builder.add_node("tools", execute_tools)

# Set the entry point — which node runs first?
graph_builder.set_entry_point("agent")

# Add the conditional edge FROM agent:
# - call should_continue(state) to determine where to go
# - "tools" → go to the tools node
# - END → end the graph
graph_builder.add_conditional_edges(
    "agent",           # FROM this node
    should_continue,   # CALL this function to decide WHERE
    {
        "tools": "tools",  # if should_continue returns "tools", go to tools node
        END: END,           # if should_continue returns END, end the graph
    }
)

# Add an unconditional edge FROM tools → always go back to agent
# (the agent needs to see the tool results and decide what to do next)
graph_builder.add_edge("tools", "agent")

# Compile the graph into a runnable app
app = graph_builder.compile()
```

The compiled graph enforces the structure you defined. You cannot accidentally call the tools node without going through the routing function. The control flow is explicit.

**Step 6: Run the Graph**

```python
from langchain_core.messages import HumanMessage

# Invoke the graph with an initial state
result = app.invoke({
    "messages": [HumanMessage(content="Is the iPad Air in stock at palo-alto? If yes, reserve one.")]
})

# result is the final state of the graph
final_message = result["messages"][-1]
print(final_message.content)
```

The entire message history — including all intermediate tool calls and results — is in `result["messages"]`. This is invaluable for debugging: you can inspect every step the agent took.

### Checkpointing and Memory

**The problem:** your agent runs 5 tool calls, produces a great answer — and then the process restarts (deployment, crash, serverless cold start). `messages` is gone. The user has to start over.

**The solution:** after every node runs, save the entire state to persistent storage. On the next request, load the saved state and continue from where it left off.

LangGraph calls this checkpointing. Here's how to add it:

```python
from langgraph.checkpoint.memory import MemorySaver

# MemorySaver: stores checkpoints in Python memory
# ONLY use for development — lost on process restart
checkpointer = MemorySaver()

# Compile the graph WITH the checkpointer
app = graph_builder.compile(checkpointer=checkpointer)

# Now every invocation requires a config with thread_id
# thread_id identifies the conversation session
config = {"configurable": {"thread_id": "user-alice-session-42"}}

# First message in the conversation
result1 = app.invoke(
    {"messages": [HumanMessage("What's my current cart total?")]},
    config=config
)
print(result1["messages"][-1].content)
# "Your cart total is $47.50 with 3 items."

# Second message — same thread_id means the graph loads the saved state
# The agent sees the entire previous conversation
result2 = app.invoke(
    {"messages": [HumanMessage("Add a red sweater to my cart")]},
    config=config
)
print(result2["messages"][-1].content)
# "Done! I've added the red sweater. Your new cart total is $95.00 with 4 items."
```

**Why `thread_id` matters:** in a multi-user application, you might have 50,000 concurrent conversations. Each conversation is a separate session with its own state. The `thread_id` is the key that distinguishes them. When `thread_id = "user-alice-session-42"` invokes the graph, LangGraph loads the checkpointed state for that specific thread.

Without `thread_id`, every invocation would start fresh — no memory between requests. With `thread_id`, the graph automatically loads the previous state and appends the new messages.

**Persistence backends:**

```python
# Development: in-memory, lost on restart
from langgraph.checkpoint.memory import MemorySaver
checkpointer = MemorySaver()

# Single-server production: persists to an SQLite file
from langgraph.checkpoint.sqlite import SqliteSaver
checkpointer = SqliteSaver.from_conn_string("agent_sessions.db")

# Multi-server production: persists to PostgreSQL, survives restarts and scaling
from langgraph.checkpoint.postgres import PostgresSaver
checkpointer = PostgresSaver.from_conn_string("postgresql://user:pass@host/db")
```

Use `MemorySaver` only when you are developing and testing. The moment your agent needs to survive a process restart (production, serverless, staged deployments), switch to `SqliteSaver` or `PostgresSaver`.

**What gets checkpointed:** the entire `AgentState` object — all messages, all custom fields. The checkpointer stores the full state after every node completes. If the process crashes mid-node, the last successful checkpoint is used on resume.

### Human-in-the-Loop

This is one of LangGraph's most powerful features, and it requires checkpointing to work.

**The problem:** your agent wants to send an email on behalf of the user. Before it does, you need to show the user the draft and ask for approval. With a simple while loop, there is no way to pause in the middle and wait for external input.

**The solution:** `interrupt_before`. This tells LangGraph to pause execution *before* a specific node, save a checkpoint, and return control to your code.

```python
# Compile with an interrupt — pause before the "send_email" node
app = graph_builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["send_email"]   # pause BEFORE this node runs
)

config = {"configurable": {"thread_id": "email-task-001"}}

# Run the agent — it will execute until it reaches the "send_email" node, then stop
state = app.invoke(
    {"messages": [HumanMessage("Draft and send an email to the team about the Q3 results")]},
    config=config
)

# At this point, the graph has PAUSED.
# The agent node ran and decided to send an email.
# The "send_email" node has NOT yet run.
# The checkpointed state includes the draft email.

# Inspect what the agent plans to do
last_message = state["messages"][-1]
print("The agent wants to send this email:")
print(last_message.tool_calls[0]["args"])  # shows the email draft
# → {"to": "team@company.com", "subject": "Q3 Results Summary", "body": "..."}

# Ask the human for approval
print("\nApprove sending this email? (y/n): ", end="")
approval = input().strip().lower()

if approval == "y":
    # Resume from the checkpoint — the "send_email" node will now execute
    final_state = app.invoke(None, config=config)  # None = continue from checkpoint
    print("Email sent!", final_state["messages"][-1].content)
else:
    # Modify the state and resume, or cancel entirely
    from langchain_core.messages import HumanMessage as HM
    final_state = app.invoke(
        {"messages": [HM("The user rejected the email. Explain why it wasn't sent.")]},
        config=config
    )
    print("Cancelled:", final_state["messages"][-1].content)
```

**Why checkpointing is required for this:** when the graph pauses at the interrupt, it has saved the complete state to the checkpointer. When you call `app.invoke(None, config)` to resume, LangGraph loads that checkpoint and continues from exactly where it stopped. Without a checkpointer, there is no saved state to resume from — the graph has no way to pick up where it left off.

**`interrupt_before` vs `interrupt_after`:**

```python
# interrupt_before: pause BEFORE the node runs
# Use when you want to preview and approve what the agent PLANS to do
# Example: review an email draft before it's sent
interrupt_before=["send_email"]

# interrupt_after: pause AFTER the node runs
# Use when you want to review RESULTS before the agent continues
# Example: review a generated report before it's forwarded
interrupt_after=["generate_report"]
```

**A complete human-in-the-loop flow:**

```
1. User: "Book a flight to Paris for next Friday"
2. Agent runs → searches for flights → [PAUSED before "book_flight" node]
3. Your code shows: "Agent wants to book: Air France AF7, $450, Fri Aug 14, 08:30"
4. User: "Approve"
5. Agent resumes → books the flight → returns "Booked! Confirmation: AF-789345"
```

The user has full visibility and control over the irreversible action. The agent did the research (the tedious part); the human made the final call (the important part).

### Streaming Intermediate State

**The problem:** a complex agent run — multiple web searches, several reasoning steps, large responses — can take 30+ seconds. During that time, the user sees nothing. This feels broken. Users abandon interactions that feel frozen.

**The solution:** stream events as they happen. LangGraph's `astream_events` yields an event every time something significant occurs: a token is generated, a node starts, a tool is called, a node finishes.

```python
import asyncio
from langchain_core.messages import HumanMessage

async def run_with_streaming(question: str):
    config = {"configurable": {"thread_id": "streaming-demo"}}
    
    async for event in app.astream_events(
        {"messages": [HumanMessage(question)]},
        config=config,
        version="v1"
    ):
        event_type = event["event"]
        
        # Stream tokens as the model generates them
        if event_type == "on_chat_model_stream":
            chunk = event["data"]["chunk"]
            if chunk.content:
                print(chunk.content, end="", flush=True)
        
        # Show which node just started running
        elif event_type == "on_chain_start":
            node_name = event.get("name", "")
            if node_name in ("agent", "tools"):
                print(f"\n[Node starting: {node_name}]")
        
        # Show which tool is being called (before it runs)
        elif event_type == "on_tool_start":
            tool_name = event["name"]
            tool_input = event["data"].get("input", {})
            print(f"\n[Calling tool: {tool_name}({tool_input})]")
        
        # Show tool results (after the tool runs)
        elif event_type == "on_tool_end":
            tool_name = event["name"]
            result = event["data"].get("output", "")
            print(f"\n[Tool result from {tool_name}: {str(result)[:100]}...]")

# Run it
asyncio.run(run_with_streaming("Research the top 3 Python web frameworks and compare them"))
```

This produces output like:

```
[Node starting: agent]
I'll research the top Python web frameworks for you.
[Calling tool: web_search({'query': 'top Python web frameworks 2026'})]
[Tool result from web_search: {'results': [{'title': 'Django vs FastAPI vs Flask'...]}]
[Node starting: agent]
Let me get more detail on each framework.
[Calling tool: fetch_page({'url': 'https://...'})]
[Tool result from fetch_page: {'content': 'Django is a high-level Python web framework...'}]
[Node starting: agent]
Based on my research, here are the top 3 Python web frameworks:

**1. Django** — a batteries-included framework ideal for...
**2. FastAPI** — optimized for APIs and asynchronous workloads...
**3. Flask** — a minimal microframework for simple applications...
```

The user sees progress continuously. They know the agent is working, what it's searching for, and what it's finding. The experience is dramatically better than 30 seconds of silence.

**Why this matters for UX:** the difference between "wait 30 seconds with no feedback" and "see the agent actively working — searching for X, reading Y, finding Z" is not cosmetic. It's the difference between a product that feels alive and one that feels broken. Stream by default in any user-facing agent.

### Multi-Agent Systems: The Supervisor Pattern

Sometimes one agent isn't enough — not because the agent isn't capable, but because the task involves fundamentally different domains that benefit from specialization.

Consider a customer service system that handles three categories:
- Technical support (debugging, code issues)
- Billing questions (invoices, refunds, payments)
- Sales inquiries (pricing, features, demos)

You could build one agent with all the tools for all three domains. But that agent has 30+ tools, and research consistently shows agents with many tools make worse decisions than agents with fewer, focused tools.

The supervisor pattern: one routing agent that reads the user's message and decides which specialized agent should handle it.

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated, Literal
import operator

class SupervisorState(TypedDict):
    messages: Annotated[list, operator.add]
    next_agent: str

# Specialized agents (each is a compiled LangGraph or simple function)
def technical_agent(state: SupervisorState) -> dict:
    """Handles technical support with debugging tools."""
    # ... implementation with tech-specific tools
    response = tech_model.invoke(state["messages"])
    return {"messages": [response]}

def billing_agent(state: SupervisorState) -> dict:
    """Handles billing with payment system access."""
    # ... implementation with billing-specific tools
    response = billing_model.invoke(state["messages"])
    return {"messages": [response]}

def supervisor(state: SupervisorState) -> dict:
    """Read the request and route to the appropriate agent."""
    last_message = state["messages"][-1].content.lower()
    
    if any(word in last_message for word in ["bug", "error", "crash", "code", "api"]):
        return {"next_agent": "technical"}
    elif any(word in last_message for word in ["invoice", "charge", "refund", "payment", "billing"]):
        return {"next_agent": "billing"}
    else:
        return {"next_agent": "general"}

def route_to_agent(state: SupervisorState) -> str:
    """Conditional edge: read next_agent from state and route."""
    return state["next_agent"]

# Build the supervisor graph
builder = StateGraph(SupervisorState)
builder.add_node("supervisor", supervisor)
builder.add_node("technical", technical_agent)
builder.add_node("billing", billing_agent)

builder.set_entry_point("supervisor")
builder.add_conditional_edges(
    "supervisor",
    route_to_agent,
    {
        "technical": "technical",
        "billing": "billing",
        "general": END,  # or a general-purpose agent
    }
)
builder.add_edge("technical", END)
builder.add_edge("billing", END)

supervisor_app = builder.compile(checkpointer=checkpointer)
```

**When to use multi-agent systems:**

Use a single agent unless you have specific evidence it's failing. Multi-agent systems add:
- Coordination complexity (the supervisor must route correctly)
- More failure modes (routing errors, inter-agent miscommunication)
- Harder debugging (a failure could be in any of several agents)

Start simple. If your single agent struggles because it has too many tools and makes poor decisions, or because different subtasks need fundamentally different context windows, *then* consider specialization.

## Best Practices

- **Explicitly type your state** — use TypedDict with annotated fields. Typed state documents the graph's data model, catches key typos at development time, and makes the graph inspectable.
- **Use `operator.add` for messages** — always annotate the messages field with `Annotated[list, operator.add]`. Without it, each node replaces the message history instead of appending to it.
- **Test nodes in isolation before assembling the graph** — each node is just a function. Call it directly with a test state dict before wiring it into the graph. This isolates bugs to the node level before graph-level routing makes them harder to trace.
- **Add streaming from day one** — `astream_events` is easy to add during development. It's harder to retrofit in production when users are complaining about long wait times.
- **Use `SqliteSaver` or `PostgresSaver` for production** — `MemorySaver` is convenient for development, but any process restart (deployment, crash, scaling) wipes all conversation history.
- **`interrupt_before` for any irreversible action** — if a node sends emails, charges payments, deletes data, or takes any action that cannot be undone, add it to `interrupt_before`. Review first, act second.
- **Start with one agent** — a supervisor plus three sub-agents is genuinely complex. Build one agent that does everything first. Add multi-agent structure only when a single agent demonstrably struggles.

## Common Interview Questions

**Q1: What is LangGraph and how does it differ from a simple tool-calling loop?**
A: LangGraph is a framework for building stateful agents as directed graphs. A simple while loop handles tool calling but gives you no state persistence, streaming, interrupt capability, or multi-agent routing. LangGraph makes the control flow explicit — you declare nodes and edges rather than embedding logic in `if` statements — and the graph engine handles checkpointing, resumption, and event streaming automatically.

**Q2: What is a checkpoint in LangGraph and why is it useful?**
A: A checkpoint is a saved snapshot of the full graph state (all messages, all state fields) after a node completes. It enables: multi-turn conversations that survive process restarts (users don't lose context), human-in-the-loop interrupts (pause, get approval, resume from exactly where the graph stopped), debugging (inspect the full state at any step of the agent's execution), and serverless deployment (stateless compute processes can pick up any checkpoint).

**Q3: How does LangGraph implement the human-in-the-loop pattern?**
A: Compile the graph with `interrupt_before=["node_name"]` for any node that requires human approval. The graph runs all nodes up to the interrupt point, saves a checkpoint, and returns. Your code shows the planned action to the human and waits for input. On approval: call `app.invoke(None, config)` to resume from the checkpoint (the interrupted node now runs). On rejection: add a message to state explaining the rejection and invoke to continue. This requires a checkpointer — without saved state, there's nothing to resume from.

**Q4: What does `Annotated[list, operator.add]` do in AgentState?**
A: It tells LangGraph to use `operator.add` (list concatenation) when merging a node's returned messages with the existing state messages. Without this annotation, a node returning `{"messages": [new_msg]}` would *replace* the entire messages list with just `[new_msg]`. With it, `[new_msg]` is *appended* to the existing list. This is how conversation history accumulates across multiple node executions.

**Q5: What is the difference between `interrupt_before` and `interrupt_after`?**
A: `interrupt_before=["node"]` pauses before the node runs — use this to preview and approve what the agent *plans* to do (e.g., review an email draft before sending). `interrupt_after=["node"]` pauses after the node has run — use this to review results before the agent continues (e.g., review a generated report before it's published). Both require a checkpointer.

**Q6: When should you use a multi-agent system instead of a single agent?**
A: When a single agent would need so many tools that it makes poor routing decisions (consistently calling the wrong tool), or when different subtasks require genuinely different specialized context that would conflict if combined. Multi-agent systems add coordination overhead, more failure modes, and harder debugging. Build one agent first; add specialization only when you have clear evidence the single-agent approach is failing.

## Key Takeaways

- LangGraph takes the while-loop agent and makes its control flow explicit as a graph. This unlocks state persistence, streaming, human-in-the-loop patterns, and multi-agent coordination.
- Nodes are functions that read state and return state updates. Edges define which node runs next. Conditional edges make routing decisions based on state.
- `Annotated[list, operator.add]` on the messages field tells LangGraph to append new messages rather than replace the list — this is how conversation history accumulates across multiple rounds.
- Checkpointing saves the complete graph state after every node. It enables: multi-turn conversations that survive restarts, human-in-the-loop interrupts, and full conversation replay for debugging.
- `interrupt_before` pauses execution before a node and saves a checkpoint. Resume with `app.invoke(None, config)`. Requires a checkpointer.
- Stream with `astream_events` from day one. Users should see the agent working, not a blank screen for 30 seconds.
- Build one agent first. Multi-agent systems add coordination complexity — only add them when a single agent demonstrably fails.
