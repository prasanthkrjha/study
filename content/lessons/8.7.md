# LangGraph & Multi-Step Agents

If Unit 8.6 covered the core tool-calling primitive, LangGraph is the framework for structuring what happens **around** repeated tool calls — state, branching, memory, and control flow for genuinely multi-step agents.

## Theory & Fundamentals

### Why LangGraph Exists

The basic tool-calling loop from Unit 8.6 is essentially:

```python
while True:
    response = call_model(messages)
    if response.stop_reason == "end_turn":
        break
    results = execute_tools(response.tool_calls)
    messages.append(results)
```

This works for simple agents. But real production agents need more:
- **Branching**: route to different tools or behaviors based on model output
- **Memory persistence**: save and restore conversation state across separate sessions
- **Streaming intermediate state**: show users what the agent is doing, not just the final answer
- **Human-in-the-loop**: pause before irreversible actions for human approval
- **Multi-agent coordination**: route subtasks to specialized sub-agents

LangGraph provides all of this as a **stateful directed graph** — nodes are processing steps, edges define routing, and the state is explicitly typed and managed.

### Graphs, Nodes, and Edges

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    messages: Annotated[list, operator.add]  # append-only list
    next_step: str

def call_model(state: AgentState) -> AgentState:
    response = model.invoke(state["messages"])
    return {"messages": [response]}

def execute_tools(state: AgentState) -> AgentState:
    last_message = state["messages"][-1]
    results = []
    for tool_call in last_message.tool_calls:
        result = run_tool(tool_call["name"], tool_call["args"])
        results.append(ToolMessage(content=str(result), tool_call_id=tool_call["id"]))
    return {"messages": results}

def should_continue(state: AgentState) -> str:
    last = state["messages"][-1]
    if hasattr(last, "tool_calls") and last.tool_calls:
        return "tools"   # route to tools node
    return END           # end the graph

graph = StateGraph(AgentState)
graph.add_node("agent", call_model)
graph.add_node("tools", execute_tools)
graph.add_conditional_edges("agent", should_continue, {
    "tools": "tools",
    END: END,
})
graph.add_edge("tools", "agent")  # after tools, loop back to agent
graph.set_entry_point("agent")

app = graph.compile()
```

The `should_continue` function is the graph's decision point: if the model's last response requested tool calls, route to the `tools` node; otherwise, end. After tools execute, control loops back to `agent` — this is the ReAct loop from Unit 8.6, made explicit as a graph instead of an implicit while-loop.

## Core Patterns / Techniques

### Persisted Memory

LangGraph supports checkpointing — saving and restoring graph state so an agent can resume a multi-turn conversation across separate requests:

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()  # in-memory; use SqliteSaver for persistence
app = graph.compile(checkpointer=checkpointer)

# First invocation — start a new session
config = {"configurable": {"thread_id": "user-123"}}
result = app.invoke({"messages": [HumanMessage("What's my cart total?")]}, config)

# Second invocation — same thread_id, agent remembers previous exchange
result2 = app.invoke({"messages": [HumanMessage("Add a red sweater")]}, config)
```

The `thread_id` identifies a conversation session. All previous messages for that thread are loaded before the agent runs, so the agent has full context without the caller managing message history.

### Human-in-the-Loop

For actions with real consequences, pause the graph before the irreversible step:

```python
from langgraph.graph import interrupt_before

app = graph.compile(
    checkpointer=checkpointer,
    interrupt_before=["execute_payment"],  # pause before this node
)

# Run until the interrupt
result = app.invoke(initial_state, config)
# → agent prepared the payment, execution paused

# Human reviews and approves
print("Agent wants to charge $129.99. Approve? [y/n]")
approval = input()

if approval == "y":
    # Resume the graph — it picks up from the interrupt point
    result = app.invoke(None, config)  # None = continue from checkpoint
```

This implements the "agent proposes, human confirms" pattern for irreversible actions.

### Streaming Intermediate State

```python
async for event in app.astream_events(initial_state, config):
    if event["event"] == "on_chat_model_stream":
        chunk = event["data"]["chunk"]
        print(chunk.content, end="", flush=True)  # stream tokens
    elif event["event"] == "on_tool_start":
        print(f"\n[Calling tool: {event['name']}...]")
```

This surfaces tokens as they're generated and shows which tool is being called, rather than a silent wait for the full response.

### Multi-Agent (Supervisor Pattern)

```python
def supervisor(state):
    # Routes tasks to specialized sub-agents based on the request
    if "database" in state["task"].lower():
        return {"next": "database_agent"}
    elif "email" in state["task"].lower():
        return {"next": "email_agent"}
    return {"next": "general_agent"}

graph.add_node("supervisor", supervisor)
graph.add_conditional_edges("supervisor", lambda s: s["next"], {
    "database_agent": "database_agent",
    "email_agent": "email_agent",
    "general_agent": "general_agent",
})
```

## Best Practices

- **Explicitly type your state** — use TypedDict for AgentState. Typed state makes the graph's behavior inspectable and prevents subtle bugs from state key typos.
- **Use `interrupt_before` for any irreversible action** — sending emails, charging payments, deleting data. The checkpoint lets you audit what the agent planned before it acts.
- **Stream to avoid "silent pause" UX** — long agent runs without streaming feel broken. Surface intermediate steps (tool calls) and tokens as they're generated.
- **Start with one agent, not a multi-agent system** — a supervisor + multiple sub-agents is genuinely complex. Build one well-tested agent first; add specialization only when a single agent demonstrably struggles.
- **Use SqliteSaver or PostgresSaver for production memory** — MemorySaver is only for development (lost on process restart).

## Common Interview Questions

**Q1: What is LangGraph and how does it differ from a simple tool-calling loop?**
A: LangGraph is a framework for building stateful agents as directed graphs. A simple while-loop handles basic tool-calling but doesn't provide state persistence, streaming, human-in-the-loop interrupts, or multi-agent routing. LangGraph makes the control flow explicit (nodes and edges), manages state across turns, and supports all these production patterns in a composable way.

**Q2: What is a "checkpoint" in LangGraph and why is it useful?**
A: A checkpoint saves the current state of a graph execution — all messages, tool results, and custom state — to persistent storage (memory, SQLite, Postgres). It enables: resuming a conversation after a process restart, human-in-the-loop interrupts (pause, get approval, resume), multi-turn conversations where each request picks up from where the last one ended, and debugging (inspect the state at any step).

**Q3: How does LangGraph implement the human-in-the-loop pattern?**
A: Compile the graph with `interrupt_before=["node_name"]` for any node that should pause for human approval. The graph runs up to that node, saves a checkpoint, and returns. The human reviews the planned action. If approved, the graph resumes from the checkpoint with `app.invoke(None, config)`. The `thread_id` in the config identifies which checkpoint to resume.

**Q4: When would you use a multi-agent system instead of a single agent?**
A: When a single agent would need too many tools (poor focus → worse decisions), when different subtasks require different specialized capabilities or context windows, or when parallelism would help (multiple agents working simultaneously). The cost: coordination overhead, harder debugging, more failure modes. Start with one agent; add specialization when you have evidence the single-agent approach is failing.

**Q5: What is `interrupt_before` vs `interrupt_after` in LangGraph?**
A: `interrupt_before=["node"]` pauses execution before the node runs — use this to preview what the agent intends to do before it does it (pre-approval for irreversible actions). `interrupt_after=["node"]` pauses after the node completes — use this to review results before continuing (e.g., review a generated report before it's sent).

## Key Takeaways

- LangGraph is the ReAct loop made explicit as a graph: agent node → conditional edge → tools node → back to agent.
- State is explicitly typed and passed through every node, enabling inspection and debugging of the full agent run.
- Checkpointing (MemorySaver, SqliteSaver) enables multi-turn conversations and human-in-the-loop patterns.
- `interrupt_before` pauses execution before a node for human approval — the key pattern for irreversible actions.
- Streaming (`astream_events`) surfaces intermediate steps and tokens in real time, avoiding "silent pause" UX.
- Start with a single agent; add multi-agent complexity only when there's evidence a single agent can't handle the task.
