# LangGraph & Multi-Step Agents

If Unit 8.6 covered the core tool-calling primitive, LangGraph is the framework for structuring what happens **around** repeated tool calls — state, branching, memory, and control flow for genuinely multi-step agents.

## State graphs (nodes/edges)

LangGraph models an agent as a graph: **nodes** are steps (call the model, run a tool, check a condition), and **edges** define what happens next based on the current state. This is a more explicit, inspectable structure than "just loop and call the model again" — you can see and control exactly which step follows which.

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict

class AgentState(TypedDict):
    messages: list
    next_step: str

def call_model(state: AgentState):
    response = model.invoke(state["messages"])
    return {"messages": state["messages"] + [response]}

def should_continue(state: AgentState):
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END

graph = StateGraph(AgentState)
graph.add_node("agent", call_model)
graph.add_node("tools", execute_tools)
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")  # after tools run, go back to reasoning
graph.set_entry_point("agent")

app = graph.compile()
```

The `should_continue` function is the graph's decision point: if the model's last response requested a tool call, route to the `tools` node; otherwise, end. After tools execute, control loops back to `agent` — this is the ReAct loop from Unit 8.6, made explicit as a graph instead of an implicit while-loop.

## Building a tool-calling chatbot

The pattern above — `agent` node calls the model, `tools` node executes any requested tool calls, loop until the model stops requesting tools — is the minimal viable shape of essentially every tool-calling chatbot, regardless of how many tools it has access to.

## Memory across turns

A single conversation needs the model to remember earlier messages; LangGraph handles this by keeping `messages` (or similar) as part of the persisted state that's passed into every node, rather than each call starting from a blank slate. For longer-running or multi-session memory, state can be checkpointed (saved) between separate conversations, so an agent can pick up context from a previous session.

## Streaming

Waiting for a full multi-step agent run to finish before showing anything feels slow to a user. LangGraph supports streaming intermediate state — you can surface "checking availability..." or partial tokens as they're generated, rather than a long silent pause followed by one final block of text.

## Human-in-the-loop feedback

For actions with real consequences (sending an email, charging a payment, booking something), you often want the graph to **pause** before an irreversible tool call and require explicit human approval before continuing. LangGraph supports interrupting execution at a specific node and resuming it later with human input injected into the state — the mechanism behind "the agent proposes, a human confirms" workflows.

## Practice tip

Extend your Unit 8.6 tool-calling loop into a small LangGraph with at least two tools and one conditional branch (e.g. "if the requested slot isn't available, suggest an alternative instead of just failing"). That branching logic is exactly what distinguishes a real agent from a single scripted tool call.
