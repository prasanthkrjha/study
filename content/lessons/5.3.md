# Data & Storage at Scale

Once a system outgrows a single database on a single machine, a new set of trade-offs shows up — this unit is about the vocabulary for that transition.

## Theory & Fundamentals

### SQL vs. NoSQL Trade-offs

**SQL** (relational) databases give you strong consistency, joins, and enforced schema/relationships — ideal when your data is genuinely relational and correctness (no orphaned or contradictory records) matters more than raw write throughput. PostgreSQL handles tens of thousands of queries per second on modern hardware; don't reach for NoSQL until SQL is actually the bottleneck.

**NoSQL** databases trade structure for horizontal scalability and flexible schemas. Different types are optimized for different access patterns:

| Type | Examples | Best for |
|---|---|---|
| Document | MongoDB, DynamoDB | Nested/flexible schemas, JSON documents |
| Key-Value | Redis, DynamoDB | Session data, caching, simple lookups by key |
| Wide-Column | Cassandra, HBase | Time-series, write-heavy, known access patterns |
| Graph | Neo4j | Highly connected data (social graphs, recommendations) |
| Search | Elasticsearch | Full-text search, log aggregation |

The right interview answer names the actual access pattern and consistency needs, not a blanket "NoSQL scales better." Cassandra writes are fast but it doesn't support joins; MongoDB is flexible but consistency is weaker; Redis is extremely fast but data fits in RAM.

### Replication

Copying data across multiple database instances, for two reasons:

1. **Fault tolerance**: if the primary dies, a replica can take over.
2. **Read scaling**: route read traffic across multiple replicas instead of hammering one instance.

The common pattern is **single-primary replication**: all writes go to one primary, which propagates changes to replicas asynchronously (or synchronously).

- **Synchronous replication**: primary waits for at least one replica to confirm the write before returning success. Stronger consistency (no data loss on primary failure) but higher write latency.
- **Asynchronous replication**: primary returns immediately, propagates in the background. Lower write latency but a "replication lag" window where replicas may serve stale data — the AP trade-off from CAP theorem.

**Read replicas**: for read-heavy applications, route SELECT queries to read replicas and reserve the primary for writes. A 90/10 read-write split (common in social apps) can 10x effective read capacity with 10 replicas.

### Sharding / Partitioning

Splitting one logical dataset **across multiple database instances**, each holding a subset of the data. Replication holds complete copies; sharding splits the data.

**Why sharding solves what replication doesn't**: if a dataset is 10TB and a single machine holds 2TB, no number of replicas fixes this — every replica also needs 10TB. Sharding puts 2TB on each of 5 machines.

**Common sharding strategies**:
- **Range-based**: shard by date ranges (2020 data on shard 1, 2021 on shard 2). Simple to implement, but can create hot spots if recent data is heavily queried.
- **Hash-based**: `hash(shard_key) % num_shards`. Even distribution, but cross-shard queries are hard and resharding requires moving half the data.
- **Directory-based**: a lookup service maps keys to shards. Flexible, but the directory becomes a bottleneck and single point of failure.

**The main cost**: cross-shard queries (joining data that lives on different shards) become application-level logic, not database-level joins. Design your schema so that queries you run frequently hit at most one shard.

### Consistent Hashing

A hashing technique that minimizes data movement when nodes are added or removed. With naive `hash(key) % num_nodes`, adding one node reshuffles nearly every key's assignment (n/n+1 of all keys move). Consistent hashing maps both nodes and keys onto a conceptual ring — adding or removing a node only affects the keys immediately adjacent to it on the ring: approximately `1/n` of keys, not `n/(n+1)`.

This is why consistent hashing is standard in distributed caches (Memcached, Redis Cluster), distributed databases, and CDN routing — it makes scale-in and scale-out operationally safe.

### Caching Strategies

A cache reduces load on the database by serving frequently-read data from fast storage (memory).

**Write strategies**:
- **Write-through**: write to cache and database simultaneously. Cache always has latest data, but writes are slower.
- **Write-back (write-behind)**: write to cache first, database asynchronously. Faster writes, but data can be lost if the cache fails before writing to the database.
- **Write-around**: write directly to database, bypassing cache. Good when data is written once and read rarely.

**Cache invalidation strategies**:
- **TTL-based expiry**: cached data expires after N seconds. Simple, but stale for up to the TTL window.
- **Explicit invalidation**: every write operation deletes or updates the corresponding cache entry. Accurate, but every code path that mutates data must remember to invalidate — easy to miss one.
- **Versioned/cache-busted keys**: append a version number to cache keys; changing the version effectively invalidates all old entries.

## Core Patterns / Techniques

### Caching Layer

```
Client → [API Server] → [Cache (Redis)] → [Database]
                              ↑ cache hit: return immediately
                              ↓ cache miss: read from DB, populate cache, return
```

The cache-aside (lazy loading) pattern:
1. Read from cache.
2. If cache miss → read from database.
3. Write result to cache with a TTL.
4. Return result.

On write: update the database, then delete (not update) the cache entry — forces a fresh read on the next access, preventing stale data from a race condition between cache-write and DB-write.

### Database Indexing

An index is a separate data structure (typically a B-tree) that lets the database find rows matching a condition without scanning the entire table.

- Without index: scan all n rows → O(n)
- With index on the queried column: B-tree lookup → O(log n), then row fetch

Costs: indexes consume storage and slow down writes (the index must be updated on every insert/update/delete). Index columns that are frequently queried but infrequently updated.

## Best Practices

- **Start with a single SQL database** — premature sharding is a common mistake. Add replicas, then caching, before considering sharding.
- **Distinguish replication from sharding** when explaining your design — replication = copies for redundancy and read scaling; sharding = partitioning for data volume.
- **Design for your shard key access pattern** — the shard key determines which shard a query hits; pick a key you'll filter on in 90% of queries to minimize cross-shard operations.
- **Cache read results, not writes** — caching is most effective for read-heavy, write-infrequent data. Session data, user profiles, and product catalog are good candidates; real-time inventory counts are not.
- **Consistent hashing is the answer** for "how do you add a cache node without invalidating everything?"

## Common Interview Questions

**Q1: What is the difference between database replication and sharding?**
A: Replication creates full copies of the dataset on multiple machines — solves fault tolerance and read scaling. Sharding splits the dataset across machines, each holding a subset — solves data volume problems (when the dataset is too large for any single machine). You can use both simultaneously: shard the data, then replicate each shard.

**Q2: When would you choose NoSQL over SQL?**
A: When you need to scale writes horizontally beyond what a single SQL primary can handle, when your data doesn't fit a rigid relational schema (flexible document structure), or when you're optimizing for a specific access pattern that a specialized data store (Redis for caching, Elasticsearch for full-text search) handles better. Not because "NoSQL is faster" — a well-indexed PostgreSQL table handles very high load.

**Q3: What is a cache eviction policy and name three types?**
A: When a cache is full and a new entry must be stored, eviction decides which entry to remove. LRU (Least Recently Used): evict the entry that hasn't been accessed for the longest time — good general default. LFU (Least Frequently Used): evict the least-accessed entry. FIFO: evict the oldest entry regardless of access pattern. LRU is the most commonly used and the default to cite in interviews.

**Q4: How does consistent hashing differ from modulo hashing?**
A: With `hash(key) % n` (modulo hashing), adding or removing one node reshuffles ~n/(n+1) of all keys. With consistent hashing, nodes and keys are placed on a ring, and adding or removing a node only affects the keys immediately adjacent to it — about 1/n of keys. This makes cluster changes operationally safe for large datasets.

**Q5: What is the "write invalidation" vs. "write update" cache strategy?**
A: On a database write, you can either: (1) delete the corresponding cache entry (invalidation), forcing the next read to fetch fresh data from the database; or (2) update the cache entry with the new value. Invalidation is safer because it avoids race conditions (if two writers update the cache simultaneously, one update can overwrite a more recent change). Prefer invalidation.

**Q6: What causes "hot spots" in a sharded database?**
A: When many queries target the same shard (e.g., all "trending" content from the same time range in a range-sharded database, or all queries for a celebrity user on a user-ID sharded database). Solutions: add a random suffix to the shard key to spread hot keys across multiple shards (at the cost of requiring scatter-gather reads), or use consistent hashing with virtual nodes to distribute load more evenly.

## Practice Exercises

1. **Scaling progression**: A social media application currently uses one PostgreSQL database. It's hitting 10,000 reads/second and 500 writes/second. Describe the sequence of architectural changes you'd make, in order, to scale to 100,000 reads/second and 5,000 writes/second.

2. **Cache invalidation**: An e-commerce product catalog is cached in Redis with a 5-minute TTL. When a product price is updated, a user might see the old price for up to 5 minutes. Redesign the caching strategy to ensure users see updated prices within 10 seconds of a change.

3. **Shard key design**: Design the sharding strategy for a ride-sharing app's trip database. The primary queries are: find all trips for a specific rider, find all trips for a specific driver, and find all trips in a geographic area. What shard key would you choose and what are its limitations?

## Key Takeaways

- SQL databases handle most applications well; reach for NoSQL only when the access pattern or scale genuinely requires it.
- Replication = copies for redundancy and read scaling; sharding = partitioning for data volume. They solve different problems.
- Single-primary replication: writes to primary, reads to replicas; asynchronous replication introduces replication lag (AP trade-off).
- Consistent hashing minimizes key redistribution when nodes are added/removed — standard for distributed caches and databases.
- Cache-aside pattern: read from cache → miss → read from DB → populate cache → return. On write: update DB → delete cache entry.
- Cache invalidation on write (delete the entry) is safer than cache update (write the new value) — avoids race conditions.
