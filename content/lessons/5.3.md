# Data & Storage at Scale

Every application starts with a single database on a single machine. For a long time, that works fine. Then, one day, it doesn't: the data is too big, the queries are too slow, or too many users are writing at once. What do you do?

This lesson teaches the vocabulary and mental models for scaling data storage. More importantly, it teaches you *how to reason* about these decisions — because the right answer is never "just use Cassandra" or "just add caching." The right answer depends on your specific access patterns, consistency requirements, and failure modes. By the end of this lesson, you'll know how to think through those trade-offs and explain them clearly.

## Theory & Fundamentals

### SQL vs. NoSQL — The Real Question

When developers hear "at scale," many immediately reach for NoSQL. This is almost always the wrong instinct. To make a good decision, you first need to understand what problem each tool actually solves.

**Start here: What is SQL (relational)?**

A relational database stores data in tables, where each row is a record and each column is an attribute. Tables relate to each other through foreign keys. You enforce a schema — every row must have the right columns with the right types. And you get ACID transactions:

- **Atomic**: a transaction either fully commits or fully rolls back. No partial updates.
- **Consistent**: every transaction takes the database from one valid state to another.
- **Isolated**: concurrent transactions don't interfere with each other.
- **Durable**: once committed, a transaction survives crashes.

This is incredibly powerful. Consider a bank transfer: deduct $100 from Alice's account AND add $100 to Bob's account. These two operations must happen together or not at all. Without ACID, a crash between the two operations leaves Alice poorer and Bob no richer. A relational database guarantees this can't happen.

SQL databases also give you something NoSQL databases largely don't: **joins**. If you store users in one table and orders in another, you can efficiently query "all orders placed by users in California" without loading everything into memory first. The database optimizer figures out how to execute this efficiently.

**Why SQL is the right default for most systems**

PostgreSQL can handle tens of thousands of queries per second on a single machine. For most applications, that's more than enough. The developer productivity gains — strong schema, joins, transactions, mature tooling — are substantial. Don't sacrifice them without a concrete reason.

The concrete reasons to look elsewhere are:
1. Your write volume exceeds what a single primary can handle
2. Your data genuinely doesn't fit a relational model
3. You need a specific capability SQL doesn't have (e.g., full-text search, graph traversal)

**What is NoSQL, exactly?**

Here's a critical point that trips up many developers: **NoSQL is not one thing**. It's a catch-all label for "not a relational database," which covers wildly different systems with wildly different trade-offs. Saying "I'll use NoSQL" is like saying "I'll use a vehicle" — a bicycle and a cargo ship are both vehicles.

The main NoSQL families, and what they're actually for:

**Document stores (MongoDB, CouchDB)**

Documents stores save records as JSON-like documents — nested objects with any structure you want. There's no enforced schema: one document can have 3 fields, the next can have 30. This is genuinely useful when your "thing" is a self-contained document with nested data that you always read as a whole.

Example: a blog post with its title, body, author info, and an array of comments is a perfect document. You always load the whole post at once. The comments are part of the post, not a separate entity you join to. Forcing this into normalized relational tables adds joins with no benefit.

Document stores are *not* good when your data is truly relational — when you need to query across entities in flexible ways. Flexible schema is also a double-edged sword: it means you can add fields without migrations, but it also means you can accidentally have some documents with "email" and others with "emailAddress" and no database-level enforcement to catch the inconsistency.

**Key-value stores (Redis, DynamoDB in its pure form)**

The simplest possible model: a key maps to a value. Give me the key, I'll give you the value. That's it.

What you lose: there's no way to query by anything other than the key. You can't say "give me all users where age > 30." You can only say "give me the value for key 'user:123'."

What you gain: this operation is extraordinarily fast. Redis can handle a million operations per second on a single instance, with sub-millisecond latency. It's perfect for:

- **Caching**: store the result of an expensive computation. Key: the query parameters. Value: the result.
- **Session storage**: key is the session token, value is the user's session data.
- **Rate limiting counters**: key is "user:123:requests:2024-01-15-14:30", value is the count.
- **Leaderboards**: Redis sorted sets make this trivial.

**Column-family stores (Cassandra, HBase)**

These are confusingly named. They don't look like columns in the way you'd think. Think of them as being optimized for a very specific access pattern: "give me all records for this partition key, optionally filtered by a range of values in a second dimension."

Cassandra is designed for high write throughput across many nodes. It can ingest millions of writes per second by distributing writes across the cluster. This makes it good for time-series data: sensor readings, event logs, activity streams. The pattern is: partition by device ID, sort within the partition by timestamp. "Give me all readings for sensor 42 between 3pm and 4pm" is an efficient Cassandra query.

Cassandra does *not* support joins. It does not support arbitrary queries. You must design your schema around your queries, not around your domain model. This is a significant trade-off.

**Graph databases (Neo4j)**

When your data fundamentally *is* a graph — entities and the relationships between them — graph databases shine. In a relational database, traversing relationships (friends of friends of friends) requires recursive joins that grow expensive quickly. In a graph database, the relationships are the primary data structure, and traversals are efficient by design.

Use cases: social networks ("who are my 2nd-degree connections?"), recommendation engines ("users who bought X also bought Y"), fraud detection ("show me all accounts connected to this flagged account within 3 hops").

For most business applications, this isn't what you need. Your data might have relationships, but that doesn't make it a graph in the performance-critical sense.

**The real question: What are my access patterns?**

Don't start with "SQL or NoSQL?" Start with:

1. **How will I read this data?** By primary key only? By range? By full-text search? With flexible filters? Across multiple entities?
2. **How will I write this data?** Infrequently? In transactions with multiple tables? At very high volume?
3. **What consistency do I need?** Must reads immediately reflect writes? Or is a few seconds' delay acceptable?
4. **What's the shape of my data?** Tabular and relational? Nested documents? Flat key-value? Graph?

Answer these, and the right database usually becomes obvious.

**Common misconception: "NoSQL is faster than SQL"**

This is one of the most persistent myths in software engineering, and it's wrong. A well-indexed PostgreSQL query that returns one row by primary key is essentially as fast as a Redis key lookup — both hit an index, both return in under a millisecond. The database type doesn't determine speed; the access pattern and indexing do.

What NoSQL databases give you is not inherent speed, but:
- **Horizontal write scaling**: you can spread writes across many nodes (SQL's write bottleneck is usually a single primary)
- **Flexible schema**: no migrations needed when your document structure changes
- **Specialized access patterns**: each NoSQL type is optimized for one thing and does that one thing very well

Choosing MongoDB over PostgreSQL because "MongoDB is faster" is like choosing a bicycle over a car because "bicycles don't get stuck in traffic" — sometimes true in specific circumstances, but not a general principle.

### Replication — Surviving Failure and Scaling Reads

Once your database is critical infrastructure, a single server creates a single point of failure. A hard drive fails. A data center loses power. An OS update goes wrong. If your database is on one machine and that machine goes down, your application goes down.

**Why replicate?**

Replication serves two purposes:

1. **Fault tolerance**: if the primary server dies, a replica can take over. Your application keeps running. This is sometimes called "high availability."
2. **Read scaling**: reads can be served by any replica. If you have 5 replicas, your effective read capacity is roughly 5x. This is enormously valuable because most applications read far more than they write — a typical social app might be 95% reads, 5% writes.

**How primary-replica replication works**

The most common pattern is called primary-replica (also called master-slave, though the newer terminology is primary-replica or leader-follower).

The rules are simple: **all writes go to the primary**. The primary records the change in a log (called a write-ahead log in PostgreSQL, a binlog in MySQL). The replicas continuously read this log and apply the changes to their own copy of the data. Reads can go to any replica (or the primary).

```
                    ┌──────────────┐
  All writes ──────▶│   PRIMARY    │────▶ Write-ahead log
                    └──────────────┘
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌─────────┐  ┌─────────┐  ┌─────────┐
         │REPLICA 1│  │REPLICA 2│  │REPLICA 3│
         └─────────┘  └─────────┘  └─────────┘
              ▲            ▲            ▲
  Reads ──────┴────────────┴────────────┘
```

**Replication lag: the hidden problem**

In asynchronous replication (the default), the primary doesn't wait for replicas to confirm before returning success to the client. This means replicas are almost always slightly behind — maybe 10ms behind, maybe 2 seconds behind during high load. This gap is called **replication lag**.

Replication lag causes a subtle bug that's easy to miss: the read-your-own-writes problem.

Imagine a user changes their profile picture. The write goes to the primary. The application immediately redirects the user to their profile page, which reads from a replica. But the replica hasn't caught up yet. The user sees their old profile picture. They refresh. They see the old picture. They think the update failed, try again, and now you have two update operations in flight.

This is disorienting and erodes trust in your application.

**Handling replication lag: read-after-write consistency**

The solution is read-after-write consistency: after a user performs a write, route their next read to the primary (or wait for the replica to catch up to the write's timestamp).

A simple implementation: when you serve a write, return the timestamp of the write in a cookie. For the next N seconds, route that user's reads to the primary. After that, they can go back to replicas.

**Synchronous vs. asynchronous replication**

You can also configure replication to be synchronous: the primary waits for at least one replica to confirm it received the write before returning success to the client. This eliminates the replication lag problem for durability purposes — if the primary crashes immediately after a write, the replica has it.

The cost is latency. Every write now has to wait for a round-trip to a replica. Depending on network distance, this could add 1-50ms to every write. For a write-heavy application, this is significant.

Most production systems use **semi-synchronous replication**: one replica must confirm synchronously (so you don't lose data on primary failure), and remaining replicas replicate asynchronously (so you don't pay the latency for all of them).

### Sharding — When One Server Isn't Enough

Replication solves the read scaling and fault tolerance problems, but it doesn't solve the data volume problem. Every replica holds the full dataset. If your dataset is 10TB and your servers hold 2TB each, adding more replicas doesn't help — each replica still needs 10TB.

Sharding (also called horizontal partitioning) is the answer: split the data across multiple servers, where each server holds a subset. Instead of one server with all your user data, you have four servers — shard 1 holds users 1-25M, shard 2 holds users 25M-50M, and so on.

**Why sharding is a last resort**

Sharding introduces significant complexity. Before you shard, make sure you've exhausted:
1. Vertical scaling (bigger machine: more CPU, RAM, faster disk)
2. Read replicas (offload read traffic)
3. Caching (remove most read traffic from the database entirely)
4. Query optimization and better indexing

Most applications never need to shard. But when they do, it's usually because a single machine literally cannot hold the data or handle the write volume.

**Choosing a shard key — the critical decision**

When you shard, you decide what attribute determines which server a piece of data lives on. This is the shard key, and choosing it correctly is the most important architectural decision in a sharded system.

The shard key must satisfy two goals:
- **Even distribution**: no single shard should have dramatically more data or traffic than others
- **Query locality**: queries should hit as few shards as possible (ideally one)

These goals often conflict, and picking the wrong shard key is a common cause of production disasters.

**Option 1: User ID as shard key**

Take the user ID, apply some function, and that determines the shard. All data for user 123 is on the same shard. Any query scoped to a single user is guaranteed to hit only one shard — efficient.

The problem: **hot shards**. If some users generate vastly more data than others (celebrities, power users, bots), the shard holding those users gets overloaded while others sit idle. Your system is now as slow as your slowest shard.

**Option 2: Geographic sharding**

US users on shard 1, EU users on shard 2, APAC users on shard 3. This can satisfy data residency requirements (GDPR requires EU user data to stay in the EU). Queries from EU users hit only the EU shard.

The problem: user distribution by geography is uneven and changes with growth. Also, a user traveling abroad hits the "wrong" shard, requiring either redirects or cross-shard access.

**Option 3: Hash-based sharding**

Hash the shard key and take modulo the number of shards: `shard = hash(user_id) % num_shards`. This gives very even distribution — hash functions produce output that's uniformly spread.

The problem: it completely breaks range queries. "Give me all events between yesterday and today" can't be answered without querying every shard, because time-ordered values are scattered randomly across shards. Also, when you add a shard, the modulo changes, so nearly every key gets reassigned — requiring a massive data migration.

**Problems sharding introduces**

1. **Cross-shard queries**: a JOIN across data on different shards has to be done in application code — fetch data from each shard, combine it in memory. This is slow and complex.

2. **Cross-shard transactions**: if a transaction touches data on two shards, you need a distributed transaction protocol (two-phase commit). These are slow and complicated, and many NoSQL databases don't support them at all.

3. **Rebalancing**: as data grows, shards become uneven. Moving data between shards while the system is live is operationally difficult.

The general wisdom: design your schema so that queries you run most frequently access only one shard. Accept that some queries will require cross-shard scatter-gather, but make sure those queries are rare and low-priority.

### Consistent Hashing — Solving Shard Rebalancing

The problem with naive hash-based sharding is what happens when you add a server. With `hash(key) % 3` servers, key "abc" might map to server 2. Now you add a fourth server. With `hash(key) % 4`, the same key maps to server 1. Every key might need to move. Moving most of your data just to add one server is operationally catastrophic.

Consistent hashing solves this with an elegant idea: **place both servers and keys on a circular ring**.

Imagine the hash function outputs values from 0 to 2^32. Arrange these values in a circle (a ring). Place your servers at arbitrary positions on the ring. When you want to store a key, hash it to a position on the ring, then walk clockwise until you hit a server — that's where the key goes.

```
                   0
                 ┌──┐
             ┌───┤  ├───┐
        330 ─┤   └──┘   ├─ 30
             │  Server C │
    300 ─┐   │  (at 0)  │   ┌─ 60
         │   └───────────┘   │
         │                   │
    270 ─┤  Server B       Server A  ├─ 90
         │  (at 240)      (at 120)   │
         │                   │
    240 ─┘   ┌───────────┐   └─ 120
             │           │
        210 ─┤           ├─ 150
             └───────────┘
                  180
```

Now, when you add a new server, you place it on the ring. Only the keys that were "pointing to" the next server clockwise from the new server's position need to move — they now point to the new server. All other keys are unaffected. This is roughly `1/n` of your keys, not `n/(n+1)`.

Real systems also use "virtual nodes": each physical server is assigned multiple positions on the ring (virtual nodes). This ensures more even distribution and smoother rebalancing. A server with 3x the capacity gets 3x more virtual nodes.

Consistent hashing is now standard in distributed caches (Redis Cluster, Memcached), distributed databases, and CDN routing. Whenever you see the question "how do you add a cache node without invalidating everything?" — consistent hashing is the answer.

### Caching — Your Most Important Scaling Tool

Even with all the above, the database is almost always the bottleneck. A fast SQL query with a good index takes about 1-5ms. At 1,000 requests/second, that's 1,000-5,000 database calls per second. Add more users, and the database becomes the single choke point.

The solution: don't query the database for the same data repeatedly. Cache the result in memory.

A cache hit typically takes under 0.1ms and puts zero load on the database. For read-heavy workloads, caching can reduce database load by 90%+ while dramatically lowering latency. It's the single highest-leverage scaling technique available.

**Why caching works: the 80/20 rule of access patterns**

Most data is accessed extremely unevenly. A small fraction of your data (the most popular posts, the most viewed products, the most-accessed user profiles) accounts for the vast majority of reads. This "hot" data is exactly what caching is designed to serve. The cache can be much smaller than the database and still provide most of the benefit.

**Cache-aside (lazy loading) — the most common pattern**

```
Application on read request:
  1. Check the cache for key K
  2. Cache HIT: return the cached value immediately (done)
  3. Cache MISS:
       a. Query the database for K
       b. Store the result in the cache with a TTL
       c. Return the result

Application on write:
  1. Write the new value to the database
  2. Delete (not update) the cache entry for K
```

Why delete rather than update? Updating the cache risks a race condition: if two writes happen simultaneously and both update the cache, the slower one might overwrite the faster one's result, leaving stale data. Deletion is safe — the next read will fetch fresh data from the database.

This pattern is called "cache-aside" because the application manages the cache explicitly. The database knows nothing about the cache. The cache knows nothing about the database.

**Write-through caching**

An alternative: on every write, update both the database and the cache simultaneously.

```
Application on write:
  1. Write to the database
  2. Write to the cache

Application on read:
  1. Read from cache (always a hit for recently written data)
```

The cache is never stale — it always has the latest value. This is great for read performance.

The cost: every write is slower (two writes instead of one). And data written but never read still takes up cache space. Write-through is best for write-once, read-many workloads.

**Write-behind (write-back) caching**

For maximum write performance: write to the cache only. A background process asynchronously flushes cache changes to the database.

The serious risk: if the cache crashes before flushing, you lose data. Use write-behind only when data loss is acceptable (logs, metrics, analytics) or when you have a way to recover (the cache is itself replicated and durable).

**Cache eviction: what happens when the cache is full?**

Caches have a fixed memory limit. When that limit is reached and a new entry must be stored, something must be evicted. The most important eviction policy is **LRU (Least Recently Used)**: evict the entry that was last accessed longest ago.

LRU is a good default because of temporal locality: data that was accessed recently is likely to be accessed again soon. The access patterns that make caching effective (popular data gets accessed frequently) also make LRU effective (popular data stays in the cache).

Other policies:
- **LFU (Least Frequently Used)**: evict the entry accessed fewest times. Better for stable "hot" data that persists over time, but more complex to implement.
- **FIFO**: evict the oldest entry regardless of access. Simple but ignores access patterns entirely.
- **Random**: evict a random entry. Surprisingly effective in practice, with very low overhead.

**Cache invalidation: the hard problem**

There's a famous joke in computer science: "There are only two hard things in computer science: cache invalidation and naming things." Cache invalidation is hard because the cache and the database can get out of sync, and there's no general solution.

When data changes in the database, how do you know which cache keys to invalidate? If the cache key is simple (user:123) and you know you're updating user 123, it's straightforward: delete cache key "user:123". But what if you're caching the result of a complex query that joins multiple tables? Changing one table might invalidate dozens of different cached query results — and you might not know which ones without re-running the queries.

Practical approaches:

1. **Key-based invalidation**: structure cache keys to include the data's identity. When that data changes, delete the key. Simple and reliable for key-value style caches.

2. **TTL (Time-To-Live)**: every cache entry expires automatically after N seconds. You never have to think about invalidation — stale data just expires. The trade-off: until the TTL expires, users might see stale data.

3. **Version in the key**: include a version number or `updated_at` timestamp in the cache key: `user:123:v42`. When user 123 is updated to version 43, the new key is `user:123:v43`. The old key is never explicitly deleted — it just becomes unreachable and eventually gets evicted. This is sometimes called cache busting.

**TTL: setting the right expiry**

TTL is a simple but powerful tool. Every cache entry should have a TTL. Without one, stale entries live forever.

Setting the right TTL requires thinking about:
- **How often does this data change?** User profile photos change rarely; product inventory changes frequently.
- **How bad is stale data?** Serving an old product description for 5 minutes is fine; serving an old bank balance is not.
- **What's the load on the database?** A long TTL means fewer database calls. A short TTL means fresher data but more calls.

Common rule of thumb: set the TTL to the maximum staleness you can tolerate. If users can accept seeing a slightly old follower count for 60 seconds, use a 60-second TTL.

## Core Patterns / Techniques

### The Scaling Progression

When someone asks "how would you scale this database?" there's a standard progression to follow. Each step adds complexity; only proceed when the previous step is genuinely exhausted:

```
Step 1: Optimize queries and add indexes
        ↓ (still too slow or too many queries)
Step 2: Add read replicas; route reads to replicas
        ↓ (read load still too high)
Step 3: Add a caching layer (Redis) in front of the database
        ↓ (write load too high, or dataset too large)
Step 4: Shard the database by shard key
        ↓ (each shard still overloaded)
Step 5: Shard each shard (rare; usually redesign instead)
```

Most applications max out at Step 3. Sharding (Step 4) is a major architectural commitment that dramatically increases operational complexity.

### Caching Layer Anatomy

```
Client
  │
  ▼
API Server
  │
  ├──▶ Redis (cache)
  │         │ HIT: return immediately
  │         │ MISS: fall through to database
  │
  ▼
Database (PostgreSQL / MySQL)
```

The cache is always checked first. Only on a miss does the request reach the database, which then populates the cache for future requests.

### Database Indexing (Bonus Pattern)

An index is a separate data structure (typically a B-tree) that lets the database find rows matching a condition without scanning the full table.

Without an index on `user_id`, this query scans every row: `SELECT * FROM orders WHERE user_id = 123`. With an index, the database goes directly to the matching rows in O(log n) time.

Costs: indexes consume storage, and every write must update all relevant indexes. Add indexes on columns you filter and sort by frequently; avoid indexing columns that change constantly.

## Best Practices

- **Default to SQL** — PostgreSQL handles very high load when properly indexed and configured. Don't pre-optimize for scale you don't have.
- **Replicate before you shard** — replication is operationally much simpler and solves the fault-tolerance and read-scaling problems. Only shard when your dataset is literally too large for one machine, or your write volume exceeds what one primary can handle.
- **Cache on the read path, invalidate on the write path** — add caching incrementally where you see database load. For each write, think: "what cached data does this invalidate?"
- **Prefer cache-aside over write-through** for most use cases — lazy loading means you only cache what's actually requested, not everything you write.
- **Always set a TTL** — a cache with no TTL accumulates stale entries forever. Even a generous TTL (1 hour) prevents indefinite staleness.
- **Choose your shard key for your primary query** — the shard key you choose determines which queries are efficient (same-shard) and which are expensive (cross-shard). Design for the query you run most.
- **Test the unhappy paths for your cache** — what happens when Redis is down? Your application must degrade gracefully (fall back to the database) rather than throwing 500 errors.

## Common Interview Questions

**Q1: What is the difference between replication and sharding?**
A: Replication creates full copies of the dataset on multiple machines — every replica holds all the data. It solves two problems: fault tolerance (if the primary dies, a replica takes over) and read scaling (spread read traffic across replicas). Sharding splits the dataset across machines — each shard holds a different subset of the data. It solves data volume: when your dataset is too large to fit on one machine. You can use both simultaneously: shard the data, then replicate each shard for redundancy.

**Q2: What is replication lag and how do you handle it?**
A: Replication lag is the delay between a write being committed on the primary and being available on replicas (in asynchronous replication). It causes the read-your-own-writes problem: a user writes data, reads from a replica immediately, and doesn't see their own write because the replica hasn't caught up. Handle it with read-after-write consistency: route a user's reads to the primary for a short window after they perform a write, or include a write timestamp in responses and route reads to the primary until a replica confirms it's past that timestamp.

**Q3: When would you choose NoSQL over SQL?**
A: When a specific access pattern or constraint genuinely requires it. Use a document store when your data is self-contained nested documents with flexible schema. Use a key-value store for caching, sessions, or any lookup by a single key. Use Cassandra for very high write throughput with known access patterns. Use a graph database when your queries fundamentally traverse relationships. Don't choose NoSQL because "it's faster" — a well-indexed SQL database is fast. Choose it for the structural or scalability properties it offers.

**Q4: How does consistent hashing work and why does it matter?**
A: Consistent hashing maps both cache nodes and data keys to positions on a conceptual ring (using a hash function). A key is stored on the first node clockwise from its ring position. When you add or remove a node, only the keys adjacent to that node's ring position need to move — about 1/n of keys. With naive modulo hashing, adding one node forces nearly every key to a new server (since `hash(key) % n` changes to `hash(key) % (n+1)`). Consistent hashing makes adding or removing cache nodes operationally safe.

**Q5: Explain the cache-aside pattern and why you delete rather than update the cache on writes.**
A: Cache-aside: on read, check the cache first; on miss, query the database, populate the cache, return. On write, update the database, then delete the cache entry (don't update it). You delete rather than update to avoid a race condition: if two concurrent writes both try to update the cache, they might execute in an order different from the database commits, leaving a stale value in the cache. Deletion is always safe — the next read will fetch a fresh value from the database.

**Q6: What is a hot shard and how do you prevent it?**
A: A hot shard is a shard that receives disproportionately more traffic than others, becoming a bottleneck while other shards are idle. It happens when the shard key is poorly chosen — for example, sharding by user ID when a small number of celebrity users generate most of the traffic. Prevention: analyze your access patterns before choosing a shard key. If some keys are inherently "hotter" (celebrity accounts), consider a tiered approach: store hot-key data differently (replicated, or served from a cache layer), and only route normal users through sharding. You can also add random suffixes to shard keys to spread a single logical key across multiple shards, then aggregate on read.

**Q7: What is write-through caching and when would you use it over cache-aside?**
A: Write-through caching updates both the database and the cache on every write. Cache-aside (lazy loading) only populates the cache on a read miss. Write-through is better when: your data is frequently written and then immediately read (so cache-aside would cause cache misses right after writes), or when you can't tolerate even brief staleness. Cache-aside is better when: much of your written data is never read (write-through wastes cache space), or when you want to keep the caching logic simple and localized to the read path.

**Q8: What is the difference between LRU and LFU eviction, and when would you use each?**
A: LRU (Least Recently Used) evicts the item that was accessed longest ago — best for data with temporal locality, where recently accessed data is likely to be accessed again soon (most general-purpose caches). LFU (Least Frequently Used) evicts the item accessed fewest times overall — better for stable "working set" data where popular items should stay in cache even if not accessed in the last few minutes (product catalog for a retail site where the same 1,000 products are always popular). LRU is the safer default; LFU can suffer from "cache pollution" by old items that were briefly popular but are no longer relevant.

## Practice Exercises

**Exercise 1 — Scaling Progression (Beginner)**

A startup's application uses a single PostgreSQL database running on a medium-sized server. The team notices the `GET /products` endpoint is slow. Tracing shows it runs `SELECT * FROM products WHERE category = 'electronics'` without an index, and this category has 500,000 products. Walk through the steps you'd take, in order, to fix this — from query optimization through (if necessary) caching and replication. At each step, explain what problem you're solving.

Hint: Start with the cheapest fix (a database index) before reaching for architectural complexity.

**Exercise 2 — Cache Design (Intermediate)**

An e-commerce site caches product data in Redis. Product objects look like `{ id, name, price, inventory_count, description, images }`. The team caches the full object with a 10-minute TTL. They've noticed that when a product goes on sale (price changes), customers see the old price for up to 10 minutes. However, inventory_count changes on every purchase — if they cache inventory, the displayed count can be wrong. How would you redesign the caching strategy to: (a) show updated prices within 30 seconds of a change, (b) avoid the stale inventory problem, while (c) still caching as much as possible?

Hint: You don't have to cache the whole object as a unit.

## Key Takeaways

- SQL is the right default. It handles enormous load when properly indexed. Only reach for NoSQL when SQL's access patterns or scalability genuinely don't fit your problem.
- NoSQL is not one thing: document stores, key-value stores, column-family stores, and graph databases are fundamentally different tools for different problems. Know why you're choosing each.
- Replication copies the full dataset for fault tolerance and read scaling. Sharding splits the dataset across servers for data volume. They solve different problems and can be combined.
- Replication lag causes read-your-own-writes problems in async replication. Handle with read-after-write consistency: route reads to the primary for a short window after writes.
- Shard key selection is the most critical decision in a sharded system. Optimize for query locality — the most common queries should hit only one shard.
- Consistent hashing minimizes data movement when nodes are added or removed. It's the standard for distributed caches.
- Caching is your highest-leverage scaling tool. Even a small cache covering the most popular 1% of data can reduce database load by 50%+.
- Cache-aside is the most common caching pattern: check cache → miss → query DB → populate cache. On write: update DB → delete cache entry (not update — deletion avoids race conditions).
- Always set a TTL. Cache invalidation is hard; TTL is a safety net that prevents indefinite staleness.
