# Data & Storage at Scale

Once a system outgrows a single database on a single machine, a new set of trade-offs shows up — this unit is about the vocabulary for that transition.

## SQL vs. NoSQL trade-offs

**SQL** (relational) databases give you strong consistency, joins, and enforced schema/relationships — ideal when your data is genuinely relational and correctness (no orphaned or contradictory records) matters more than raw write throughput. **NoSQL** databases (document, key-value, wide-column, graph) trade some of that structure for horizontal scalability and flexible schemas — ideal when you need to scale writes massively, your data doesn't fit a rigid relational shape, or you're optimizing for a specific access pattern (e.g. a key-value store for session data). Neither is universally "better" — the right interview answer names the actual access pattern and consistency needs of the specific system being designed, not a blanket preference.

## Replication

Copying data across multiple database instances, for two reasons: **fault tolerance** (if the primary dies, a replica can take over) and **read scaling** (route read traffic across multiple replicas instead of hammering one instance). The common pattern is single-primary replication: all writes go to one primary, which asynchronously (or synchronously) propagates changes to replicas. Asynchronous replication is faster but has a "replication lag" window where a replica might briefly serve stale data — relevant to the CAP theorem trade-off from 5.1.

## Sharding / partitioning

Splitting one logical dataset **across multiple database instances**, each holding a subset of the data (as opposed to replication, where each instance holds a full copy). A common approach: shard by a key (e.g. `user_id % number_of_shards`, or a hash of the key) so each user's data always lands on the same shard. Sharding solves the problem replication doesn't — when the total dataset is too large for any single machine, no number of full replicas fixes that, since every replica would need to hold everything. The cost: cross-shard queries (joining data that lives on different shards) become much harder.

## CDN caching

A Content Delivery Network caches static assets (images, JS bundles, videos) at edge locations physically close to users, so a user in Mumbai doesn't fetch a static asset from a server in Virginia every time. This reduces latency and offloads traffic from your origin server. CDNs work well for content that's the same for every user and doesn't change often — they're the wrong tool for personalized, frequently-changing data.

## Cache-invalidation strategies

The hard part of any cache (CDN or Redis, see Unit 2.3) is knowing **when** cached data has gone stale. Common strategies: TTL-based expiry (simple, but data can be stale for up to the TTL window), explicit invalidation on write (more accurate, but requires every code path that mutates data to remember to invalidate — easy to miss one), and versioned/cache-busted URLs for static assets (append a content hash to the filename, so a new version is automatically a cache miss).

## Consistent hashing

A hashing technique used for both sharding and load balancing that minimizes redistribution when nodes are added or removed. With naive `hash(key) % number_of_nodes`, adding one node reshuffles almost every key's assignment. Consistent hashing maps both nodes and keys onto a conceptual ring, so adding or removing a node only affects the keys immediately adjacent to it on the ring — a small fraction, not everything. This is why it's the standard technique behind distributed caches and databases that need to scale nodes up and down without a full data reshuffle.

## Practice tip

Practice explaining replication vs. sharding as **two different problems** ("too much traffic" vs. "too much data") — conflating them is one of the most common system design interview mistakes.
