# Core Concepts (System Design)

System design is the skill of making big architectural decisions: how should multiple computers work together to serve millions of users reliably? Before you can design any specific system, you need to deeply understand a handful of core trade-offs that appear in every design problem. These aren't trivia to memorize — they're the reasoning tools you reach for when you're standing in front of a whiteboard trying to figure out what to build.

This lesson teaches those fundamentals from the ground up. By the end, you'll understand *why* each concept exists, not just what it means — and you'll be able to apply them to problems you've never seen before.

## Theory & Fundamentals

### Vertical vs. Horizontal Scaling

#### The Problem: Your App Gets Popular

Imagine you've built a web app. It runs on your laptop: one process handling requests, a database file on disk, and users are happy. Then something happens — you get featured on a popular blog, or go viral on social media — and suddenly you have 10,000 users instead of 100.

Your laptop starts struggling. Response times go from 50ms to 5 seconds. Then requests start failing entirely. The CPU is maxed out, memory is full, and the disk can't keep up with the database queries. You have a scaling problem.

What can you do?

#### Solution 1: Vertical Scaling (Scale Up)

The first instinct is to get a bigger machine. Instead of a laptop, buy a server. Instead of 8GB of RAM, get 256GB. Instead of 4 CPU cores, get 64. This is **vertical scaling** — making one machine more powerful.

This is the right first move. It's simple: you don't change your application code at all. You just migrate to a bigger box and everything works the same way, just faster.

But vertical scaling has two fundamental problems:

**Problem 1: There's a ceiling.** You can buy a machine with 64 cores and 512GB of RAM. But there's no machine with 1 million cores. At some point, you've bought the biggest box that exists, and if you need more capacity, you're stuck. The biggest machines are also extraordinarily expensive — a server with 192 cores and 6TB of RAM can cost hundreds of thousands of dollars per year.

**Problem 2: Single point of failure.** If that one giant machine crashes (and machines do crash — hardware fails, software bugs occur, someone trips over a power cable), your entire application goes down. Every user sees an error. For a business, that's a disaster.

```
Vertical Scaling:
  
  Small server     →   Medium server    →   Huge server
  [CPU: 4 cores]       [CPU: 32 cores]      [CPU: 128 cores]
  [RAM: 8 GB]          [RAM: 64 GB]         [RAM: 512 GB]
  
  ✓ Simple            ✓ Still simple       ✗ Extremely expensive
  ✓ No code changes   ✓ No code changes    ✗ Ceiling reached
                                           ✗ Still one point of failure
```

#### Solution 2: Horizontal Scaling (Scale Out)

The second approach is to add more machines and split the load across them. Instead of one huge server, you have ten normal servers — and when you need more capacity, you add more servers.

This is **horizontal scaling** — scaling out instead of up.

```
Horizontal Scaling:
  
  Load Balancer
       ↓
  ┌────┬────┬────┐
  │ S1 │ S2 │ S3 │   ← Multiple servers, each handling a portion of traffic
  └────┴────┴────┘
  
  ✓ No theoretical ceiling (just add more servers)
  ✓ If one server crashes, the others keep serving traffic
  ✓ Cloud providers make adding servers fast and cheap
```

Sounds great. Why doesn't everyone just do this from day one?

Because **horizontal scaling requires your application to be designed for it**, and most naive implementations aren't. To understand why, you need to understand the concept of stateless services.

#### The Key Prerequisite: Stateless Services

Here's the problem. Imagine a user logs in to your app. Your server creates a "session" — it remembers that user #42 is logged in and stores that fact in memory on Server 1. Now the user makes their next request (clicks a link). The load balancer looks at its list of servers and decides to send this request to Server 2. Server 2 has no idea who this user is. It has no session data for them. The user appears to be logged out.

This is the **sticky session problem**, and it's the central challenge of horizontal scaling.

```
The Problem with Stateful Servers:

Request 1 (login) → Server 1
  Server 1 memory: { userId: 42, isLoggedIn: true }

Request 2 (view profile) → Load Balancer → Server 2 (oops!)
  Server 2 memory: { }  ← no session data!
  Result: User is logged out. Broken experience.
```

There are two ways to handle this:

**Approach A: Sticky Sessions (a workaround, not a fix)**  
Configure the load balancer to always send user #42's requests to Server 1. Now session data is safe. But you've broken the load balancer's ability to distribute traffic freely. If Server 1 is overwhelmed and Server 2 is idle, you can't move user #42's traffic. And if Server 1 crashes, all users whose sessions live there are suddenly logged out. This is treating the symptom, not the disease.

**Approach B: Stateless Services (the real fix)**  
Don't store session data on the server at all. Instead, store it in a shared external store — a database or a fast in-memory store like Redis — that every server can access. When a request arrives, the server reads the session data from Redis, processes the request, and returns a response. The server itself holds nothing between requests.

```
Stateless Services: Any Server Can Handle Any Request

Request 1 (login) → Server 1
  Server 1: reads nothing from memory, writes session to Redis
  Redis: { sessionId: "abc123", userId: 42, isLoggedIn: true }

Request 2 (view profile) → Server 2
  Server 2: reads session "abc123" from Redis → user is logged in ✓
  Works perfectly, even though a different server handled it
```

A **stateless service** holds no user-specific data in its own memory between requests. All persistent state lives in a shared external store. This is the single most important architectural decision for horizontal scalability: if any server can handle any request, adding servers is just a configuration change.

#### The Architecture Progression

In practice, systems grow through a predictable series of stages:

```
Stage 1: Single server (works for small apps)
  [Server: app + database]

Stage 2: Vertical scaling (when traffic grows)
  [Bigger Server: app + database]

Stage 3: Separate the database, add a load balancer
  [Load Balancer]
       ↓
  [App Server 1] [App Server 2]    ← multiple stateless app servers
       ↓               ↓
  [Shared Database]

Stage 4: Database becomes the bottleneck (reads dominate)
  [Load Balancer]
       ↓
  [App Server 1] [App Server 2]
       ↓
  [Primary DB] → [Read Replica 1] [Read Replica 2]
                 ← app servers read from replicas, write to primary

Stage 5: Database write throughput is the bottleneck (sharding)
  Split data across multiple databases by some key (user ID % 4, for example)
  [DB Shard 0] [DB Shard 1] [DB Shard 2] [DB Shard 3]
```

Each stage adds complexity but solves a real problem. The art of system design is knowing which stage you actually need for your requirements.

### CAP Theorem

#### Why Does This Exist?

As soon as you have more than one server holding data, you have a distributed system. And distributed systems have a fundamental problem that single-server systems don't: **the computers in the system can lose the ability to talk to each other**.

Networks fail. Cables get cut. Hardware malfunctions. Routing software has bugs. In any distributed system running long enough, you will experience a **network partition** — a situation where some nodes in your system can't communicate with other nodes.

To make this concrete: imagine you run a bank with two data centers, one in New York and one in London. Both centers hold a copy of account data. A submarine cable is cut, and for 30 minutes, New York and London can't communicate with each other. Users are still making requests. What should each data center do?

This is the problem CAP theorem addresses.

#### The Three Letters

**C — Consistency**  
Every read returns the most recent write. If you write a value and then immediately read it (from any node in the system), you get back the value you just wrote. All nodes see the same data at the same time.

In the bank example: both New York and London always show the same account balance. If you withdraw $100 in New York, London immediately knows you only have $X-100 left.

**A — Availability**  
The system always responds to requests. Every request gets a response — not an error, not a timeout. It might not be the freshest data, but you always get something back.

In the bank example: both New York and London always respond to requests, even if the cable is cut. They just might show different balances temporarily.

**P — Partition Tolerance**  
The system keeps operating even when network partitions occur. If New York and London lose communication, both sides keep working instead of shutting down entirely.

#### Why You Always Need P

Here's the insight that makes CAP theorem practically useful: **in a real distributed system, you cannot avoid network partitions**. Networks fail. It's not a matter of if — it's when. If you're not partition tolerant, your entire system goes down whenever there's a network hiccup. That's not a viable option for any production system.

So the real question is: **given that a network partition will happen, what do you sacrifice — Consistency or Availability?**

You're not choosing between C, A, and P. You're choosing between CP (consistency + partition tolerance) and AP (availability + partition tolerance). The real trade-off is: **during a partition, do you reject requests to stay consistent, or do you serve possibly stale data to stay available?**

#### CP Systems: Consistency Over Availability

During a partition, a CP system will refuse to serve requests (or will serve errors) rather than risk serving inconsistent data.

**When is this the right choice?**

- **Banking and financial systems.** If you withdraw money in New York, London must not also allow you to withdraw the same money. Better to show a user an error ("service temporarily unavailable") than to allow them to overdraw their account.
- **Stock trading.** A trade at the wrong price due to stale data could cost a company millions. Reject the trade if you can't guarantee consistency.
- **Inventory management.** If there's one item left in stock, better to show "out of stock" to some users than to sell it to multiple users simultaneously.

Examples of CP databases: traditional relational databases (PostgreSQL with a primary), HBase, Zookeeper.

#### AP Systems: Availability Over Consistency

During a partition, an AP system keeps serving requests, but it might return stale data. It accepts that different nodes might show slightly different data for a period of time (eventual consistency — they'll sync up once the partition heals).

**When is this the right choice?**

- **Social media likes and view counts.** If Twitter shows 10,423 likes and another server shows 10,421, nobody is harmed. The counts will sync up soon. Showing an error is worse than showing a slightly off count.
- **Shopping cart.** Amazon famously chose AP for their cart system. They'd rather let you add an item (even if they're not 100% sure you haven't added it elsewhere) than show you an error. Conflicts (duplicate items) can be resolved later.
- **DNS.** DNS updates (like changing where a domain points) can take up to 48 hours to propagate globally. DNS is inherently eventually consistent. This is accepted because availability is critical.

Examples of AP databases: Cassandra, CouchDB, DynamoDB (configurable).

#### The Common Misconception

Many people hear "CAP theorem" and think it means "a distributed system can only have two of these three properties at all times." That's not accurate.

**CAP only applies during a network partition.** When your network is healthy and all nodes can communicate freely, you can have all three: consistency (everyone sees the same data), availability (everyone gets responses), and partition tolerance (you're designed to handle partitions, even though none is occurring right now).

The theorem says: **when a partition occurs, pick one of C or A to sacrifice**. When everything is working, you don't have to sacrifice anything.

```
┌─────────────────────────────────────────┐
│   Network is healthy                    │
│   ✓ Consistency                         │
│   ✓ Availability                        │ ← No sacrifice needed
│   ✓ Partition Tolerance                 │
└─────────────────────────────────────────┘
               ↓ Network partition occurs
┌─────────────────────────────────────────┐
│   YOU MUST CHOOSE:                      │
│   CP: Reject requests, stay consistent  │
│   AP: Serve stale data, stay available  │
└─────────────────────────────────────────┘
```

### Latency vs. Throughput

#### A Restaurant Analogy

Imagine two restaurants:

**Restaurant A** is a fine dining establishment. When you order, a chef personally prepares your dish. From order to plate: 45 minutes. But the restaurant only seats 20 people.

**Restaurant B** is a fast-food chain. From order to getting your food: 3 minutes. And they serve 500 customers per hour.

- **Latency** is how long one request takes: the time from ordering to getting your food.
- **Throughput** is how many requests the system handles per unit time: how many customers served per hour.

Restaurant A has low throughput but the food is worth waiting for (let's say). Restaurant B has high throughput but you're eating it in 3 minutes.

Notice something important: these are independent axes. You can have:
- Low latency + low throughput (fast but can't serve many people)
- High latency + high throughput (slow per request, but process huge volumes)
- Low latency + high throughput (the holy grail — also the hardest)

#### Why They Can Conflict: The Batching Trade-off

One of the most common patterns for improving throughput is **batching** — instead of processing one request at a time, collect multiple requests and process them together.

Imagine a database that can write 100 rows per second if inserting them one at a time, or 10,000 rows per second if inserting them in batches of 1,000. Batching gives 100x better throughput!

But there's a cost. To batch 1,000 rows, you have to wait until you've collected 1,000 rows. If rows arrive at a rate of 10 per second, you're waiting 100 seconds to fill a batch. Every row sits in a queue for up to 100 seconds before it's written.

```
Individual writes:    request → [process immediately] → done   (low latency, low throughput)

Batched writes:       request → [wait... wait... wait... batch full] → [process all at once] → done
                                (100 seconds of latency, 100x better throughput)
```

This is the fundamental tension: **optimizing for throughput often means accepting higher latency, and optimizing for latency often limits throughput**.

#### Real-World Examples

**Low-latency requirements dominate:**

- **Real-time multiplayer games**: a 100ms delay feels like lag. If your shot takes 100ms to register, you'll lose. Throughput (how many shots per second) matters less; each one must respond instantly.
- **High-frequency trading**: traders make money by executing orders milliseconds before competitors. A system that takes 50ms instead of 5ms loses money. Each trade is worth executing fast.
- **Interactive UIs**: a user who clicks a button expects a response within 200ms or it feels broken. You can't batch user clicks.

**High-throughput requirements dominate:**

- **Data pipelines**: processing server logs, training machine learning models, aggregating analytics. No human is waiting on a specific result. You want to process 1 billion records in 1 hour. Whether each record takes 1ms or 100ms doesn't matter as long as the batch finishes in time.
- **Email delivery**: nobody expects email to arrive in 10ms. Bulk email systems batch and queue heavily to maximize delivery throughput.
- **Batch ETL jobs**: nightly database migrations, report generation. Latency of minutes is fine.

**Most web applications: balance both:**

The sweet spot for typical consumer-facing apps is: respond to each request in under 200ms (latency) while handling thousands of concurrent requests (throughput). Achieving this requires careful design — caching, efficient database queries, and horizontal scaling — but it's the default target.

#### The Interview Implication

When you hear a system design question, one of your first questions should be: "What are the latency requirements? What are the throughput requirements?" These answers fundamentally change the design. A system that must respond in 10ms cannot use the same architecture as one where 5-second responses are acceptable.

### Availability: Understanding the Nines

#### What Do the Numbers Actually Mean?

Availability is expressed as a percentage of uptime over a year. The percentages look small, but the real-world impact is large:

| Availability | "Nines" | Downtime per Year | Downtime per Month |
|---|---|---|---|
| 99% | Two nines | ~87.6 hours | ~7.3 hours |
| 99.9% | Three nines | ~8.76 hours | ~43.8 minutes |
| 99.99% | Four nines | ~52.6 minutes | ~4.4 minutes |
| 99.999% | Five nines | ~5.26 minutes | ~26.3 seconds |

Let that sink in. **99% availability means your app could be down for almost 4 days per year**. If you're running an e-commerce site during the holiday season, 4 days of downtime could cost millions of dollars.

99.9% is often the default target for internal tools and low-stakes applications. 99.99% is typical for important consumer services. 99.999% (five nines) is rare and extremely expensive — reserved for systems where downtime has catastrophic consequences (hospital systems, financial infrastructure).

#### Why Each Additional Nine Gets Dramatically Harder

Going from 99% to 99.9% means reducing downtime from 87.6 hours to 8.76 hours. That might just require fixing the most common failure mode.

Going from 99.9% to 99.99% means reducing downtime from 8.76 hours to 52 minutes. You have to fix every failure mode that caused the previous 8+ hours of downtime — not just the biggest one, but all of them.

Going from 99.99% to 99.999% means you have 52 minutes to work with and you need to get down to 5. At this level, you're handling scenarios like: a single rack in one data center loses power, and your system must automatically route traffic to another data center with no user-visible interruption — in seconds.

Each additional nine requires handling failure modes that are increasingly rare, increasingly costly to engineer for, and increasingly complex in their interactions.

#### Techniques That Buy You More Nines

**Redundancy (Multiple Instances)**  
If a single server has 99% uptime, two independent servers each with 99% uptime have a combined downtime of only when *both* are down simultaneously: 1% × 1% = 0.01% → effectively 99.99% availability. Running multiple instances behind a load balancer is the most fundamental availability technique.

**Health Checks and Automatic Failover**  
The load balancer periodically checks if each server is healthy. If a server stops responding, the load balancer stops sending traffic to it within seconds. Users experience a brief hiccup (the in-flight requests to that server fail) but traffic is quickly rerouted. Without automatic failover, you'd need a human to notice the failure and intervene — which might take hours.

**Geographic Distribution**  
An entire data center can go down: power outages, natural disasters, network outages. Running in multiple geographic regions (e.g., US-East, US-West, Europe) means a regional failure only affects users in that region. With DNS-level failover, traffic can be rerouted to another region automatically.

**Graceful Degradation**  
Instead of failing completely when a dependency is down, return a partial response. If the recommendation service is down, show the feed without recommendations instead of showing an error. Users get a degraded experience instead of no experience — which is often acceptable and much better for business continuity.

#### The Key Business Question

Before designing for high availability, ask: **what is the business cost of N minutes of downtime per year?**

If the answer is "a few angry emails," you probably need 99.9% (three nines). If the answer is "we lose $50,000 per hour of downtime and it makes the news," you need 99.99% or better. The engineering investment to go from three nines to four nines is substantial — you should be able to justify it with real numbers.

## Core Patterns / Techniques

### Back-of-Envelope Estimation: The Skill of Informed Guessing

Back-of-envelope estimation is the practice of doing rough math — in your head or on a whiteboard — to figure out whether a proposed design can actually work at the stated scale. It's not about getting the exact answer. It's about finding the right order of magnitude.

The point of this exercise isn't the number itself — it's what the number reveals about where the hard problems are.

#### The Building Blocks: Numbers to Internalize

Before you can estimate anything, you need a feel for some basic numbers:

```
Time units:
  1 second = 1,000 milliseconds
  1 day = 86,400 seconds ≈ 100,000 seconds (close enough for estimation)
  1 month ≈ 30 days = 2.6 million seconds ≈ 3 million seconds
  1 year ≈ 365 days = 31.5 million seconds ≈ 30 million seconds

Storage units:
  1 KB = 1,000 bytes
  1 MB = 1,000 KB = 1,000,000 bytes
  1 GB = 1,000 MB
  1 TB = 1,000 GB
  1 PB = 1,000 TB

Useful storage benchmarks:
  A short text tweet: ~280 bytes ≈ 300 bytes
  A typical metadata record: ~1 KB
  A compressed web image: ~300 KB
  An HD photo: ~3 MB
  A 4-minute MP3: ~5 MB
  An HD movie: ~3-5 GB

Server throughput:
  A simple web server: ~10,000 requests/second
  A database query: ~1-10ms (so one DB server: ~100-1,000 queries/sec)
  SSD read speed: ~500 MB/s
  Network: ~1-10 Gbps in a data center

Common read/write ratios:
  Twitter: heavily read-skewed (~15:1)
  Instagram: very read-heavy (~100:1 or more)
  Email: roughly balanced
```

#### A Complete Walk-Through: Estimating Twitter's Scale

Let's work through a realistic estimation for a Twitter-like system. The goal: figure out how much storage we need and how many reads/writes per second we're handling, so we know what to design for.

**Step 1: State your assumptions**

- 300 million daily active users (DAU)
- Average user posts 1 tweet per day
- Average user reads their feed 10 times per day
- Each tweet: 280 characters of text + metadata = ~300 bytes average
- System stores tweets for 5 years

**Step 2: Calculate write throughput**

Tweets per day = 300M users × 1 tweet/user = 300 million tweets/day

Tweets per second = 300M tweets/day ÷ 100,000 seconds/day = **3,000 tweets/second**

That's the write throughput the system must handle.

**Step 3: Calculate read throughput**

Feed reads per day = 300M users × 10 reads/user = 3 billion reads/day

Reads per second = 3B ÷ 100,000 = **30,000 reads/second**

Read:write ratio = 30,000 / 3,000 = **10:1** — reads dominate.

This tells you immediately: **optimize for reads**. Your architecture should have caching, read replicas, and CDN in it. Write scaling is almost a secondary concern compared to making reads fast.

**Step 4: Calculate storage**

Storage per day = 300M tweets × 300 bytes = 90 GB/day ≈ **100 GB/day**

Storage per year = 100 GB × 365 = **36.5 TB/year**

Storage for 5 years = 36.5 TB × 5 = **~180 TB**

Note: this is only for tweet text. If you store images and videos, multiply by 100-1000x — media storage would dominate completely.

**Step 5: Calculate bandwidth**

Assuming each tweet served is ~300 bytes and we're serving 30,000 reads/second:

Bandwidth = 30,000 requests/second × 300 bytes/request = 9 MB/second ≈ **~10 MB/s outbound**

For a major service, this is very manageable. But if tweets included images (300 KB each), that's 30,000 × 300 KB = **9 GB/second** — a completely different problem requiring CDN.

**Step 6: What does the math tell you?**

- Reads dominate writes 10:1 → you need aggressive caching (Redis, CDN for media)
- Storage is manageable for text (~180 TB over 5 years) → text isn't your problem
- Media changes everything → a CDN is mandatory if you serve images/video
- 3,000 writes/second → a single primary database can't handle this → you'll need sharding or a write-optimized store

**This is the point of estimation**: you didn't design anything yet, but you already know your most important design decisions.

### Stateless Services

A stateless service holds no user-specific data in memory between requests. All session or user state lives in a shared external store (database, Redis) rather than in the server process itself.

This deserves a concrete before/after comparison:

```
Stateful (problematic):
  
  Server 1 memory: { sessionId: "abc", userId: 42, cart: [...] }
  Server 2 memory: { sessionId: "xyz", userId: 99, cart: [...] }
  
  Problem: User 42's next request MUST go to Server 1.
  If Server 1 is overloaded or crashes, User 42's session is gone.

Stateless (correct):
  
  Server 1 memory: { }  ← empty, no user state
  Server 2 memory: { }  ← empty, no user state
  Redis: { "abc": { userId: 42, cart: [...] }, "xyz": { userId: 99, ... } }
  
  Any server reads from Redis and can handle any request.
  If Server 1 crashes, Server 2 picks up with no data loss.
  If you add Server 3, it immediately handles full load.
```

The statefulness lives in the data store, not the app server. App servers become interchangeable. This is the prerequisite for seamless horizontal scaling.

## Best Practices

- **Always clarify requirements before designing.** Ask: how many users? Read-heavy or write-heavy? What's the acceptable latency? What's the availability requirement? The answers fundamentally change the design. A system designed for 1,000 users/day looks completely different from one designed for 100M users/day.
- **Do rough capacity math before proposing solutions.** The estimate often reveals the actual bottleneck. Don't propose a caching layer if your math shows the bottleneck is write throughput — you'd be solving the wrong problem.
- **State trade-offs explicitly.** "This choice gives us lower latency but more complexity" is senior-level thinking. Interviewers are evaluating your ability to reason about trade-offs, not your ability to recite correct answers.
- **Distinguish CAP during partitions vs. normal operation.** CAP only forces a choice when a network partition is occurring. During normal operation, well-designed systems appear to offer all three properties.
- **Don't over-engineer for scale you don't have.** A startup with 1,000 users doesn't need sharding. Pick the simplest design that meets current requirements and has a clear upgrade path.
- **Design for failure explicitly.** Ask: "What happens when this component fails?" If the answer is "everything breaks," you have a single point of failure to address.

## Common Interview Questions

**Q1: What is horizontal vs. vertical scaling and when would you choose each?**
A: Vertical scaling means making one machine more powerful (more CPU, RAM). It's simple — no code changes — but has a hard ceiling on how big one machine can be and creates a single point of failure. Horizontal scaling means adding more machines and distributing load across them. It scales much further and eliminates single points of failure, but requires your application to be stateless (any server can handle any request). In practice: start with vertical for simplicity, design for horizontal when you anticipate significant growth. The key signal that you need horizontal scaling: you're running the biggest machine that exists, or you need to eliminate a single point of failure.

**Q2: Explain CAP theorem in plain terms. Give a concrete example of a CP vs. AP choice.**
A: CAP theorem says: in a distributed system that can experience network partitions (and real systems always can), you have to choose whether to prioritize consistency or availability when a partition occurs. CP example: a banking system. If New York and London data centers lose connectivity, the London system should reject transaction requests rather than risk double-spending someone's money. AP example: a social media like count. If servers can't communicate, it's fine to show a slightly stale count (10,423 vs. 10,421) — eventually they'll sync. The key insight: P is not really a choice. You always need partition tolerance in a real distributed system. The real choice is C vs. A during a partition.

**Q3: What is the difference between latency and throughput? Can a system be optimized for both simultaneously?**
A: Latency is how long one request takes (milliseconds). Throughput is how many requests the system handles per unit time (requests per second). They often trade off against each other: batching (grouping many requests together) dramatically increases throughput but increases latency (each request waits for the batch to fill). A real-time game needs sub-10ms latency and can sacrifice throughput. A data pipeline needs maximum throughput and can tolerate high per-record latency. Most web apps balance both: < 200ms latency while handling thousands of requests per second. Achieving both simultaneously requires horizontal scaling, caching, and efficient algorithms.

**Q4: What does "five nines availability" mean in practice? Why is it so hard to achieve?**
A: 99.999% availability means approximately 5 minutes of total downtime per year. Achieving it requires that every possible failure mode be handled automatically: server failures route around within seconds, entire data center failures trigger automatic failover to another region, deployments happen without any downtime. Each additional "nine" requires handling rarer and more complex failure scenarios. Most systems don't need five nines — three nines (8.76 hours/year downtime) is often sufficient and dramatically simpler to achieve.

**Q5: Why must services be stateless to scale horizontally?**
A: If a server stores session data in its own memory, the load balancer must always send that user's requests to the same server (sticky sessions). This prevents you from freely distributing load, complicates failure recovery (if that server dies, the session data is lost), and limits how many servers you can effectively use. Stateless services store all user state in an external shared store (Redis, database) so any server can handle any request. Adding a new server immediately increases capacity with no coordination needed.

**Q6: Walk me through a back-of-envelope estimation for a system. What's the point of doing it?**
A: The point is to identify the real bottleneck before you start designing. For example, estimating Twitter: 300M DAU × 10 feed reads/day = 3 billion reads/day = 30,000 reads/second. 300M DAU × 1 tweet/day = 3,000 writes/second. Read:write ratio = 10:1 → reads dominate → invest in caching and read replicas rather than write optimization. Storage: 3,000 tweets/second × 300 bytes = ~1 MB/second → ~85 GB/day of text data → manageable, but add media and you need CDN. The estimate shapes the entire design by revealing where the hard problems actually are.

A company's internal dashboard currently runs on a single EC2 instance and has 98% availability (about 175 hours of downtime per year). They want to reach 99.9%. Design the changes to the infrastructure that would get them there. What are the most likely causes of the current downtime? What architectural decisions will reduce each cause?

**Exercise 5 — Throughput vs. Latency Trade-off (Advanced)**  
You're designing a logging system that receives log messages from 1,000 servers and writes them to a database. Currently you write each log message immediately as it arrives (low latency, low throughput). You need to increase throughput 50x. Design a batching system. What parameters do you tune (batch size, flush interval)? How does each parameter affect latency? What happens to logs in memory if your logging server crashes before flushing a batch? How do you handle that risk?

## Key Takeaways

- Vertical scaling (bigger machine) is simple but has a ceiling and a single point of failure. Horizontal scaling (more machines) scales further and improves reliability but requires stateless services.
- Stateless services are the prerequisite for horizontal scaling — store all user state in external shared stores (Redis, database), not in server memory.
- CAP theorem forces a choice during network partitions: CP systems reject requests to stay consistent (good for banking); AP systems serve possibly stale data to stay available (good for social feeds). Partition tolerance is non-negotiable in real distributed systems.
- Latency (how long one request takes) and throughput (how many requests per unit time) are different dimensions that often trade off against each other. Know which one your system needs to optimize for.
- Availability nines: 99% = 87 hours of downtime/year; 99.9% = 8.7 hours; 99.99% = 52 minutes; 99.999% = 5 minutes. Each additional nine requires handling progressively rarer failure scenarios.
- Back-of-envelope estimation reveals the actual bottleneck before you commit to a design. The goal isn't precision — it's finding the right order of magnitude so you know what to solve.
- Always state trade-offs explicitly in system design discussions. That's how interviewers evaluate senior-level thinking.
