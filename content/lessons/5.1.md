# Core Concepts (System Design)

Every system design answer, no matter the specific question, draws on the same handful of core trade-offs. Get these solid before touching specific "design X" problems.

## Theory & Fundamentals

### Vertical vs. Horizontal Scaling

**Vertical scaling** (scale up): give one machine more CPU/RAM. Simple, but has a hard ceiling (there's a biggest machine you can buy) and creates a single point of failure. **Horizontal scaling** (scale out): add more machines and distribute load across them. More complex (now you need load balancing, and your app must be stateless or share state externally), but scales much further and improves fault tolerance — losing one of ten machines is a blip, not an outage.

The general industry direction for anything expected to grow: design for horizontal scaling from the start, even if you only run one instance today. Designing stateless services (no local session state) is the prerequisite — if each request can be handled by any server, adding servers is seamless.

### CAP Theorem

In a distributed system, when a network partition occurs (some nodes can't talk to others), you must choose between:

- **Consistency** — every read gets the most recent write, or an error.
- **Availability** — every request gets a response, even if it might not reflect the latest write.

You can't have both **during a partition** (you can always have both when the network is healthy — CAP is specifically about the partition case). This is why different databases make different defaults: traditional relational databases lean CP (reject requests rather than serve stale data), many NoSQL stores lean AP (serve slightly stale data rather than error out). The interview-relevant skill: name which one a specific system needs ("would you rather show a slightly outdated cart, or show an error?") rather than just reciting the acronym.

### Latency vs. Throughput

**Latency** is how long a single request takes. **Throughput** is how many requests the system handles per unit time. These aren't the same axis — a system can have low latency but low throughput (fast per-request, but can't handle many at once), or high throughput but higher latency (batches requests to process many at once, at the cost of per-request speed). Optimizing for one can hurt the other; know which one a given problem actually cares about before proposing a solution.

Typical interview framing: "The feed must load in under 200ms" (latency target). "The system must handle 10,000 writes per second at peak" (throughput target). These drive different design choices.

### Availability

Usually expressed as a percentage of uptime:
- 99% ("two nines"): ~87.6 hours downtime/year
- 99.9% ("three nines"): ~8.7 hours downtime/year
- 99.99% ("four nines"): ~52 minutes downtime/year
- 99.999% ("five nines"): ~5 minutes downtime/year

Each additional nine is dramatically harder and more expensive. The primary technique for high availability is **redundancy**: no single point of failure. Multiple instances behind a load balancer, database replicas, multi-region deployment for the most demanding requirements.

## Core Patterns / Techniques

### Estimating Scale

Before designing anything, back-of-envelope math tells you where the hard problems are:

```
Example: Design Twitter's feed
- 300M daily active users
- 200M tweets/day = ~2,300 writes/second
- Feed reads: each user checks feed 10x/day = 3B reads/day = ~35,000 reads/second
- Read:write ratio ≈ 15:1 → optimize for reads

Storage: 100 bytes/tweet × 200M tweets/day = 20GB/day
         = ~7TB/year of tweet data

Conclusion: reads dominate → caching is critical; write throughput is manageable.
```

This calculation tells you to invest in a read-optimized design (caching, CDN, fan-out) rather than worrying about write scaling first.

### Stateless Services

A stateless service holds no user-specific data in memory between requests. All session or user state lives in a shared store (database, Redis) rather than in the server process. This is what makes horizontal scaling seamless — any server can handle any request, so adding servers is just a configuration change.

Stateful services (servers that remember which users they're serving) require sticky sessions, which complicates load balancing and makes scale-out harder.

## Best Practices

- **Always clarify requirements first** — "how many users?", "read-heavy or write-heavy?", "strong or eventual consistency?" — before drawing any diagrams.
- **Do rough capacity math** before proposing solutions — it often reveals which component is actually the bottleneck.
- **Distinguish "can't have both" from "which is the default"** — CAP says you can't have consistency and availability *during a network partition*, not in general.
- **Name trade-offs explicitly** — "this choice gives us X but costs Y" demonstrates senior-level thinking and is what interviewers are actually evaluating.

## Common Interview Questions

**Q1: What is horizontal vs. vertical scaling and when would you choose each?**
A: Vertical (scale up): bigger machine. Simple, no code changes, but has a ceiling and is a single point of failure. Horizontal (scale out): more machines behind a load balancer. Requires stateless services, but scales further and improves fault tolerance. Use vertical for early simplicity; design for horizontal when you anticipate significant growth.

**Q2: Explain CAP theorem in your own words.**
A: In a distributed system that can experience network partitions, you must choose between consistency (every read reflects the latest write) and availability (every read gets a response). You can't guarantee both when nodes can't communicate. The choice depends on the business: a banking system chooses consistency (never show stale balances); a social feed chooses availability (a slightly outdated post count is fine).

**Q3: What is the difference between latency and throughput?**
A: Latency = how long one request takes (milliseconds). Throughput = how many requests the system handles per second. A queue-based system can have high throughput but high latency (processes many things but each waits in a queue). An in-memory cache has low latency but limited throughput (one machine, limited connections). Optimize for the one your requirements actually specify.

**Q4: What does "five nines availability" mean in practice?**
A: 99.999% uptime = about 5 minutes of total downtime per year. Achieving this typically requires multi-region deployment (a region-wide outage is planned for), automatic failover, and the ability to deploy without downtime. It's expensive and most systems don't need it — three nines (8.7 hours/year) is often sufficient.

**Q5: Why must services be stateless to scale horizontally?**
A: If a server stores session data locally, a user's next request must go to the same server (sticky sessions). This complicates load balancing, prevents failed servers from being removed cleanly, and limits how much you can distribute load. Stateless services can route any request to any server, making scale-out trivial.

**Q6: What does back-of-envelope calculation tell you in a system design interview?**
A: It reveals the actual bottleneck. Is write throughput the problem? Read throughput? Storage size? Bandwidth? Without math, you might design for the wrong constraint. An interviewer asking you to "estimate scale" wants to see that you think about whether a given design is even technically feasible at the stated load.

## Practice Exercises

1. **Estimation exercise**: Estimate the storage and bandwidth requirements for a photo-sharing app with 50M daily active users, each uploading an average of 2 photos per day at 3MB each and viewing 50 photos per day. How does this change your design priorities?

2. **CAP trade-off**: Design a shopping cart system. What consistency model would you choose (strong vs. eventual) and why? What are the consequences of each choice when a network partition occurs?

3. **Scaling progression**: Describe how you would scale a simple Node.js + PostgreSQL application from 100 to 1,000 to 100,000 concurrent users, naming each architectural change you'd introduce at each scale and the specific problem each change solves.

## Key Takeaways

- Vertical scaling has a ceiling; horizontal scaling requires stateless services but scales further.
- CAP theorem applies during network partitions — choose consistency (CP) or availability (AP) based on business requirements.
- Latency and throughput are different axes — know which one your system needs to optimize for.
- Availability nines: each additional 9 is dramatically harder; most applications don't need five nines.
- Back-of-envelope estimation reveals the actual bottleneck before you commit to a design.
- Name trade-offs explicitly — this is the primary signal interviewers use to assess senior-level thinking.
