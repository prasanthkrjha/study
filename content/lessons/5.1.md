# Core Concepts (System Design)

Every system design answer, no matter the specific question, draws on the same handful of core trade-offs. Get these solid before touching specific "design X" problems.

## Vertical vs. horizontal scaling

**Vertical scaling** (scale up): give one machine more CPU/RAM. Simple, but has a hard ceiling (there's a biggest machine you can buy) and creates a single point of failure. **Horizontal scaling** (scale out): add more machines and distribute load across them. More complex (now you need load balancing, and your app must be stateless or share state externally), but scales much further and improves fault tolerance — losing one of ten machines is a blip, not an outage.

The general industry direction for anything expected to grow: design for horizontal scaling from the start, even if you only run one instance today.

## CAP theorem

In a distributed system, when a network partition occurs (some nodes can't talk to others), you must choose between:

- **Consistency** — every read gets the most recent write, or an error.
- **Availability** — every request gets a response, even if it might not reflect the latest write.

You can't have both **during a partition** (you can always have both when the network is healthy — CAP is specifically about the partition case). This is why different databases make different defaults: traditional relational databases lean CP (reject requests rather than serve stale data), many NoSQL stores lean AP (serve slightly stale data rather than error out). Knowing which one your system needs — "would you rather show a slightly outdated cart, or show an error?" — is the actual interview-relevant skill, not reciting the acronym.

## Latency vs. throughput

**Latency** is how long a single request takes. **Throughput** is how many requests the system handles per unit time. These aren't the same axis — a system can have low latency but low throughput (fast per-request, but can't handle many at once), or high throughput but higher latency (batches requests to process many at once, at the cost of per-request speed, like a queue-based system). Optimizing for one can hurt the other; know which one a given problem actually cares about before proposing a solution.

## Availability

Usually expressed as a percentage of uptime ("three nines" = 99.9%, "five nines" = 99.999%). Each additional nine is dramatically harder and more expensive to achieve — 99.9% allows about 8.7 hours of downtime a year, 99.999% allows about 5 minutes. Redundancy (no single point of failure) is the core technique: multiple instances behind a load balancer, database replicas, multi-region deployment for the most demanding cases.

## How to use these in an interview

These four ideas are your **vocabulary**, not your answer. A strong system design response names the relevant trade-off explicitly ("this is a CP choice — we're prioritizing consistency because double-charging a customer is worse than a brief unavailability") rather than just listing components. Practice narrating the trade-off out loud, not just drawing the diagram.
