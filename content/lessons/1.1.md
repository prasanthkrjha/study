# Complexity Analysis

Before you can compare two solutions to a problem, you need a shared language for "how fast" and "how much memory." That language is Big-O notation. It lets you describe algorithmic efficiency in terms of how runtime or memory usage grows as the input size grows — not the exact count of operations, just the growth trend. Every topic in this course assumes you can look at a loop and immediately state its complexity, so building that reflex here pays dividends for every unit that follows.

Big-O matters in interviews for two reasons. First, interviewers routinely ask "what's the time and space complexity of your solution?" as a follow-up after you code. Second, and more importantly, knowing complexity guides you to the right solution before you write a single line — if you can see that a brute-force approach is O(n²) and the constraint is n = 10⁵, you know it will time out and you need a better algorithm. Developing the instinct to estimate complexity before coding is what separates engineers who "see" solutions from those who guess and check.

This unit is intentionally placed first because every subsequent lesson (hashing, two pointers, binary search, trees, graphs) introduces complexity improvements that only make sense if you understand what you're improving from. Return here whenever you encounter a new algorithm and need to analyze it from scratch.

## Theory & Fundamentals

### What Big-O Actually Measures

Big-O notation describes the **asymptotic upper bound** of a function's growth rate. When we say an algorithm is O(f(n)), we mean: for sufficiently large inputs, the runtime (or memory) grows no faster than some constant multiple of f(n). We drop constants and lower-order terms because they become irrelevant at scale — O(2n + 100) and O(n) describe the same growth behavior.

The formal definition: T(n) is O(f(n)) if there exist constants c > 0 and n₀ such that T(n) ≤ c·f(n) for all n ≥ n₀. In practice, you never use this definition directly — you use the simplification rules below.

### Common Complexity Classes

```
Growth rate comparison (slower = better):

O(1)       ──────────────────────────────── flat
O(log n)   ──────────────────╮ rises slowly
O(n)       ────────────────────────╮ linear
O(n log n) ──────────────────────────────╮
O(n²)      ──────────────────────────────────╮ steep
O(2ⁿ)      ──────────────────────────────────────╮ explosive
O(n!)      ──────────────────────────────────────────╮
```

| Notation    | Name          | Real-world example                             |
|-------------|---------------|------------------------------------------------|
| O(1)        | Constant      | Array index access, hashmap lookup (average)   |
| O(log n)    | Logarithmic   | Binary search, balanced BST operations         |
| O(n)        | Linear        | Single loop over input                         |
| O(n log n)  | Linearithmic  | Merge sort, heapsort                           |
| O(n²)       | Quadratic     | Nested loops over the same input               |
| O(n³)       | Cubic         | Triple nested loops (matrix multiplication)    |
| O(2ⁿ)       | Exponential   | Subset enumeration, naive recursive Fibonacci  |
| O(n!)       | Factorial     | Brute-force permutations                       |

### Time vs. Space Complexity

**Time complexity** counts the number of operations relative to n. **Space complexity** counts the extra memory your algorithm allocates relative to n — this includes the call stack during recursion, not just arrays you explicitly create.

A recursive function that recurses n levels deep with O(1) work per frame has O(n) time and O(n) space (for the call stack), even if it creates no extra arrays. This is why iterative solutions are sometimes preferred over recursive ones in memory-constrained environments.

### Best, Average, and Worst Case

The same algorithm can have different complexities depending on the input:

- **Best case** (Ω notation): the fastest the algorithm can run on any input of size n.
- **Average case** (Θ notation): performance over the space of all inputs of size n.
- **Worst case** (O notation): the slowest the algorithm can run on any input of size n.

Interviewers almost always want **worst-case** complexity unless they explicitly say otherwise. The notable exception is hash table operations, which are O(1) average but O(n) worst case due to hash collisions — interviewers accept "O(1) amortized" for these.

### The Simplification Rules

1. Drop constant multipliers: O(3n) → O(n), O(n/2) → O(n)
2. Drop non-dominant terms: O(n² + n) → O(n²), O(n + log n) → O(n)
3. Different inputs, different variables: a loop over array A followed by a loop over array B is O(a + b), not O(n)
4. Nested loops multiply: an outer loop of n and inner loop of m is O(n·m)

## Core Patterns / Techniques

### Analyzing Loops

A single loop over n elements is O(n). Two sequential (non-nested) loops over n elements are O(n) + O(n) = O(n). Two **nested** loops over n elements are O(n²).

```js
// O(n) — one loop
for (let i = 0; i < n; i++) { /* O(1) work */ }

// O(n) — two sequential loops, not nested
for (let i = 0; i < n; i++) { /* O(1) work */ }
for (let j = 0; j < n; j++) { /* O(1) work */ }

// O(n²) — nested loops
for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) { /* O(1) work */ }
}

// O(n log n) — outer linear, inner halves each time
for (let i = 0; i < n; i++) {
  for (let j = 1; j < n; j *= 2) { /* O(1) work */ }
}
```

### Analyzing Recursion

For recursive algorithms, count: (number of recursive calls)^(depth of recursion).

```js
// Factorial: one call per level, depth n → O(n) time, O(n) space
function factorial(n) {
  if (n <= 1) return 1;
  return n * factorial(n - 1);
}

// Naive Fibonacci: branches 2x per level, depth n → O(2ⁿ) time
function fib(n) {
  if (n <= 1) return n;
  return fib(n - 1) + fib(n - 2);
}

// Binary search: one call, halves each time → O(log n)
function bSearch(arr, lo, hi, target) {
  if (lo > hi) return -1;
  const mid = (lo + hi) >> 1;
  if (arr[mid] === target) return mid;
  if (arr[mid] < target) return bSearch(arr, mid + 1, hi, target);
  return bSearch(arr, lo, mid - 1, target);
}
```

### Halving = Logarithm

Whenever the problem space is halved at each step, the depth is log₂(n). This is why binary search is O(log n) — after k halvings, the remaining space is n/2^k = 1, so k = log₂(n).

```
n = 16:  16 → 8 → 4 → 2 → 1   (4 steps = log₂(16))
n = 1024: 10 steps = log₂(1024)
```

### Amortized Analysis

Some operations are occasionally expensive but cheap on average. JavaScript's `Array.push()` is O(1) amortized: most pushes are O(1), but when the underlying array needs to resize it's O(n). Over a sequence of n pushes, the total work is O(n), so each push costs O(1) on average.

## Code Examples

### Example 1: Recognizing Complexity in Real Code

```js
// Problem: find all pairs in an array that sum to target
// Brute force: O(n²) time, O(1) space

function twoSumBrute(nums, target) {
  for (let i = 0; i < nums.length; i++) {        // O(n) outer
    for (let j = i + 1; j < nums.length; j++) {  // O(n) inner → total O(n²)
      if (nums[i] + nums[j] === target) {
        return [i, j];
      }
    }
  }
  return [];
}

// Optimized: O(n) time, O(n) space
// Trade memory for time — the core complexity tradeoff

function twoSumOptimal(nums, target) {
  const seen = new Map(); // O(n) space: at most n entries

  for (let i = 0; i < nums.length; i++) { // O(n) time: single pass
    const complement = target - nums[i];
    if (seen.has(complement)) {            // O(1) hashmap lookup
      return [seen.get(complement), i];
    }
    seen.set(nums[i], i);                  // O(1) hashmap write
  }
  return [];
}

// Summary:
// Brute force: O(n²) time, O(1) space
// Optimal:     O(n)  time, O(n) space
// The extra O(n) memory buys us an O(n) time improvement
```

### Example 2: Space Complexity with Recursion

```js
// Computing sum of array recursively
// Illustrates how call stack contributes to space complexity

function recursiveSum(arr, i = 0) {
  // Base case
  if (i === arr.length) return 0;
  // Each call adds one frame to the call stack
  // Depth = arr.length = n → O(n) space even with no extra data structures
  return arr[i] + recursiveSum(arr, i + 1);
}

// Iterative equivalent: O(n) time, O(1) space (no call stack growth)
function iterativeSum(arr) {
  let total = 0;
  for (const n of arr) total += n; // one variable, no recursion
  return total;
}

// Memoized Fibonacci: reduces time from O(2ⁿ) to O(n)
// at the cost of O(n) extra space for the cache
function fibMemo(n, memo = new Map()) {
  if (n <= 1) return n;
  if (memo.has(n)) return memo.get(n); // O(1) lookup avoids recomputation
  const result = fibMemo(n - 1, memo) + fibMemo(n - 2, memo);
  memo.set(n, result);
  return result;
}
// Time: O(n) — each subproblem computed once
// Space: O(n) — memo cache + O(n) call stack
```

## Best Practices

- **Always state complexity proactively** — don't wait for the interviewer to ask. Say it as soon as your solution is clear: "This is O(n) time and O(n) space."
- **Count operations, not lines** — a single line `arr.sort()` is O(n log n), not O(1).
- **Remember that built-in methods have costs** — `.includes()` on an array is O(n); `Set.has()` is O(1). Using `.includes()` inside a loop creates hidden O(n²) code.
- **Use different variable names for different input sizes** — if a function takes two arrays of sizes `a` and `b`, the complexity involves both: O(a + b), not O(n).
- **Recursion adds stack space** — a recursion depth of n adds O(n) to your space complexity, even with tail calls in non-optimizing runtimes.
- **Amortized is not worst-case** — always clarify which you mean. `Array.push` is O(1) amortized but O(n) worst case.
- **Drop constants, but track them mentally** — O(3n) and O(n) are the same class, but an algorithm that does 3 passes will be slower in practice than one that does 1 pass. Use Big-O to pick the algorithm; use common sense to optimize the constant factor.

## Common Interview Questions

**Q1: What is the difference between O(n) and Θ(n)?**
A: O(n) is an upper bound — the algorithm runs in at most n time. Θ(n) is a tight bound — it runs in exactly n time (both upper and lower bounded). In interviews, "O(n)" is conventionally used to mean tight bound, though technically it only means upper bound.

**Q2: Why do we drop constants in Big-O?**
A: Because Big-O describes asymptotic behavior — how the algorithm scales as n approaches infinity. For any constant c, c·n grows at the same rate as n, so they're in the same complexity class. The constant matters for real-world performance but not for algorithmic classification.

**Q3: An algorithm has two nested loops, but the inner loop always runs exactly 10 times regardless of n. What's the complexity?**
A: O(n). The inner loop is O(1) (constant, not dependent on n), so outer O(n) × inner O(1) = O(n).

**Q4: What's the space complexity of a recursive function that recurses n levels deep with O(1) work per frame?**
A: O(n) — the call stack holds n frames simultaneously. Even though no extra data structures are created, each function call takes stack space.

**Q5: What's the time complexity of sorting an array in JavaScript?**
A: O(n log n) — `Array.prototype.sort()` uses TimSort (a merge sort variant) internally. This is also the theoretical lower bound for comparison-based sorting.

**Q6: What does "amortized O(1)" mean?**
A: It means that while a single operation might occasionally be expensive (e.g., O(n) when a dynamic array resizes), the average cost over many operations is O(1). The total cost of n operations is O(n), so each operation costs O(1) on average.

**Q7: Is O(n log n) always better than O(n²)?**
A: Asymptotically yes, but for very small n, the constant factors can make O(n²) faster in practice. Most interview problems have n large enough that O(n log n) is strictly preferred.

**Q8: If I use a hashmap inside a loop, what's the total complexity?**
A: Each hashmap operation (get/set/has) is O(1) average, so one loop with a hashmap operation per iteration is O(n) average. If the interviewer asks about worst case, it's O(n²) due to pathological hash collisions — but this is almost never relevant in practice.

## Practice Exercises

**Exercise 1 — Complexity Identification (Beginner)**
Given the following code snippet, determine the time and space complexity:
```js
function mystery(arr) {
  let result = [];
  for (let i = 0; i < arr.length; i++) {
    for (let j = 0; j < arr.length; j++) {
      if (arr[i] + arr[j] === 0) result.push([arr[i], arr[j]]);
    }
  }
  return result;
}
```
Hint: Count the loop iterations and the size of the result array in the worst case.

**Exercise 2 — Optimization Challenge (Beginner-Intermediate)**
Rewrite `mystery` from Exercise 1 to run in O(n log n) time. Then rewrite it again to run in O(n) time. For each version, state the space complexity and explain what you traded to achieve the speedup.
Hint: The O(n log n) version uses sorting. The O(n) version uses a data structure that allows O(1) lookup.

**Exercise 3 — Recursion Analysis (Intermediate)**
Analyze the time and space complexity of this function:
```js
function f(n) {
  if (n <= 0) return 0;
  return f(n - 1) + f(n - 1);
}
```
Draw the recursion tree. How many total calls are made? How deep is the call stack at any one time?
Hint: At each level, the number of calls doubles. Count the levels and total nodes.

**Exercise 4 — Real-World Hidden Complexity (Intermediate)**
A developer writes this code to find duplicates in an array:
```js
function hasDuplicate(arr) {
  for (const x of arr) {
    if (arr.filter(y => y === x).length > 1) return true;
  }
  return false;
}
```
What is the actual time complexity? Rewrite it to be O(n). What is the space complexity of your optimized version?
Hint: `Array.filter` is O(n). Calling it inside a loop makes the whole thing O(n²).

**Exercise 5 — Amortized Analysis (Advanced)**
Implement a stack using two queues such that push is O(1) amortized and pop is O(n) worst case. Then design an alternative where pop is O(1) amortized and push is O(n) worst case. Analyze both implementations. Which would you prefer for a workload that pushes 1000 items and pops 1 item?
Hint: Think about where you pay the cost — you can choose to pay on push or pay on pop.

## Key Takeaways

- Big-O describes growth rate as input size grows — constants and lower-order terms are dropped.
- The most important complexity classes from best to worst: O(1), O(log n), O(n), O(n log n), O(n²), O(2ⁿ).
- Time complexity counts operations; space complexity counts extra memory including the call stack.
- Interviewers default to worst-case complexity — always report worst case unless asked otherwise.
- Nested loops multiply complexities; sequential loops add them.
- Halving the search space at each step produces O(log n) — the signature of binary search and balanced trees.
- The most common optimization pattern: trade O(n) space for a hashmap to reduce O(n²) time to O(n).
- Always state the complexity of your solution out loud — it demonstrates algorithmic thinking and is expected at every top-company interview.
