# Complexity Analysis

Before you can compare two solutions to a problem, you need a shared language for "how fast" and "how much memory." That language is Big-O notation. Every DSA topic after this one assumes you can look at a loop and immediately say its complexity — so this unit is short, but skipping it makes everything downstream harder.

## What Big-O actually measures

Big-O describes how the **runtime or memory** of an algorithm grows as the input size (`n`) grows — not the exact number of operations, just the growth trend. We drop constants and lower-order terms because they stop mattering at scale: `O(2n)` and `O(n + 100)` are both just `O(n)`.

Common complexities, from fastest to slowest growth:

| Notation | Name | Example |
|---|---|---|
| O(1) | Constant | array index access, hashmap lookup |
| O(log n) | Logarithmic | binary search |
| O(n) | Linear | single loop over an array |
| O(n log n) | Linearithmic | efficient sorting (merge sort, quicksort avg case) |
| O(n²) | Quadratic | nested loops over the same input |
| O(2ⁿ) | Exponential | naive recursive Fibonacci, brute-force subsets |
| O(n!) | Factorial | brute-force permutations |

## Time vs. space complexity

**Time complexity** counts operations relative to `n`. **Space complexity** counts extra memory your algorithm allocates relative to `n` — this includes recursion call-stack depth, not just arrays you explicitly create. A recursive function with no extra arrays can still be `O(n)` space if it recurses `n` levels deep.

## Best, average, and worst case

The same algorithm can have different complexities depending on the input shape:

```js
function findTarget(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) return i; // best case: O(1), target is first
  }
  return -1; // worst case: O(n), target is absent or last
}
```

Interviewers almost always want **worst-case** complexity unless they say otherwise — average case matters more for things like hash tables (average O(1) lookup, worst case O(n) with pathological collisions).

## How to analyze a piece of code quickly

1. Find the loops. A single loop over `n` items is O(n). Two nested independent loops over `n` is O(n²).
2. Loops that halve the search space each time (binary search, balanced tree descent) are O(log n).
3. Recursion: multiply the number of recursive calls per level by the number of levels. Fibonacci's naive recursion branches twice per call, `n` levels deep → O(2ⁿ).
4. Hashmap/hashset operations (get, set, has) are O(1) average — this is the single most common way a brute-force O(n²) solution becomes O(n).

## Practice tip

Whenever you finish a problem, say its time and space complexity out loud before moving on. This habit is what makes complexity analysis automatic by the time you're in a real interview.
