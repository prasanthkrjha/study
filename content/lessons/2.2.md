# PostgreSQL & Database Design

Knowing SQL syntax is half the job; designing a schema that doesn't fall apart under real usage is the other half. This unit is about the design decisions that separate a "tutorial schema" from one you'd defend in a system design interview.

## Primary and foreign keys

A **primary key** uniquely identifies a row (`id SERIAL PRIMARY KEY`, or a UUID). A **foreign key** references another table's primary key, enforcing that the referenced row must actually exist:

```sql
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id),
  total NUMERIC(10, 2) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

This is what prevents an `orders` row from ever pointing at a `user_id` that doesn't exist — the database rejects the insert instead of your application silently creating orphaned data.

## Normalization (1NF → 3NF)

Normalization is about eliminating redundancy so updates don't require touching the same fact in multiple places:

- **1NF:** every column holds a single atomic value (no comma-separated lists in a cell).
- **2NF:** every non-key column depends on the **whole** primary key, not just part of it (relevant for composite keys).
- **3NF:** every non-key column depends **only** on the primary key, not on another non-key column. Example violation: storing both `user_id` and `user_email` on an `orders` table — email depends on the user, not on the order, so it belongs only in `users`.

In practice: normalize by default, then deliberately **denormalize** specific columns later if you have a measured read-performance problem — don't start denormalized "for speed" before you have evidence you need it.

## Indexing

An index is a separate data structure (usually a B-tree) that lets Postgres find rows matching a condition without scanning the whole table:

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

Add indexes on columns you frequently filter (`WHERE`), join (`ON`), or sort (`ORDER BY`) by. The trade-off: indexes speed up reads but slow down writes slightly (every insert/update must also update the index) and take extra disk space — so don't index every column reflexively.

## Transactions

A transaction groups multiple statements so they either **all** succeed or **all** roll back — critical for anything involving multiple related writes (e.g. deducting inventory and creating an order):

```sql
BEGIN;
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 42;
INSERT INTO orders (user_id, product_id) VALUES (7, 42);
COMMIT; -- or ROLLBACK if something failed
```

Without a transaction, a crash between the two statements leaves your data inconsistent (inventory decremented but no order recorded).

## Practice tip

Design a schema for something you'd actually use — not a Mario database from a tutorial. Add foreign keys and at least one index, then intentionally try to insert bad data and watch Postgres reject it. That failure is the feature.
