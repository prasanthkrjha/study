# PostgreSQL & Database Design

Knowing SQL syntax is only half the picture. Designing a schema that remains correct and performant as data grows — and as requirements change — is the other half, and it is the half that separates engineers who can build systems from those who can only follow tutorials. Database design decisions made early are expensive to change later: a missing foreign key constraint or a poorly chosen normalization level can require a painful migration once millions of rows exist.

PostgreSQL is the most full-featured open-source relational database and the dominant choice in modern full-stack projects. Beyond standard SQL, it provides rich data types (JSONB, arrays, enums, UUID), powerful indexing options (partial indexes, GIN indexes for full-text search), advanced transaction controls, and excellent performance at scale. Understanding its specific behavior — how it enforces constraints, how its planner uses indexes, what its MVCC transaction model means for concurrent access — is directly applicable on the job.

Schema design is fundamentally about making the database enforce the rules your application depends on. Every constraint you push down to the database level is a rule that cannot be violated even if application code has a bug. Every constraint you leave to application code alone is a rule that will eventually be violated.

## Theory & Fundamentals

### Normalization

Normalization is the process of structuring tables to eliminate redundant storage of the same fact. When a fact is stored in only one place, updating it requires touching only one row — no risk of the same fact being inconsistently updated in some places but not others.

**First Normal Form (1NF):** Each column holds a single atomic value. No comma-separated lists, no arrays of values stuffed into a text column. Violation example: storing `"tag1,tag2,tag3"` in a `tags` column — those values cannot be individually queried or indexed. Fix: a separate `post_tags` join table.

**Second Normal Form (2NF):** Every non-key column depends on the entire primary key, not just part of it. Only relevant when the primary key is composite. Violation example: a table with primary key `(order_id, product_id)` that also stores `product_name` — product name depends only on `product_id`, not on the full composite key. Fix: move product name to the products table.

**Third Normal Form (3NF):** Every non-key column depends only on the primary key, not on another non-key column (no transitive dependencies). Violation example: storing both `user_id` and `user_email` on an `orders` table — email depends on the user, not on the order. Fix: join to the users table when you need the email.

The practical rule: normalize to 3NF by default, then deliberately denormalize specific columns only after you have measured evidence of a performance problem that normalization is causing. "I might need it to be faster" is not evidence.

### MVCC (Multi-Version Concurrency Control)

PostgreSQL uses MVCC to allow concurrent reads and writes without readers blocking writers or vice versa. Each transaction sees a consistent snapshot of the database as of its start time. Old row versions are kept alongside new ones until no running transaction can see them, then cleaned up by VACUUM. This model provides high concurrency but means you need to understand what "consistent snapshot" means for your transaction isolation level.

### Transaction Isolation Levels

PostgreSQL supports four isolation levels. The default is Read Committed: each statement in a transaction sees only committed data at the moment that statement runs (not at transaction start). Repeatable Read gives a stable snapshot for the entire transaction. Serializable provides the strongest guarantee — concurrent transactions behave as if they ran one at a time. Most application code runs at Read Committed; use Serializable for operations where phantom reads would be dangerous (e.g., double-booking prevention).

## Core Concepts / Techniques

### Primary Keys and Foreign Keys

```sql
-- UUID primary keys: better for distributed systems, no sequential guessing
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

CREATE TABLE users (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email      TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Foreign key with ON DELETE behavior
CREATE TABLE orders (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  -- ON DELETE RESTRICT: prevent deleting user if orders exist
  -- ON DELETE CASCADE: delete orders when user is deleted
  -- ON DELETE SET NULL: set user_id to NULL when user is deleted
  status     TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'processing', 'shipped', 'completed', 'cancelled')),
  total      NUMERIC(12, 2) NOT NULL CHECK (total >= 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Constraints as Correctness Guarantees

```sql
-- NOT NULL: the column must always have a value
-- UNIQUE: no two rows can share this value
-- CHECK: arbitrary boolean condition must be true
-- REFERENCES: the value must exist in the referenced table

CREATE TABLE products (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sku         TEXT NOT NULL UNIQUE,
  name        TEXT NOT NULL,
  price_cents INTEGER NOT NULL CHECK (price_cents > 0),
  stock       INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0),
  category_id UUID NOT NULL REFERENCES categories(id)
);

-- Multi-column unique constraint (same user can't review same product twice)
CREATE TABLE reviews (
  user_id    UUID NOT NULL REFERENCES users(id),
  product_id UUID NOT NULL REFERENCES products(id),
  rating     INTEGER NOT NULL CHECK (rating BETWEEN 1 AND 5),
  body       TEXT,
  PRIMARY KEY (user_id, product_id)   -- composite PK also enforces uniqueness
);
```

### Indexing

```sql
-- B-tree index (default): good for equality, range queries, ORDER BY
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_orders_created_at ON orders(created_at DESC);

-- Compound index: efficient for queries filtering on both columns
-- Column order matters: put the most selective column first
CREATE INDEX idx_orders_status_created ON orders(status, created_at DESC);

-- Partial index: only indexes rows matching a condition
-- Much smaller than a full index if the condition filters most rows
CREATE INDEX idx_pending_orders ON orders(created_at)
WHERE status = 'pending';

-- Unique index: enforces uniqueness and also speeds lookups
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- Check which indexes exist on a table
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'orders';

-- EXPLAIN ANALYZE to see if an index is being used
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 'abc-123' AND status = 'pending';
```

### Transactions

```sql
-- Multiple statements that must all succeed or all roll back
BEGIN;

-- Deduct stock
UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0;

-- Check the update actually happened (row might have been at 0)
-- Application code checks affected row count; if 0, ROLLBACK

-- Create the order
INSERT INTO orders (user_id, product_id, total)
VALUES ($2, $1, $3);

-- Create the order item
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES (lastval(), $1, 1, $3);

COMMIT;

-- If any statement errors, or application explicitly calls:
ROLLBACK;  -- all changes are undone, as if none happened
```

### Migrations

```sql
-- Schema changes should be applied as numbered, sequential migration files
-- Never edit a migration that has already run in production

-- Migration 0003_add_user_preferences.sql
ALTER TABLE users
  ADD COLUMN preferences JSONB NOT NULL DEFAULT '{}';

-- Safe column addition: adding a nullable column or one with a default
-- is instant in PostgreSQL 11+ (default is stored in catalog, not rewritten)

-- Adding NOT NULL to an existing column: requires backfilling first
UPDATE users SET preferences = '{}' WHERE preferences IS NULL;
ALTER TABLE users ALTER COLUMN preferences SET NOT NULL;
```

## Code Examples

### Full Schema: E-Commerce Core

```sql
-- Clean schema with proper constraints and indexes

CREATE TABLE users (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email      TEXT NOT NULL,
  name       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT users_email_unique UNIQUE (email),
  CONSTRAINT users_email_format CHECK (email LIKE '%@%')
);

CREATE TABLE categories (
  id        UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name      TEXT NOT NULL UNIQUE,
  parent_id UUID REFERENCES categories(id)  -- self-referencing for hierarchy
);

CREATE TABLE products (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  category_id   UUID NOT NULL REFERENCES categories(id),
  name          TEXT NOT NULL,
  price_cents   INTEGER NOT NULL CHECK (price_cents > 0),
  stock         INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  status      TEXT NOT NULL DEFAULT 'pending',
  total_cents INTEGER NOT NULL DEFAULT 0 CHECK (total_cents >= 0),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT orders_status_check CHECK (
    status IN ('pending','processing','shipped','completed','cancelled')
  )
);

CREATE TABLE order_items (
  order_id   UUID NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id UUID NOT NULL REFERENCES products(id),
  quantity   INTEGER NOT NULL CHECK (quantity > 0),
  unit_price INTEGER NOT NULL CHECK (unit_price > 0),
  PRIMARY KEY (order_id, product_id)
);

-- Indexes for common access patterns
CREATE INDEX ON orders(user_id);
CREATE INDEX ON orders(status, created_at DESC);
CREATE INDEX ON order_items(product_id);
CREATE INDEX ON products(category_id);
```

### Using EXPLAIN to Diagnose Slow Queries

```sql
-- EXPLAIN shows the query plan without running the query
-- EXPLAIN ANALYZE actually runs it and shows real timings
EXPLAIN ANALYZE
SELECT u.email, COUNT(o.id) AS order_count
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.created_at > NOW() - INTERVAL '30 days'
GROUP BY u.id, u.email
HAVING COUNT(o.id) > 2;

-- Look for:
-- "Seq Scan" on a large table = likely missing index
-- High "rows" estimates that differ widely from actual = stale statistics
-- "Hash Join" vs "Nested Loop" vs "Merge Join" — planner picks based on row counts
-- Run ANALYZE tablename; to refresh statistics if estimates are way off
```

## Best Practices

- **Always use foreign key constraints** — they are the only reliable way to prevent orphaned records; application code alone will eventually fail to enforce referential integrity.
- **Use `TIMESTAMPTZ` (timestamp with time zone) instead of `TIMESTAMP`** — stores UTC internally, renders correctly for any time zone, and avoids entire classes of daylight-saving bugs.
- **Store money as integer cents** — floating-point types (`FLOAT`, `DOUBLE`) cannot represent all decimal values exactly and will silently accumulate rounding errors in financial calculations; `NUMERIC(12,2)` or integer cents avoids this.
- **Add `NOT NULL` to every column that always has a value** — NULL means "unknown," and columns that should always have a value being nullable causes confusion in aggregates and join logic.
- **Index foreign keys** — PostgreSQL does not automatically index foreign key columns (unlike some other databases), so a lookup of "all orders for user X" on an unindexed `user_id` is a full table scan.
- **Use `ON DELETE RESTRICT` as the safe default for foreign keys** — it prevents deletion of referenced rows, which forces you to handle cleanup explicitly rather than accidentally cascading deletes; use `CASCADE` only when child row deletion is genuinely desired.
- **Run migrations in transactions** — wrap schema changes in `BEGIN`/`COMMIT` so a failed migration is automatically rolled back rather than leaving the schema in a half-applied state.

## Common Interview Questions

**Q: What is the difference between a primary key and a unique constraint?**
A: Both enforce uniqueness, but a table can have only one primary key (which also implicitly adds NOT NULL) and can have many unique constraints. The primary key is the canonical identifier for a row and is what foreign keys in other tables reference.

**Q: What are the three normal forms and why do we normalize?**
A: 1NF requires atomic column values (no lists in a cell). 2NF requires every non-key column to depend on the whole primary key. 3NF requires no transitive dependencies between non-key columns. Normalization eliminates redundant storage so each fact exists in exactly one place, preventing update anomalies.

**Q: What is an index and what is the trade-off of adding one?**
A: An index is a separate data structure (typically a B-tree) that maps column values to their row locations, allowing the database to find matching rows without scanning every row in the table. Trade-off: faster reads at the cost of slower writes (every insert/update/delete must also update each index) and additional disk space.

**Q: What does ON DELETE CASCADE vs ON DELETE RESTRICT mean?**
A: ON DELETE CASCADE automatically deletes child rows when the referenced parent row is deleted. ON DELETE RESTRICT (default) prevents deletion of the parent row if any child rows reference it. CASCADE is convenient but dangerous if applied broadly; RESTRICT forces explicit handling of related data before deletion.

**Q: What is a database transaction and what does ACID mean?**
A: A transaction is a group of statements that execute as a single atomic unit. ACID: Atomicity (all succeed or all roll back), Consistency (the database moves from one valid state to another), Isolation (concurrent transactions don't see each other's intermediate state), Durability (committed transactions survive crashes).

**Q: When should you use a UUID primary key instead of a serial integer?**
A: UUIDs are better when: records are created across multiple services or databases that must merge (no collision risk), IDs must not be sequentially guessable for security, or you need to assign an ID before the row is committed. Serial integers are simpler, smaller (4 vs 16 bytes), and slightly faster for index lookups.

**Q: What is a partial index and when is it useful?**
A: A partial index only indexes rows that match a WHERE condition. It is useful when most queries target a specific subset of rows (e.g., only pending orders, only active users) — the index is smaller and faster to maintain than a full-table index.

**Q: What does EXPLAIN ANALYZE tell you and when should you use it?**
A: EXPLAIN ANALYZE runs the query and shows the actual query plan, estimated vs. actual row counts, and execution time at each step. Use it when a query is slow to diagnose whether it is doing a full table scan instead of using an index, or when the planner's row estimates are wildly off (suggesting stale statistics).

## Practice Exercises

1. **Schema design from scratch**: Design a schema for a blog platform with users, posts, comments, and tags. Define all primary keys, foreign keys, and NOT NULL constraints. Add at least two indexes based on the access patterns you would expect, and justify each one.

2. **Normalization exercise**: Given this denormalized table — `orders(order_id, user_id, user_email, user_name, product_id, product_name, product_category, quantity, unit_price)` — identify which normal form is violated and produce a fully normalized 3NF schema.

3. **Transaction safety**: Write a SQL transaction that transfers "loyalty points" from one user to another. The transfer should fail atomically if either the deduction or the credit fails, and should prevent the balance from going negative.

4. **Index diagnosis**: Given a slow query that filters `orders` by `status = 'pending'` and `created_at > NOW() - INTERVAL '7 days'`, use EXPLAIN ANALYZE output to determine whether an index is being used. Write the CREATE INDEX statement that would help this query and explain why you chose the column order.

5. **Constraint design**: Add a CHECK constraint to an `events` table to enforce that `end_time > start_time`. Then write a migration that adds a `cancelled_at` column (nullable TIMESTAMPTZ) and a partial index on `user_id` that only covers events where `cancelled_at IS NULL`.

## Key Takeaways

- Schema constraints (NOT NULL, UNIQUE, FOREIGN KEY, CHECK) are correctness guarantees enforced by the database itself — they are more reliable than application-level validation alone.
- Normalization (1NF → 3NF) ensures each fact is stored in one place, eliminating update anomalies; denormalize deliberately and measurably, never preemptively.
- Foreign keys must always be indexed in PostgreSQL — they are not indexed automatically, and unindexed FK columns cause full table scans on parent-child joins.
- Transactions group multiple statements into an atomic unit; if any statement fails or the application calls ROLLBACK, all changes in the transaction are undone.
- EXPLAIN ANALYZE is the primary tool for diagnosing slow queries — look for sequential scans on large tables as a signal that an index is missing.
- Use TIMESTAMPTZ not TIMESTAMP, and store monetary values as integer cents rather than floating-point — these two decisions prevent entire categories of subtle bugs.
- A partial index that targets only the rows most queries touch is often more efficient than a full index — smaller, faster to maintain, and just as useful for those queries.
- Schema migrations should be versioned, sequential, run inside transactions, and never edited after they have been applied to any environment.
