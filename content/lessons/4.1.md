# Docker

Docker solves the "it works on my machine" problem by packaging an application together with everything it needs to run — the runtime, dependencies, configuration, and operating system libraries — into a portable, reproducible unit called a container. This means the same container that runs correctly on your laptop runs identically in a CI pipeline, on a staging server, and in production. That guarantee is what makes Docker table-stakes for modern deployment workflows.

The fundamental distinction in Docker is between an image and a container. An image is an immutable, layered snapshot of a filesystem — your code, its runtime, and its dependencies frozen at a point in time. A container is a running instance of an image — a live process with an isolated filesystem, network, and resource view. You build images; you run containers from them. The same image can be used to start many containers simultaneously, each independent.

Understanding Docker well means understanding how the layer cache works, because that knowledge directly translates to faster build times. Docker builds images in layers, one instruction at a time. If the filesystem state for a layer has not changed since the last build, Docker reuses the cached layer instead of rebuilding it. The practical implication: put instructions that change infrequently (installing OS packages, copying package.json) before instructions that change frequently (copying source code), so source code changes only invalidate the last few layers.

## Theory & Fundamentals

### Docker Architecture

The Docker daemon (`dockerd`) is a background service that manages images, containers, networks, and volumes. The Docker CLI (`docker`) sends commands to the daemon via a REST API. Images are stored in a registry (Docker Hub is the public default; AWS ECR, GitHub Container Registry, and self-hosted registries are common alternatives). When you run `docker pull image:tag`, the daemon downloads layers from the registry; when you run `docker push`, it uploads them.

### Image Layers

Every instruction in a Dockerfile creates a new read-only layer on top of the previous one. Layers that have not changed are cached and reused. A final union view of all layers makes up the image's filesystem. When a container starts, a thin writable layer is added on top — changes the container makes are written to this writable layer and discarded when the container stops (unless mounted on a volume).

### Networking

Docker containers run in isolated network namespaces. By default, containers can reach the internet (via network address translation through the host) but are not reachable from outside unless ports are explicitly published. Docker provides built-in DNS — in a Docker network, containers can reach each other by their service or container name, not by IP address. This is why `docker-compose.yml` services can reference each other by name.

### Volumes

Container filesystems are ephemeral — when a container stops or is removed, any data written to its filesystem is lost. Named volumes and bind mounts persist data across container restarts. A named volume is managed by Docker and stored in Docker's storage area. A bind mount maps a specific path on the host machine into the container — useful during development to get live code reloading without rebuilding the image.

## Core Concepts / Techniques

### Writing a Dockerfile

```dockerfile
# Start from an official base image — tag explicitly to avoid surprise upgrades
FROM node:20-alpine

# Set the working directory inside the container
WORKDIR /app

# Copy dependency manifests first — this layer changes only when
# package.json or package-lock.json changes, allowing layer caching
COPY package*.json ./

# Install production dependencies only
# npm ci is faster and stricter than npm install (requires package-lock.json)
RUN npm ci --omit=dev

# Copy the rest of the source code
# This layer invalidates on ANY source file change — comes after npm ci
# so dependency installation is still cached on source-only changes
COPY . .

# Build the application
RUN npm run build

# Document which port the app listens on (informational — doesn't publish it)
EXPOSE 3000

# The default command to run when a container starts from this image
CMD ["node", "dist/server.js"]
```

### Multi-Stage Builds

```dockerfile
# Stage 1: build
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Stage 2: production image
# Only the compiled output is copied — node_modules for dev and build tools are excluded
FROM node:20-alpine AS runner
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev   # install only production deps in the final image
COPY --from=builder /app/dist ./dist

ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "dist/server.js"]
# Result: a much smaller production image — no devDependencies, no source files
```

### Essential Docker Commands

```bash
# Build an image from the Dockerfile in the current directory
docker build -t my-app:latest .
docker build -t my-app:v1.2.3 .       # with a specific tag
docker build --target builder .         # stop at a specific multi-stage stage

# Run a container
docker run -p 3000:3000 my-app:latest           # host:container port mapping
docker run -d -p 3000:3000 my-app:latest        # -d: detached (background)
docker run -e DATABASE_URL=postgres://... my-app # pass environment variables
docker run --rm my-app npm test                  # --rm: delete container after it exits

# View running containers
docker ps
docker ps -a  # all containers, including stopped ones

# View logs
docker logs <container-id>
docker logs -f <container-id>  # follow (stream) logs

# Execute a command in a running container
docker exec -it <container-id> sh  # open an interactive shell

# Stop and remove
docker stop <container-id>
docker rm <container-id>

# Image management
docker images
docker rmi my-app:latest
docker system prune  # remove all stopped containers, unused images, networks
```

## Code Examples

### Docker Compose for a Full-Stack App

```yaml
# docker-compose.yml
version: '3.9'

services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: production
      DATABASE_URL: postgres://appuser:apppass@db:5432/appdb
      REDIS_URL: redis://cache:6379
    depends_on:
      db:
        condition: service_healthy   # wait for the healthcheck to pass
      cache:
        condition: service_started
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: appuser
      POSTGRES_PASSWORD: apppass
      POSTGRES_DB: appdb
    volumes:
      - db-data:/var/lib/postgresql/data    # named volume: data persists
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql  # run on first start
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser -d appdb"]
      interval: 5s
      timeout: 5s
      retries: 5

  cache:
    image: redis:7-alpine
    volumes:
      - redis-data:/data
    command: redis-server --appendonly yes   # enable AOF persistence

volumes:
  db-data:    # named volume: managed by Docker, persists across restarts
  redis-data:
```

### Development Compose Override

```yaml
# docker-compose.dev.yml — override for local development
# Usage: docker compose -f docker-compose.yml -f docker-compose.dev.yml up
version: '3.9'

services:
  app:
    build:
      target: builder          # use the dev/build stage instead of production
    volumes:
      - .:/app                 # bind mount: source changes reflected instantly
      - /app/node_modules      # anonymous volume: don't overwrite node_modules from host
    environment:
      NODE_ENV: development
    command: npm run dev       # hot-reload dev server instead of production start
```

### .dockerignore

```
# .dockerignore — same syntax as .gitignore
# Prevents these files from being sent to the Docker daemon as build context
node_modules
.git
.env
.env.local
dist
coverage
*.log
.DS_Store
README.md
```

## Best Practices

- **Use specific image tags** (`node:20-alpine`, not `node:latest`) — `latest` can change when a new major version is released, silently breaking your build; pin to a specific version.
- **Order Dockerfile instructions from least to most frequently changed** — put `COPY package*.json` and `RUN npm ci` before `COPY . .` so source code changes do not invalidate the dependency installation layer.
- **Use multi-stage builds for production images** — the builder stage can include devDependencies and build tools; the final stage includes only what is needed to run the application, producing a significantly smaller and more secure image.
- **Never put secrets in a Dockerfile or commit them in a build context** — secrets in Dockerfile instructions are baked into image layers and visible in `docker history`; pass them at runtime via environment variables or Docker secrets.
- **Use a `.dockerignore` file** — prevents `node_modules`, `.git`, `.env`, and other unnecessary files from being included in the build context, which speeds up builds and avoids accidentally baking local secrets into images.
- **Use named volumes for database data** — bind mounts for databases are unreliable across platforms; named volumes managed by Docker are portable and correctly persist data across container restarts.
- **Use health checks in production Compose files** — `depends_on` with `condition: service_healthy` ensures dependent services wait for a database to actually be ready to accept connections, not just for the container process to have started.

## Common Interview Questions

**Q: What is the difference between a Docker image and a Docker container?**
A: An image is an immutable, read-only snapshot of a filesystem containing an application and its dependencies. A container is a running instance of an image — a live, isolated process. Multiple containers can be started from the same image simultaneously, and they are independent of each other.

**Q: How does Docker's layer cache work and how does it affect Dockerfile ordering?**
A: Each Dockerfile instruction creates a cached layer. If nothing affecting a layer has changed since the last build, Docker reuses the cached version instead of re-executing the instruction. This means frequently changing instructions (like copying source code) should come after infrequently changing ones (like installing dependencies) — otherwise a source code change invalidates the dependency installation cache.

**Q: What is a multi-stage build and why is it useful?**
A: Multi-stage builds use multiple `FROM` instructions in a single Dockerfile. Each stage can have a different base image. The final stage copies only the output of previous stages — for example, compiled binaries from a build stage — and excludes build tools, devDependencies, and source files. The result is a smaller, more secure production image.

**Q: What is the difference between a named volume and a bind mount?**
A: A named volume is managed by Docker and stored in Docker's internal storage area; it is portable and platform-independent, recommended for databases and persistent application data. A bind mount maps a specific host filesystem path into the container; it is tied to host path structure and commonly used in development to share source code for live reloading.

**Q: How do containers in Docker Compose communicate with each other?**
A: Docker Compose places all services in the same project on a shared Docker network. Each service is reachable by its service name as a DNS hostname. For example, an `app` service can connect to a `db` service at `db:5432` without any extra network configuration.

**Q: What happens to data written inside a container when the container stops?**
A: Data written to the container's writable layer is lost when the container is stopped and removed. To persist data beyond a container's lifetime, it must be stored in a named volume or a bind mount, which exist independently of any specific container.

**Q: What is the purpose of EXPOSE in a Dockerfile?**
A: `EXPOSE` is documentation — it indicates which port the application inside the container listens on. It does NOT publish the port to the host machine. To publish a port, you must use `-p host:container` with `docker run` or `ports` in docker-compose.yml.

## Practice Exercises

1. **Containerize an existing app**: Take a Node.js/Express application and write a Dockerfile for it. Use a multi-stage build: a build stage that installs all dependencies and compiles TypeScript, and a production stage that contains only the compiled JavaScript and production `node_modules`. Verify the production image runs correctly with `docker run`.

2. **Docker Compose setup**: Write a `docker-compose.yml` that runs your app alongside PostgreSQL and Redis. Configure the app to connect to both using service names as hostnames. Add a healthcheck to the database service and use `depends_on: condition: service_healthy` to prevent the app from starting before the database is ready.

3. **Development workflow**: Create a `docker-compose.dev.yml` override file that bind-mounts your source code into the container and runs the app with hot-reloading (`nodemon` or equivalent). Verify that changing a source file without rebuilding the image is reflected in the running container.

4. **Layer cache optimization**: Given a Dockerfile that copies all files first and then runs `npm install`, explain why this is suboptimal and rewrite it to maximize cache utilization. Verify your improvement by timing both build approaches after making a trivial source code change.

5. **Environment variable security**: Starting from a Dockerfile that has a hardcoded database password in an `ENV` instruction, refactor it to accept secrets only at runtime via environment variables. Write the `docker run` command that passes the secret value, and explain why baking secrets into images is a security risk (hint: `docker history`).

## Key Takeaways

- An image is an immutable snapshot; a container is a running instance — multiple containers can run from the same image, each isolated from the others.
- Docker builds images in layers; unchanged layers are cached — order Dockerfile instructions from least to most frequently changed to maximize cache reuse.
- Multi-stage builds produce smaller, more secure production images by excluding build tools, devDependencies, and source files from the final stage.
- Container filesystems are ephemeral — use named volumes for databases and persistent data; use bind mounts during development for live source code reloading.
- Docker Compose services communicate via DNS using their service names as hostnames; no hardcoded IPs are needed or desirable.
- Never put secrets in a Dockerfile — they are stored in image layers and visible in `docker history`; pass them at runtime via environment variables.
- `.dockerignore` reduces build context size, speeds up builds, and prevents local secrets (`.env` files) from being sent to the Docker daemon.
- Health checks with `depends_on: condition: service_healthy` ensure dependent services wait for actual readiness, not just for a container process to have started.
