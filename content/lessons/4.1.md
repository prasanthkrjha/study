# Docker

Docker is table-stakes for "owns a feature end-to-end" positioning — it's the difference between "runs on my machine" and a reproducible, deployable unit.

## Images vs. containers

An **image** is a read-only template (your app's code + runtime + dependencies, frozen at a point in time). A **container** is a running instance of an image — you can start many containers from the same image, each isolated from the others. The analogy: image is a class, container is an instance of that class.

## Dockerfile syntax

```dockerfile
FROM node:20-alpine
WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY . .
RUN npm run build

EXPOSE 3000
CMD ["npm", "start"]
```

Order matters for build speed: `COPY package*.json` and `RUN npm ci` happen **before** `COPY . .` so Docker can cache the (usually slower) dependency-install layer and only re-run it when `package.json` actually changes — not on every source-code edit.

## Docker Compose (multi-container apps)

Compose defines and runs multiple related containers (your app + a database + Redis) together, with one command:

```yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://user:pass@db:5432/mydb
    depends_on:
      - db
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: pass
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

Notice the app connects to `db` — Compose gives each service a DNS name matching its key, so containers can reach each other by name instead of hardcoded IPs.

## Volumes

Container filesystems are ephemeral by default — delete the container, lose the data. A **volume** persists data outside the container's lifecycle (`db-data` above), which is why the database's actual data survives `docker compose down` and comes back on `docker compose up`.

## Basic networking

By default, Compose puts all services in one project on a shared network, so `app` can reach `db:5432` without any extra configuration. Exposing a port to your host machine (`"3000:3000"`) is a separate concern from inter-container networking — you only need host port mapping for whatever you actually access from outside Docker (usually just the app, not the database).

## Practice tip

Containerize an existing Node/Next app end-to-end: write the Dockerfile, add Postgres via Compose, and get the app talking to the database entirely inside Docker. That full loop — not just `docker run hello-world` — is what Month 2's project actually asks for.
