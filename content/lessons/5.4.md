# Async & Messaging

When someone places an order on an e-commerce site, the server has to: validate the cart, charge the payment, send a confirmation email, update the inventory count, notify the warehouse system, and update the search index. How long should the user have to wait while all of that happens?

The intuitive answer — just do all of it before responding — creates fragile, slow systems. If the email service is temporarily slow, the user waits 8 seconds. If the warehouse notification service is down, the entire checkout fails. Everything is coupled to everything else.

Asynchronous messaging breaks this coupling. It lets you build systems where each component does its job independently, failures don't cascade, and slow services don't make fast services slow. Understanding this pattern deeply is essential for designing any non-trivial distributed system.

## Theory & Fundamentals

### The Problem with Synchronous Everything

To understand why asynchronous communication matters, let's look closely at what happens in the synchronous model.

Service A calls Service B and **waits**. Service B must be:
- **Up**: if B is down, A gets an error (or hangs)
- **Fast**: if B is slow, A is slow too — the user waits
- **Available**: if B is overloaded, A is overloaded too

This creates a chain of dependencies. In a system with 10 services that all call each other synchronously, the availability of the whole system is the **product** of each service's availability. If each service is up 99.9% of the time (impressive), the chain is up 99.9%^10 = 99.0% of the time. That's almost 9 hours of downtime per year, even though every individual service is highly reliable.

The performance problem is equally severe. Suppose the checkout flow calls 5 services sequentially, each taking 100ms:

```
User waits for:
  validate_cart()    → 100ms
  charge_payment()   → 200ms (payment processors are slow)
  send_email()       → 150ms
  update_inventory() → 80ms
  notify_warehouse() → 120ms
  ─────────────────────────
  Total wait:          650ms
```

Now imagine the email service has an outage. The `send_email()` call times out after 5 seconds. Your checkout now takes 5.65 seconds, and if the email service stays down, your checkout fails entirely — even though the important parts (payment charged, order saved) worked perfectly.

**The key insight: most of that work doesn't need to happen before you respond to the user.**

The user needs to know their payment was accepted and their order is saved. They do not need to wait for the warehouse notification to complete. They don't need to wait for the search index to update. Those things just need to happen *eventually*.

Asynchronous messaging lets you respond to the user as soon as the critical work is done, and push the rest to a queue for background processing.

### Message Queues — The Foundation

A message queue is the simplest async primitive: a buffer that sits between a producer (the thing that creates work) and a consumer (the thing that does the work).

```
Producer                Queue                  Consumer(s)
───────            ──────────────           ──────────────
API Server  ──▶   [ msg1 | msg2 | msg3 ]  ──▶  Worker
(enqueues          (persistent storage)         (processes)
immediately,
returns 200)
```

The producer puts a message in the queue and immediately moves on. It doesn't wait for the consumer to process it — the queue accepts the message and takes responsibility for delivering it. The consumer pulls messages when it's ready, processes them at its own pace, and acknowledges each one when done.

This gives you four powerful properties:

**1. Decoupled availability**

The producer and consumer don't need to be running at the same time. If the consumer crashes and restarts, messages that arrived during the downtime are still in the queue waiting. The producer keeps running and keeps producing — it doesn't even know the consumer was down.

**2. Message durability**

Good message queue systems persist messages to disk. If the queue server itself crashes and restarts, messages survive. The contrast: an in-memory channel or a direct HTTP call is not durable — if the process crashes during transit, the message is lost.

**3. Load buffering**

If traffic suddenly spikes (Black Friday at midnight), the producer can enqueue messages faster than the consumer processes them. The queue absorbs the burst. Consumers process at a steady rate, protecting downstream systems from being overwhelmed. Without a queue, the spike hits the downstream service directly and potentially crashes it.

**4. Work distribution**

Multiple consumer instances can pull from the same queue, splitting the work. If you have 100 messages and 10 workers, each worker gets roughly 10 messages. Scaling the consumer is as simple as starting more worker processes.

**What's in a message?**

A message is typically a small JSON payload describing the work to be done:

```json
{
  "messageId": "msg-abc-123",
  "type": "order.placed",
  "orderId": "ord-456",
  "userId": "user-789",
  "timestamp": "2024-01-15T14:30:00Z",
  "data": {
    "items": [...],
    "total": 99.99
  }
}
```

Notice the `messageId`. This will become important when we discuss idempotency.

**Acknowledgment and redelivery**

When a consumer receives a message, it doesn't automatically disappear from the queue. The message is held in a "processing" state. Only after the consumer explicitly acknowledges it (says "I processed this successfully") does the queue delete it.

If the consumer processes the message but then crashes before acknowledging, the queue's timer expires and it redelivers the message to another consumer. This is what makes message queues reliable: messages are not lost if a consumer crashes mid-processing.

This design decision — acknowledge only after successful processing — is fundamental. Configure your queue system this way. Don't use "fire and forget" mode where messages are deleted as soon as they're delivered; that mode loses messages on consumer crashes.

**Common queue systems**

- **Amazon SQS**: managed, highly reliable, simple API. No setup. Good default for AWS-based systems.
- **RabbitMQ**: self-hosted, feature-rich, supports complex routing. Good when you need flexible routing rules.
- **BullMQ**: Node.js library built on Redis. Great for application-level job queues where you're already using Redis.
- **Kafka**: not a queue but a persistent log (more on this later — it has different semantics).

**Dead-letter queues — handling the unfixable**

Some messages fail to process not because of a transient error (network blip, temporary service outage) but because of a fundamental problem with the message itself: malformed data, a referenced record that doesn't exist, a bug in the consumer code. These are called **poison messages**.

Without handling poison messages, a retried poison message loops forever: the consumer picks it up, fails, it goes back to the queue, repeat. This blocks other messages from being processed and causes alert fatigue.

The solution: configure a **dead-letter queue (DLQ)**. After a message fails processing N times (e.g., 5 retries), the queue moves it to the DLQ instead of retrying again. The main queue keeps processing. An operator can inspect the DLQ to understand why messages failed, fix the underlying bug, and then replay the messages through the main queue.

DLQs are essential for production systems. Setting them up takes 10 minutes and prevents a category of incident that would otherwise require manual intervention at 3am.

### Pub/Sub — Fan-out Communication

A standard message queue delivers each message to **one** consumer. This is the right model for task distribution: you want exactly one worker to process each order, not multiple workers doing the same work in parallel.

But sometimes you want **multiple independent systems** to react to the same event. When a user signs up, you want to: send a welcome email, create their analytics record, provision their trial, and add them to your CRM. These are four separate concerns, and you don't want the signup process to know about all of them.

This is the Publish-Subscribe (pub/sub) pattern.

```
Auth Service publishes: "user.signed_up" event
          │
          ▼
      [Topic/Bus]
          │
    ┌─────┼─────┐─────────┐
    ▼     ▼     ▼         ▼
  Email  Anal- Trial    CRM
  Svc   ytics  Svc      Svc
        Svc
```

The publisher (Auth Service) emits an event to a topic without knowing who subscribes. Subscribers register their interest in the topic and receive a copy of each event. Adding a new subscriber (say, a fraud detection service) requires no changes to the publisher.

**Why this decoupling matters**

In the synchronous world, if you want to add a "send to CRM" step to signup, you modify the signup code. You need to know about the CRM service, import its client, handle its errors, add its latency to the signup response time. Over time, the signup endpoint accumulates 15 different concerns and becomes impossible to modify safely.

With pub/sub, signup emits one event. Adding CRM integration means adding one new subscriber — a separate service, separate deployment, separate team — with zero changes to the signup service. The publisher doesn't even know it happened.

**The concrete example: growing a "user.signed_up" topic**

```
Day 1 (v1):
  Auth Service → "user.signed_up" → Email Service (sends welcome email)

Day 30 (v2, zero changes to Auth Service):
  Auth Service → "user.signed_up" → Email Service
                                  → Analytics Service

Day 90 (v3, still zero changes to Auth Service):
  Auth Service → "user.signed_up" → Email Service
                                  → Analytics Service
                                  → Trial Provisioner
                                  → CRM Connector
```

Each new subscriber was added independently. The Auth Service code never changed. This is the architectural leverage of pub/sub.

**Point-to-point vs. pub/sub: when to use which**

| Scenario | Pattern | Why |
|---|---|---|
| "Process this order" | Queue (point-to-point) | One worker should process each order exactly once |
| "A user signed up" | Pub/sub | Multiple services need to react independently |
| "Send this email" | Queue | One email sender should handle each job |
| "This metric was recorded" | Pub/sub | Multiple consumers (alerting, dashboard, logging) need it |

The rule: use a queue when you want exactly one thing to do the work. Use pub/sub when you want every interested party to react.

**Common pub/sub systems**

- **Amazon SNS + SQS**: SNS is the pub/sub layer (topics, fan-out). Each subscriber gets its own SQS queue. This gives each subscriber independent scaling, retry logic, and DLQ configuration. Very common in AWS architectures.
- **Apache Kafka**: a persistent, ordered log that supports multiple consumer groups reading the same data independently. More like pub/sub than a traditional queue, but with much higher throughput and replay capability.
- **Redis Pub/Sub**: simple, in-memory. No persistence — if no subscriber is connected when a message is published, it's lost. Use only for fire-and-forget notifications, not business-critical events.

### Idempotency — Handling Duplicate Delivery

Here's the critical property of almost every real-world message queue and pub/sub system: **messages are delivered at least once**. Not exactly once. At least once.

Why? Consider what happens when a consumer processes a message successfully but then crashes before sending the acknowledgment. The queue doesn't know the message was processed — from its perspective, the message timed out. So it redelivers the message. Now the message gets processed twice.

This is not a bug in the queue system. It's an unavoidable consequence of the fundamental trade-off: to guarantee delivery, you must accept possible duplication. The alternative (exactly-once, where you're guaranteed no duplicates) requires expensive distributed transactions and is either very slow or, in many systems, impossible to truly guarantee.

**What idempotency means**

An operation is **idempotent** if performing it multiple times produces the same result as performing it once.

- HTTP GET is idempotent: reading the same resource twice doesn't change anything.
- "Set user's email to x@example.com" is idempotent: doing this twice still results in email = x@example.com.
- "Charge user $10" is NOT idempotent: doing this twice charges $20.
- "Create a user record" is NOT idempotent: doing this twice creates two records (or an error on the second attempt).
- "Send a welcome email" is NOT inherently idempotent: doing this twice sends two emails.

**Why messaging systems require idempotent consumers**

If your message queue delivers messages at least once, and your consumer is not idempotent, then duplicate delivery will cause bugs. At low scale, duplicates are rare and you might not notice. At high scale, "at-least-once" becomes "definitely sometimes twice," and bugs become frequent.

The pattern: **make your consumers idempotent so duplicate delivery is harmless**.

**Implementation: the idempotency key**

The most common approach: include a unique ID with each message. Before processing, check if you've already processed this ID. If yes, skip. If no, process and record the ID.

```js
async function processPaymentMessage(message) {
  const { messageId, userId, amount } = message;

  // Check if we've already processed this message
  const alreadyProcessed = await db.query(
    'SELECT id FROM processed_messages WHERE message_id = $1',
    [messageId]
  );

  if (alreadyProcessed.rows.length > 0) {
    console.log(`Skipping duplicate message ${messageId}`);
    return; // Idempotent: do nothing
  }

  // Process the payment
  await chargeUser(userId, amount);

  // Record that we processed this message
  // (in the same transaction as the business logic, if possible)
  await db.query(
    'INSERT INTO processed_messages (message_id, processed_at) VALUES ($1, NOW())',
    [messageId]
  );
}
```

The critical detail: inserting the processed record and performing the business operation should happen in the same database transaction. If the business operation succeeds but the record insert fails, you'll process the same message again on retry. If the record insert succeeds but the business operation fails, you'll skip it on retry even though it didn't complete. Transaction semantics give you safety.

**Natural idempotency**

Some operations are naturally idempotent and don't need explicit deduplication logic. Prefer these:

```
NOT idempotent: "Add $10 to user 123's balance"
    → processing twice adds $20

Idempotent equivalent: "Set user 123's balance to $110"
    → processing twice still sets balance to $110
```

```
NOT idempotent: "Create a user record for alice@example.com"
    → processing twice may create duplicate records

Idempotent equivalent: "Upsert: if user with alice@example.com
    doesn't exist, create; if it does, update with these fields"
    → safe to run twice
```

When designing the messages your consumers receive, lean toward naturally idempotent operations where possible. Reserve the explicit idempotency-key approach for operations that can't be made naturally idempotent (like sending emails or charging payments).

**Common mistake: "duplicates rarely happen, so I don't need to handle them"**

At 100 requests per day, duplicates might happen once a month. At 100 million requests per day, duplicates happen thousands of times a day. "Rarely" at small scale becomes "constantly" at large scale. Build idempotency into your consumers from the start — retrofitting it after a double-charge incident is much harder.

### Event-Driven Architecture — The Big Picture

Individual message queues and pub/sub topics are tools. Event-driven architecture is the broader pattern that emerges when you build an entire system around these tools.

In a traditional synchronous system, services know about each other and call each other directly:

```
OrderService calls PaymentService calls InventoryService
     ↓                  ↓                    ↓
     (tight coupling — changing one requires updating all callers)
```

In an event-driven system, services communicate only through events. No service calls another service directly:

```
OrderService  →  "order.created" event  →  [Event Bus]
                                                │
                                    ┌───────────┼───────────┐
                                    ▼           ▼           ▼
                              PaymentSvc  InventorySvc  EmailSvc
                              (subscribes)(subscribes) (subscribes)
```

Each service subscribes to the events it cares about and reacts independently. OrderService doesn't know PaymentService exists. If you add a new FraudDetectionService tomorrow, you subscribe it to "order.created" — the OrderService never changes.

**The advantages**

- **Loose coupling**: services don't know about each other. Changing one service doesn't break others.
- **Easy extensibility**: add a new feature by adding a new subscriber, not by modifying existing services.
- **Natural resilience**: a slow or down subscriber doesn't affect the publisher.
- **Audit trail**: the event stream is a record of everything that happened in your system, in order.

**The challenges**

- **Debugging complexity**: when something goes wrong, the chain of events is spread across multiple services and asynchronous processes. Tracing a bug requires distributed tracing tools and careful log correlation.
- **Eventual consistency**: changes in one service take time to propagate to others. The system is only eventually consistent. This is fine for most operations but requires careful thinking for anything user-facing.
- **Event ordering**: events can arrive out of order. If "order.cancelled" arrives before "order.created" due to network conditions, consumers need to handle this gracefully.
- **Testing is harder**: unit testing a service that emits events is straightforward; integration testing a multi-service event-driven flow is complex.

**Event sourcing: storing events instead of state**

Event sourcing is a more radical application of the event-driven idea: instead of storing the current state of a record (user balance = $150), you store the sequence of events that produced that state (deposited $200, withdrew $50). The current state is computed by replaying the event log.

Benefits: complete audit history, ability to reconstruct state at any point in time, natural fit for event-driven architecture.

Costs: more complex to query (you can't just `SELECT balance FROM accounts`), eventual consistency by nature, and replaying a long event log can be slow (mitigated by periodic snapshots).

Event sourcing is powerful but adds significant complexity. Use it when the audit history IS the core value (financial systems, compliance-heavy domains, collaborative editors) and avoid it otherwise.

### Delivery Guarantees — At-Most-Once, At-Least-Once, Exactly-Once

Not all messaging systems make the same delivery promises. Understanding these guarantees — and their implications — is essential for designing reliable systems.

**At-most-once delivery**

The message is delivered zero or one times. The system won't retry on failure, so messages can be dropped.

```
Producer → [Network] → Consumer
           (if network fails, message is lost)
```

This sounds bad, but there are legitimate use cases:
- **Metrics and telemetry**: losing 0.1% of metric data points is acceptable
- **Log ingestion**: dropping a few log lines during a network hiccup is fine
- **Real-time notifications**: if you miss a "user is typing" notification, nobody cares

The advantage: no complexity around deduplication, no storage overhead, low latency. Use at-most-once only when losing a fraction of messages is genuinely acceptable.

**At-least-once delivery**

The message is delivered one or more times. The system persists the message and retries until the consumer acknowledges it.

This is the most common delivery guarantee for business systems. Messages are never lost (the system keeps retrying), but they might be delivered more than once. This is why **idempotency is required** for at-least-once delivery.

Most message queues (SQS, RabbitMQ) provide at-least-once delivery by default. It's the right choice for any event where losing a message would have business impact: orders, payments, user registrations.

**Exactly-once delivery**

The holy grail: every message is delivered exactly one time, with no duplicates. Sounds ideal, right?

Here's the problem: truly guaranteeing exactly-once delivery in a distributed system is theoretically possible but practically very hard and expensive. It requires coordination between the producer, the broker (queue), and the consumer — all three must agree on state, which requires distributed transactions. In the face of network failures and crashes, maintaining this coordination is slow.

What Kafka calls "exactly-once" is more precisely "effectively exactly-once" through a combination of:
- Idempotent producers (Kafka deduplicates producer retries)
- Transactional publishing (multiple messages committed atomically)
- Consumer-side idempotency

This is very powerful but adds significant operational complexity. In practice, most systems use **at-least-once delivery with idempotent consumers**, which achieves the same result for business purposes at much lower cost.

**Choosing the right guarantee**

| Scenario | Guarantee | Why |
|---|---|---|
| Metrics, telemetry | At-most-once | Occasional loss is fine; simplicity wins |
| Email notifications | At-least-once + idempotent consumer | Can't lose it; duplicate detection needed |
| Payment processing | At-least-once + idempotent consumer | Critical to not lose; double-charge must be prevented |
| Real-time dashboard updates | At-most-once | Stale data is refreshed soon anyway |
| Order processing | At-least-once + idempotent consumer | Can't lose orders; idempotent handlers prevent double processing |

## Core Patterns / Techniques

### Separating the Request Path from the Background Path

One of the most valuable techniques in system design: for every operation, explicitly identify what the user needs to wait for vs. what can happen in the background.

```
User places an order:

Request path (user waits for response):
  ├─ Validate cart (items exist, prices correct)
  ├─ Charge payment (synchronous — user needs confirmation)
  ├─ Save order to database (durable, user needs confirmation)
  └─ Return 201 Created with order ID    ← RESPOND HERE

Background path (enqueued for async processing):
  ├─ Send confirmation email
  ├─ Update inventory count
  ├─ Notify warehouse system
  ├─ Update search index
  └─ Create analytics event
```

The request path is kept minimal — just the operations the user needs to know the result of. Everything else is pushed to a queue. Response time drops from 650ms to perhaps 150ms. Availability improves because failures in email/warehouse/search don't fail the order.

In system design interviews, explicitly drawing this line demonstrates sophisticated thinking about user experience and system resilience.

### Fan-Out with SNS + SQS (AWS Pattern)

When multiple services need to react to the same event, the SNS + SQS combination gives each subscriber independent failure handling:

```
Order Service
      │
      ▼
 SNS Topic: "order.placed"
      │
   ┌──┼──┐──────────────┐
   ▼  ▼  ▼              ▼
  SQS SQS SQS          SQS
   │   │   │            │
Email  Inv  Warehouse  Analytics
Worker Wkr  Worker     Worker
(5 retries) (5 retries) (no DLQ — best effort)
```

Each SQS queue can have different retry policies, DLQ configurations, and visibility timeouts. The email worker can retry aggressively; the analytics worker can be configured as fire-and-forget. The SNS topic doesn't care — it just fans out.

### The Idempotency Key Pattern

```js
// Standard idempotency key implementation for a message consumer

async function processMessage(message) {
  const idempotencyKey = message.messageId;

  // Atomic check-and-set: if key doesn't exist, set it (returns true)
  // If key already exists, don't overwrite (returns false)
  const isNew = await redis.set(
    `processed:${idempotencyKey}`,
    '1',
    'EX', 86400,  // 24-hour TTL (clean up old keys)
    'NX'          // Only set if Not eXists
  );

  if (!isNew) {
    // Already processed — skip safely
    return { status: 'skipped', reason: 'duplicate' };
  }

  // Process the message for the first time
  await doBusinessLogic(message);
  return { status: 'processed' };
}
```

Note the Redis `SET ... NX` (set if not exists) command — this is atomic in Redis, preventing race conditions between two consumer instances simultaneously processing the same message.

### Dead-Letter Queue Topology

```
Main Queue ──▶ Consumer ──▶ Success: acknowledge, done
                    │
                    └──▶ Failure (retry 1)
                               │
                               └──▶ Failure (retry 2)
                                          │
                                          └──▶ Failure (retry 3)
                                                     │
                                                     ▼
                                              Dead Letter Queue
                                              (retained for inspection)
                                                     │
                                                     ▼
                                              Alerts/Dashboard
                                              (notify on-call)
```

Monitor your DLQ. A sudden spike in DLQ messages means a bug in your consumer or a corrupt batch of messages. Set an alert for any DLQ with >0 messages.

## Best Practices

- **Always use acknowledgment-after-processing semantics** — configure your queue to mark messages in-flight, not deleted, on delivery. Only delete after the consumer explicitly acknowledges. This prevents message loss on consumer crashes.
- **Set up dead-letter queues from day one** — configure them before you go to production, not after your first poison-message incident.
- **Design consumers to be idempotent from the start** — retrofitting idempotency after a double-processing incident is much harder than building it in initially.
- **Keep messages small** — a message should contain an event description and identifiers, not large payloads. If a consumer needs more data, let it fetch it. Large messages slow down queue throughput.
- **Set a message retention policy** — messages in a queue should expire if not processed within a reasonable window (e.g., 4 days for SQS max). Stale messages often indicate a consumer bug and should expire rather than waiting forever.
- **Use exponential backoff for retries** — on failure, don't immediately retry. Wait 1 second, then 2, then 4, then 8. Immediate retries on a failing consumer can overwhelm a struggling downstream dependency.
- **Log the message ID at the start of processing** — this makes tracing duplicate delivery incidents trivial: search your logs for a specific message ID and see exactly how many times it was processed and what happened each time.
- **Think carefully before using at-most-once** — it's tempting to skip idempotency work, but at-most-once means accepting message loss. Make this a deliberate choice with explicit product/engineering sign-off.

## Common Interview Questions

**Q1: What is the difference between a message queue and pub/sub?**
A: A message queue delivers each message to exactly one consumer — used for work distribution where you want one worker to handle each job. Pub/sub delivers each event to all subscribers — used for fan-out where multiple independent systems need to react to the same event. In practice, systems like SNS+SQS combine both: SNS does pub/sub (fan-out to multiple subscribers), and each subscriber gets its own SQS queue (point-to-point delivery to workers).

**Q2: Why is at-least-once delivery the standard instead of exactly-once?**
A: Because exactly-once delivery requires coordination between the queue, producer, and consumer to survive failures — essentially a distributed transaction. This adds significant latency and complexity, and in systems with certain failure modes, true exactly-once is actually impossible. At-least-once is achievable reliably with much lower overhead. The trade-off — accepting duplicate delivery and requiring idempotent consumers — is almost always better than paying the cost of exactly-once semantics.

**Q3: What is a dead-letter queue and when does a message end up there?**
A: A DLQ is a special queue for messages that have failed processing too many times. When a message fails to process (consumer throws an error, or times out) and gets retried, most queue systems will try it a configured number of times (e.g., 5). After the last retry fails, the message is moved to the DLQ instead of being discarded or retried again. This isolates "poison messages" (those that always fail due to a bug or bad data) from the main queue, lets the main queue continue processing, and gives you a place to investigate failures.

**Q4: How do you design an idempotent consumer?**
A: Two main approaches. First, make the operation naturally idempotent: design the operation so that doing it twice has the same effect as once (e.g., "set email to X" rather than "append X to email list"). Second, use an idempotency key: each message carries a unique ID. Before processing, check whether you've already processed this ID (stored in a database or cache). If yes, skip. If no, process and record the ID. The check-and-process should ideally be in the same database transaction to prevent race conditions.

**Q5: What is the fan-out-on-write vs. fan-out-on-read trade-off?**
A: Fan-out-on-write: when an event occurs, immediately push it to all interested parties. Reads are fast because data is pre-computed. Writes are expensive for high-fan-out events (e.g., a celebrity posting to 10M followers). Fan-out-on-read: when a user requests data, compute it on the fly from multiple sources. Writes are cheap, but reads are slow and put load on the database. The hybrid approach: fan-out-on-write for most cases, fan-out-on-read for very high fan-out cases (celebrities). This is how Twitter's news feed actually works.

**Q6: How does async messaging improve system resilience?**
A: By decoupling producer availability from consumer availability. If the email service is down in a synchronous system, any operation that sends emails fails. In an async system, the "send email" message is placed in a queue. The operation that triggered it succeeds immediately. When the email service recovers, it drains the queue and sends all the emails. The queue absorbed the failure and retained the work. This also means slow consumers don't make producers slow: the producer enqueues and moves on regardless of how backed up the consumer is.

**Q7: What is event sourcing and when is it appropriate?**
A: Event sourcing stores a sequence of events (what happened) rather than current state (what is). The current state is derived by replaying events from the beginning (or from a snapshot). It's appropriate when: audit history is a core product requirement (financial transactions, compliance systems), you need point-in-time state reconstruction, or the domain naturally has event semantics. It adds complexity (queries are harder, replaying long logs is slow) and is a significant architectural commitment. Avoid it when current-state storage meets your needs.

**Q8: What is the difference between Kafka and a traditional message queue like SQS?**
A: Kafka is a persistent, ordered, replayable log. Messages are retained for a configurable time (days to weeks) even after consumption. Multiple consumer groups can independently read the same messages at their own pace. It handles very high throughput (hundreds of thousands of messages/second). Messages are ordered within a partition. SQS is a simpler task queue: messages are deleted after successful processing, there's no replay, and ordering is best-effort (not guaranteed). Use Kafka for event streaming, event sourcing, and audit trails where you need replay and multiple consumers. Use SQS for simpler "process this task once" background jobs.

**Exercise 1 — Sync to Async Redesign (Beginner)**

An e-commerce checkout API makes these calls synchronously, in order:
1. Validate cart items and prices (50ms)
2. Reserve inventory (80ms)
3. Charge the credit card (300ms)
4. Save the order to the database (40ms)
5. Send a confirmation email (200ms)
6. Update the product search index (150ms)
7. Notify the warehouse API (120ms)
8. Create a analytics event (60ms)

Total current latency: ~1,000ms. The payment processor and warehouse API are third-party and occasionally slow.

Which steps must remain synchronous (the user needs the result before you respond)? Which can be moved to an async queue? What would the new latency be? What happens to the user experience if the warehouse API goes down after your redesign?

Hint: The user cares about inventory (they need to know their item is reserved), payment result, and order confirmation. They do not need to wait for downstream notifications.

**Exercise 2 — Idempotent Consumer Design (Intermediate)**

A payment processor sends webhook events to your API when a payment completes. The event looks like:

## Key Takeaways

- Synchronous communication couples services together: slow downstream makes upstream slow, and down downstream makes upstream fail. Async messaging breaks this coupling.
- A message queue sits between producers and consumers, providing durable storage, load buffering, work distribution, and decoupled availability.
- Pub/sub (one event, many subscribers) is for fan-out. Point-to-point queues (one message, one consumer) are for task distribution. Use each for its purpose.
- At-least-once delivery is the standard: messages are never lost, but can be delivered more than once. This is why idempotency is required for all message consumers.
- An idempotent consumer produces the same result whether it processes a message once or a hundred times. Implement via idempotency keys (unique message IDs stored in a database) or naturally idempotent operations.
- Dead-letter queues are essential: they isolate poison messages after N retries, let the main queue keep moving, and give you a place to investigate failures.
- Separate the request path (user waits) from the background path (async). Keep the request path minimal: accept, validate, persist the critical data, return. Push everything else to a queue.
- Event-driven architecture maximizes loose coupling: services communicate only through events, new features are added as new subscribers, and failures are contained.
- Exactly-once delivery is very hard in distributed systems. At-least-once delivery with idempotent consumers achieves the same practical result at much lower cost.
