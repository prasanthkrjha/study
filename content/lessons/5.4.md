# Async & Messaging

Not every operation needs to happen synchronously in the request/response cycle. This unit covers the tools for decoupling "the user needs an immediate response" from "the work actually needs to happen."

## Message queues

A queue sits between a **producer** (something that creates work) and a **consumer** (something that processes it), holding messages until a consumer is ready. This decouples the two: the producer doesn't need the consumer to be available or fast at the moment of sending, it just enqueues and moves on.

```
Producer → [ Queue: order-processing ] → Consumer
```

Example: when a user places an order, the API can immediately respond "order received" while a queued job handles sending the confirmation email, updating inventory, and notifying a warehouse system — none of which the user needs to wait for.

## Why this matters for reliability, not just speed

Queues also add resilience: if a consumer crashes mid-processing, most queue systems (with acknowledgment semantics) redeliver the message instead of losing it. This is a meaningfully different reliability model than a direct synchronous call, which simply fails if the downstream service is down at that exact moment.

## Pub/sub (publish-subscribe)

A related but distinct pattern: a publisher emits an event without knowing (or caring) who's listening, and any number of subscribers can independently receive and react to it.

```
Publisher → topic: "user.signed_up" → Subscriber A (send welcome email)
                                     → Subscriber B (create analytics record)
                                     → Subscriber C (add to CRM)
```

The key difference from a queue: a queue message is typically consumed by **one** worker (work distribution); a pub/sub event can be received by **many** independent subscribers (fan-out/notification). Choose a queue when you want exactly one worker to do a piece of work; choose pub/sub when multiple independent systems all need to react to the same event.

## Event-driven architecture

A broader architectural style where services communicate primarily by emitting and reacting to events, rather than calling each other directly (synchronous request/response). Benefits: services are more decoupled (a new subscriber can be added without touching the publisher), and the system is naturally more resilient to a single service being temporarily down. Costs: harder to trace a request's full path (it's spread across multiple asynchronous event handlers instead of one call stack), and you have to design for eventual consistency — other parts of the system won't reflect an event immediately, only shortly after.

## Recognizing when async/messaging is the right call

Ask: "Does the user need to wait for this specific piece of work to finish before they get a response?" If the answer is no (sending an email, generating a report, updating a search index, notifying a third-party webhook), it's a strong candidate to move off the synchronous request path and into a queue or event. If the user needs the result immediately to proceed (checking whether a payment succeeded), it usually stays synchronous.

## Practice tip

For any "design X" system design question, explicitly separate the request path (what the user waits for) from the background path (what can happen asynchronously afterward) — this separation is often the single most valuable thing you can draw on the whiteboard.
