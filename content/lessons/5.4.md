# Async & Messaging

Not every operation needs to happen synchronously in the request/response cycle. This unit covers the tools for decoupling "the user needs an immediate response" from "the work actually needs to happen."

## Theory & Fundamentals

### Why Async Processing

When a user places an order, the API server needs to: save the order to the database, charge the payment, send a confirmation email, update inventory, notify the warehouse, and update the search index. If all of this happens synchronously, the user waits for all of it. More importantly, if the email service is slow or down, the entire request fails.

Async processing solves both problems: the API responds as soon as the critical path is complete (order saved, payment processed), and the non-critical work (email, search indexing, warehouse notification) happens in the background — faster responses and isolated failures.

### Message Queues

A queue sits between a **producer** (creates work) and a **consumer** (processes work), holding messages until the consumer is ready:

```
Producer → [ Queue: order-processing ] → Consumer(s)
```

**Core properties**:
- **Decoupled**: producer doesn't need the consumer to be available at the moment of enqueue
- **At-least-once delivery**: most queue systems redeliver a message if the consumer crashes before acknowledging it — the message isn't lost
- **Load buffering**: a spike in producer activity fills the queue; consumers process at their own rate, preventing downstream overload
- **Work distribution**: multiple consumer instances pull from the same queue, splitting work evenly (competing consumers pattern)

**Common queue systems**: SQS (AWS, managed), RabbitMQ (self-hosted, feature-rich), BullMQ (Node.js + Redis, simple).

### Pub/Sub (Publish-Subscribe)

A related but distinct pattern: a publisher emits an event without knowing who's listening; any number of subscribers independently receive and react to it:

```
Publisher → topic: "user.signed_up"
              ├→ Subscriber A: send welcome email
              ├→ Subscriber B: create analytics record
              └→ Subscriber C: add to CRM
```

**The key distinction**: a queue message is typically consumed by **one** worker (work distribution — "do this task once"). A pub/sub event is received by **many** independent subscribers (fan-out — "everyone who cares, react now"). Choose a queue when exactly one worker should do a piece of work. Choose pub/sub when multiple independent systems need to react to the same event.

**Common pub/sub systems**: SNS + SQS (AWS, fan-out to queues), Kafka (high-throughput streaming, persistent log), Redis Pub/Sub (simple, in-memory, no persistence).

### Event-Driven Architecture

A broader architectural style where services communicate primarily by emitting and reacting to events, rather than calling each other synchronously:

```
Traditional (synchronous):
OrderService → calls → EmailService → calls → InventoryService → ...

Event-driven (asynchronous):
OrderService → emits "order.placed" → [message bus]
                                          ├→ EmailService (subscribes)
                                          └→ InventoryService (subscribes)
```

**Benefits**:
- Services are decoupled — a new subscriber can be added without touching the publisher
- Natural resilience — a subscriber being down doesn't fail the publisher; it just processes events when it recovers
- Better scalability — each service scales independently

**Costs**:
- Harder to trace a full request (spread across multiple async handlers instead of one call stack)
- **Eventual consistency** — other parts of the system won't reflect an event immediately, only after processing
- Complex error handling — a failed subscriber may retry indefinitely; you need dead-letter queues for unprocessable messages

### Dead-Letter Queues

When a consumer repeatedly fails to process a message (after N retries), instead of losing the message or retrying forever, move it to a **dead-letter queue (DLQ)** — a separate queue for failed messages that require manual inspection or a different processing path.

Without DLQs, a single poison message (one that always fails) can block a queue indefinitely. With DLQs, the poison message is isolated after N retries, the main queue continues processing, and an operator can inspect the failed message.

## Core Patterns / Techniques

### The Request Path vs. Background Path

For any "design X" question, explicitly separate:

1. **Request path** — what the user synchronously waits for. Minimize this: accept, validate, and persist the triggering action. Return quickly.
2. **Background path** — what can happen asynchronously. Defer all non-critical work here.

```
User places order:
  Request path:  validate order → charge payment → save order → return 201
  Background:    send email, update inventory, notify warehouse, update search index
```

### Idempotency

Because queues deliver at least once, a consumer may process the same message more than once (e.g., if it crashes after processing but before acknowledging). Design consumers to be **idempotent** — processing the same message twice has the same result as processing it once.

Technique: include a unique `messageId` with each event. The consumer checks if it has already processed this ID (stored in a database or cache) and skips if so.

### Fan-Out Pattern with SNS + SQS

```
Order Service → publishes to SNS topic "order.placed"
                  ├→ SQS queue → Email Worker
                  ├→ SQS queue → Inventory Worker
                  └→ SQS queue → Analytics Worker
```

Each downstream service gets its own SQS queue subscribed to the SNS topic. This gives each service independent scaling, retry policies, and DLQ configurations.

## Best Practices

- **Ask "does the user need to wait for this?" for every operation** — if no, move it to a background queue.
- **Always use acknowledgment semantics** — don't configure queues for "delete on receipt." Delete only after successful processing, so failed messages are redelivered.
- **Set retry limits and dead-letter queues** — without them, a poison message causes infinite retries and blocks the queue.
- **Design consumers to be idempotent** — at-least-once delivery is the norm; assume your consumer will process the same message more than once.
- **Separate queue vs. pub/sub by the fan-out requirement** — one consumer → queue; multiple independent consumers → pub/sub topic.
- **Kafka for streaming, SQS/RabbitMQ for task queues** — Kafka is a persistent, ordered log suited for high-throughput event streaming and replay. SQS/RabbitMQ are simpler and better for "process this task once and move on."

## Common Interview Questions

**Q1: What is the difference between a message queue and pub/sub?**
A: A queue typically delivers each message to one consumer (work distribution — exactly one worker does the job). Pub/sub delivers each event to all subscribers (fan-out — every subscriber independently reacts). Use a queue for tasks; use pub/sub for notifications/events that multiple systems care about.

**Q2: Why is at-least-once delivery the standard for message queues, rather than exactly-once?**
A: Exactly-once delivery is very hard to guarantee across distributed systems — it requires distributed transactions between the queue and the consumer's data store. At-least-once is easier: if a consumer fails after processing but before acknowledging, the queue redelivers. The cost is that consumers must handle duplicate delivery, which is why idempotency is required.

**Q3: What is a dead-letter queue and why is it important?**
A: A DLQ receives messages that have failed processing after a configured number of retries. Without a DLQ, a "poison message" (one that always causes the consumer to throw an error) would be retried indefinitely, blocking the queue and preventing other messages from being processed. With a DLQ, the poison message is isolated after N retries, allowing the queue to continue, and an operator can inspect and fix the bad message.

**Q4: What is the difference between Kafka and a traditional message queue like SQS or RabbitMQ?**
A: Kafka is a persistent, ordered, replay-able log. Messages are retained for a configurable period (days/weeks) and can be re-read from any offset. Multiple consumer groups can independently read the same stream at their own pace. It's designed for high-throughput event streaming (100,000s of messages/second). SQS/RabbitMQ are simpler task queues — messages are deleted after successful processing and are intended to be processed once. Use Kafka for event sourcing, stream processing, and audit trails; use SQS/RabbitMQ for background job processing.

**Q5: How does async messaging improve system resilience?**
A: If the email service is down and you call it synchronously, the order request fails. With async messaging, the order is saved and the email event is enqueued — the request succeeds. When the email service recovers, it processes the queued events. The queue buffers the failure, decoupling the upstream service's availability from the downstream service's availability.

**Q6: What is eventual consistency and when is it acceptable?**
A: Eventual consistency means all parts of the system will eventually reflect the latest state, but not immediately. After an order is placed, the inventory count in the search index might lag by a few seconds. This is acceptable when the user doesn't need immediate confirmation that every downstream system has updated. It's not acceptable for payment processing (a user needs to know synchronously if their payment succeeded) or any operation where the user makes decisions based on the result.

## Practice Exercises

1. **Async redesign**: An e-commerce checkout endpoint currently makes 6 synchronous calls: validate cart, charge payment, send confirmation email, update inventory, create shipping label, and send notification to a third-party analytics service. The endpoint takes 4 seconds on average. Identify which operations must stay synchronous and which can be moved async. Estimate the new response time.

2. **Idempotent consumer**: A payment processor sends webhook events to your API: "payment.succeeded" with a payment_id. Design the consumer such that processing the same webhook twice (due to network retry) does not charge the user twice. What data do you need to store and when?

3. **Queue topology**: Design the messaging topology for an order service that: (1) sends a confirmation email, (2) updates inventory in a separate inventory service, and (3) streams all events to an analytics system for real-time dashboards. Each has different failure handling requirements: email and inventory failures should retry up to 5 times; analytics failures can be tolerated (best-effort). Design the queues/topics/DLQs.

## Key Takeaways

- Async processing decouples response time from the completion of non-critical work — the user gets a fast response while background work completes independently.
- Queue: one message, one consumer (work distribution). Pub/sub: one event, many subscribers (fan-out/notification).
- At-least-once delivery means consumers must be idempotent — use a unique message ID to deduplicate.
- Dead-letter queues isolate poison messages after N retries, preventing one bad message from blocking the entire queue.
- Explicitly separate the request path (user waits) from the background path (async) in every design — this is one of the most valuable things you can communicate in a system design interview.
- Kafka for high-throughput persistent streaming (event sourcing, replay); SQS/RabbitMQ for simpler task queue workloads.
