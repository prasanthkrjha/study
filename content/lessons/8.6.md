# AI Agents & Tool-Calling

This unit marks the shift from "retrieves information" (RAG) to "takes action" — the differentiator explicitly named in senior AI job postings, and Month 4's central theme.

## Function/tool-calling: the core primitive

Every agent framework — LangGraph, AutoGen, the Claude Agent SDK, OpenAI's Agents SDK — is built on one underlying mechanism: the model is given a list of available "tools" (functions with a name, description, and parameter schema), and instead of only generating text, it can generate a **request to call one of those tools** with specific arguments. Your code executes the actual function and returns the result to the model, which then continues reasoning with that new information.

```python
tools = [
    {
        "name": "check_availability",
        "description": "Check if a time slot is available for booking",
        "parameters": {
            "type": "object",
            "properties": {"date": {"type": "string"}, "time": {"type": "string"}},
            "required": ["date", "time"],
        },
    }
]

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Is 3pm on Friday available?"}],
    tools=tools,
)

# The model responds with a tool call request instead of plain text:
# { "name": "check_availability", "arguments": {"date": "Friday", "time": "15:00"} }

# Your code executes the real function, then sends the result back:
result = check_availability(date="Friday", time="15:00")
# ...append result to the conversation, call the model again for a final natural-language response
```

The model never directly executes code — it only ever *requests* a call, with structured arguments. Your application is always the one actually running the function, which is what makes tool-calling safe to build guardrails around (validate arguments, restrict which tools are available, log every call).

## The ReAct pattern (Reason → Act → Observe)

ReAct is the loop that turns a single tool call into multi-step problem-solving: the model **reasons** about what to do next, **acts** by calling a tool, **observes** the result, and repeats — reasoning again with the new information — until it has enough to give a final answer.

```
Reason: I need to know if Friday 3pm is available before I can book it.
Act: call check_availability(date="Friday", time="15:00")
Observe: { "available": true }
Reason: It's available. I can now book it.
Act: call create_booking(date="Friday", time="15:00", name="Prasanth")
Observe: { "booking_id": "abc123", "status": "confirmed" }
Reason: The booking succeeded. I can tell the user it's confirmed.
```

This is the mechanism underneath "the assistant checked availability and booked a slot" — not a single clever prompt, but a loop of tool calls chained by the model's own reasoning between each one.

## The difference between a RAG pipeline and an agent

RAG retrieves information and generates a grounded answer — it's fundamentally a **read** operation, one pass through retrieve-then-generate. An agent can **act**: call tools that check state, mutate data, or trigger external systems, and it can chain multiple actions based on what earlier actions returned. Being able to state this distinction crisply, in one sentence, is explicitly called out as an interview-readiness target for Month 4.

## Practice tip

Build the smallest possible real tool-calling loop yourself: one tool, one realistic task (checking availability, looking up a record), and watch the model decide when to call it versus when to just answer from the conversation. That's the entire mechanism — everything in LangGraph (Unit 8.7) is this same primitive with more structure around multi-step state.
