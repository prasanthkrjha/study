# AI Agents & Tool-Calling

This unit marks the shift from "retrieves information" (RAG) to "takes action" — the differentiator explicitly named in senior AI job postings, and the central theme of Month 4.

## Theory & Fundamentals

### The Core Distinction: RAG vs. Agent

**RAG** retrieves information and generates a grounded answer — it's fundamentally a **read** operation. One pass: retrieve → generate. The model never acts on the outside world.

**An agent** can **act**: call tools that check state, mutate data, or trigger external systems, and chain multiple actions based on what earlier actions returned. The model decides what to do at each step based on what it's learned so far.

Being able to state this distinction crisply, in one sentence, is the interview-readiness target for this unit.

### Function/Tool-Calling: The Core Primitive

Every agent framework — LangGraph, the Claude Agent SDK, OpenAI's Agents SDK — is built on one mechanism: the model is given a list of available "tools" (functions with a name, description, and parameter schema), and instead of only generating text, it can generate a **request to call one of those tools** with specific arguments. Your code executes the actual function and returns the result to the model, which continues reasoning with that new information.

The model never directly executes code — it only ever *requests* a call. Your application is always the one running the function. This is what makes tool-calling safe to build guardrails around: validate arguments, restrict available tools, log every call.

### The ReAct Pattern (Reason → Act → Observe)

ReAct turns a single tool call into multi-step problem-solving:

```
Reason: I need to know if Friday 3pm is available before I can book it.
Act: call check_availability(date="Friday", time="15:00")
Observe: { "available": true }
Reason: It's available. I can now book it.
Act: call create_booking(date="Friday", time="15:00", name="Alice")
Observe: { "booking_id": "abc123", "status": "confirmed" }
Reason: Booking confirmed. I can tell the user.
Final answer: "Your appointment is confirmed for Friday at 3pm. Booking ID: abc123."
```

This is the mechanism underneath "the assistant checked availability and booked a slot" — not a single prompt, but a loop of tool calls chained by the model's own reasoning.

## Core Patterns / Techniques

### Basic Tool-Calling Loop

```python
import anthropic
import json

client = anthropic.Anthropic()

tools = [
    {
        "name": "check_availability",
        "description": "Check if a time slot is available for booking",
        "input_schema": {
            "type": "object",
            "properties": {
                "date": {"type": "string", "description": "Date in YYYY-MM-DD format"},
                "time": {"type": "string", "description": "Time in HH:MM format"},
            },
            "required": ["date", "time"],
        },
    },
    {
        "name": "create_booking",
        "description": "Create a booking for an available time slot",
        "input_schema": {
            "type": "object",
            "properties": {
                "date": {"type": "string"},
                "time": {"type": "string"},
                "name": {"type": "string", "description": "Name for the booking"},
            },
            "required": ["date", "time", "name"],
        },
    }
]

def run_tool(name, inputs):
    if name == "check_availability":
        return {"available": True}  # real impl would check a database
    if name == "create_booking":
        return {"booking_id": "abc123", "status": "confirmed"}

# The agent loop
messages = [{"role": "user", "content": "Book me a slot on 2026-08-10 at 15:00 under Alice"}]

while True:
    response = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=1024,
        tools=tools,
        messages=messages,
    )

    messages.append({"role": "assistant", "content": response.content})

    if response.stop_reason == "end_turn":
        # Model is done — extract the final text response
        final = next(b for b in response.content if b.type == "text")
        print(final.text)
        break

    # Process any tool calls
    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            result = run_tool(block.name, block.input)
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": json.dumps(result),
            })

    messages.append({"role": "user", "content": tool_results})
```

### Tool Definition Best Practices

```python
# Good tool definition — clear description, precise parameter descriptions
{
    "name": "search_products",
    "description": "Search the product catalog by keyword. Returns up to 10 matching products with their IDs, names, prices, and availability.",
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": "Search term. Use specific product features, not vague descriptions."
            },
            "max_price": {
                "type": "number",
                "description": "Optional maximum price in USD. Omit to include all prices."
            }
        },
        "required": ["query"]
    }
}

# Bad tool definition — vague, model will misuse it
{
    "name": "search",
    "description": "Search for stuff",
    "input_schema": {"type": "object", "properties": {"q": {"type": "string"}}}
}
```

The model uses your description and parameter descriptions to decide when and how to call the tool. Poor descriptions lead to incorrect calls.

## Best Practices

- **Validate tool inputs before executing** — the model generates arguments; treat them like user input. Check types, ranges, and permissions before running the actual function.
- **Log every tool call and result** — tool calls that mutate state (create a booking, send an email, charge a payment) must be logged for debugging and auditing.
- **Limit tool scope** — only give the agent the tools it needs for a specific task. An agent with 50 tools makes worse decisions than one with 5 focused tools.
- **Add guardrails for irreversible actions** — for actions that can't be undone (sending emails, charging payments, deleting records), add a confirmation step or require human approval before executing.
- **Design tools to be atomic** — one tool should do one thing. Avoid tools that do two different things depending on the arguments.

## Common Interview Questions

**Q1: What is the difference between a RAG pipeline and an agent?**
A: RAG is a read operation — retrieve information, generate a grounded answer, done. An agent can take actions: call tools that check or modify state, chain multiple tool calls based on what earlier calls returned, and loop until it has enough information to give a final answer. The key is that an agent acts in addition to reasoning.

**Q2: What is tool-calling and how does it work mechanically?**
A: The model is given a list of tools (name, description, parameter schema). Instead of generating only text, the model can generate a "tool use" request with specific arguments. The application executes the actual function, returns the result to the model as a tool result, and the model continues reasoning. The model never runs code directly — it requests function calls that your application executes.

**Q3: What is the ReAct pattern?**
A: Reason → Act → Observe, looped. The model reasons about what to do next, acts by calling a tool, observes the result, reasons again with the new information, and repeats until it has enough to give a final answer. It's the mechanism that turns a single tool call into multi-step problem-solving.

**Q4: How do you prevent an agent from taking destructive or unauthorized actions?**
A: Multiple layers: (1) Only include tools the agent actually needs (principle of least privilege). (2) Validate all tool inputs before executing. (3) For irreversible actions (delete, send, charge), require a separate confirmation step or human approval before executing. (4) Log all tool calls for auditing. (5) Implement rate limits on expensive tools.

**Q5: What happens if a tool call fails in the middle of a multi-step agent task?**
A: The tool returns an error result, which is added to the conversation. The model sees the error and decides what to do next: retry with different arguments, try an alternative approach, or return an error message to the user. Design your tools to return informative error messages that the model can act on rather than just exceptions.

## Practice Exercises

1. **Minimal agent**: Build the smallest possible tool-calling loop: one tool (e.g., look up a weather API or query a local database), one task, the full ReAct loop. Observe the conversation structure as the model reasons, calls the tool, and formulates the final answer.

2. **Multi-tool agent**: Extend to two tools: `check_availability` and `create_booking`. The model must call the first, evaluate the result, then decide whether to call the second. Add a third tool: `suggest_alternative_times` for when the requested slot is unavailable.

3. **Guardrails**: Add input validation to the `create_booking` tool: verify the date is in the future, the time is a valid time slot, and the booking doesn't duplicate an existing one. Return a structured error object (not an exception) when validation fails, and verify the model handles the error response correctly.

## Key Takeaways

- RAG reads information; agents take action — they call tools that can check or modify external state.
- Tool-calling is the core primitive: the model generates a tool-call request with arguments; your application runs the actual function and returns the result; the model continues reasoning.
- ReAct (Reason → Act → Observe) is the loop that chains tool calls into multi-step problem-solving.
- The model never executes code directly — always validate tool inputs as you would user input.
- Guardrails for irreversible actions (human-in-the-loop, confirmation steps) are the key safety pattern for production agents.
- Tool descriptions are part of the system prompt the model reasons over — poor descriptions lead to incorrect tool calls.
