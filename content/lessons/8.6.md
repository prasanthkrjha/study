# AI Agents & Tool-Calling

This unit marks a fundamental shift in what AI systems can do. Up to this point, you have built systems that *retrieve and generate* — they find relevant information and write an answer. But there's a whole category of tasks that retrieval cannot handle: "book me a flight," "send this email," "check if this product is in stock and order it," "search the web, find the three most relevant papers, and summarize their findings."

These tasks require *action* — the ability to interact with external systems, observe the results, and decide what to do next. That capability is what makes a system an *agent* rather than a pipeline.

This unit teaches you exactly how agents work at the mechanical level — not hand-waving about "AI reasoning," but the exact sequence of API calls, data structures, and loops that make agents possible.

## Theory & Fundamentals

### The Key Distinction: RAG vs. Agents

Let's be precise about the difference, because "AI system" covers too broad a range.

**RAG (Retrieval-Augmented Generation):**
- Input: user question
- Process: retrieve relevant chunks → stuff into prompt → generate answer
- Output: text answer
- What it *cannot* do: take any action, check live data, use external systems, make decisions over multiple steps

This is fundamentally a *read* operation. One pass: retrieve, generate, done. No loops. No decisions. No external calls beyond the embedding search and the model call.

**Agents:**
- Input: user goal (which may require multiple steps to achieve)
- Process: reason → call a tool → observe the result → reason again → call another tool → ... → generate final answer
- Output: text answer, but also real-world actions taken along the way
- What it *can* do: call APIs, search the web, read files, send messages, book things, check databases

The key difference is not intelligence — it's capability. An agent has *tools* it can use. A tool is just a function. The model decides when to call which tool, with what arguments, based on the current goal and what previous tools returned.

**Concrete example of the capability gap:**

Question: "Is the iPhone 15 in stock at the downtown store, and if so, reserve one for me?"

RAG: retrieves documents about iPhone 15, generates text like "iPhone 15 features include..." — completely useless.

Agent: calls `check_inventory(product="iPhone 15", store="downtown")` → result: "3 in stock" → calls `create_reservation(product="iPhone 15", store="downtown", customer_id=...)` → result: "Reserved, confirmation #R123" → generates "Done! I've reserved an iPhone 15 at the downtown store. Confirmation: #R123."

The agent actually did something. RAG only talked.

### How Tool Calling Works — Step by Step

This is the most important thing to understand in this lesson. Tool calling seems magical from the outside but is completely mechanical underneath. Let's trace through every step.

**Without tool calling:** you send a prompt, you get text back. That's the entire interaction.

**With tool calling:** you send a prompt *plus a list of tool definitions*. The model can respond with either text OR a request to call one of those tools.

Here is the exact flow for a weather query:

```
Step 1: USER SENDS MESSAGE
─────────────────────────────────────────────────
User: "What's the weather in Paris right now?"

Step 2: YOUR CODE SENDS TO THE API
─────────────────────────────────────────────────
{
  "model": "claude-sonnet-5",
  "messages": [
    {"role": "user", "content": "What's the weather in Paris right now?"}
  ],
  "tools": [
    {
      "name": "get_weather",
      "description": "Get the current weather for a city. Returns temperature in Celsius and conditions.",
      "input_schema": {
        "type": "object",
        "properties": {
          "city": {"type": "string", "description": "City name, e.g. 'Paris' or 'New York'"}
        },
        "required": ["city"]
      }
    }
  ]
}

Step 3: MODEL RESPONDS — NOT WITH TEXT, WITH A TOOL CALL
─────────────────────────────────────────────────────────
{
  "stop_reason": "tool_use",
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_01abc123",
      "name": "get_weather",
      "input": {"city": "Paris"}
    }
  ]
}

Step 4: YOUR CODE EXECUTES THE ACTUAL FUNCTION
──────────────────────────────────────────────
# The model doesn't run this — YOUR CODE does
result = get_weather("Paris")
# → {"temperature": 15, "conditions": "cloudy", "humidity": 72}

Step 5: YOUR CODE SENDS THE RESULT BACK TO THE MODEL
─────────────────────────────────────────────────────
{
  "messages": [
    {"role": "user", "content": "What's the weather in Paris right now?"},
    {"role": "assistant", "content": [tool_use_block_from_step_3]},
    {
      "role": "user",
      "content": [
        {
          "type": "tool_result",
          "tool_use_id": "toolu_01abc123",
          "content": '{"temperature": 15, "conditions": "cloudy", "humidity": 72}'
        }
      ]
    }
  ]
}

Step 6: MODEL GENERATES THE FINAL ANSWER
─────────────────────────────────────────
{
  "stop_reason": "end_turn",
  "content": [
    {
      "type": "text",
      "text": "The weather in Paris right now is 15°C (59°F) and cloudy, with 72% humidity."
    }
  ]
}
```

Six steps, not one. The model makes a decision, your code does work, you show the model the result, the model finishes. This loop is the core of every agent.

**The critical security insight:** the model CANNOT call your function. It produces a text document that says "I would like to call this function with these arguments." Your code reads that document and decides whether to actually execute it. This is the control boundary. It means:
- You can validate the arguments before running the function
- You can reject calls that don't meet your rules
- You can log every intended action before it happens
- You can require human approval before execution

If the model could call functions directly, none of this would be possible.

### Tool Definition Schema

A tool definition has three components. The most important one is often the one people rush past.

```python
{
    "name": "search_knowledge_base",       # (1) The name — how the model refers to it
    "description": "...",                   # (2) When to use it — THE CRITICAL FIELD
    "input_schema": {...}                   # (3) The arguments — their types and descriptions
}
```

**The description is the most important field.** The model reads it to decide:
- Whether to call this tool at all
- Whether this is the right tool for the current situation
- How this tool differs from other similar tools

A vague description produces incorrect tool selection. A precise description produces correct tool selection.

```python
# BAD — model will not know when or how to use this
{
    "name": "search",
    "description": "Search for stuff",
    "input_schema": {
        "type": "object",
        "properties": {
            "q": {"type": "string"}
        }
    }
}

# GOOD — model knows exactly when to call this and what to expect back
{
    "name": "search_knowledge_base",
    "description": (
        "Search the internal company knowledge base for policies, procedures, "
        "and documentation. Use this when the user asks about company policies, "
        "HR procedures, benefits, or internal processes. Returns the top 3 matching "
        "documents with their titles, excerpts, and last-updated dates."
    ),
    "input_schema": {
        "type": "object",
        "properties": {
            "query": {
                "type": "string",
                "description": (
                    "A specific search query. Use precise terminology — "
                    "for example 'vacation day accrual rate' rather than 'time off'."
                )
            },
            "category": {
                "type": "string",
                "enum": ["hr", "engineering", "finance", "legal", "all"],
                "description": "Filter by document category. Use 'all' if unsure."
            }
        },
        "required": ["query"]
    }
}
```

**Common mistakes in tool definitions:**

1. **Vague names:** `search`, `get`, `process` — the model can't distinguish these from each other or reason about when to use them.

2. **Missing edge cases in descriptions:** if `get_user` can fail when the user doesn't exist, the description should say "returns null if the user is not found." Otherwise the model won't know how to handle the failure.

3. **Too many tools:** if you give the model 30 tools, it struggles to pick the right one — the same way a human struggles to remember the purpose of 30 keyboard shortcuts. Keep tool sets focused (5-10 tools) and well-named.

4. **Tools that do two things:** a tool called `create_or_update_record` that creates when the record doesn't exist and updates when it does is harder to describe and more likely to be misused. Separate tools with clear single responsibilities.

### The ReAct Loop

ReAct stands for Reason → Act → Observe. It's the pattern that turns a single tool call into multi-step problem-solving.

The key insight: after a tool call, you send the result back to the model, and the model reasons again with the new information. This is a loop. The model decides when it has enough information to stop.

```
User: "Is the iPad Air in stock at any Bay Area store? If yes, book the nearest one."

[Round 1]
Reason: I need to check stock levels. I'll search all Bay Area stores.
Act:    check_inventory(product="iPad Air", region="bay_area")
Observe: {"stores": [{"name": "San Jose", "stock": 0}, {"name": "Palo Alto", "stock": 3}]}

[Round 2]
Reason: There's stock in Palo Alto. I need the user's location to find the nearest store.
        But I don't have their location — I should proceed with the only available option.
Act:    create_reservation(product="iPad Air", store="Palo Alto", customer_id="user-456")
Observe: {"reservation_id": "R789", "status": "confirmed", "pickup_window": "2 hours"}

[Round 3]
Reason: Reservation confirmed. I have everything I need to answer.
Final:  "Good news! The iPad Air is in stock at the Palo Alto store. I've made a reservation
        for you (ID: R789). You have a 2-hour pickup window."
```

Each round: reason about what to do, act by calling a tool, observe the result, add that result to the conversation, reason again. The model "sees" the entire growing conversation — all previous reasoning and all tool results — when it decides what to do next.

This is what makes agents "agentic": they don't just call one tool and stop. They iterate, adjust, and make decisions based on what they've learned.

## Core Patterns / Techniques

### The Basic Tool-Calling Loop

Here is the complete, runnable implementation of the pattern described above. Read every comment.

```python
import anthropic
import json

client = anthropic.Anthropic()

# ─── Tool Definitions ────────────────────────────────────────────────────────
# Describe each tool precisely. The model reads these descriptions.
tools = [
    {
        "name": "check_inventory",
        "description": (
            "Check how many units of a product are available at a specific store. "
            "Returns the stock count and whether the item can be reserved. "
            "Use this before attempting to create a reservation."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "product": {
                    "type": "string",
                    "description": "Exact product name, e.g. 'iPad Air 5th Gen 64GB'"
                },
                "store_id": {
                    "type": "string",
                    "description": "Store identifier, e.g. 'palo-alto' or 'san-jose-downtown'"
                }
            },
            "required": ["product", "store_id"]
        }
    },
    {
        "name": "create_reservation",
        "description": (
            "Reserve a product at a specific store for the current customer. "
            "Only call this after confirming stock with check_inventory. "
            "Returns a reservation ID and pickup window. "
            "This action CANNOT be undone automatically — require confirmation first."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "product": {"type": "string"},
                "store_id": {"type": "string"},
                "customer_id": {
                    "type": "string",
                    "description": "Customer account ID"
                }
            },
            "required": ["product", "store_id", "customer_id"]
        }
    }
]

# ─── Tool Implementations ─────────────────────────────────────────────────────
# These are the actual functions. The model cannot see this code — it only sees
# the tool definitions above and the return values below.
def check_inventory(product: str, store_id: str) -> dict:
    # In production: query your inventory database
    # Here: simulated response
    inventory = {
        ("iPad Air", "palo-alto"): {"stock": 3, "reservable": True},
        ("iPad Air", "san-jose"): {"stock": 0, "reservable": False},
    }
    key = (product, store_id)
    if key in inventory:
        return inventory[key]
    return {"error": f"No inventory data found for {product} at {store_id}"}

def create_reservation(product: str, store_id: str, customer_id: str) -> dict:
    # In production: create a record in your reservation system
    return {
        "reservation_id": "R-20260808-001",
        "product": product,
        "store": store_id,
        "customer": customer_id,
        "status": "confirmed",
        "pickup_expires": "2026-08-08T19:00:00Z"
    }

def execute_tool(name: str, inputs: dict) -> dict:
    """Dispatch function — routes tool calls to the right implementation."""
    if name == "check_inventory":
        return check_inventory(**inputs)
    elif name == "create_reservation":
        return create_reservation(**inputs)
    else:
        return {"error": f"Unknown tool: {name}"}

# ─── The Agent Loop ───────────────────────────────────────────────────────────
def run_agent(user_message: str, customer_id: str = "user-456") -> str:
    """
    Run the ReAct loop until the model produces a final text answer.
    
    The messages list grows with each round:
    - Round 1: [user message]
    - After model responds with tool call: [user, assistant(tool_call)]
    - After tool result: [user, assistant(tool_call), user(tool_result)]
    - Round 2: model sees all of the above and reasons with new info
    - ... continues until stop_reason == "end_turn"
    """
    messages = [{"role": "user", "content": user_message}]
    
    print(f"\n=== Agent starting for: '{user_message}' ===\n")
    
    while True:
        # Call the model with current message history + tool definitions
        response = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=1024,
            tools=tools,
            messages=messages,
        )
        
        print(f"Model response (stop_reason: {response.stop_reason}):")
        
        # The model is done — extract the final text answer
        if response.stop_reason == "end_turn":
            final_text = next(
                block.text for block in response.content if block.type == "text"
            )
            print(f"  Final answer: {final_text}")
            return final_text
        
        # The model wants to call tools
        if response.stop_reason == "tool_use":
            # Add the model's response to the conversation history
            # (important: this includes the tool_use blocks, not just text)
            messages.append({"role": "assistant", "content": response.content})
            
            # Execute each tool the model requested
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    print(f"  Tool call: {block.name}({block.input})")
                    
                    # THIS IS THE SAFETY BOUNDARY:
                    # Validate inputs here before executing anything irreversible
                    result = execute_tool(block.name, block.input)
                    
                    print(f"  Tool result: {result}")
                    
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,   # links result to the specific tool call
                        "content": json.dumps(result),
                    })
            
            # Add all tool results to the conversation as a "user" message
            # (The API protocol requires tool results to be sent as user-role messages)
            messages.append({"role": "user", "content": tool_results})
            
            # Loop back — model will reason again with the tool results in context
        else:
            # Unexpected stop reason
            print(f"  Unexpected stop_reason: {response.stop_reason}")
            break
    
    return "Agent terminated unexpectedly"

# ─── Run It ───────────────────────────────────────────────────────────────────
result = run_agent("Is the iPad Air in stock at palo-alto? If yes, reserve one for me.")
```

When you run this, you'll see the loop in action:

```
=== Agent starting for: 'Is the iPad Air in stock at palo-alto? ...' ===

Model response (stop_reason: tool_use):
  Tool call: check_inventory({'product': 'iPad Air', 'store_id': 'palo-alto'})
  Tool result: {'stock': 3, 'reservable': True}

Model response (stop_reason: tool_use):
  Tool call: create_reservation({'product': 'iPad Air', 'store_id': 'palo-alto', 'customer_id': 'user-456'})
  Tool result: {'reservation_id': 'R-20260808-001', ...}

Model response (stop_reason: end_turn):
  Final answer: "Great news! The iPad Air is in stock at Palo Alto (3 units available).
  I've reserved one for you. Reservation ID: R-20260808-001. ..."
```

### Building a Research Agent

Let's build something more realistic — an agent that searches the web, reads specific pages, and synthesizes an answer. This pattern is the backbone of research assistants, competitor analysis tools, and any system that needs to gather information from multiple sources.

```python
import anthropic
import json
import urllib.request

client = anthropic.Anthropic()

# ─── Tool Definitions ────────────────────────────────────────────────────────
research_tools = [
    {
        "name": "web_search",
        "description": (
            "Search the web for current information on a topic. "
            "Returns a list of search results with titles, URLs, and short excerpts. "
            "Use this first to find relevant sources, then use fetch_page to read them in detail."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "query": {
                    "type": "string",
                    "description": "Search query. Be specific. Use quotes for exact phrases."
                },
                "num_results": {
                    "type": "integer",
                    "description": "Number of results to return (1-10, default 5)",
                    "default": 5
                }
            },
            "required": ["query"]
        }
    },
    {
        "name": "fetch_page",
        "description": (
            "Fetch and read the full text content of a specific web page. "
            "Use this after web_search to get the full content of a promising result. "
            "Returns the page title and main text content."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "url": {
                    "type": "string",
                    "description": "Full URL of the page to fetch, including https://"
                }
            },
            "required": ["url"]
        }
    }
]

# ─── Implementations ──────────────────────────────────────────────────────────
def web_search(query: str, num_results: int = 5) -> dict:
    # In production: use a real search API (Serper, Brave Search, etc.)
    # Here: simulated results to show the pattern
    print(f"  [searching web for: {query!r}]")
    return {
        "results": [
            {
                "title": f"Example result 1 for '{query}'",
                "url": "https://example.com/article-1",
                "excerpt": "This is a relevant excerpt from the first result..."
            },
            {
                "title": f"Example result 2 for '{query}'",
                "url": "https://example.com/article-2",
                "excerpt": "This is a relevant excerpt from the second result..."
            }
        ]
    }

def fetch_page(url: str) -> dict:
    # In production: use requests + BeautifulSoup to extract main content
    print(f"  [fetching page: {url}]")
    return {
        "url": url,
        "title": "Example Page Title",
        "content": "Full page content would appear here in a real implementation..."
    }

def run_research_agent(question: str) -> str:
    """Research agent that searches the web and synthesizes an answer."""
    messages = [
        {
            "role": "user",
            "content": (
                f"Research this question thoroughly and provide a well-sourced answer:\n\n{question}\n\n"
                "Use web_search to find relevant sources, then fetch_page to read the most "
                "promising ones in detail. Cite your sources in the final answer."
            )
        }
    ]
    
    max_iterations = 10  # prevent infinite loops
    iteration = 0
    
    while iteration < max_iterations:
        iteration += 1
        print(f"\n--- Iteration {iteration} ---")
        
        response = client.messages.create(
            model="claude-sonnet-5",
            max_tokens=2048,
            tools=research_tools,
            messages=messages,
        )
        
        if response.stop_reason == "end_turn":
            return next(b.text for b in response.content if b.type == "text")
        
        messages.append({"role": "assistant", "content": response.content})
        
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                if block.name == "web_search":
                    result = web_search(**block.input)
                elif block.name == "fetch_page":
                    result = fetch_page(**block.input)
                else:
                    result = {"error": f"Unknown tool: {block.name}"}
                
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": json.dumps(result)
                })
        
        messages.append({"role": "user", "content": tool_results})
    
    return "Research agent exceeded maximum iterations"

# Run the research agent
answer = run_research_agent("What are the main tradeoffs between FAISS and Pinecone for vector search?")

    {"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": "toolu_03", "content": '{"content": "..."}'},

```

The model sees the entire conversation at every step. It uses all previous tool results to decide what to do next. This is how "context" accumulates in an agent loop.

### Agent Guardrails and Safety

Without guardrails, an agent with write access can cause real damage. An agent that can send emails can send emails to the wrong people. An agent that can delete records can delete the wrong records. An agent that can charge payments can charge the wrong amount.

The key insight: **irreversibility is the risk.** Reading data is safe to do without human confirmation. Writing, deleting, charging, sending — these cannot be undone.

**Guardrail 1: Validate tool inputs before executing**

```python
def execute_with_validation(name: str, inputs: dict) -> dict:
    """Validate all tool inputs before executing anything."""
    
    if name == "create_reservation":
        # Validate date is in the future
        import datetime
        pickup_date = inputs.get("pickup_date", "")
        try:
            dt = datetime.datetime.fromisoformat(pickup_date)
            if dt < datetime.datetime.now():
                return {"error": "Cannot create reservations for past dates"}
        except ValueError:
            return {"error": f"Invalid date format: {pickup_date}"}
        
        # Validate customer exists
        if not customer_exists(inputs.get("customer_id", "")):
            return {"error": f"Customer {inputs['customer_id']} not found"}
    
    elif name == "send_email":
        # Validate the recipient is an internal email before sending
        recipient = inputs.get("to", "")
        if not recipient.endswith("@company.com"):
            return {
                "error": f"Can only send to @company.com addresses, got: {recipient}"
            }
    
    # All validation passed — execute
    return execute_tool(name, inputs)
```

**Guardrail 2: Human confirmation for irreversible actions**

```python
IRREVERSIBLE_TOOLS = {"send_email", "charge_payment", "delete_record", "create_reservation"}

def execute_with_confirmation(name: str, inputs: dict) -> dict:
    """Require human approval before irreversible actions."""
    
    if name in IRREVERSIBLE_TOOLS:
        print(f"\n⚠️  Agent wants to execute: {name}")
        print(f"   Arguments: {json.dumps(inputs, indent=2)}")
        approval = input("   Approve? (y/n): ").strip().lower()
        
        if approval != "y":
            return {
                "error": "Action rejected by user",
                "message": "The user declined to execute this action."
            }
    
    return execute_tool(name, inputs)
```

**Guardrail 3: Maximum iterations**

```python
MAX_TOOL_CALLS = 20  # prevent infinite loops

tool_call_count = 0

def execute_with_limit(name: str, inputs: dict) -> dict:
    global tool_call_count
    tool_call_count += 1
    
    if tool_call_count > MAX_TOOL_CALLS:
        raise RuntimeError(
            f"Agent exceeded maximum tool calls ({MAX_TOOL_CALLS}). "
            "This likely indicates an infinite loop or misrouted task."
        )
    
    return execute_tool(name, inputs)
```

**Guardrail 4: Tool whitelisting per task**

Not every task needs every tool. An agent handling customer questions should not have access to the `delete_record` or `admin_override` tools, even if they exist in your codebase.

```python
def build_agent_for_task(task_type: str) -> list:
    """Return only the tools appropriate for this task type."""
    
    all_tools = {
        "check_inventory": inventory_tool_def,
        "create_reservation": reservation_tool_def,
        "send_email": email_tool_def,
        "delete_record": delete_tool_def,
        "admin_override": admin_tool_def,
    }
    
    task_tools = {
        "customer_support": ["check_inventory", "create_reservation"],
        "admin_operations": ["check_inventory", "create_reservation", "delete_record", "admin_override"],
        "notifications": ["send_email"],
    }
    
    allowed = task_tools.get(task_type, [])
    return [all_tools[name] for name in allowed if name in all_tools]
```

## Best Practices

- **Validate tool inputs before executing** — the model generates arguments; treat them exactly like user input. Check types, ranges, and permissions. Never trust that the model produced valid arguments.
- **Log every tool call and result** — especially for tools that mutate state. You need an audit trail for debugging and compliance.
- **Set a maximum iteration count** — a bug or unclear task can cause an agent to loop forever. A limit of 10-20 tool calls is reasonable for most tasks; adjust based on task complexity.
- **Write precise tool descriptions** — the description is the model's only guide for when to call a tool. "Search for stuff" will be misused. "Search the internal company knowledge base for policies..." will be used correctly.
- **Give the agent only the tools it needs** — fewer tools = better decisions. An agent with 5 focused tools outperforms one with 50 unfocused tools.
- **Handle tool errors gracefully** — return structured error objects (not exceptions) so the model can read the error and decide what to do next. An exception crashes the loop; a `{"error": "..."}` return lets the model adapt.

## Common Interview Questions

**Q1: What is the difference between a RAG pipeline and an agent?**
A: RAG is a read operation — retrieve information from a knowledge base, stuff it into a prompt, generate an answer. Done in one pass. An agent can take action: call tools that interact with external systems, chain multiple tool calls based on what earlier ones returned, and loop until the task is complete. The key difference is whether the system just reads information or also acts on the world.

**Q2: What is tool calling and how does it work mechanically?**
A: You send the model a prompt plus a list of tool definitions (name, description, argument schema). Instead of generating only text, the model can respond with `stop_reason: "tool_use"` and a list of tool call requests — each with a tool name and specific arguments. Your code executes the actual functions and returns the results as "tool result" messages. The model then reasons again with those results in its context and decides whether to call more tools or produce a final answer.

**Q3: What is the ReAct pattern and why does it matter?**
A: ReAct = Reason → Act → Observe, repeated in a loop. The model reasons about what to do, acts by calling a tool, observes the result, and reasons again with the new information. This turns a single tool call into multi-step problem-solving — the model can gather information progressively, change its approach based on what it finds, and handle tasks that require multiple sequential decisions.

**Q4: Why can't the model call functions directly?**
A: By design. The model produces text — including text that describes a function call it wants to make. Your code reads that text and decides whether to execute the function. This creates the safety boundary: you can validate arguments, reject dangerous calls, require human approval, and log everything before anything actually runs.

**Q5: How do you prevent an agent from taking destructive actions?**
A: Multiple layers. First, only give the agent the tools it needs for the current task — don't include delete or admin tools if the task is answering customer questions. Second, validate all tool arguments before execution, just like you'd validate user input. Third, for irreversible actions (send, charge, delete), require explicit human confirmation before executing. Fourth, set a maximum iteration count to catch infinite loops.

**Q6: What happens when a tool call fails?**
A: Return a structured error object as the tool result — not an exception. For example: `{"error": "User not found", "user_id": "xyz"}`. The model sees this error in its context and decides what to do: retry with different arguments, try a different approach, or return an error message to the user. If you let an exception propagate, the agent loop crashes and the conversation ends — the model never gets a chance to recover.

## Key Takeaways

- RAG retrieves and generates. Agents retrieve AND act — they can call tools that interact with external systems.
- Tool calling is purely mechanical: model produces a tool call request → your code executes the function → your code returns the result → model reasons with the result. The model never runs code directly.
- The ReAct loop (Reason → Act → Observe) is what makes agents multi-step: tool results flow back into the model's context, enabling progressive information gathering and adaptive decision-making.
- Tool descriptions are the most important field in a tool definition. The model reads them to decide when and how to call a tool. Vague descriptions = incorrect tool use.
- The safety boundary: your code controls execution. Validate inputs, log calls, require confirmation for irreversible actions, set iteration limits.
- Return structured error objects, not exceptions. Errors become tool results that the model can reason about and recover from.
