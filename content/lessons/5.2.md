# Networking & APIs (System Design)

Once you understand the core trade-offs from 5.1 (scaling, CAP, latency/throughput), the next question is: what are the specific components that connect clients to your application logic, and how does each one actually work? This lesson covers the infrastructure between a user's browser and your code: load balancers, API gateways, the three major API styles, rate limiting, CDNs, and WebSockets.

For each component, we'll start with the problem it solves — because understanding why something was invented is the fastest way to understand how to use it correctly.

## Theory & Fundamentals

### Load Balancers

#### The Problem: One Server Is Never Enough

Imagine your application runs on a single server. This creates two problems:

**Problem 1: Capacity.** One server can handle maybe 10,000 requests per second under ideal conditions. If 50,000 requests per second arrive, most of them fail or time out. You can't serve more traffic than one server can handle.

**Problem 2: Single point of failure.** If that one server crashes — hardware failure, software bug, out-of-memory kill — your entire application is down. Every user sees an error. Recovery requires human intervention and may take minutes or hours.

The solution to both problems is the same: add more servers. But adding more servers immediately raises a new question: **how does a user's request know which server to go to?**

The answer is a **load balancer** — a component that sits in front of your servers, receives all incoming requests, and distributes them across the available servers.

```
Without a load balancer:

  User → Server 1   (what if it's overloaded? what if it crashes?)

With a load balancer:

  User → [Load Balancer] → Server 1  ↑
                         → Server 2  | requests distributed across all servers
                         → Server 3  ↓
```

Think of the load balancer as a receptionist at a doctor's office. When you walk in, the receptionist doesn't just send everyone to Doctor 1 until she's completely swamped. She distributes patients across all available doctors based on who's available and what each patient needs.

The load balancer does the same: it's the entry point for all traffic, and it decides which server (which "doctor") handles each incoming request.

#### Load Balancing Algorithms

Different algorithms for distributing requests solve different problems:

**Round Robin**  
The simplest algorithm: rotate through servers in order. Request 1 goes to Server 1, request 2 to Server 2, request 3 to Server 3, request 4 to Server 1 again, and so on.

This works well when all requests cost roughly the same to handle and all servers are equally capable. It's easy to implement and requires no state tracking.

What goes wrong: if request costs vary significantly, round robin distributes unfairly. Imagine Server 1 is handling one expensive database-heavy request (taking 5 seconds) while Server 2 and 3 are idle after finishing quick requests. Round robin might still send the next request to Server 1, which is already overwhelmed, even though Server 2 is just sitting there.

**Least Connections**  
Send the next request to whichever server has the fewest active connections right now.

This solves the round robin problem: a server that's busy with many active requests won't receive new ones until it finishes some. A server that just finished its work immediately becomes the best candidate for the next request.

The cost: the load balancer must track how many active requests each server is handling at all times. This requires maintaining state, which adds a tiny bit of overhead. For most applications, this overhead is worthwhile.

**IP Hash (Session Affinity / "Sticky Sessions")**  
Hash the client's IP address and always route that client to the same server.

When is this needed? When your backend servers are still stateful — they store session data in local memory rather than a shared external store. In this case, a user's subsequent requests must go to the same server that holds their session data.

The important thing to understand: **IP hash is a workaround for stateful servers, not a good long-term strategy**. It limits the load balancer's ability to distribute traffic freely (a heavy user might always go to the same server), and it doesn't handle server failures gracefully (if that user's server crashes, they're logged out). The real fix is making services stateless (see 5.1).

**Weighted Round Robin**  
Some servers are more powerful than others (different hardware, different instance types). Weighted round robin gives more traffic to more powerful servers. Server A might get 60% of traffic, Server B 40%.

Useful during rolling deployments: you start a new version on one server and send it only 10% of traffic to verify it works, then gradually increase the weight.

#### Health Checks: How Load Balancers Know Who's Alive

The load balancer periodically sends a request (called a "health check" or "ping") to each server, typically to a dedicated endpoint like `/health`. If the server responds with HTTP 200 (OK), it's healthy and receives traffic. If it fails to respond (timeout) or returns an error code, the load balancer marks it as unhealthy and **stops sending traffic to it** — automatically, without human intervention.

```
Health check cycle:
  
  Load Balancer → GET /health → Server 1  → 200 OK  → healthy, keep sending traffic
  Load Balancer → GET /health → Server 2  → timeout → unhealthy! stop sending traffic
  Load Balancer → GET /health → Server 3  → 200 OK  → healthy, keep sending traffic
  
  Traffic now distributes only between Server 1 and Server 3.
  When Server 2 recovers and starts returning 200, it automatically re-enters the pool.
```

This is a core availability mechanism. A server can crash or be taken down for deployment at any time, and the load balancer routes around it within seconds. No human has to be paged at 3am to manually redirect traffic.

#### Layer 4 vs. Layer 7 Load Balancing

The networking model divides communication into layers. Layer 4 is the transport layer (TCP/UDP, IP addresses and ports). Layer 7 is the application layer (HTTP — URLs, headers, cookies, request bodies).

**Layer 4 load balancers** route based purely on IP address and port. They don't read the HTTP request itself. This makes them very fast — they can route millions of connections per second — but they can only do simple routing: "everything coming in on port 443 goes to this pool of servers."

**Layer 7 load balancers** read the HTTP request and can make routing decisions based on its content:

- Route `/api/*` to your API server pool and `/static/*` to your static file servers
- Route requests with `Host: admin.example.com` to admin servers and `Host: example.com` to app servers
- Route requests with a specific cookie to a canary deployment (for testing a new version)
- Terminate SSL/TLS (decrypt HTTPS at the load balancer, forward plain HTTP to backend servers)

For most web applications, Layer 7 is the right choice — the added routing capabilities are extremely useful, and the performance difference rarely matters at typical scales. Layer 4 is used when you need raw speed and don't need HTTP-aware routing.

### API Gateways

#### The Problem: Microservices Chaos

Imagine you've broken your application into microservices — separate, independently deployable services for users, orders, inventory, payments, notifications, etc. You might have 20, 50, or 100 different services.

Now a mobile app client needs to: fetch the user's profile, get their order history, check inventory for a product, and show pending notifications. That's four different services. Should the mobile app make four separate network calls to four different endpoints?

This creates several problems:
1. Clients need to know the address of every service — which changes as services are deployed and scaled.
2. Every service has to implement authentication, rate limiting, and logging independently. That's 50 services each reimplementing the same logic.
3. If the mobile app is on a slow network, four round trips to four services makes the experience slow.
4. You're exposing your internal service architecture directly to clients — if you restructure services internally, every client breaks.

The solution is an **API Gateway** — a single entry point that sits in front of all your services.

#### What an API Gateway Handles

```
                    ┌──────────────────────────────────┐
  Client ──────────▶│          API Gateway              │
                    │                                  │
                    │  ✓ Authentication (check JWT)    │
                    │  ✓ Rate limiting                 │
                    │  ✓ Request routing               │
                    │  ✓ SSL termination               │
                    │  ✓ Logging and tracing           │
                    │  ✓ Response aggregation          │
                    └──────┬────────┬────────┬─────────┘
                           │        │        │
                      User Svc  Order Svc  Payment Svc
```

**Authentication / Authorization**: The gateway checks whether a request includes a valid JWT token (or API key) before forwarding it to any service. Without a gateway, every service would need to validate tokens independently — using the same library, keeping the same secret, making the same checks. Centralize it once in the gateway.

**Rate limiting**: Enforce request quotas at the gateway. A client sending 1,000 requests per second gets rejected at the gateway, before that traffic ever reaches your services.

**Request routing**: `GET /users/*` goes to the User Service. `POST /orders` goes to the Order Service. The gateway knows the map; clients just talk to one address.

**SSL termination**: HTTPS connections from clients are decrypted at the gateway. Traffic from the gateway to internal services travels over plain HTTP within the private network. Backend services are relieved of encryption overhead, and you manage one certificate instead of one per service.

**Response aggregation (BFF pattern)**: Instead of the mobile app making four requests to four services, it makes one request to the gateway. The gateway fans out to those four services in parallel, aggregates the responses, and returns one response to the client. This is the **Backend for Frontend (BFF)** pattern — the gateway adapts the API to what each type of client actually needs.

#### Load Balancer vs. API Gateway: The Distinction

These are often confused. The key difference:

- A **load balancer** distributes traffic across multiple instances of **the same service**. All the servers it routes to are interchangeable — they all do the same thing.
- An **API gateway** routes different requests to **different services**. It reads the request content to decide where it goes.

In a real architecture, you often have both: a load balancer in front of the API gateway itself (so the gateway can scale horizontally), and the gateway routing to different services (each of which may also have its own load balancer).

```
Internet → [Load Balancer] → [API Gateway instances] → [Service A load balancer] → [Service A instances]
                                                     → [Service B load balancer] → [Service B instances]
```

### REST vs. gRPC vs. GraphQL

Before diving into each one, understand the key insight: **these three technologies solve different problems**. Choosing between them isn't just a matter of preference — it's about what problem you have.

- REST is the simple, universal default.
- GraphQL solves the problem of clients needing different data shapes.
- gRPC solves the problem of fast, typed communication between internal services.

#### REST: The Standard

REST (Representational State Transfer) is the dominant style for web APIs. You model your data as **resources** (nouns: users, orders, products), and you interact with them using standard HTTP methods (verbs):

- `GET /users/42` — fetch user 42
- `POST /users` — create a new user
- `PUT /users/42` — update user 42
- `DELETE /users/42` — delete user 42

REST uses JSON, which humans can read, browser dev tools understand, and every programming language can parse. It works over standard HTTP/1.1, meaning existing infrastructure (proxies, CDNs, browser caches) works with it out of the box.

**When REST is the right choice:**
- Public APIs (when you don't know who's consuming it, REST's simplicity and universal support matter)
- Simple CRUD services (create, read, update, delete operations on resources)
- When you want easy caching (GET requests cache automatically in HTTP infrastructure)
- When broad client compatibility matters (REST works from any programming language, from curl, from browsers)

**REST's two main problems:**

**Over-fetching**: You get back more data than you need. Your mobile app only needs a user's name and avatar, but `GET /users/42` returns 30 fields including address history, billing info, and preferences. You're wasting bandwidth sending data the client ignores.

**Under-fetching (N+1 problem)**: One request doesn't return all the data you need, so you make multiple requests. You call `GET /users/42` to get the user, then `GET /orders?userId=42` to get their orders, then `GET /products/productId` for each product in those orders. A single "view" in your UI requires 10+ API calls, each adding latency.

#### GraphQL: When Clients Need Different Shapes

GraphQL was invented at Facebook to solve REST's over-fetching and under-fetching problems. The fundamental idea: **let the client specify exactly what data it needs, and return exactly that — no more, no less**.

Instead of many endpoints, there's one endpoint (usually `POST /graphql`). The client sends a query document describing the shape of data it wants:

```graphql
query {
  user(id: 42) {
    name
    avatar
    recentOrders(limit: 3) {
      orderId
      total
      items {
        productName
        quantity
      }
    }
  }
}
```

The server executes this query against its data graph and returns exactly that shape — user name, avatar, their last 3 orders, and the items in each order. One network round trip. No wasted fields. No N+1 calls.

**When GraphQL is the right choice:**
- You have multiple client types with different data needs. A mobile app needs minimal data (small payload, battery life). A desktop web app can afford richer data. A partner integration might need entirely different fields. With REST you'd create multiple endpoints or add complex field filtering. With GraphQL each client just queries what it needs.
- Your data is a rich graph of related types. GraphQL excels when queries naturally traverse relationships: users → orders → products → reviews.
- You're building an internal tool or a well-defined partner API where the query complexity is acceptable.

**GraphQL's costs:**
- More complex to implement on the server (you define a schema and resolver functions for every field)
- HTTP caching doesn't work well (all queries are POST requests to the same endpoint)
- Steeper learning curve for API consumers (need to learn the query language)
- Can be abused by clients sending extremely expensive queries (requires query complexity limiting)

#### gRPC: Fast Internal Service Communication

gRPC is built on two key technologies that make it dramatically faster than REST for internal service-to-service calls:

**Protocol Buffers (Protobuf)**: Instead of JSON (text, human-readable but large), gRPC uses a binary format. You define the message structure in a `.proto` file:

```proto
message User {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
```

The gRPC tooling generates client and server code automatically in your language of choice. The binary encoding is 3-10x smaller than JSON and much faster to serialize/deserialize.

**HTTP/2**: gRPC runs over HTTP/2, which supports multiplexing — multiple requests can fly over the same connection simultaneously. HTTP/1.1 requires a new connection per request (or sequentializes requests on keep-alive connections). HTTP/2 eliminates this overhead, which matters enormously for microservices that make hundreds of internal calls per second.

**When gRPC is the right choice:**
- Internal service-to-service communication at scale (the performance difference matters)
- When you want strong typing and auto-generated clients (no more hand-writing API clients)
- Streaming scenarios (gRPC supports server-streaming, client-streaming, and bidirectional streaming natively)
- Polyglot environments (gRPC generates clients in Go, Java, Python, Node, C++, etc. from the same `.proto` file)

**gRPC's costs:**
- Not human-readable (binary format, can't use curl to debug)
- No native browser support (browsers can't speak HTTP/2 at the transport level needed)
- Requires generating client code from `.proto` files (adds a build step)

#### Decision Tree

```
Is this a public-facing API that external developers will use?
  └── YES → REST (simple, universally supported, cacheable)

Do you have multiple client types (web, mobile, partners) that need
different subsets of the same underlying data?
  └── YES → GraphQL (clients query exactly what they need)

Is this service-to-service communication inside your infrastructure,
where performance and strong typing matter?
  └── YES → gRPC (binary protocol, auto-generated clients, HTTP/2)

No strong reason for the others?
  └── Default to REST (you'll never be wrong for the basic case)
```

### Rate Limiting

#### Why It Exists

Without rate limiting, your service is vulnerable to:

**Accidental abuse**: A bug in a client application causes it to make requests in a tight loop — 10,000 requests per second instead of 10. Your server crashes for all users because one buggy client is eating all the resources.

**Intentional abuse**: A malicious user or bot scripts requests to exhaust your system, either to cause downtime or to scrape your data.

**Business enforcement**: Your free tier gets 100 requests per minute. Your paid tier gets 10,000. Without rate limiting, free-tier users could use as much as they want, destroying your business model.

Rate limiting is the mechanism that says: "this client has used their allocation for this time window — reject further requests until the window resets."

When a request is rejected by rate limiting, the correct HTTP response is **429 Too Many Requests**, optionally with a `Retry-After` header telling the client how many seconds to wait:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{ "error": "Rate limit exceeded. Try again in 60 seconds." }
```

#### The Token Bucket Algorithm: The Most Important One to Know

The token bucket is the most widely used rate limiting algorithm, and it's worth understanding deeply because it models real-world traffic patterns well.

Imagine a physical bucket that holds tokens:

1. The bucket starts full (say, 100 tokens).
2. Tokens are added back into the bucket at a fixed rate (say, 10 tokens per second). The bucket never overflows — if it's full, new tokens are discarded.
3. Each incoming request costs one token. If a token is available, take it and process the request. If the bucket is empty, reject the request.

```
Token Bucket State:
  
  Capacity: 100 tokens
  Refill rate: 10 tokens/second
  
  t=0:   bucket = 100  (full)
  t=0:   5 requests arrive → take 5 tokens → bucket = 95 → all served
  t=1:   bucket refills → bucket = 100 (was 95 + 10, capped at 100)
  t=1:   120 requests arrive → take 100 tokens → bucket = 0 → 100 served, 20 rejected
  t=2:   bucket refills → bucket = 10
  t=2:   5 requests arrive → take 5 tokens → bucket = 5 → all served
```

**The key property: bursting is allowed.** A client that hasn't made requests for a while has a full bucket — they can make 100 requests instantly before hitting the limit. This models legitimate user behavior well: someone who hasn't used the app for an hour might click around a lot when they return.

But the long-term rate is still enforced: no matter how many tokens are in the bucket, the client can only *sustain* 10 requests/second (the refill rate) over the long run.

#### The Leaky Bucket Algorithm

The leaky bucket is conceptually inverted: imagine a bucket that leaks at a fixed rate at the bottom. Requests fill the bucket from the top. The rate at which requests flow out (are processed) is always constant.

If requests arrive faster than the leak rate, the bucket fills up and overflows (requests are rejected). If requests arrive slower, they flow through immediately.

The difference from token bucket: **no bursting**. The output rate is fixed regardless of how long the client waited. This produces smoother, more predictable traffic — useful for cases where you need a guaranteed constant rate of downstream requests (protecting a database that can't handle bursts).

Use token bucket when you want to allow short bursts (better user experience). Use leaky bucket when you want to enforce a strict, constant rate (protecting brittle downstream systems).

#### The Critical Implementation Detail: Why You Need Redis

Here's a subtle problem that trips up many engineers: if you implement rate limiting in each application server's memory, it doesn't work correctly.

Imagine you're allowing 100 requests per minute per user. You have 5 application servers. A user makes 50 requests that go to Server 1 (half of their limit) and 50 more requests that go to Server 2 (half of their limit from Server 2's perspective). Each server thinks the user is within their quota. But the user has actually made 100 requests — they've hit the limit!

```
Wrong (in-process per-server counters):

  User makes 80 requests, load balanced across 2 servers:
  Server 1: counts 40 requests → "user is under the 100 limit, allow"
  Server 2: counts 40 requests → "user is under the 100 limit, allow"
  Result: user made 80 requests, no server triggered the limit.
  If you have 10 servers, a user can make 1,000 requests before hitting any server's limit.

Correct (shared Redis counter):

  User makes 80 requests → all servers increment the SAME Redis counter
  Redis: { "user:42:count": 80 }
  Server 1: checks Redis → 80/100 → allow, increment to 81
  Server 2: checks Redis → 81/100 → allow, increment to 82
  ...
  Server 5: checks Redis → 99/100 → allow, increment to 100
  Server 3: checks Redis → 100/100 → REJECT, return 429
```

The Redis implementation uses atomic operations to avoid race conditions:

```
INCR user:42:requests       ← atomically increment counter, returns new value
EXPIRE user:42:requests 60  ← key expires (resets) after 60 seconds
```

If the returned value after `INCR` exceeds the limit, reject the request. `EXPIRE` ensures the counter automatically resets at the end of each window.

#### Where to Implement Rate Limiting

- **At the API Gateway**: the most common place. Centralized, applies before any request reaches a service.
- **In a reverse proxy (Nginx)**: Nginx has built-in rate limiting modules. Very fast.
- **In application code with Redis**: more flexibility (you can rate limit based on business logic, not just IP), but adds Redis as a dependency.

For a system design interview, when asked "design a rate limiter," the canonical answer is: **Redis with INCR + EXPIRE**, rate limiting at the API gateway.

## Core Patterns / Techniques

### CDN (Content Delivery Network)

#### The Problem: Geography Is Slow

The speed of light is fast — but even light traveling through fiber optic cables across the Pacific Ocean takes about 80ms one way. A user in Tokyo trying to load images from a server in Virginia experiences 160ms of round-trip latency just from physics, before any server processing happens.

For a page with 50 images, this adds up. Even with HTTP/2 multiplexing, loading content from halfway around the world is measurably slower than loading it from nearby.

#### What a CDN Does

A **Content Delivery Network** is a geographically distributed set of servers (called **edge nodes** or **Points of Presence / PoPs**) that cache copies of your content close to users around the world. Major CDNs (Cloudflare, Fastly, AWS CloudFront, Akamai) have hundreds of edge nodes in every major city.

```
Without CDN:
  User in Tokyo ←→ [Pacific Ocean: ~80ms RTT] ←→ Origin Server in Virginia
  
  Loading 50 images: 50 × 160ms RTT + server processing = very slow

With CDN:
  User in Tokyo → CDN Edge Node in Tokyo → cache HIT → user gets image in ~5ms
                                         → cache MISS → Edge Node fetches from Origin once,
                                                        caches it, serves future requests locally
```

On a cache hit (the content is already in the edge node), the user's request never reaches your origin server. The CDN serves the response entirely from the edge node near the user. This reduces latency for the user and reduces load on your origin server simultaneously.

#### What Gets Cached on a CDN

CDNs are appropriate for content that is:
- **The same for every user**: images, CSS files, JavaScript bundles, fonts, videos
- **Changes infrequently**: static assets don't change often; when they do, you update the CDN
- **Tolerates eventual consistency**: it's okay if different edge nodes around the world show the previous version briefly after you deploy an update

CDNs are **not appropriate** for:
- Personalized API responses (different per user — can't be cached)
- Real-time data (a cached stock price from 10 seconds ago is wrong)
- User-specific pages (your home feed is unique to you)

#### Cache Invalidation: When You Update a File

CDNs cache content with a TTL (time to live). When the TTL expires, the edge node fetches a fresh copy from the origin. But what if you update a file and want the CDN to serve the new version immediately?

**TTL-based expiry**: Set short TTLs (5 minutes) for content that changes often. Content is eventually refreshed. Simple but means stale content can linger for up to the TTL duration.

**Manual purge**: When you deploy, call the CDN's API to explicitly invalidate specific URLs. The CDN immediately drops the cached copy; the next request fetches from origin. More control, but requires coordinating deploys with cache purges.

**Content-hash URLs (the best approach for static assets)**: Instead of `/static/app.js`, name the file `/static/app.3f9a2b.js` where `3f9a2b` is a hash of the file's content. When the file changes, its hash changes, so its URL changes. The CDN caches `/static/app.3f9a2b.js` with a very long TTL (1 year). The next deploy produces `/static/app.7c1e4d.js` — a completely different URL. Old cached copies at the old URL are never "stale" because nobody requests them anymore. New copies at the new URL are fetched from origin on first access and then cached.

This technique allows aggressive CDN caching (long TTLs) without ever serving stale content — because a changed file is a different URL.

### WebSockets

#### The Limitation of HTTP: Request-Response

Standard HTTP is a request-response protocol. The client sends a request. The server responds. The connection closes (or returns to a pool for the next request). **The server can never initiate communication** — it can only respond when the client asks.

This works fine for most web browsing: you click a link, the server sends a page, done. But what about these scenarios?

- **Chat application**: when someone sends you a message, your browser should display it immediately — without you clicking anything.
- **Live sports scores**: the score updates without you refreshing the page.
- **Collaborative document editing**: when your colleague types a word in a shared Google Doc, you see it appear in real-time.
- **Multiplayer game**: when an opponent moves, you see it immediately.

In all these cases, **the server has data to push to you at unpredictable times**, without you asking for it. HTTP can't do this cleanly.

#### The Workarounds (and Why They're Suboptimal)

**Short Polling**: The client sends a request every N seconds: "Do you have anything new for me?" The server responds immediately with whatever is available, or an empty response if nothing is new.

```
Client: GET /messages?since=t  → Server: [] (nothing new)   — wasted request
Client: GET /messages?since=t  → Server: [] (nothing new)   — wasted request
Client: GET /messages?since=t  → Server: [{ "text": "hi" }] — finally!
(this repeats every N seconds, N*1000 times per day per user)
```

Problems: wastes bandwidth on empty responses, introduces up to N seconds of delay before new messages appear, and hammers the server with constant requests even when nothing is happening.

**Long Polling**: The server holds the connection open until it has something to send (or a timeout occurs). Once it sends data, the client immediately opens a new long-poll connection.

```
Client: GET /messages → Server: [waits silently...] → [receives new message] → sends response → Client reconnects
```

Better latency, but there's still overhead per message (a new HTTP connection for each response), and it requires the server to hold many open connections simultaneously (which consumes resources).

#### WebSockets: The Real Solution

WebSockets provide a **persistent, bidirectional communication channel** between client and server. Once established, either side can send messages at any time, with minimal overhead per message.

The connection starts with a standard HTTP "upgrade" handshake:

```
Client → Server:
  GET /ws HTTP/1.1
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==

Server → Client:
  HTTP/1.1 101 Switching Protocols
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

After this handshake, the protocol switches from HTTP to WebSocket. The connection stays open. Both sides can now send "frames" (small messages) at any time with essentially no overhead — no HTTP headers, no TCP connection setup, just the payload.

```
Connection established ────────────────────────────────────────────────►
                           │          │              │         │
                      Server → Client │       Client → Server │
                      "User X joined" │       "Hello!"        │
                                 Server → Client         Server → Client
                                 "Hello!"                "User Y left"
```

This is how chat apps, live dashboards, collaborative editors, and multiplayer games work. The server can push data to the client at any time without waiting for a request.

**Server-Sent Events (SSE)**: a middle ground worth knowing about. SSE is a simpler protocol where the server can push data to the client, but the client can't send data back after the initial connection. One-directional push. Simpler to implement than WebSockets. Use SSE when you only need server-to-client push (live news feeds, notifications, status updates). Use WebSockets when you need truly bidirectional communication (chat, games, collaborative editing).

#### When to Use What

```
Use case: user manually clicks "refresh" to get updates
  → Regular HTTP request-response (no realtime needed)

Use case: server pushes infrequent updates (a notification, a report finishing)
  → Server-Sent Events (simpler than WebSockets, one-directional push is fine)

Use case: high-frequency, bidirectional communication (chat, games, collaborative editing)
  → WebSockets

Use case: polling as a fallback for legacy environments
  → Long polling (WebSockets don't work in all corporate proxies and firewalls)
```

## Best Practices

- **Use Layer 7 load balancing for HTTP applications.** L7 enables path-based routing, host-based routing, and SSL termination — capabilities that L4 doesn't support. The only reason to use L4 is when raw throughput matters more than routing flexibility.
- **Every service must expose a health check endpoint.** The load balancer needs to know when a service is unhealthy. `/health` should return 200 when the service is functioning and a non-200 when it's not. This is not optional infrastructure — it's the mechanism for automatic recovery from failures.
- **Rate limit at the gateway, not in each service.** Centralizing rate limiting means one implementation, one configuration, and one place to monitor. Per-service rate limiting leads to inconsistencies and duplicated logic.
- **REST for public APIs, gRPC for internal.** gRPC's binary protocol and generated clients are meaningful performance gains for internal service-to-service traffic. For public-facing APIs, the tooling complexity and lack of browser support outweigh the benefits — REST's simplicity and universal compatibility win.
- **CDNs are not just for performance — they're for resilience.** A CDN absorbs traffic spikes. If your origin server goes down, the CDN can continue serving cached content (depending on TTL settings). This keeps your site partially functional during origin failures.
- **For distributed rate limiting, Redis INCR + EXPIRE is the canonical answer.** Atomic operations in Redis give you a shared, accurate counter across any number of application servers. In-process counters don't work in a horizontally scaled deployment.
- **Design WebSocket infrastructure to scale horizontally.** WebSocket connections are stateful (persistent, server holds connection open). If you add a second WebSocket server, it doesn't automatically know about connections open on server 1. Use a pub/sub system (Redis Pub/Sub, Kafka) so any server can broadcast to all connected clients.

## Common Interview Questions

**Q1: What's the difference between a load balancer and an API gateway?**
A: They solve related but different problems. A load balancer distributes traffic across multiple identical instances of the same service — it's about traffic distribution and high availability. An API gateway sits in front of multiple different services and handles cross-cutting concerns: authentication, rate limiting, routing different requests to different services, and response aggregation. In a real architecture, you often see both: a load balancer in front of the API gateway (so the gateway itself can scale), and the gateway routing to different services (each of which may have its own load balancer). If you're told "use a load balancer," the request usually goes to multiple copies of one service. If you're told "use an API gateway," the request might go to any of many different services.

**Q2: Why does rate limiting state need to be stored in Redis when you have multiple servers?**
A: Each server has its own isolated memory. If you store a rate-limit counter in-process, Server 1 counts its own requests and Server 2 counts its own — but users can make requests to both, splitting the count and effectively multiplying their quota by the number of servers. With 10 servers and a 100 req/min limit, users could make 1,000 requests per minute. Redis provides a single, shared, atomic counter that all servers read and write. The `INCR` command in Redis is atomic, so two servers can't simultaneously increment and both think the count is one less than the limit.

**Q3: When would you choose GraphQL over REST?**
A: When multiple different clients need different subsets of the same data. The classic example: a mobile app that needs only `name` and `avatar` (small payload to conserve battery/bandwidth) and a desktop web app that needs the full user profile with order history, billing info, and preferences. With REST, you either over-fetch on mobile or create two different endpoints. With GraphQL, mobile queries only the fields it needs, and desktop queries more. GraphQL is also valuable when your data has rich relationships that clients want to traverse in complex ways. The trade-off: more complex server implementation, no HTTP caching, and a learning curve for consumers.

**Q4: What is SSL termination at a load balancer and why is it done there rather than at each service?**
A: SSL/TLS encryption and decryption is computationally expensive. SSL termination means the load balancer handles the HTTPS connection from the internet — it decrypts incoming requests and encrypts outgoing responses. Backend services receive plain HTTP, which they can handle much faster. Three reasons to terminate at the load balancer: (1) backend services are relieved of crypto overhead, (2) you manage one certificate in one place instead of one certificate per service, (3) traffic from the load balancer to backend services travels inside the private network where plain HTTP is typically acceptable. If your security requirements mandate encryption even inside the private network, you'd use "end-to-end SSL" where the load balancer re-encrypts before forwarding.

**Q5: What is a WebSocket and when should you use it?**
A: A WebSocket is a persistent, bidirectional TCP connection established via an HTTP upgrade handshake. After the connection is established, either the client or server can send messages at any time without waiting for a request. Use WebSockets when the server needs to push data to clients in real-time at unpredictable times — chat applications, multiplayer games, live dashboards, collaborative editors. The key question: does the server need to send data without being asked? If yes, WebSockets (or Server-Sent Events for one-directional push) are the answer. Regular HTTP polling is simpler but wasteful and slow; WebSockets solve the problem efficiently.

**Q6: What does a CDN cache invalidation strategy look like?**
A: Three approaches, from simplest to most robust. (1) TTL-based expiry: cached content automatically expires after a set time (e.g., 5 minutes for images that update occasionally, 1 hour for rarely-changing assets). Simple, but data can be stale for up to the TTL duration. (2) Explicit purge on deploy: when you update a file, send an API call to the CDN to invalidate specific URLs. More accurate but requires coordination between your deploy pipeline and the CDN. (3) Content-hash URLs: append a hash of the file content to the filename (`app.3f9a2b.js`). A changed file gets a new hash and therefore a new URL. Set aggressive TTLs (1 year) because a changed file is never served from the old URL again — it's a new URL. This is the recommended approach for static assets: aggressive caching without ever serving stale content.

**Q7: How does the token bucket rate limiting algorithm work, and why is it preferred over simpler approaches?**
A: A token bucket is a counter with two properties: it has a maximum capacity, and it refills at a fixed rate. Each request consumes one token; when the bucket is empty, requests are rejected. Why it's preferred: it allows bursting. A user who hasn't made requests recently has a full bucket and can make many requests immediately before hitting the limit. This matches real user behavior (someone returning after an hour of inactivity might click around a lot) while still enforcing a long-term rate limit. A simple fixed-window counter has boundary problems: a user can make the full quota in the last second of one window and immediately make the full quota again in the first second of the next window — effectively 2x the quota in 2 seconds. The token bucket's continuous refill avoids this.

**Q8: In a microservices architecture, what does an API gateway give you over just having clients call services directly?**
A: Four major benefits. (1) Single entry point: clients know one address, not 50 service addresses that change as services are deployed. (2) Centralized cross-cutting concerns: authentication, rate limiting, and logging implemented once in the gateway rather than reimplemented in every service. (3) Internal implementation hiding: restructure your services internally without breaking clients (the gateway's API can remain stable even as the services behind it change). (4) Protocol translation: clients speak REST or GraphQL to the gateway; the gateway can speak gRPC to internal services. The cost: the gateway becomes a potential bottleneck and single point of failure, so it must be run in a clustered, highly available configuration.

## Practice Exercises

**Exercise 1 — Load Balancer Algorithm Selection (Beginner)**  
For each of the following applications, choose a load balancing algorithm (round robin, least connections, IP hash, or weighted) and explain your reasoning:
1. A stateless REST API where all requests take approximately equal time
2. An API that mixes fast requests (milliseconds) with slow requests (several seconds for video processing)
3. A legacy application that stores session data in server memory and can't be immediately refactored
4. A gradual rollout: 90% of traffic to the stable version, 10% to a new version being tested

**Exercise 2 — Rate Limiter Design (Intermediate)**  
Design a distributed rate limiter that enforces: 100 requests per minute per user, across any number of API servers. Specify: (a) the Redis data structure and exact commands used, (b) how you handle the race condition where two servers check the limit simultaneously, (c) how you handle Redis being temporarily unavailable (fail open — allow requests — or fail closed — reject requests — and why).

**Exercise 3 — API Technology Choice (Intermediate)**  
You're building a social media platform with:
- A web app (React)
- An iOS app (needs minimal data, sensitive to payload size)
- An Android app (same constraints as iOS)
- 30 internal microservices that call each other ~100,000 times/second in aggregate

Choose REST, GraphQL, or gRPC for: (a) the client-facing API, (b) the internal service-to-service communication. Justify each choice. What are the trade-offs you're accepting?

**Exercise 4 — WebSocket Architecture (Advanced)**  
Design a chat application that supports 10 million concurrent WebSocket connections, where any user can send a message to any other user in real-time. Your design must handle: (a) routing a message from User A (connected to Server 1) to User B (connected to Server 5), (b) a WebSocket server crashing — what happens to connected users?, (c) horizontal scaling of WebSocket servers. What pub/sub infrastructure would you use and why?

**Exercise 5 — CDN Strategy (Intermediate)**  
An e-commerce site has two types of content: (a) product images (same for every user, change occasionally when the product team updates photos), (b) personalized recommendations (unique per user, change every hour based on browsing behavior). Design a CDN strategy for each. For product images, specify the caching approach and cache invalidation strategy. Explain why the personalization content cannot go through a standard CDN cache.

## Key Takeaways

- Load balancers distribute traffic across multiple instances of the same service and automatically route around unhealthy instances via health checks. Layer 7 load balancers read HTTP requests and can route by URL path, headers, and host — essential for web applications.
- API gateways sit in front of multiple different services, centralizing cross-cutting concerns (auth, rate limiting, routing, logging). The difference from a load balancer: a load balancer routes to instances of the same service; a gateway routes to different services entirely.
- REST is the universal default (simple, cacheable, broad support). GraphQL solves the over/under-fetching problem when multiple clients need different data shapes. gRPC is the high-performance choice for internal service-to-service communication (binary protocol, HTTP/2, generated clients).
- Rate limiting requires shared state across all servers — in-process counters undercount in horizontally scaled deployments. Redis with atomic INCR + EXPIRE is the standard solution. Return HTTP 429 Too Many Requests with a Retry-After header.
- CDNs cache static assets at edge nodes near users, reducing latency and origin server load. Content-hash URLs (hashing the file content into the filename) enable aggressive CDN caching without ever serving stale content.
- WebSockets provide persistent, bidirectional connections that enable the server to push data at any time — essential for chat, games, collaborative editing, and live dashboards. HTTP polling is wasteful; WebSockets solve the real-time push problem efficiently.
