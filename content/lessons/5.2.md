# Networking & APIs (System Design)

Once you've internalized the core trade-offs (5.1), this unit is about the specific components that sit between a client and your application logic.

## Theory & Fundamentals

### Load Balancers

A load balancer distributes incoming requests across multiple backend instances — the component that actually makes horizontal scaling work in practice. Common strategies:

- **Round-robin**: rotate evenly across all instances. Simple, works well when all requests are roughly equal cost.
- **Least-connections**: send new requests to whichever instance has the fewest active connections. Better for long-lived or variable-cost requests.
- **IP-hash**: same client IP consistently routed to the same instance (session affinity / "sticky sessions"). Necessary when the server holds per-user state locally, but restricts scaling flexibility.
- **Weighted**: some instances receive more traffic than others (useful during gradual rollouts).

A load balancer also does **health checks**, automatically routing around instances that stop responding. This is a core availability mechanism — instances can be removed for deployment or failure without downtime, as long as enough healthy instances remain.

**Layer 4 vs. Layer 7**: L4 load balancers route based on TCP/UDP (IP + port), fast but less flexible. L7 load balancers inspect HTTP content (URL, headers, cookies) enabling routing by path (`/api/*` vs. `/static/*`), host-based routing (multiple domains on one load balancer), and SSL termination.

### API Gateways

A single entry point in front of multiple backend services, handling cross-cutting concerns once instead of in every service:

- **Authentication/Authorization**: verify JWTs or API keys centrally
- **Rate limiting**: cap requests per API key or IP
- **Request routing**: forward `/users/*` to the user service, `/orders/*` to the order service
- **Response aggregation**: combine calls to multiple internal services into one client-facing response (BFF — Backend for Frontend pattern)
- **Logging/tracing**: emit a correlation ID on every request

Without a gateway, each of 10 services has to reimplement auth and rate limiting independently. A gateway centralizes this, but also becomes a potential bottleneck and single point of failure — run it clustered.

### REST vs. RPC vs. GraphQL

| Criterion | REST | gRPC (RPC) | GraphQL |
|---|---|---|---|
| Transport | HTTP/1.1, cacheable | HTTP/2, binary | HTTP, usually POST |
| Typing | Loose (JSON) | Strong (Protobuf) | Schema (SDL) |
| Over/under-fetching | Common | Rare (typed contracts) | Solved by design |
| Best for | Public APIs, simple CRUD | Internal service-to-service | Multiple frontends with different data needs |
| Caching | Easy (HTTP cache) | Hard | Hard (single endpoint) |

**The trade-off, not just the definitions**: REST is the safe, simple default for public-facing APIs. gRPC wins for internal, performance-sensitive service-to-service calls (binary protocol, generated client/server code, streaming support). GraphQL earns its complexity when multiple frontends (web, mobile, partners) have different data requirements and you want to avoid both over-fetching (getting unused fields) and under-fetching (multiple round trips for related data).

### Rate Limiting

Protects a system from being overwhelmed by a bug, a traffic spike, or intentional abuse.

**Token bucket**: a bucket refills with tokens at a fixed rate; each request consumes a token; requests are rejected when the bucket is empty. Allows bursts up to the bucket size — a user who hasn't made requests recently can temporarily exceed the average rate.

**Sliding window counter**: counts requests in a rolling time window. Smoother enforcement than a fixed window — a fixed 60-second window can allow 2x the intended rate at the window boundary (60 requests at 11:59:59 + 60 at 12:00:00 = 120 in two seconds).

**Where does rate-limiter state live?** A single-instance in-memory counter doesn't work once you have multiple API servers — each instance tracks its own separate count. Centralize counters in Redis (`INCR` with `EXPIRE`) for an atomic, shared counter across all instances.

## Core Patterns / Techniques

### CDN (Content Delivery Network)

A geographically distributed cache for static assets (images, JS/CSS bundles, videos). A user in Mumbai fetching a video from a Virginia origin server has high latency; the same user fetching it from a Mumbai CDN edge node has low latency.

CDNs work well for: content that's the same for every user, changes infrequently, and tolerates eventual consistency (cache invalidation takes time to propagate globally). Wrong tool for: personalized content, frequently-changing data, or real-time APIs.

```
Without CDN: Browser → [Atlantic/Pacific Ocean] → Origin (Virginia) → [Ocean] → Browser
With CDN:    Browser → Edge Node (Mumbai) → Browser   (cache hit: no ocean crossing)
             Edge Node ← [ocean] ← Origin             (cache miss: first request only)
```

### WebSockets vs. HTTP Polling

For real-time features (chat, live updates, notifications):

- **HTTP short polling**: client polls every N seconds. Simple but wasteful — most polls return nothing, and there's a delay of up to N seconds before updates appear.
- **HTTP long polling**: server holds the request open until it has something to send, then the client immediately reconnects. Better latency, but still has overhead per message.
- **WebSockets**: bidirectional, persistent connection. Server can push data to the client at any time with minimal overhead. Correct answer for: chat, live collaboration, real-time dashboards, multiplayer games.
- **Server-Sent Events (SSE)**: one-directional (server → client only), simpler than WebSockets when the client doesn't need to send data after the initial connection. Good for: notifications, live feeds.

## Best Practices

- **Use L7 load balancing for HTTP** — it enables path-based routing and SSL termination, which L4 cannot do.
- **Health check endpoints are required infrastructure** — every service should expose a `/health` endpoint that the load balancer polls. A 200 response means "route traffic here"; anything else means "route around this instance."
- **Rate limit at the gateway, not the service** — implementing rate limiting in every service independently leads to inconsistencies and duplicated logic.
- **REST for public APIs, gRPC for internal** — gRPC's binary protocol and generated clients are a meaningful performance gain for internal calls, but the tooling overhead isn't worth it for a public-facing API where flexibility matters more.
- **For "design a rate limiter" specifically**: Redis with `INCR` + `EXPIRE` is the canonical answer for distributed rate limiting.

## Common Interview Questions

**Q1: What's the difference between a load balancer and an API gateway?**
A: A load balancer distributes traffic across multiple instances of the same service (traffic distribution + health checks). An API gateway sits in front of multiple different services and handles cross-cutting concerns: authentication, rate limiting, routing requests to the right service, and response aggregation. They're often both present — an API gateway behind a load balancer.

**Q2: Why does rate limiting state need to be stored in Redis when you have multiple servers?**
A: Each server has its own memory. If you store rate-limit counters in-process, server A counts its own 50 requests and server B counts its own 50 requests, but the user has effectively made 100 requests without triggering any limit. Redis provides a shared, atomic counter (`INCR` + `EXPIRE`) that all servers read and write to, giving you accurate cross-server counting.

**Q3: When would you choose GraphQL over REST?**
A: When multiple different clients (web, iOS, Android, partner integrations) need different subsets of the same underlying data, and you want to avoid creating separate REST endpoints for each client's needs. The query language lets each client request exactly the fields it needs. The cost: more complex server implementation, harder HTTP caching, and a steeper learning curve for API consumers.

**Q4: What is SSL termination at a load balancer and why is it done there?**
A: SSL/TLS encryption/decryption is computationally expensive. Terminating SSL at the load balancer means: traffic from the internet is encrypted (HTTPS), the load balancer decrypts it, and then communicates with backend services over plain HTTP within a trusted private network. Backend services are relieved of SSL overhead, and certificate management is centralized at the load balancer.

**Q5: What is a WebSocket and when should you use it?**
A: A WebSocket is a persistent, bidirectional TCP connection that stays open between client and server. Use it when the server needs to push data to the client in real time with low latency — chat, notifications, live collaboration, real-time analytics. HTTP polling simulates this but is wasteful (most polls return nothing). Use WebSockets when latency matters and the server has data to push unpredictably.

**Q6: What does a CDN cache invalidation strategy look like?**
A: Three main approaches: (1) TTL-based — cached content expires automatically after a set time; simple but data can be stale for up to the TTL. (2) Explicit purge — when content changes, send an API call to the CDN to invalidate specific URLs; more accurate but requires every deploy to trigger purges. (3) Content-hash URLs — append a hash of the file content to the filename (`app.3f9a2b.js`); a changed file is a different URL, so the old cache entry is never stale and expires naturally.

## Practice Exercises

1. **Load balancer design**: A web application currently runs as one server with sticky sessions. You need to scale to 10 servers. What changes are required in the application and infrastructure? What happens to active sessions during the migration?

2. **Rate limiter implementation**: Design a distributed rate limiter that allows at most 100 requests per minute per user ID across any number of API servers. Specify the Redis data structure, the INCR/EXPIRE sequence, and how you handle clock skew across servers.

3. **API technology choice**: You're building a social media platform with a web app, iOS app, and Android app, all of which need different amounts of user profile data. You also have internal services that call each other 50,000 times/second. Choose REST, gRPC, or GraphQL for each use case and explain the trade-offs.

## Key Takeaways

- Load balancers distribute traffic and automatically route around unhealthy instances; Layer 7 load balancers can route by URL path and terminate SSL.
- API gateways centralize cross-cutting concerns (auth, rate limiting, routing) across multiple services.
- REST for public APIs (simple, cacheable); gRPC for internal service-to-service (fast, typed); GraphQL when multiple clients have different data requirements.
- Rate limiter state must be centralized (Redis) when multiple servers share the limit — per-server in-memory counters undercount.
- CDNs cache static assets at edge locations near users; they don't work for personalized or frequently-changing content.
- WebSockets are the correct choice for real-time bidirectional communication; Server-Sent Events for server-to-client-only push.
