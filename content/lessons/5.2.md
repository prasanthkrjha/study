# Networking & APIs (System Design)

Once you've internalized the core trade-offs (5.1), this unit is about the specific components that sit between a client and your application logic.

## Load balancers

A load balancer distributes incoming requests across multiple backend instances — the component that actually makes horizontal scaling work in practice. Common strategies: round-robin (rotate evenly), least-connections (send to whichever instance has the fewest active requests), and IP-hash (same client consistently routed to the same instance, useful when you need session affinity). A load balancer also does health checks, automatically routing around instances that stop responding — this is a big part of how a system stays available when one server dies.

## API gateways

A single entry point that sits in front of multiple backend services, handling cross-cutting concerns once instead of in every service: authentication, rate limiting, request routing, and sometimes response aggregation (combining calls to multiple internal services into one client-facing response). This becomes especially relevant once you have more than one backend service — without a gateway, every service has to reimplement auth and rate limiting independently.

## REST vs. RPC vs. GraphQL

- **REST** — resources identified by URLs, manipulated via HTTP verbs (`GET /users/42`, `POST /orders`). Simple, cacheable (HTTP caching works naturally), but can lead to over-fetching (getting fields you don't need) or under-fetching (needing multiple round trips for related data).
- **RPC** (e.g. gRPC) — call a function on a remote service as if it were local (`getUser(42)`). Often faster (binary protocol, strongly typed contracts) and a natural fit for internal service-to-service communication, less natural for public-facing APIs consumed by arbitrary clients.
- **GraphQL** — the client specifies exactly which fields it needs in a single query, solving over/under-fetching, at the cost of more complex server-side implementation and harder HTTP-level caching (most requests are POSTs to one endpoint).

Know the trade-off, not just the definitions: REST is the safe, simple default; GraphQL earns its complexity when clients have very different, unpredictable data needs (e.g. a public API used by many different frontends); RPC wins for internal, performance-sensitive service-to-service calls.

## Rate limiting

Protects a system from being overwhelmed — by a bug, a traffic spike, or abuse — by capping how many requests a client can make in a given window. Common algorithms:

- **Token bucket** — a bucket refills with tokens at a fixed rate; each request consumes a token; requests are rejected when the bucket is empty. Allows short bursts up to the bucket size.
- **Sliding window** — counts requests in a rolling time window, giving smoother enforcement than a fixed window (which can allow 2x the intended rate right at a window boundary).

"Design a rate limiter" is one of the classic system design interview questions precisely because it's small enough to fully design in 30–45 minutes while still touching real trade-offs (memory vs. accuracy, distributed vs. single-instance state).

## Practice tip

For each concept here, be ready to answer "why would I choose this over the alternative?" — that comparative framing is what interviewers are actually listening for, more than definitions recited in isolation.
