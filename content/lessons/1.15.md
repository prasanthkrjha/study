# Greedy

A greedy algorithm makes the locally best choice at every step and never reconsiders it — no backtracking, no exploring alternatives. The hard part isn't writing greedy code (it's usually short); it's **proving the greedy choice is actually safe**, because greedy is wrong far more often than it's right.

## Activity selection

Given a set of activities with start/end times, select the maximum number that don't overlap. The greedy insight: always pick the activity that **finishes earliest** among the remaining valid options — this leaves the most possible room for everything after it.

```js
function maxActivities(activities) {
  activities.sort((a, b) => a.end - b.end);
  let count = 0, lastEnd = -Infinity;
  for (const { start, end } of activities) {
    if (start >= lastEnd) { count++; lastEnd = end; }
  }
  return count;
}
```

This is the same shape as the interval-scheduling example in the Intervals unit — it's the textbook proof case for why "sort by end time" is provably optimal here.

## The exchange argument

This is *how* you prove a greedy strategy correct, and it's worth understanding even at a conceptual level for interviews: assume there's some optimal solution that does **not** follow the greedy rule at some step. Show that you can swap ("exchange") that step for the greedy choice without making the solution any worse. If that's always true, greedy is at least as good as optimal — so greedy IS optimal.

For activity selection: suppose an optimal solution's first pick isn't the earliest-finishing activity. Swap it for the earliest-finishing one — since it finishes no later, it can't block any activity the original first pick didn't already block. The solution stays valid and no shorter. Hence picking earliest-finish-first is safe.

## When greedy fails

Greedy does **not** work for 0/1 knapsack (picking the best value/weight ratio item first can lock you out of a better combination later) — that's exactly why 0/1 knapsack needs dynamic programming instead. The difference: knapsack's choices interact (taking one item affects what fits later in a way that isn't monotonic), while activity selection's choices don't (an earlier-finishing activity never disadvantages you).

## Recognizing when greedy is safe

Ask: "If I make the locally best choice now, could it ever come back to hurt me later?" If you can construct even one counterexample, greedy is wrong and you need DP or backtracking instead. If the problem has a clean sorting order and each choice provably doesn't foreclose better future choices (classic tell: interval/scheduling problems), greedy is usually the intended — and much faster — solution.
