# Unit Testing with Jest

Testing is not about proving your code works once — it is about detecting future changes that break something that used to work. A test suite is a safety net that gives you confidence to refactor, add features, and merge pull requests from others without needing to manually re-verify the entire system. Interviewers screen for testing knowledge because untested code in production creates fragile systems and slows teams down.

Jest is the de facto standard test runner for JavaScript and TypeScript. It provides a test runner, assertion library, and mocking framework in a single package — no configuration required for most projects. It runs tests in parallel (in separate worker processes, each with its own module registry), generates coverage reports, and has deep integration with React via `@testing-library/react`. Understanding how Jest works — not just the API surface — makes the difference between tests that catch real bugs and tests that are more brittle than the code they cover.

The most important principle in unit testing is isolation: a unit test should test one thing in isolation from its dependencies. If a test calls a real database, real network endpoint, or relies on system time, it is no longer a unit test — it is an integration test that happens to use Jest as its runner. Isolation is achieved through mocking, and knowing when and how to mock is the core skill this module builds.

## Theory & Fundamentals

### What is a Unit Test?

A unit is the smallest testable piece of behavior in your application — typically a single function, method, or module. A unit test verifies that unit's behavior in isolation: given some input (or some preconditions), a specific output (or side effect) is expected. Crucially, "isolation" means the unit's external dependencies (databases, HTTP clients, file system, `Date.now()`) are replaced with controlled fakes during the test.

Why isolation? Real dependencies are slow (network), non-deterministic (time, random), stateful (databases), and may not be available in a CI environment. A mocked dependency is instant, deterministic, and always available.

### The Test Pyramid

The test pyramid is a mental model for distributing test types: many unit tests (fast, isolated, cheap to write and run), fewer integration tests (test multiple components working together), and even fewer end-to-end tests (simulate a full user flow, expensive and slow). Unit tests form the base because they are the fastest feedback loop during development.

### Arrange-Act-Assert

Every well-written test follows three phases: Arrange (set up the preconditions and inputs), Act (invoke the code under test), Assert (verify the output or side effects match expectations). Keeping these phases visually distinct makes tests easy to read and diagnose when they fail.

### Test Names as Documentation

Test names should describe behavior, not implementation. "returns 0 for empty array" describes what the function should do. "loops through array and checks each element" describes how, which breaks when the implementation changes (even if the behavior is correct). Tests named as behavior specifications serve as living documentation that stays in sync with the code.

## Core Concepts / Techniques

### describe / it / test Structure

```javascript
// describe groups related tests; it/test declares a single expected behavior
describe('calculateDiscount', () => {
  it('applies 10% discount for silver tier users', () => {
    const result = calculateDiscount(100, 'silver');
    expect(result).toBe(90);
  });

  it('applies 20% discount for gold tier users', () => {
    const result = calculateDiscount(100, 'gold');
    expect(result).toBe(80);
  });

  it('returns full price for unknown tiers', () => {
    const result = calculateDiscount(100, 'unknown');
    expect(result).toBe(100);
  });

  it('throws for negative prices', () => {
    expect(() => calculateDiscount(-10, 'silver')).toThrow('Price must be positive');
  });
});
```

### Assertions

```javascript
// Primitive equality — uses ===
expect(result).toBe(42);
expect(result).not.toBe(0);

// Deep structural equality for objects and arrays — does NOT use ===
expect(user).toEqual({ id: 1, name: 'Prasanth', active: true });
expect(tags).toEqual(['js', 'sql', 'redis']);

// Truthiness matchers
expect(value).toBeTruthy();
expect(value).toBeFalsy();
expect(value).toBeNull();
expect(value).toBeUndefined();
expect(value).toBeDefined();

// Number comparisons
expect(result).toBeGreaterThan(0);
expect(result).toBeLessThanOrEqual(100);
expect(result).toBeCloseTo(3.14, 2); // floating-point safe comparison

// String matchers
expect(message).toMatch(/error/i);         // regex match
expect(message).toContain('required');     // substring

// Array matchers
expect(items).toHaveLength(3);
expect(items).toContain('apple');
expect(items).toContainEqual({ id: 1 });  // deep equality for objects in array

// Error assertions
expect(() => fn(invalidInput)).toThrow();
expect(() => fn(invalidInput)).toThrow('specific message');
expect(() => fn(invalidInput)).toThrow(ValidationError); // error class
```

### Mocking with jest.fn() and jest.spyOn()

```javascript
// jest.fn(): create a standalone mock function
const mockSendEmail = jest.fn();
mockSendEmail.mockReturnValue({ sent: true });
mockSendEmail.mockReturnValueOnce({ sent: false }); // only for the FIRST call
mockSendEmail.mockResolvedValue({ sent: true });     // async — returns a promise

// Assert on how the mock was called
expect(mockSendEmail).toHaveBeenCalled();
expect(mockSendEmail).toHaveBeenCalledTimes(2);
expect(mockSendEmail).toHaveBeenCalledWith('user@example.com', expect.any(String));
expect(mockSendEmail).not.toHaveBeenCalled();

// jest.spyOn(): wrap an existing module method to observe/control it
import * as emailService from './emailService.js';
const spy = jest.spyOn(emailService, 'send');
spy.mockResolvedValue({ sent: true });

// After the test, restore the original implementation
spy.mockRestore();
```

### Mocking Modules

```javascript
// Mock an entire module — every import of this module in the test file
// gets the mocked version
jest.mock('./database.js', () => ({
  query: jest.fn(),
  getUser: jest.fn().mockResolvedValue({ id: 1, name: 'Prasanth' })
}));

// Mock a node module
jest.mock('nodemailer', () => ({
  createTransport: jest.fn().mockReturnValue({
    sendMail: jest.fn().mockResolvedValue({ messageId: 'test-id' })
  })
}));

// Accessing the mock in tests to assert or configure per-test behavior
import { query } from './database.js';
query.mockResolvedValueOnce([{ id: 1, name: 'Prasanth' }]);
```

### Setup and Teardown

```javascript
describe('UserService', () => {
  let service;
  let mockDb;

  beforeAll(() => {
    // Runs once before all tests in this describe block
    // Good for expensive setup that all tests share
    console.log('Setting up test suite');
  });

  afterAll(() => {
    // Runs once after all tests — clean up shared resources
    console.log('Tearing down test suite');
  });

  beforeEach(() => {
    // Runs before EACH test — provides a fresh, clean state
    mockDb = { query: jest.fn() };
    service = new UserService(mockDb);
  });

  afterEach(() => {
    // Runs after EACH test — clear mocks so tests don't interfere
    jest.clearAllMocks();
    // clearAllMocks: clears call counts and return values
    // resetAllMocks: also resets mock implementations
    // restoreAllMocks: restores spies to original implementations
  });

  it('creates a user', async () => {
    mockDb.query.mockResolvedValue({ rows: [{ id: 'uuid-1', name: 'Alice' }] });
    const user = await service.createUser({ name: 'Alice' });
    expect(user.id).toBeDefined();
    expect(mockDb.query).toHaveBeenCalledWith(
      expect.stringContaining('INSERT'),
      expect.arrayContaining(['Alice'])
    );
  });
});
```

## Code Examples

### Testing an Async Service Function

```javascript
// src/services/orderService.js
export async function placeOrder(userId, items) {
  if (!items.length) throw new Error('Order must have at least one item');

  const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  const order = await db.createOrder({ userId, total });
  await emailService.sendOrderConfirmation(order);
  return order;
}

// src/services/orderService.test.js
import { placeOrder } from './orderService.js';
import * as db from '../db.js';
import * as emailService from './emailService.js';

jest.mock('../db.js');
jest.mock('./emailService.js');

describe('placeOrder', () => {
  const mockOrder = { id: 'order-1', userId: 'user-1', total: 50 };

  beforeEach(() => {
    db.createOrder.mockResolvedValue(mockOrder);
    emailService.sendOrderConfirmation.mockResolvedValue(undefined);
  });

  afterEach(() => jest.clearAllMocks());

  it('calculates total and creates an order', async () => {
    const items = [
      { price: 25, quantity: 1 },
      { price: 12.50, quantity: 2 }
    ];

    const result = await placeOrder('user-1', items);

    expect(db.createOrder).toHaveBeenCalledWith({ userId: 'user-1', total: 50 });
    expect(result).toEqual(mockOrder);
  });

  it('sends a confirmation email after creating the order', async () => {
    await placeOrder('user-1', [{ price: 10, quantity: 1 }]);
    expect(emailService.sendOrderConfirmation).toHaveBeenCalledWith(mockOrder);
  });

  it('throws when the items array is empty', async () => {
    await expect(placeOrder('user-1', [])).rejects.toThrow('Order must have at least one item');
    expect(db.createOrder).not.toHaveBeenCalled();
  });
});
```

### Testing with Fake Timers

```javascript
// Testing code that depends on time
import { generateSessionId, isSessionExpired } from './session.js';

describe('isSessionExpired', () => {
  beforeEach(() => jest.useFakeTimers());
  afterEach(() => jest.useRealTimers());

  it('returns false for a fresh session', () => {
    const session = { createdAt: Date.now(), ttlMs: 3600_000 };
    expect(isSessionExpired(session)).toBe(false);
  });

  it('returns true after the TTL elapses', () => {
    const session = { createdAt: Date.now(), ttlMs: 3600_000 };
    jest.advanceTimersByTime(3600_001); // advance 1 hour + 1ms
    expect(isSessionExpired(session)).toBe(true);
  });
});
```

## Best Practices

- **Test behavior, not implementation** — assert on outputs and observable side effects, not on internal state, private methods, or which internal functions were called. Tests that couple to implementation break when you refactor (even correctly).
- **Each test should have exactly one reason to fail** — testing multiple behaviors in a single `it` block makes failures ambiguous; one assertion per logical behavior (not per `expect` call) is the rule.
- **Use `beforeEach` for state setup, not `beforeAll`** — shared state across tests through `beforeAll` causes tests to interfere with each other; `beforeEach` guarantees a clean slate for every test.
- **Clear mocks between tests** — call `jest.clearAllMocks()` in `afterEach` to prevent call count accumulation and return value leakage between tests.
- **Use `toEqual` for objects and arrays, `toBe` for primitives** — `toBe` uses reference equality (`===`); two separately created objects that look identical will not `toBe` equal.
- **Name tests as sentences describing expected behavior** — "returns an empty array when no items match the filter" is useful documentation; "test filter function" is not.
- **Treat a test failure as a first-class event** — a failing test is telling you something real: either the code has a bug, the test has a bug, or the requirements changed. Deleting or skipping a failing test is the worst of the three options.

## Common Interview Questions

**Q: What is the difference between a unit test and an integration test?**
A: A unit test tests a single function or module in isolation, with all external dependencies replaced by mocks. An integration test tests multiple components working together — for example, a service function calling a real database. Unit tests are faster and more targeted; integration tests are slower but catch problems that only appear when real components interact.

**Q: What is the difference between toBe and toEqual in Jest?**
A: `toBe` uses strict reference equality (`===`) — two separately created objects with identical contents will not pass `toBe`. `toEqual` performs deep structural comparison — two objects with the same keys and values pass `toEqual` even if they are different references. Use `toBe` for primitives and `toEqual` for objects and arrays.

**Q: What is jest.fn() and why do we use it?**
A: `jest.fn()` creates a mock function that records how it was called (arguments, call count, return values) without executing any real logic. We use it to replace real dependencies (database calls, network requests) so tests are fast, deterministic, and do not depend on external services being available.

**Q: What is the difference between jest.clearAllMocks(), jest.resetAllMocks(), and jest.restoreAllMocks()?**
A: `clearAllMocks` clears mock call history and results but keeps implementations. `resetAllMocks` also removes any mock implementations set with `mockReturnValue` etc. `restoreAllMocks` goes furthest — it restores spies created with `jest.spyOn` back to the original implementation. Call the appropriate one in `afterEach` based on what you want preserved.

**Q: How do you test a function that uses setTimeout or Date.now()?**
A: Use `jest.useFakeTimers()` to replace real timer functions with Jest-controlled fakes. Then use `jest.advanceTimersByTime(ms)` or `jest.runAllTimers()` to simulate the passage of time without actual waiting. Fake timers also affect `Date.now()` when Jest replaces it.

**Q: What is code coverage and what are its limitations?**
A: Code coverage measures the percentage of lines, branches, functions, and statements executed by tests. It reveals which code has zero test coverage. Its limitation is that coverage says nothing about assertion quality — a test that executes a function but only asserts `expect(result).toBeDefined()` adds coverage without verifying correct behavior.

**Q: How would you mock a module that makes HTTP requests in tests?**
A: Use `jest.mock('moduleName')` to replace the module entirely, then configure the mock with `mockResolvedValue` or `mockReturnValue` to return controlled responses. For HTTP libraries, `jest.spyOn(axios, 'get').mockResolvedValue({ data: {...} })` works well. For fetch-based code in integration-style tests, consider `msw` (Mock Service Worker) which intercepts at the network level.

**Q: What is test isolation and why does it matter?**
A: Test isolation means each test is independent — its outcome does not depend on whether other tests ran before it or what order they ran in. It matters because non-isolated tests produce unreliable results: they can pass when run in one order and fail in another, making failures intermittent and hard to diagnose.

## Practice Exercises

1. **Pure function testing**: Write tests for a `calculateCartTotal(items, discountCode)` function that handles: empty carts, invalid discount codes, valid percentage discounts, and a maximum discount cap. Write at least one test for each behavior branch.

2. **Async service with mocks**: Write tests for a `registerUser(email, password)` function that validates email format, hashes the password using a `bcrypt` module, and saves to a database module. Mock both `bcrypt` and the database module. Test the happy path, duplicate email error, and invalid email validation.

3. **Timer-based function**: Implement and test a `debounce(fn, delayMs)` function using fake timers. Test that: the function is not called immediately, it is called after the delay elapses, multiple rapid calls result in only one invocation (the last one), and the delay resets on each new call.

4. **Error propagation**: Write tests for a middleware function that calls an async route handler and forwards any thrown error to Express's `next(err)`. Test that errors are correctly forwarded and that `next` is not called when the handler succeeds.

5. **Retrofit existing tests**: Take a function you have already written without tests and add a test suite for it. Identify what dependencies need to be mocked, what edge cases exist, and what the failure behavior should be. Aim for meaningful assertions, not just coverage.

## Key Takeaways

- Unit tests verify isolated behavior — every external dependency (database, network, time) must be replaced with a controlled mock so tests are fast, deterministic, and environment-independent.
- `describe` groups related tests; `it`/`test` declares a single expected behavior; test names should be readable sentences describing what the code should do, not how it does it.
- `toBe` uses reference equality; `toEqual` uses deep structural equality — use `toEqual` for objects and arrays.
- `jest.fn()` creates mock functions that record calls; `jest.mock('module')` replaces entire modules; `jest.spyOn` wraps existing methods to observe or override them.
- `beforeEach` provides clean state before every test, preventing shared state between tests from causing interference; `afterEach` with `jest.clearAllMocks()` resets mock state.
- Code coverage is a signal for gaps, not a quality metric — 100% coverage with weak assertions is worse than 70% coverage with assertions that verify real behavior.
- Tests that couple to implementation (asserting internal state or which private methods were called) break on correct refactors; tests that assert on observable output are resilient to implementation changes.
- Fake timers (`jest.useFakeTimers`) allow testing time-dependent code without real delays — `jest.advanceTimersByTime` simulates the passage of time synchronously.
