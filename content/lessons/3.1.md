# Unit Testing (Jest)

Testing is one of the cheapest gaps to close and one of the most commonly screened-for skills — "write clean, maintainable code and perform unit testing" shows up almost verbatim in real job postings.

## Test structure: describe / it

```js
describe("calculateTotal", () => {
  it("sums item prices", () => {
    expect(calculateTotal([{ price: 10 }, { price: 5 }])).toBe(15);
  });

  it("returns 0 for an empty cart", () => {
    expect(calculateTotal([])).toBe(0);
  });
});
```

`describe` groups related tests under a shared label; `it` (or `test`) declares a single expected behavior. Name each `it` block as a sentence describing behavior ("returns 0 for an empty cart"), not implementation ("loops through array") — the test name is documentation.

## Assertions

```js
expect(result).toBe(5);                 // strict equality (===)
expect(result).toEqual({ a: 1 });       // deep equality for objects/arrays
expect(fn).toThrow("Invalid input");    // asserts an error is thrown
expect(array).toContain(3);
expect(value).toBeNull();
```

`toBe` vs `toEqual` trips people up constantly: `toBe` compares references for objects (two separately-created identical objects are `toBe`-unequal), `toEqual` compares structural/deep equality. Use `toEqual` for objects and arrays.

## Mocking functions

Replace a real dependency (an API call, a database, `Date.now()`) with a fake you control, so the test is isolated and deterministic:

```js
const fetchUser = jest.fn().mockResolvedValue({ id: 1, name: "Prasanth" });

test("greets the fetched user", async () => {
  const user = await fetchUser();
  expect(fetchUser).toHaveBeenCalledTimes(1);
  expect(greet(user)).toBe("Hello, Prasanth");
});
```

Mocking is what keeps unit tests fast and reliable — a real network call would make the test slow, flaky, and dependent on an external service being up.

## beforeEach / afterEach

Run shared setup/teardown around every test in a block, so each test starts from a known clean state instead of leaking state between tests:

```js
let db;
beforeEach(() => { db = createInMemoryDb(); });
afterEach(() => { db.close(); });
```

## Code coverage

Coverage reports (`jest --coverage`) tell you what percentage of lines/branches your tests actually execute — useful as a **signal for gaps**, not a target to game. 100% coverage with weak assertions (`expect(result).toBeDefined()` everywhere) is worse than 70% coverage that actually verifies behavior. Use coverage to find code nobody is testing, not as the definition of "done."

## Practice tip

Retrofit tests onto one existing component you already built, rather than starting from a fresh toy example — testing real code (with its real edge cases and real dependencies to mock) is what actually builds the skill the roadmap's Month 1 project asks for.
