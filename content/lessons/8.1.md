# Prompt Engineering

This is the entry point to the entire AI Engineering track — every technique in later units (RAG, agents, evaluation) is built on reliably getting an LLM to do what you want via its input.

## Zero-shot vs. few-shot prompting

**Zero-shot**: ask the model to do a task with no examples, relying entirely on its pretrained knowledge:

```
Classify the sentiment of this review as positive, negative, or neutral:
"The battery life is disappointing but the camera is excellent."
```

**Few-shot**: include a handful of example input/output pairs in the prompt before the real task, which steers the model toward your exact desired format and reasoning style:

```
Review: "Fast shipping, terrible packaging." -> Sentiment: mixed
Review: "Best purchase this year." -> Sentiment: positive
Review: "The battery life is disappointing but the camera is excellent." -> Sentiment:
```

Few-shot typically improves reliability and format consistency at the cost of a longer (more expensive, slower) prompt — use it when zero-shot output is inconsistent or the format is unusual.

## Chain-of-thought

Explicitly asking the model to reason step-by-step before giving a final answer measurably improves accuracy on multi-step problems (arithmetic, logic, multi-hop questions):

```
Question: A store had 120 items. It sold 35% on Monday and 20 more on Tuesday.
How many are left? Let's think step by step.
```

The mechanism: generating intermediate reasoning tokens gives the model more "compute" (more forward passes) to work through the problem, rather than jumping straight to an answer it has to get right in one shot.

## System vs. user prompts

The **system prompt** sets persistent behavior, role, and constraints for the whole conversation ("You are a helpful support assistant. Never provide medical diagnoses, only general wellness information."). The **user prompt** is the specific request in a given turn. This separation is what lets you build guardrails once (in the system prompt) rather than re-stating them in every user message — directly relevant to the guardrail/red-flag detection work described in your own Physynex assistant.

## Structured / JSON outputs

When your code needs to parse the model's response programmatically (not just display it to a human), ask explicitly for structured output and describe the exact shape:

```
Extract the person's name, age, and city from the text below.
Respond with ONLY valid JSON in this exact shape: {"name": string, "age": number, "city": string}

Text: "Prasanth, 25, lives in Bengaluru."
```

Many providers also offer a dedicated structured-output / JSON-mode feature that constrains the model's output to match a schema — more reliable than prompt instructions alone, since it's enforced at the decoding level rather than just requested in natural language.

## Prompt evaluation

A prompt that works on your three test cases can silently fail on the fifth real user input — prompt engineering without evaluation is just guessing. At minimum: keep a small, growing set of representative inputs (including edge cases and adversarial ones) and re-run them whenever you change a prompt, so you can see regressions before users do. This is the seed of the more formal evaluation harnesses covered in Unit 8.9.

## Practice tip

Take one real prompt you'd use in a project and deliberately break it: feed it an edge case, an adversarial input, or a request slightly outside its intended scope. Watching where a prompt fails is more instructive than watching it succeed.
