# Redis & Caching

Caching is one of the highest-leverage performance tools in backend engineering — a cache hit can be thousands of times faster than a database query or external API call. But caching is also one of the easiest tools to misuse: applied carelessly, it creates two sources of truth that silently diverge, making bugs harder to reproduce and harder to diagnose than the original slowness would have been.

Redis is the dominant in-memory data store for caching in web applications. It stores all data in RAM, making read and write latency sub-millisecond even under heavy load. Beyond simple key-value storage, Redis supports strings, hashes, lists, sets, sorted sets, and streams — each with its own set of atomic commands. Most application-layer caching uses only the string type (serialized JSON values), but the richer types are valuable for leaderboards, rate limiters, real-time feeds, and session storage.

The fundamental mental model for caching: the database is the source of truth and always will be; the cache is a disposable speed layer that can be wiped and rebuilt at any time without losing real data. If wiping the cache would cause data loss, you are using the cache as a database — which is a different problem with different operational requirements.

---

## Theory & Fundamentals

### Why Memory Is Different

Fetching a value from RAM is on the order of nanoseconds. Fetching a row from a database on the same machine involves disk I/O (or page cache), query parsing, locking, and B-tree traversal — typically 1–50 milliseconds for a simple indexed query. Fetching from an external API adds network round-trip time on top of that. A cache eliminates all of that overhead when it has the value you need.

The catch: memory is finite and expensive. Redis evicts keys based on a configurable eviction policy (`LRU`, `LFU`, `volatile-lru`, etc.) when it approaches its memory limit. This means your cache may silently discard data — write code that handles cache misses gracefully, always, because a cache miss is not an error condition.

### Cache Patterns

**Cache-aside (lazy loading):** The application checks the cache before querying the database. On a miss, it queries the database and writes the result to the cache. The database remains the authoritative source.

**Write-through:** On every write, the application writes to both the cache and the database simultaneously. Cache is always warm but every write pays the cost of a cache update.

**Write-behind (write-back):** The application writes only to the cache; a background process flushes changes to the database asynchronously. Lower write latency, but higher risk of data loss if the cache fails before flushing.

**Read-through:** The cache itself fetches from the database on a miss, rather than the application managing that logic. The application talks only to the cache layer. Common in managed caching services.

For most web applications, cache-aside is the right default — it is simple to reason about and keeps the database as the clear source of truth.

### Cache Invalidation

Phil Karlton's observation — "there are only two hard things in computer science: cache invalidation and naming things" — is an honest assessment. The hard part is not storing things in the cache; it is knowing with certainty when a cached value is no longer valid.

Three strategies: TTL-based expiry (evict automatically after N seconds — simple, but the cache may serve stale data for up to the TTL window), explicit invalidation on write (when you update the database, immediately delete or update the cache key — accurate, but requires every write code path to remember to invalidate), and versioned keys / cache-busted URLs for static assets (a new version generates a new key, so old caches never serve it).

## Core Concepts / Techniques

### Basic Key-Value Operations

```bash
# SET and GET — the fundamental operations
SET user:42 '{"name":"Prasanth","plan":"pro"}'
GET user:42
DEL user:42

# SET with expiry (EX = seconds, PX = milliseconds)
SET session:abc123 "user-42" EX 3600    # expires in 1 hour
SET rate:192.168.1.1 0 PX 60000         # expires in 60 seconds

# Check time remaining on a key
TTL session:abc123     # seconds remaining (-1 = no expiry, -2 = key gone)
PTTL session:abc123    # milliseconds remaining

# SET with options: NX = only if Not eXists, XX = only if eXists
SET lock:resource-1 "worker-a" EX 30 NX   # distributed lock pattern

# Atomic increment/decrement
INCR rate:192.168.1.1         # atomic: no race condition risk
INCRBY counter:visits 5
DECRBY stock:product:99 1
```

### Hash Type (Structured Objects)

```bash
# Store structured data without serializing to JSON
HSET user:42 name "Prasanth" email "p@example.com" plan "pro"
HGET user:42 name            # get one field
HGETALL user:42              # get all fields and values
HINCRBY user:42 login_count 1

# More efficient than storing JSON string when you update individual fields
```

### Sorted Sets (Leaderboards, Rate Limiting)

```bash
# ZADD adds members with a numeric score
ZADD leaderboard 1500 "user:42"
ZADD leaderboard 2300 "user:17"
ZADD leaderboard 900  "user:88"

# ZRANGE returns members in score order
ZRANGE leaderboard 0 -1 WITHSCORES    # lowest to highest
ZREVRANGE leaderboard 0 9 WITHSCORES  # top 10, highest first

# ZRANK returns the rank (0-indexed) of a member
ZRANK leaderboard "user:42"
```

### TTL and Eviction

```bash
# Set TTL on an existing key
EXPIRE key:name 300     # seconds
PERSIST key:name        # remove TTL, make permanent

# Redis eviction policies (set in redis.conf or CONFIG SET)
# volatile-lru: evict keys with TTL using LRU algorithm
# allkeys-lru: evict any key using LRU (recommended for pure cache use)
# volatile-ttl: evict keys with TTL, preferring those with shortest TTL
# noeviction: return error when memory full (for permanent storage use cases)
```

## Code Examples

### Cache-Aside Pattern in Node.js

```javascript
import { createClient } from 'redis';
import { pool } from './db.js';

const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

const CACHE_TTL = 300; // 5 minutes

/**
 * Fetch a user by ID, checking Redis first.
 * Cache stores serialized JSON; database is always the source of truth.
 */
async function getUserById(userId) {
  const cacheKey = `user:${userId}`;

  // 1. Check cache
  const cached = await redis.get(cacheKey);
  if (cached) {
    return JSON.parse(cached); // cache hit — return immediately
  }

  // 2. Cache miss — query database
  const { rows } = await pool.query(
    'SELECT id, name, email, plan FROM users WHERE id = $1',
    [userId]
  );
  const user = rows[0] ?? null;

  // 3. Write result to cache (even null, to avoid cache stampede on missing users)
  if (user) {
    await redis.set(cacheKey, JSON.stringify(user), { EX: CACHE_TTL });
  }

  return user;
}

/**
 * Update a user and invalidate their cache entry.
 * Always update DB first, then invalidate — never update cache directly.
 */
async function updateUserPlan(userId, newPlan) {
  await pool.query(
    'UPDATE users SET plan = $1 WHERE id = $2',
    [newPlan, userId]
  );

  // Invalidate cache — next read will fetch fresh data from DB
  await redis.del(`user:${userId}`);
}
```

### Rate Limiter Using Redis

```javascript
/**
 * Sliding-window rate limiter using Redis sorted sets.
 * Allows `maxRequests` per `windowMs` milliseconds per identifier.
 */
async function isRateLimited(identifier, maxRequests = 100, windowMs = 60_000) {
  const now = Date.now();
  const windowStart = now - windowMs;
  const key = `rate:${identifier}`;

  const pipeline = redis.multi();

  // Remove entries outside the current window
  pipeline.zRemRangeByScore(key, 0, windowStart);

  // Count requests in the window
  pipeline.zCard(key);

  // Add the current request
  pipeline.zAdd(key, { score: now, value: `${now}-${Math.random()}` });

  // Set expiry so keys self-clean after inactivity
  pipeline.expire(key, Math.ceil(windowMs / 1000));

  const results = await pipeline.exec();
  const requestCount = results[1]; // count after removal, before adding current

  return requestCount >= maxRequests; // true = rate limited
}

// Usage in Express middleware
app.use(async (req, res, next) => {
  const identifier = req.ip;
  if (await isRateLimited(identifier)) {
    return res.status(429).json({ error: 'Too many requests' });
  }
  next();
});
```

### Session Storage Pattern

```javascript
import { randomUUID } from 'crypto';

const SESSION_TTL = 7 * 24 * 60 * 60; // 7 days in seconds

async function createSession(userId, metadata = {}) {
  const sessionId = randomUUID();
  const sessionData = { userId, ...metadata, createdAt: Date.now() };

  await redis.set(
    `session:${sessionId}`,
    JSON.stringify(sessionData),
    { EX: SESSION_TTL }
  );

  return sessionId;
}

async function getSession(sessionId) {
  const data = await redis.get(`session:${sessionId}`);
  if (!data) return null;

  // Refresh TTL on active sessions (sliding expiry)
  await redis.expire(`session:${sessionId}`, SESSION_TTL);

  return JSON.parse(data);
}

async function destroySession(sessionId) {
  await redis.del(`session:${sessionId}`);
}
```

## Best Practices

- **Always set a TTL** on cache keys unless you have a specific, deliberate reason not to — a cache with no TTLs silently accumulates stale data and eventually fills available memory.
- **Use structured key names** (e.g., `resource:id:aspect` like `user:42:profile`) to make keys readable, debuggable, and easy to target for bulk deletion with SCAN patterns.
- **Invalidate on write, not on read** — when the underlying data changes, immediately delete the cache key; the next read will repopulate it from the fresh database value.
- **Handle cache misses gracefully** — a Redis instance restart, eviction, or TTL expiry is not an error; your application must fall back to the database transparently.
- **Use pipelines and multi-exec for atomic multi-command operations** — multiple round trips to Redis are slower than a single pipeline; MULTI/EXEC ensures a group of commands executes atomically.
- **Cache at the right layer** — caching computed or aggregated results (a user's order count, a product's average rating) is higher leverage than caching raw database rows; the heavier the computation, the more the cache earns its complexity.
- **Do not use Redis as your only copy of important data** — by default Redis is not durable; a crash without AOF/RDB persistence loses data since the last snapshot. If durability matters, configure persistence or use a database.

## Common Interview Questions

**Q: What is the cache-aside pattern and how does it differ from write-through?**
A: Cache-aside (lazy loading): the application checks the cache, fetches from the DB on a miss, and writes the result back to the cache. The cache is populated lazily on demand. Write-through: on every write, the application updates both the cache and the database simultaneously, keeping the cache always warm. Cache-aside is simpler and avoids caching data that's never read; write-through avoids cache misses after writes but wastes resources caching data that may not be read again.

**Q: What is cache invalidation and why is it difficult?**
A: Cache invalidation is the process of removing or updating cached data when the underlying source of truth changes. It is difficult because every write code path must correctly identify and invalidate all cache keys that depend on the changed data — a missed invalidation means stale data is served indefinitely. TTL-based expiry is simpler but allows a staleness window; explicit invalidation is accurate but brittle.

**Q: What is a cache stampede and how do you prevent it?**
A: A cache stampede (also called thundering herd) occurs when a popular cached item expires, causing many concurrent requests to all miss the cache simultaneously and all query the database at once. Prevention strategies: probabilistic early expiration (refresh the cache slightly before it actually expires), locking (only one process fetches from the DB; others wait), or background refresh (a scheduled job refreshes popular keys before they expire).

**Q: What TTL would you use for user profile data vs. product inventory?**
A: User profile data changes rarely but user experience depends on seeing their own changes reflected immediately — use a moderate TTL (5–30 minutes) and invalidate explicitly when the user updates their profile. Product inventory changes with purchases and restocks — use a short TTL (30–60 seconds) or invalidate on every inventory change, depending on how critical real-time accuracy is.

**Q: What are the differences between Redis data types and when would you use each?**
A: Strings: general caching, counters, session tokens. Hashes: structured objects where individual fields need to be updated without deserializing the whole value. Lists: queues, activity feeds, recent items. Sets: unique membership (e.g., "which users have seen this notification"). Sorted sets: leaderboards, rate limiting with time-based scores. Streams: event logs, message queues with consumer group support.

**Q: How does Redis handle persistence and what are the trade-offs?**
A: Redis offers two persistence modes: RDB (snapshot) saves the dataset to disk at configurable intervals — low overhead but can lose recent writes. AOF (append-only file) logs every write command — more durable but larger files and slower replay on restart. Both can be used together. For a pure cache (no durability needed), persistence is optional. For session storage or queuing, AOF is appropriate.

**Q: How would you implement a distributed rate limiter using Redis?**
A: Use Redis INCR with EXPIRE: on each request, INCR a key based on the client IP and endpoint; if the count exceeds the limit, reject the request. Use EXPIRE to reset the count after the window. Alternatively, use a sorted set (ZADD with timestamp as score, ZREMRANGEBYSCORE to clear old entries, ZCARD to count) for a sliding window without fixed resets.

## Key Takeaways

- Redis stores all data in RAM, making reads and writes sub-millisecond; it is a speed layer, not a system of record — always keep the database as the authoritative source of truth.
- Always set a TTL on cache entries; without expiry, stale data accumulates and memory fills until the eviction policy kicks in.
- Cache-aside is the most common pattern: check cache, fall through to database on miss, write result to cache; invalidate the cache key when the database is updated.
- Cache invalidation is the primary source of bugs in caching — explicit invalidation on write is more accurate than TTL alone but requires discipline to apply at every write path.
- Redis data types beyond strings — hashes, sorted sets, lists, sets — enable efficient implementations of leaderboards, rate limiters, queues, and session stores without application-level locking.
- Use atomic commands (INCR, SETNX, MULTI/EXEC pipelines) to avoid race conditions in shared cache state accessed by multiple application instances.
- Cache misses must never be treated as errors — they are normal events (TTL expiry, first access, cache restart) and the code must always handle them with a graceful fallback.
- Cache at computed results, not just raw rows — the higher the computation cost of the cached value, the greater the cache's impact on performance.
