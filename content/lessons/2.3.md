# Redis & Caching

Caching is one of the highest-leverage performance techniques in a system — and one of the easiest to misuse. This unit covers the mental model, not just the API.

## Key-value caching

Redis stores everything as key → value, entirely in memory, which makes reads and writes extremely fast (sub-millisecond) compared to a disk-backed database:

```
SET user:42:profile '{"name":"Prasanth","plan":"pro"}'
GET user:42:profile
DEL user:42:profile
```

The trade-off for that speed: memory is finite and (by default) not durable the way a database is — Redis is a cache and ephemeral store first, not your system of record.

## TTL / expiry

Every cached key can have a time-to-live after which Redis automatically evicts it — essential for anything that goes stale (session tokens, rate-limit counters, "trending" lists):

```
SET session:abc123 "user-42" EX 3600   -- expires in 1 hour
TTL session:abc123                       -- check remaining seconds
```

Without a TTL, a cache silently accumulates stale data forever — this is a common production bug: someone caches something "temporarily" and forgets the expiry.

## Cache-aside pattern

The most common caching strategy: your application checks the cache first; on a miss, it reads from the real database, then **writes that result back into the cache** for next time.

```js
async function getUser(id) {
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);

  const user = await db.query("SELECT * FROM users WHERE id = $1", [id]);
  await redis.set(`user:${id}`, JSON.stringify(user), "EX", 300);
  return user;
}
```

The database remains the source of truth; the cache is a disposable speed layer that can be wiped and rebuilt at any time without losing real data.

## When caching helps vs. hides a real problem

Caching genuinely helps when: the same data is read far more often than it changes, and recomputing/refetching it is expensive relative to how cheap a cache hit is. Caching becomes a trap when it's used to paper over a slow query or a bad schema instead of fixing the root cause — you end up with two sources of truth that can silently drift apart (**cache invalidation** is famously one of the two hard problems in computer science). A good rule: profile first, cache the specific hot path you measured, and always have a clear invalidation strategy (TTL, explicit delete-on-write, or both) before you ship it.

## Practice tip

Add a Redis cache in front of one real, slightly-slow query in a project you've built. Measure the response time before and after — that measured number is worth more in an interview than reciting the cache-aside pattern from memory.
